=== el1_features: what a guest at EL1 under Hypervisor.framework can ACTUALLY do ===
    every probe runs in its own forked VM; the vCPU is put in EL1h (CPSR=0x3c5) before
    its first MRS, and VBAR_EL1 points at our own vector table so an undef is survivable

=== 2. does the write APPLY, or merely stick? =================================
  TCR_EL1.EPD0=1 then load VA_A:
      before: read 0x0 (expect MAGIC_A)   after: TIMEOUT ESR_EL1=0x86000004 EC=0x21 translation fault
      => TCR_EL1 did NOT visibly apply -- inspect
  TTBR0_EL1 switched to an alternate root:
      root1 -> 0xaaaa0000aaaa0001   root2 -> 0xbbbb0000bbbb0001  => TTBR0_EL1 APPLIES
  MAIR_EL1 attr1 Normal-WB -> Device-nGnRnE, then an unaligned load:
      control (Normal) unaligned load: 0xaaaa0000aaaa00   after: EXC_EL1 EC=0x25 ALIGNMENT fault
      => MAIR_EL1 APPLIES (memory type changed: alignment fault on Device memory)
  SCTLR_EL1.A = 1, then an unaligned load:
      SCTLR readback 0x30901187   after: EXC_EL1 EC=0x25 ALIGNMENT fault
      => SCTLR_EL1 (beyond .M) APPLIES
  VBAR_EL1 moved to a second table, then SVC:
      outcome EXC_EL1, ELR=0x40020010, readback=0x40005000 (expect 0x40005000)
      => VBAR_EL1 APPLIES (the SVC landed in the NEW table, whose handler reports out)
  guest EL0: read TPIDR_EL0/TPIDRRO_EL0, then write TPIDRRO_EL0:
      outcome UNDEF_EL1  CurrentEL(x2)=0x3c0  CNTVCT(x3)=0x0  ESR_EL1=0x2000000 EC=0x00 (unknown/undef)
      => a write to TPIDRRO_EL0 from EL0 raises an undef INTO THE GUEST's OWN VECTOR (no host exit)
