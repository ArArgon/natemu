## Independent challenge findings

Inferred, scoped to the I arm's abstract SC lifetime model: the stated
load/advertise/revalidate algorithm has the expected retirement argument.
If reader revalidation of the old entry precedes replacement, its hazard
advertisement precedes revalidation, replacement, and the writer's scan in
SC order. A scan cannot miss that hazard unless the reader has subsequently
cleared it after returning, or is no longer protecting the old generation.
If advertisement occurs after the scan, revalidation observes the replacement
because old tokens are not republished. Immutable, retained descriptors avoid
a metadata use-after-free before validation. This justifies proceeding to the
required independent finite-state/code tests for I once the method defects
below are repaired; it proves neither executable-byte coherence nor an Arm
or macOS publication protocol.

S states a meaningful exclusion interval: all exact-epoch acknowledgements
precede mutation, and workers cannot re-enter until matching RESUME. M scopes
MAP_FIXED to previously owned non-JIT data extents and deliberately separates
JIT protection capability from executable remapping. Those boundaries are
sound at the proposal level. E and the shared invalidation surrogate need
more precise ordering to meet the same standard.

Counterexample to bare “revalidate before publication”: translator reads page
version v, builds code, and rechecks v; another actor increments to v+1,
completes invalidation; translator then stores the old translation entry.
This violates the proposed post-acknowledgement version contract without
violating the written recheck-before-store rule. Coordinator serialization
can exclude it, but the current method does not state that version mutation,
the final recheck, entry installation, and invalidation completion share that
ownership/linearization domain. The existing hook before recheck does not
specifically test the gap after a successful recheck.

Counterexample to the universal hook expectation: in I, hold the writer after
cache maintenance but before entry publication. A reader may validly enter
and finish the still-current old generation; it need not block or reject a
stale token. The method's blanket instruction that every competing actor
“either blocks or rejects a stale token” would reject this correct execution
or add synchronization that masks the intended behavior.

## Required changes

1. R1 — investigation owner, method gate: remove or explicitly archive the
   second Controls, Confounders, Metrics, and Sample plan sections after the
   concrete cost sample plan. Keep one operative oracle/sample contract. In
   particular, reconcile the duplicate “no reader ... references a retired
   generation” oracle with the precise rule that code can be retired while
   immutable descriptors remain allocated and safe to inspect, and with
   permitted completion of SUPERSEDED generations. No old pending stub should
   govern a proposed concrete arm or override its negative/sensitivity split.
2. R2 — method/protocol owner, method gate: make E and invalidation transitions
   executable specifications. Name the atomic objects and memory orders for
   entry/version publication, epoch request, exact-epoch acknowledgement,
   post-ack pointer reload and retirement; state what prevents re-entry to the
   retired version and how repeated epochs/writers are serialized. Explicitly
   place the translator's final version check and entry installation in the
   same ownership/linearization domain as page-version changes/invalidation,
   or provide an equivalent checked protocol. Add a deterministic hook after
   successful final validation and before publication, and a schedule where
   invalidation attempts to complete there. Require rejection/revalidation or
   ordered serialization, never stale installation after completed invalidation.
   Carry the precise page-version acknowledgement/re-entry rule into V as well.
3. R3 — method/oracle owner, method gate: replace the universal block-or-reject
   hook expectation with a per-arm transition/outcome table or equivalently
   precise rules. Distinguish allowed progress on a protected/current old
   generation, delayed publication/reclamation, revalidation retry, and actual
   protocol violation. Retain the immutable writer-before-publication example
   above as an allowed-progress case. State exactly which actor is held and
   which event establishes each observation; forbid the hook instrumentation
   from adding a stronger reader/writer exclusion than the candidate protocol.
   Existing independent model, executable hold, and deterministic negatives
   remain required after this contract is fixed.
4. R4 — measurement owner, method gate: distinguish zero back-to-back clock
   deltas (possible quantization of a valid finite-resolution clock) from zero
   elapsed measurement batches, backwards readings, and arithmetic overflow.
   The current “minimum positive” selection followed by “Zero differences ...
   invalidate” is contradictory and can reject a valid clock solely because
   two calibration reads share a tick. Specify whether any zero batch makes
   that candidate size insufficient, how all-zero calibration is reported,
   which pre/post calibration statistic fixes the threshold, and require every
   retained evidence batch to meet the frozen resolution criterion or report
   unresolved resolution without selecting favorable positive durations.
   Retain the external timer-result prerequisite, same-coordinator intervals,
   nested-sample labeling and absence of pure-API subtraction claims.

These issues remain within Q-01-18 and its already recorded measurement and
invalidation owners; no new backlog identifier is needed. No implementation
or evidence run should begin on this proposal before independent return.
