### R1 — a late rejected input leaks histogram and timing claims

The single-result CLI calls main directly. Main emits histogram diagnostics
and timing thresholds before all fields used by later report calculations
have been validated/evaluated. If a later calculation raises an exception,
CLI prints a failure saying no claims were produced, but it cannot retract
the already emitted claims.

Independent non-evidence reproducer: load the submitted synthetic valid
fixture in memory, change only `fallback_global_lock.ns_per_op` to the string
`"malformed"`, and present that object to the actual CLI's JSON load. No file
was modified. All historical integrity and H-input checks pass; the CLI then
returns1 with this output sequence:

- Eight histogram comparison rows, including one `corroboration=ELIGIBLE`.
- One `MEET T1` timing/categorical threshold row.
- `RESULT: FAIL (input rejected; no histogram/threshold claims): '<' not supported between instances of 'str' and 'int'`.

This contradicts the new fail-closed output promise and permits a consumer to
extract eligible/MEET rows from a failed report. The missing input validation
is not a new architectural rule and does not require changing the historical
threshold predicates. Build/validate the complete report before publishing
claim-bearing output, or validate every field needed by it first, with a
transactional failure path for later rendering errors. Apply the same
no-partial-claim contract to any cohort report/rendering failure. Add a
late-failure regression distinct from existing early integrity/H-input tests,
asserting nonzero failure and no H comparison, ELIGIBLE, MEET or MISS output.
Do not merely alter the final diagnostic to admit that claims already leaked.
