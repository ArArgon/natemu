### RC1 — control raws' compiled-source digest: closed

`src/authorization.py:279` now adds `d.get("compiled_bundle_sha256") ==
authorization["code_bundle_sha256"]` to the per-member producer-binding
requirement, inside the `if d is not None:` block that runs for every campaign
member carrying a raw. Re-derived first-hand against HEAD in a scratch
directory: `build_synthetic_campaign` produces an honest five-member campaign
that `validate_campaign` accepts; stamping `compiled_bundle_sha256 = "0"*64`
on the three control raws REV-218 named and rehashing each
raw→receipt→manifest→campaign chain is now refused with `ValueError: control
raw producer binding mismatch`. I additionally confirmed the same refusal for
each member in isolation — `negative`, `fallback-drop-write`,
`fallback-lock-error` and `normal` separately — and for a raw that simply
omits the key. The fix is load-bearing rather than incidental: re-running the
identical transplant against an in-memory copy of `authorization.py` with only
that one conjunct removed accepts the campaign, reproducing REV-218's finding
exactly.

No regression: the compiled digest is emitted unconditionally in the raw
header at `src/litmus.c:516-520`, before the `standalone`/negative/normal
branches, so every mode that produces a raw stamps it; `unexpected-fault`
never opens an output file and is exempt through the `d is not None` guard.
A legitimate campaign therefore cannot be refused by this rule. The new
regression test `test_campaign_rejects_control_compiled_bundle_transplant`
(`tests/fallback-fixtures.py:644-673`) mutates all three controls at once, so
it would still pass if only one member were bound; my per-member
reproductions above cover that gap in the test, and the fix itself lives in
the shared member loop, so it is an observation about test granularity, not a
defect.

### Validation-kind versus evidence-kind authorization paths

`load_authorization` returns immediately after the `validation` branch
(`src/authorization.py:142-144`), so a validation envelope never carries a
clock packet and never reaches the applicability rules; it is restricted to
the four non-timing modes, refused for `normal`/`negative`, and an unknown
mode is refused before anything else (`src/authorization.py:119-120`). Every
consumer of timing requires the other kind: `validate_result_binding` refuses
a validation envelope ("validation is not timing evidence",
`src/authorization.py:189`) and `campaign` refuses one before creating any
directory (`src/supervisor.py:338`). `run_child` reads the declared `kind`
from the envelope before loading it, but the subsequent `load_authorization`
call re-reads and re-validates the same file, so the preliminary read cannot
widen anything. Individual validation runs therefore still cannot be
assembled into a timing-eligible campaign.
