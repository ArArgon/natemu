## Required changes

1. `INV-01-09` owner, return to adversarial gate: record that this experiment
   has **no positive control for `vmnet` success**. State in Alternative
   explanations (and in `CLM-01-09-14`'s applicability cell) that no arm ever
   observed `VMNET_SUCCESS`, that the observed code is the general
   `VMNET_FAILURE` rather than either of the two access/authorization codes,
   and that the run therefore does not attribute the *unentitled* failure to
   the absent entitlement — only the *restricted* arm's termination is
   attributed, and that by the benign control rather than by any status code.
   Soften "ruled out by observation" for the degraded-mode alternative to what
   the data support: a degraded-but-working mode is excluded, the *cause* of
   the failure is not established.
2. `INV-01-09` owner, return to adversarial gate: carry the L2/bridging
   consequence into the `KA-08` disposition rather than leaving it as an
   unexercised-mode note. State that the surviving network backing on this
   host is the BSD-socket path, which `BP-01-09-start` already recorded as
   having no L2 bridging, and that a `Q-01-13` machine contract exposing
   virtio-net must therefore be fed by a user-space network stack on this
   host — naming the question that owns the consequence (`Q-01-13` for the

## Verdict

- Verdict: `revise`
- Rationale: the counterexamples this review went looking for mostly did not
  land, and that is itself the finding. The machine-contract table's Open
  cells are not treated as settled anywhere downstream — `INV-01-13` is
  substantively unchanged by the evidence round and remains more conservative
  than `INV-01-09` licenses it to be. The `KA` dispositions follow from what
  was observed and are bounded where they are stated: a capability run is not
  allowed to close `KA-08`, two working mechanisms are not allowed to close
  `KA-13`, and the mechanism the run proved unavailable is reported as a
  confirmed unavailability that narrows the memory design rather than as an
  inconvenience. The family implications correctly find no discriminator among
  F1–F4. The `BP-00-end` implication is answered in both halves and honestly
  left open for `Q-02-04` to adopt. The gate rows are honest. Two findings do
  require return. First, the experiment has no positive control for `vmnet`
  success, so the general `VMNET_FAILURE` observed in every checkable arm
  cannot be attributed to the missing entitlement — the individual claims
  respect this but the Alternative-explanations wording does not. Second, and
  more consequential, `KA-08`'s network clause now survives only through the
  disjunct that cannot do L2 bridging, a narrowing the record's own breadth
  pass predicted and its own run made concrete, and which the record leaves as
  a note about unexercised modes rather than as an implication for `Q-01-13`.
  Neither finding overturns a result; both are cases where the record's
  conclusion outruns, or fails to carry, what the evidence actually shows.
  `accept` is prohibited while they are open.
- Applicability limitations: this adversarial review covers `INV-01-09`,
  `INV-01-13`, and `INV-01-14` only. It establishes no macOS behavior, no
  device-backing or machine-contract or budget finding of its own, and no
  `KA-08`/`KA-12`/`KA-13` closure. Everything it accepts is bounded to
  `Mac16,10` (M4) / macOS 26.6.2 (`25G83`) / `MacOSX26.4.sdk`, ad-hoc-signed,
  unsandboxed, `uid=501`, `vmnet` host mode only, two same-day runs on one
  machine, with `P1` replication owed; `INV-01-13` is additionally bounded to
  Linux `v6.12` with 6.18 not re-verified. It supplies no experiment, no
  source acceptance, no architecture selection, no licensing conclusion, and
  no synthesis outcome, and authorizes no planning and no implementation. Its
  own weakest point is disclosed above: it is written by the reviewer that
  accepted this group's source, method, code, and replication gates, and
  should be revisited by a reviewer with no prior involvement.
