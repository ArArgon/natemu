### R1 — unexpected exception messages can echo claim text

The normal finding object is serialized before it is printed. However,
check.main's exception branch emits str(error) for arbitrary TypeError,
ValueError, OSError and other late exceptions. A pure in-memory complete-CLI
challenge mocked load_child (no file/host operation) and made validate_child
raise:

`TypeError('partial: STRUCTURAL_PASS findings T1 strict_100ns_meet=true')`

Actual returncode was1 and output was:

```json
{"status": "INVALID", "errors": ["partial: STRUCTURAL_PASS findings T1 strict_100ns_meet=true"]}
```

This is not a false structural status and there is no actual findings key:
a consumer correctly parsing status would reject it. The narrower defect is
that arbitrary exception text can reintroduce earlier claim/PASS/T1 content
into the nominal no-claims failure channel. The existing late-cell test uses
a trusted fixed Invalid code and does not challenge this path or a late JSON
rendering exception. This is the same exception-message boundary hardened in
the INV08 transactional reporter, not a newly observed clock failure.

Required correction: keep bounded trusted error codes for the expected
Invalid/Unresolved paths; report unexpected exception types or fixed codes,
not arbitrary messages. Add complete-CLI late-validation and late-rendering
exceptions whose messages intentionally contain claim text, requiring no
leakage, no findings section and nonzero exit. This finding does not justify
changing arithmetic or excluding a required clock cell. Owner: root checker
author; return: code196 on corrected hashes.
