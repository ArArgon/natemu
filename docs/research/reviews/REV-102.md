## Verdict

- Verdict: `accept`
- Rationale: **The claimed result reproduced.** The approved code was taken out
  of git at `22d8516` with `git archive` rather than from the working tree, and
  all four extracted source digests match `git show 22d8516:` and the digests
  the original run recorded — so the replicated object is provably the same
  code, not merely a tree that diffs empty. It was driven by a runner and judged
  by a checker this reviewer wrote, the checker built from the method of record
  rather than from `src/check.py` so that a shared defect could not hide in
  both; it makes 69 assertions per document and carries a 20-mutation self-check
  that passed before and after the run. Every deterministic value reproduced
  exactly: 27 of 27 compared guest counters agree and are constant across all
  five repetitions in both runs, the four fault-log entries are identical
  between the runs, the parallelism ratio is 2.00 in five of five, ThreadSanitizer
  reports zero races, and the build is bit-reproducible for the guest object,
  the generated blob and both non-sanitizer binaries. The controls reproduce
  too, each rejected by the reviewer's checker and each firing every targeted
  invariant under the subject's, with no `UNWITNESSED`. The predeclared
  stochastic miss also reproduced as a miss, which is the outcome that supports
  the record's honesty rather than undermining it. Only scheduling-dependent
  quantities differ, and the identity the record actually claims holds in all
  ten repetitions across both runs. No required action arises against the
  subject, every applicable challenge dimension carries a disposition, and
  independence from the author is met under the limits disclosed above, so
  `accept` is permitted for the replication gate.
- Applicability limitations: **This replication widens nothing.** It ran on the
  same machine — `Mac16,10` (Apple M4) / macOS 26.6.2 (25G83) / SDK 26.4, ad-hoc
  signing in the same two configurations — so the Observed findings remain
  valid for this host and OS only, and `P1` (M1 Pro / Sequoia 15) replication is
  still owed before any platform-wide use, per the executor guide's incremental
  replication rule. It reaches neither the 4- nor the 8-vCPU acceptance
  topology, uses the same synthetic guest, and establishes no performance
  result, no `KA-04`, `KA-06` or `KA-11` disposition beyond what `REV-101`
  reviewed, no family judgment, and no synthesis outcome. The review
  concentration disclosed above — one reviewer across source, method, code,
  result, replication and adversarial — is itself a limit on how much assurance
  this record's review history carries. Nothing here authorizes planning or
  implementation.
