- **RR1 — The ring-buffer capacity rule voids every worker cell it is meant
  to protect (R9 not closed).** Lines 173–175 size each thread-private buffer
  "for the longest observation window in this method (T1, 30 minutes) … at the
  timer thread's 100 ms cadence, with headroom" — roughly 1.8×10^4 records
  plus headroom. But line 160 has each busy worker append a heartbeat "every
  2^16 iterations" of a counter-increment spin loop. To fit 1.8×10^4 records
  in 30 minutes a worker would have to take 100 ms per 65,536 iterations, that
  is ~1.5 µs per increment; a real M4 spin iteration with one atomic flag poll
  is on the order of 1–2 ns, giving ~10^4 heartbeats per second per thread and
  ~10^7 records per worker over the T1 window — three orders of magnitude
  over capacity. Under the fail-closed rule at lines 177–183 every worker
  buffer therefore fills within seconds, the dropped-record counter goes
  nonzero, and "that thread's classification for that repetition [is]
  `insufficient-samples` by construction". Every worker in every arm, and the
  entire worker-progress and worker-sampled clock-continuity classification,
  is void before the induction is ever performed — including the C2 negative
  control, which lines 510–516 require to show `advanced`/`continuous`, so the
  campaign cannot even pass its own baseline. Sizing the buffer to the true
  worker cadence is not a fix either: ~10^7 records × 8 threads at ~64 bytes
  per record is tens of gigabytes. Bound the worker heartbeat in *time* rather
  than in iterations (for example, at most one heartbeat per fixed interval on
  the named reference clock, with the iteration counter carried in the record
  so throughput information is not lost), recompute the capacity from that
  cadence and the 30-minute window, and state the resulting record count and
  byte size in the same paragraph so the arithmetic is auditable at the code
  gate. This also removes the tension R5 identified for good, since the
  heartbeat cadence would then no longer move with T4/T5.

- **RR2 — The supervisor's clock does the opposite of what the record states
  (R10 not closed).** Lines 574–582 name the supervisor's own
  `clock_gettime(CLOCK_MONOTONIC)` and then reason: "its `CLOCK_MONOTONIC`
  ceiling does not tick during system sleep, so a 30-minute T1 ceiling is
  measured only across the host's awake time and the supervisor cannot itself
  expire mid-sleep." On Darwin this is inverted. `clock_gettime(3)`, present
  in this very SDK at `usr/share/man/man3/clock_gettime.3` (SHA-256
  `d09d561f…7242fc`), states at lines 67–69 that `CLOCK_MONOTONIC` "will
  continue to increment while the system is asleep", and at lines 78–81 that
  `CLOCK_UPTIME_RAW` "does not increment while the system is asleep" and is
  "identical to the result of `mach_absolute_time()` after the appropriate
  `mach_timebase` conversion". The sleep-excluding clock is
  `CLOCK_UPTIME_RAW`/`mach_absolute_time`, not `CLOCK_MONOTONIC`. As written
  the supervisor's ceiling burns through the sleep interval, and any T1
  repetition whose sleep plus awake time exceeds 30 minutes is killed at or
  before wake and recorded `timed-out` — the arm's data is lost exactly when
  the induction succeeded. Either name the clock that actually excludes sleep
  and say so, or keep `CLOCK_MONOTONIC` and state the true consequence (the
  ceiling spans sleep, so it must exceed the maximum planned sleep duration
  plus the awake window) and set the ceiling accordingly. Correct line 243's
  claim that `CLOCK_UPTIME_RAW` has "no header capture in this SDK at all …
  not yet located" in the same edit, and register `clock_gettime(3)` at that
  pinned path and digest as the named supplement candidate for all five clock
  IDs — the man-page-capture form `INV-01-18` already uses for `SRC-071`/
  `SRC-072`. The R10 kill-versus-`stalled` rule at lines 582–593 is correct
  and needs no change.

- **RR3 — The delivery-validity control validates a different delivery path
  than three of the four arms it gates (R3 not closed).** Lines 498–501
  require the control on the `NSWorkspace` screen/session surfaces "once per
  repetition of T1, T3a, T3b, and T4". `NSWorkspace.h` line 33 states that all
  notifications in that header "must be registered on this notification
  center. If you register on other notification centers, you will not receive
  the notifications." The accepted packet's own `NSProcessInfo.h` states at
  lines 231 and 240 — inside `SRC-156`'s accepted pin — that the thermal and
  power-state notifications are "posted on the global dispatch queue. Register
  for it using the default notification center." These are two distinct
  delivery mechanisms, and the transition-specific surface for T3a/T3b (Low
  Power Mode) and T4 (thermal) is the second one. A `bracketed` `NSWorkspace`
  control therefore establishes nothing about whether the `NSProcessInfo`
  path is live in this process configuration, so for those three arms the
  dead-instrument-versus-genuine-`not-bracketed` separation the control was
  required to create does not exist, and `CLM-01-21-03`'s falsifier would
  again be charged to the host on harness evidence. Either add a
  default-center delivery-validity check that does not use the property under
  test, or — the honest and cheaper option, consistent with the R7 treatment
  of T2 — narrow `CLM-01-21-03`'s falsifier so that only T1 (whose surface is
  on the same `NSWorkspace` center the control validates) can contribute to
  it, and record T3a/T3b/T4 detectability as diagnostic-only. Record the
  `NSWorkspace.h` line 33 notification-center statement as a supplement
  request in the Source inventory the way R2 handles `mach_time.h` line 53: it
  is load-bearing for this control and it is outside `SRC-157`'s pinned
  319–330.

- **RR4 — Notification callbacks write into a buffer the design declares
  thread-private.** Lines 190–197 have the control thread install the
  `NSProcessInfo` thermal and Low-Power-Mode observers and then run a run
  loop, with "Every observer callback appends one control-thread record" to
  its buffer, against the design rule at lines 159–165 that every ring buffer
  is thread-private with no cross-thread writes. The accepted packet says
  those two notifications are posted on the global dispatch queue (lines 231,
  240 of `NSProcessInfo.h`), so those callbacks execute on arbitrary
  concurrency-managed threads, not the control thread's run loop: as
  specified, this is an unsynchronized cross-thread append to the record that
  carries the detectability evidence. Predeclare the delivery target — an
  explicit serial queue or a run-loop hop that restores single-producer

- Verdict: `revise`
- Rationale: the return is substantial and largely honest work. Eight of

  three orders of magnitude apart — so under the new fail-closed rule every
  worker cell, including the C2 baseline the campaign must pass, is

  write (RR4). Ten required changes remain unresolved, so `accept` is
