### RC2 — lock-error control accepts a raw missing `first_error` on non-injected workers

- Location: `src/supervisor.py:119-120` (the per-worker loop inside
  `control_oracle`'s `fallback-lock-error` branch) and `src/supervisor.py:143`
  (the repaired copy's unconditional `first_error=None` restamp).
- Fixture first (failing before the fix): a new mutation was added to the
  existing `test_lock_error_rejects_concealed_original_status_and_bool_confusion`
  (`tests/fallback-fixtures.py:424-464`): `lambda x: [w.pop("first_error")
  for w in x["fallback_global_lock"]["workers"] if w["id"] != 0]`, deleting
  the `first_error` key from workers 1, 2, and 3 of the well-formed
  lock-error baseline and asserting `sup.control_oracle("fallback-lock-error",
  receipt, mutated, "")` returns `False`. Run against the pre-fix code, this
  assertion failed with `AssertionError: True is not false` — the mutated
  raw, whose non-injected workers omit `first_error` entirely, was wrongly
  accepted, matching `validate_fallback`'s independent `FAIL F3: worker
  error absent` on the same original (`src/fallback.py:85`), and matching
  the drop-write branch's already-correct rejection of the identical
  omission pattern.
- Fix: `src/supervisor.py:119-121` now reads
  `if worker["id"] != 0 and ("first_error" not in worker or
  worker["first_error"] is not None): return False`, so a missing key no
  longer satisfies the same test a present `None` value does. This check
  runs in the loop that inspects the *original* raw, before the repaired
  copy at `src/supervisor.py:133-145` is ever built, so the unconditional
  `first_error=None` restamp at line 143 can no longer conceal the omission
  — by the time that repair runs, every non-injected worker's `first_error`
  key is already confirmed present and `None`.
- Before/after evidence: against the pre-fix snapshot (`src/supervisor.py`
  SHA-256 `eb8ca2baf90f4a34c9b5fe2bb7662dc384888df6852797dd2ae9d7633b372246`,
  matching REV-217/REV-218's pin), `sup.control_oracle("fallback-lock-error",
  receipt, mutated, "")` returned `True` for the field-deletion mutation.
  Against the corrected code (`src/supervisor.py` SHA-256
  `8d7a9e55d2077da0f7db70925f9778a39e047a36013936abf55f4afd8454652e`), the
  same mutation returns `False`, and the well-formed baseline and every one
  of the seven pre-existing mutations in the same test still return `True`/
  `False` as before (the well-formed baseline is unaffected because its
  workers 1–3 already carry an explicit `first_error: None`, which satisfies
  `"first_error" not in worker or worker["first_error"] is not None` as
  `False or False` = `False`, i.e. does not reject).
