## Per-item closure detail

### R1 — cap accounting now re-derived, not self-reported

*Fix:* `check.py:386-405` (function `check`, right after `setup_publications` is
computed). Recomputes `expected_tokens`/`expected_request_cap` from
`header`/`job`-derived quantities (`expected_warmup`, `expected_publications`,
`owners`, `held_count`, `scratch_count`, `replacement_count`) using
`protocol.c:1028-1034`'s exact formula, and requires exact equality against
`allocation[0]`/`allocation[1]` (`ALLOCATION_PLAN_TOKENS`/
`ALLOCATION_PLAN_REQUEST_CAP`). Additionally requires
`allocation[0] >= complete[4] and allocation[1] >= complete[5]`
(`ALLOCATION_PLAN_UNDERCOUNTS`, an actual-usage floor from the trace itself)
and `setup_plan[4] == allocation[2]` (`ALLOCATION_PLAN_INCONSISTENT`, the
one-line cross-check `REV-200` named), plus a lower bound
`allocation[2] >= allocation[0]*allocation[4] + allocation[1]*allocation[5]`
(`ALLOCATION_PLAN_BYTES_UNDERCOUNTS`) using the already-validated per-token/
per-request sizes.

*Narrowed, not fixed:* `bytes` (`allocation[2]`) is bounded and cross-checked
but not byte-for-byte re-derived from `sizeof(Trace)`/`sizeof(Worker)`. Doing
so would require hardcoding this checker's own copy of the compiled struct
layout (pointer size, alignment padding for `Worker`'s `unsigned id` +
`pthread_t thread` + arrays) — exactly the kind of fragile, silently-driftable
duplication R1 objects to in spirit. `tokens` and `request_cap` need no such
duplication (they are pure integer arithmetic over `header`/`job` fields) and
are now exactly re-derived, which is what actually falsifies `REV-200`'s M4b
counterexample (a plan collapsed to `tokens=1` against a much larger real
descriptor count is now rejected regardless of what `bytes` claims).

*Fixture:* `tests.py`'s base `fixture()` now emits a formula-correct
`allocation-plan`/`setup-plan` pair (`tokens=53, request_cap=172` for the
`n=1`, `pressure=normal`, control-mode topology; previously placeholder
`100,100`). Two new mutations reproduce and then reject `REV-200`'s M4b
pattern: `("allocation-plan",0,1,"ALLOCATION_PLAN_TOKENS")` (tokens collapsed
to 1) and `("setup-plan",4,1,"ALLOCATION_PLAN_INCONSISTENT")` (the two
independently-emitted `bytes` copies disagree). Verified directly: loading
`check.py` from `git show HEAD:experiments/INV-01-18/check.py` (the exact
pre-fix version `REV-200` reviewed) into a standalone module and running it
against the first mutation's trace returns `correctness-qualified` —
reproducing `REV-200`'s M4b acceptance byte-for-byte before editing; the
edited `check.py` rejects the identical trace with `ALLOCATION_PLAN_TOKENS`.

### R2 — narrowed, not fixed (disclosed)

*Why not fixed:* soundly relating a coordinator `retire` record to a reader's
later `admit` would need genuine cross-actor ordering evidence — e.g. a
per-page monotone admission index tied to the retiring epoch, checked the way
`resumed_epochs`/STOP already ties admissions to RESUME for S/M. That is a
trace-schema/instrumentation change to what the method requires recording,
not a checker-only fix, and risks being unsound given the checker's own
documented premise ("actor sequence numbers are local order, never a global
timestamp/SC-order proof"). Implementing it without that risk was judged out
of scope for a minimal-diff return; per the task's explicit fallback, the
claim is narrowed instead of the method being silently changed.

*Fix (narrowing):* `check.py:1-14` (module docstring) now states the exact
bound: retirement-before-execution is enforced only by the in-process state
read at admission time (`protocol.c:410`, mirrored as `RETIRED_ADMISSION`)
and by per-page version floors (`STALE_ADMISSION`); the streamed checker has
no cross-actor invariant relating a `retire` record to a later `admit`/`call`
of the same token. A matching comment sits directly above the
`RETIRED_ADMISSION` check (`check.py:464-470`). `README.md`'s I-retirement
sentence (line 59, REV-200's cited claim location) and the pressure-hold
sentence (line 118, REV-200's `README.md:114` before this session's edits
shifted it) are both narrowed to state the same bound instead of presenting
RETIRED as an established, checked lifetime property.

*Fixture:* `tests.py` adds a characterization fixture (comment-labelled,
inserted after the `ADMISSION_BEFORE_RESUME` test): a well-formed `retire`
record for the live page-0 token is inserted before its first admission
(mirroring `REV-200`'s M3), sequence-renumbered, and asserted **accepted**
(`correctness-qualified`) — documenting exactly what the checker does not
reject, matching the narrowed claim. The existing `("admit",1,4,
"RETIRED_ADMISSION")` mutation continues to demonstrate what the checker
*does* reject (an admission whose own state field already reads RETIRED).
