## Independent method findings

The proposal is a bounded experiment, not a claim that public declarations
prove working delivery. REV-187 closes its documentary prerequisites at the
pinned version. Narrowing claim -19 to EXC_BAD_ACCESS matches the already
BAD_ACCESS-only method; the corpse exception therefore does not change the
experiment. The corrected opaque-layout premise likewise agrees with the
method's explicit compile-configuration capture and accessor-only inspection.

The state-only interface genuinely lacks thread/task identity arguments.
M06-M1 does not fabricate them: one registered receive port identifies the
candidate worker, and cookie, exact armed PC, SP range, nonce and address
independently constrain application attribution. One outstanding event per
worker and release/acquire publication constrain stale descriptors. The port
map is not kernel-origin authentication, and the method explicitly excludes
malicious same-process actors and exported capabilities. Separate crafted
preflight messages cannot count as kernel-delivery evidence. These limits
must survive code implementation and results.

The positive oracle is not merely KERN_SUCCESS. A server repairs only the
dedicated data page in ordinary thread context, returns unchanged general
state with the exact count/flavor, and requires the resumed assembly to execute
the original load/store, check data and untouched sentinels/SP, and commit
once. Repeated fault, skip, wrong state and duplicate markers fail. General
state is explicitly not ESR, NEON/SME or per-thread JIT permission state.
Immutable-JIT execution follows a non-JIT baseline; write-window behavior is
still Q19 composition work, not inferred from this experiment.

Forwarding is an owned, same-flavor, one-hop RPC chain with an independent
prior server. It does not assume that returning failure invokes a saved
same-level handler. The front checks the prior reply and exact unchanged
state before replying to the worker; routing and final continuation counts
are separately required. Unknown prior thread handlers block a positive
baseline. Task handlers are recorded but untouched. The separate unhandled
diagnostic records what occurs without prescribing a signal or treating
server death as ordinary forwarding failure.

Restoration is tested after admission closes and every worker is disarmed,
all in-flight messages/replies drain, and producers stop. Semantic selected-
mask/port/behavior/flavor equality includes originally null portions without
depending on row ordering. The owned-prior case must receive a subsequent
event after restoration. Rights remain owned until restoration is confirmed;
failed restoration terminates the sacrificial child, never resumes an
unclassified positive campaign. Exact reference ownership, generated wire
layout and disposal branches are properly reserved for the separate code
gate, not asserted as established by this method review.

The two service topologies have distinct permissible progress. A held shared
serial server may queue unrelated faults; a held per-worker server cannot
create a dependency on another eligible server or the blocked worker.
Named holds cover receive/validate/repair/reply, forwarding, post-resume and
restore/disposal boundaries. The competitor's recorded attempt precedes hold
release. Teardown remains pending while a fault/reply is outstanding. These
are finite schedule checks, not proof of simultaneous physical-core execution
or every interleaving.

The fixed coverage manifest crosses local signing, 1/2/4/8 worker counts,
non-JIT/immutable-JIT, load/store, shared/per-worker service and direct/owned
forwarding. Warm-up failures count; fixed seeds and fresh children prevent
outcome-driven replenishment. All unavailable, invalid, timeout and not-run
cells remain visible. Server/worker/controller counts are separate, so helper
overhead cannot masquerade as guest vCPU coverage. No timer-qualified cost
or deadline conclusion is made; parent watchdog budgets are operational
containment, not a measured latency bound.

The required offline mutations and sacrificial runtime negatives cover
identity/count/layout errors, lost/duplicate records or replies, wrong state,
stale restore snapshots, right-disposal defects, omitted repair, server death,
reply failure and unexpected helper faults. Their implementation and actual
outcomes remain unproven until the code/validation gate. A failure cannot be
reclassified as successful fallback or silently excluded.
