## Question and decision relevance

- Question ID and text: `Q-01-18` — What host-side cross-thread protocol makes
  a shared code cache and process-wide mapping changes safe while other vCPU
  threads execute—code publication and instruction-cache coherence, live-code
  patching, and quiescence/safepoint entry and exit—and at what latency and
  cost?
- Decisions affected: translation-family admissibility under SMP; the
  `INV-01-02` family register; `Q-01-19`; correctness work in `Q-02-02`; and
  the later cost model in `Q-04-01`.
- Why this must be resolved now: accepted mechanism probes cover only pieces
  of the composition. None establishes that concurrently executing vCPU
  threads can safely observe, stop for, patch, invalidate, and reclaim shared
  translated code at the required 2/4/8-vCPU topologies.

## Assumptions

- Declared assumptions: routine operation is unprivileged and uses public APIs;
  the acceptance topology is 2/4/8 vCPUs; correctness failures invalidate cost
  measurements; observations remain host/OS/signing-cell specific.
- Assumptions to challenge: a shared mutable cache is necessary; writer-side
  cache invalidation is sufficient for every reader; atomic entry publication
  makes code bytes coherent; all vCPUs can reach a safe point promptly; and
  single-thread transition costs transfer to contended publication.

### Objects, execution oracle, and lifetime definitions

Use one MAP_JIT arena per process, divided into host-page-aligned slots, and
separate non-executable metadata, mailboxes, traces and mapping-test pages.
The host page size is measured; guest page IDs are synthetic 4 KiB units.
Each slot has a nonwrapping 64-bit generation token and guest-page version.
Descriptors are immutable after publication and remain allocated until all
threads join, even after their code slot is reclaimed. No reader dereferences
a potentially freed descriptor to validate it.

Generated AArch64 blocks have 64, 256 or 4096 bytes, with a reviewed bounded
instruction sequence returning two independently encoded 64-bit generation
values. Padding and return position are explicit in disassembly. All changed
immediate fields participate in the returned pair; choose each transition so
every changed field differs and independently enumerate mixed old/new field
combinations at code validation to show the oracle rejects them. This finite
check does not prove arbitrary torn instruction detection. Each actual call
records token, expected pair, returned pair, worker/iteration and mapping
version in a preallocated per-thread trace; the checker compares each return,
not only a final checksum. No trace overflow or missing tail is a pass.

States are BUILDING, PUBLISHED, SUPERSEDED, RETIRED, and REUSED. Unpublishing a
block makes it SUPERSEDED; an already protected reader may still finish it.
RETIRED means the protocol has established no reader can execute its code or
use a retained code pointer; only then may the slot be overwritten/reused.
Immutable descriptor inspection remains permitted while those descriptors
are allocated. Therefore executing a
superseded generation is not automatically stale execution. A reader that
begins after an acknowledged invalidation must use the new guest-page version.
All correctness cutoffs use protocol tokens/handshakes, not timestamp order.

### Candidate protocols and exact transitions

| Arm | Candidate and transitions | What the result can address |
| --- | --- | --- |
| I | Immutable publication with SC entry token and one SC hazard token per reader. Reader loads entry, advertises that token in its hazard, rereads entry and retries on mismatch; only after agreement may it access descriptor/code, execute ISB and call. It clears the hazard after return. Writer builds an unpublished slot through a non-nesting write callback, returns to executable state, invalidates its entire byte range, then SC-stores the new entry. It may retire the old code only after SC-scanning all hazards and finding none equal to the old token. All accesses to entry/hazards are SC; no weaker-memory-order variant is implied. | Concurrent immutable publication plus protected-reader retirement. The total-order argument is a candidate derivation to challenge: a reader that passed revalidation before replacement must be visible to the scan; one advertising after the scan must observe replacement on revalidation. Exact token identity prevents ABA. No generic RCU correctness result. |
| S | Stop-and-quiesce in-place patch. Coordinator release-publishes STOP(epoch) to each worker. Workers finish the current bounded block, clear hazards, discard cached entry pointers, and release-acknowledge that exact epoch from the host dispatcher. They then wait for matching RESUME(epoch). After acquiring every acknowledgement and checking empty hazards, writer patches via callback, returns, invalidates the changed range and SC-publishes new entry/version then release-publishes RESUME. Workers acquire RESUME, reread entry and execute ISB before the next call. | Modification of previously published code with no reader executing during the patch. This is live patching under quiescence, not an attempt to rely on restricted concurrent CMODX replacements. |
| E | Epoch retirement alternative. Coordinator SC-publishes the next entry, then release-stores an exact request epoch and target page-version floor to each reader mailbox. At its host dispatcher each reader acquire-loads its request, completes/drops its prior call and pointer before release-acknowledging that exact epoch, then SC-reloads the entry instead of reusing its old local pointer. It may execute only a nonempty entry at or above the acquired page-version floor, after ISB. Coordinator acquire-loads every matching acknowledgement before retiring old code. The detailed ordering/serialization rule below is mandatory. No hazard optimization is combined with E. | Explicit epoch-boundary reclamation and finite progress under controlled holds, not generic RCU or an unbounded scheduling guarantee. |
| V | Per-vCPU immutable slots and data indirection. Worker builds its own unpublished slot in the host dispatcher, returns from its callback and invalidates; coordinator alone may install its submitted descriptor in that worker's SC entry slot after the serialized version check below. The worker SC-loads the installed entry before ISB/call. Guest invalidation uses E's acquire-request, drop-pointer, exact release-acknowledgement and post-ack SC-reload/version-floor rule for every worker. Reuse waits for that worker's completed call plus removal of its old entry; no old entry can be republished. | Avoids cross-thread execution of constructed bytes while preserving invalidation coordination; coordinator metadata installation does not itself supply instruction visibility. |
| M | Process-wide mapping changes under the exact S rendezvous, for separate data windows and separately for JIT-arena protection. Data window: all workers initially read a known file-backed page; after quiescence replace that same owned extent using MAP_FIXED with a different page-aligned offset containing a distinct version, then resume. Separate protection arm changes a dedicated data extent to PROT_NONE and back. Separate JIT protection arm applies PROT_NONE to the single arena only while all readers are stopped, then requests its original protections, restores each thread's documented write-protection state outside callbacks, invalidates and resumes with ISB. All return codes and actual mapped addresses are checked. | Data-remap contents, process-wide protection, and whether the tested JIT protection round trip is available and composes on this signing cell. No executable MAP_FIXED/alias replacement guarantee follows; that candidate stays open pending its source/API study under Q-01-01/18. |

All MAP_FIXED operations target a page-aligned extent whose complete address,
length and ownership were recorded by this child before starting threads;
they replace only that extent. They never touch stack, metadata, traces,
allocator storage or the JIT arena. File offsets are prepopulated and immutable.
No remapping or protection change is attempted until all matching safe-point
acknowledgements are observed. The JIT protection arm cannot establish an
executable VA-to-PA replacement path and must not be reported as one.

One coordinator publishes serial writer requests by release/acquire mailboxes.
The one-writer cell performs them itself; the two-writer cell has two producer
threads submit distinct immutable work records, with explicit coordinator
ownership grants and completions before the next grant. Requests overlap but
mutation ownership never does. Its oracle rejects a second simultaneous grant;
it does not claim lock-free multiwriter publication. Neither producers nor
instrumentation write shared non-atomic trace records. Protocol state and
injection mailboxes use declared atomics; generated byte writes occur only in
unpublished slots or after quiescence. Sanitizer runs validate the host model,
not instruction-cache coherence, and are separate from unsanitized samples.

For E and V the following objects and orders are part of the candidate, not
implementation discretion. Each page has an SC atomic `page_version[p]` and
SC atomic generation-token `entry[p]` (V: `entry[reader,p]`); zero denotes no
admitted entry. Only the coordinator changes these objects. It initializes an
immutable request record containing epoch, affected pages and minimum versions,
then release-stores that epoch to each reader's atomic `req_epoch[i]`. The
reader acquire-loads its request, completes its prior call and drops every
retained code pointer, then release-stores the exact epoch to `ack_epoch[i]`.
Its next admission SC-reloads the entry; it must not reuse a pre-ack pointer.
Zero waits, and a descriptor below any acquired page-version floor is rejected.
The request's release/acquire edge carries the preceding entry/version changes
to this reload. The coordinator acquire-loads every exact acknowledgement
before retiring the covered generations. Immutable descriptor inspection is
permitted even after code retirement; executing through its retired code
pointer is not. Epoch and generation counters are 64-bit and must never wrap.

Only one coordinator epoch may be outstanding: no next request is issued until
all exact acknowledgements of the current epoch arrive. Readers need no writer
grant to acknowledge. A V reader building a slot finishes its write callback
before acknowledgement, then may submit/wait with no retained old code pointer;
it must not wait for installation while withholding an acknowledgement. S and
M retain their stronger matching-RESUME admission rule; E and V do not wait
for RESUME and may admit a valid new entry immediately after acknowledgement.

All candidate arms use one coordinator-owned serialization domain for guest
page-version mutation, final translation validation and entry installation.
A producer may prepare unpublished bytes outside it, but only the coordinator
may perform the final SC version comparison and SC entry installation, without
releasing ownership between those actions. An invalidation transaction holds
the same ownership while it increments affected SC page versions, zeroes all
obsolete entry slots, release-issues the exact epoch request, acquires every
acknowledgement, and records completion. No installation or other version
mutation occurs during that transaction, including its acknowledgement wait.
For S/M those acknowledgements are their STOP acknowledgements; readers resume
only after the matching RESUME. For I, readers also clear their hazards before
acknowledging and apply the same acquired version floor and post-ack entry
reload, followed by I's hazard/revalidation admission; code retirement still
requires I's hazard rule. Zero is never callable in any arm. All arms use SC
entry loads/stores; S/M additionally
use the release/acquire STOP/RESUME exclusion. Therefore an
installation either precedes invalidation and is removed/drained by it, or
follows invalidation and must pass the new version check. A check followed by
an unowned delayed install is forbidden. This deliberately serialized research
candidate does not select a production architecture or prove progress without
the declared bounded-call and scheduled-reader assumptions.

### Guest invalidation surrogate and interleaving schedule

The surrogate is a synthetic guest page/version table, not an x86 guest. A
writer changes a page version, requests invalidation, and considers it complete
only when every reader acknowledges after dropping stale translated entries.
Stimuli cover same-page SMC, another worker writing that page, and two guest
virtual IDs changing their backing page/version. Writes to an unrelated page
must preserve unaffected versions. A translator delayed after reading the old
version must revalidate and install within the single ownership interval above;
stale translations are rejected. Version validation alone is not sufficient.
This checks the emulator-side invalidation contract. Real x86 serialization,
TLB and Linux correctness remain Q-02-02/Q-02-03.

Each protocol has named hook points, recorded before code exists: reader
before entry load; after load/before hazard; after hazard/before revalidation;
after revalidation/before call; inside a special bounded generated block;
after return/before clearing hazard; after safe-point acknowledgement/before
resume; writer after partial construction; after complete write/before cache
maintenance; after maintenance/before publication; after publication/before
retirement scan; after all acknowledgements/before mutation; after mutation/
before resume; before reuse; translator after version read/before final check;
and coordinator after successful final check/before entry installation.
Inapplicable hooks have explicit NA rows per arm; they are never silently
counted as covered.

At each applicable hook the controller holds exactly one designated actor
until the competitor reaches a recorded attempt point. The allowed outcome is
the arm-specific rule below, not a universal requirement to block or reject.
Rotate the held worker through every reader and both producer identities. Include an
all-but-one stopped schedule, an old-epoch acknowledgement, delayed producer,
and attempted generation/address reuse. The generated-block hold uses a
reviewed load of an atomic release flag and no unbounded guest instruction;
the normal cost blocks contain no such instrumentation. Model entry safety
and the executable-block hold are both required; neither substitutes for the
other. The schedule is finite coverage of these named states, not exhaustive
coverage of all machine interleavings.

| Held actor/state | Competing action and required allowed outcome |
| --- | --- |
| Any reader before entry load | Writer/coordinator may advance the protocol without that reader owning a code token. On release the reader applies its current request, version floor and arm admission rules; S/M cannot bypass an outstanding STOP. |
| I/E writer after partial/complete construction or cache maintenance, before publication | Reader may complete a call through the still-current old entry. It must not execute the unpublished candidate. This old call is valid, not a stale-token rejection. V permits this for a different worker; the same worker cannot simultaneously build and execute and is NA. |
| I reader after entry load, before hazard advertisement | Writer may replace the entry and retire an unprotected old generation. Reader must revalidate on release and retry if the entry changed; it cannot dereference/call the old token before successful revalidation. |
| I reader after hazard advertisement, before revalidation | Writer may replace the entry but its scan must retain the advertised generation until the hazard clears. On release the reader retries/clears the hazard if revalidation observes replacement; only successful revalidation admits a call. |
| I reader after successful revalidation, in call, or after return before hazard clear | Writer may publish a replacement, but retirement/reuse of the held token must remain pending. The protected superseded call may finish. A scan witnessing the held hazard must not retire that token. |
| I writer after publication, before retirement scan | New readers may call the new entry and already protected old readers may finish. Retirement is not established until the declared scan; the hold does not itself block readers or authorize reuse. E/V use their exact acknowledgement condition instead of a scan; scan-specific hook is NA there. |
| E/V reader before requested epoch boundary, including an old in-flight call | Old call may finish; that reader's acknowledgement, retirement dependent on it, and invalidation completion remain pending. After acknowledgement every new admission reloads an entry meeting the acquired version floor. |
| E/V reader after exact acknowledgement, before entry reload | Coordinator may finish invalidation and retire old code. On release the reader reloads, waits on zero or admits a current version; retaining the old pointer is a violation. No artificial RESUME wait is added to E/V. |
| S/M reader before exact STOP acknowledgement | Its existing bounded call may finish; mutation remains pending until all exact acknowledgements. Stale-epoch acknowledgement cannot satisfy the wait. |
| S/M writer after all acknowledgements, through mutation, before RESUME | Readers make no new admission until matching RESUME, then reread the entry/version and apply the declared ISB. Mapping old/new observations follow this boundary. |
| Translator before final validation | Invalidation may complete first; the subsequently submitted old-version translation is rejected at final validation. |
| Coordinator after successful final validation, before installation | A competing invalidator may enqueue its request but cannot acquire ownership or complete. Installation occurs first; the later invalidation must remove and drain it before completion. The inverse schedule invalidates first and rejects the stale candidate. Bypassing this ownership rule is a deterministic negative, not a permitted interleaving. |
| Writer before reuse while an I/E/V/S reader retains an execution right | Reuse waits for the arm's retirement/quiescence condition. After that condition reuse at the same address with a new token is allowed; admission using the old token is not. |
| Delayed producer or second producer seeking ownership | Readers may continue under their arm's admission rule; the second mutation grant cannot overlap the first. No claim requires all readers to block. |

The frozen hook manifest maps every named hook to a row and actor/arm, or
records a justified NA (for example hazards in E, or concurrent same-worker
construction/execution in V). Coordinator sequence numbers and causal
arrive/attempt/release handshakes establish order, not timestamps. Hook
mailboxes do not clear hazards, acknowledge on behalf of readers, grant
mutation ownership, or introduce a new global reader lock. For the held
generated call, the code-review packet must specify a bounded host-helper
handoff and atomic release-flag access; the hook cannot invent an unreviewed
machine-code atomic operation. The unhooked stress stage remains separate.

## Controls

- Positive controls must witness every reader execute at least two valid
  generations, a superseded reader safely finish before retirement, an actual
  slot reuse at the same address with a new token, every worker stop/resume,
  and every mapping worker observe old and then new data. Readable-neighbor
  and restored-protection controls accompany PROT_NONE tests.
- Required deterministic negatives are early publication of an intentionally
  complete *wrong-generation* block; corrupted returned generation; forced
  stale translation publication; stale acknowledgement; double writer grant;
  early retirement while a held reader owns the token; same-address/new-token
  ABA; delayed installation bypassing version/invalidation ownership; dropped
  reader acknowledgement; and missing/truncated/duplicate trace
  records. Each must trigger its named oracle. Early-retirement/double-grant
  negatives first fail the pre-execution state oracle; they must not obtain
  a success merely by deliberately creating a C data race or arbitrary UAF.
- Protection negatives launch separate child processes before threads exist,
  write a durable pre-access marker, then attempt one known forbidden access;
  normal signal termination and the paired accessible/restored controls are
  checked. No signal handler returns to modified JIT code. Missing child
  status, unrelated early failure, or absent pre-access marker is invalid.
- Omitted cache invalidation, omitted reader ISB and early cache publication
  with otherwise valid bytes are **sensitivity arms**, isolated from accepted
  protocols. They may pass on this finite run; absence of a mismatch is
  INCONCLUSIVE and never rejects the oracle or disproves the source obligation.
  No primary acceptance criterion requires a hardware race to appear.
- Baselines: immutable single-thread diagnostic, patch-free data indirection,
  and the same coordinator handshakes with no code/mapping operation. They
  characterize instrumented overhead; they are not a QEMU comparison or a
  promised subtraction isolating one API's intrinsic cost.

## Confounders

- Preflight captures exact model, OS build, SDK/compiler, page size, logical
  and physical CPU counts, process limits, power/thermal/load observations,
  signing flags and entitlements, sandbox state, requested/returned QoS and
  executable hashes. No instruction is inferred from source spelling alone.
  Placement is uncontrolled unless an independently accepted instrument can
  sample it; no presumed P/E pinning or CPU overlap percentage is reported.
- Deterministic hook runs add synchronization and can mask races; unhooked
  stress runs are separately required. SC hazards deliberately strengthen
  data ordering, so success cannot transfer to a release/acquire-only hazard
  variant. Trace writes are thread-private and preallocated; trace-enabled
  cost includes their overhead. Writer serialization and bounded generated
  blocks limit the liveness claim.
- Migration, thermal/load drift, scheduler preemption, cache warmth and
  quiescence policy may dominate tails. Timeouts and capability denials stay
  visible. Sleep/wake, cancellation, asynchronous faults during write, dynamic
  vCPU addition/removal and resource exhaustion beyond the cap below remain
  explicit unresolved cells with the existing owners, not passed controls.

### Quantitative instrument and validation stage

After the INV-01-07 prerequisite passes, collect 10000 back-to-back clock pairs
per worker/coordinator before and after each cost process, timebase numerator/
denominator, and exact integer conversion fixtures. Use the coordinator's
clock for every reported interval. No reader timestamp is subtracted from a
writer timestamp; no forward latency is derived from half a round trip.
The instrument does not assume timestamps are comparable across threads.
The pre/post p99 and resolution thresholds below use the coordinator's pair
sets only. Worker pair sets are retained diagnostics, never pooled into that
threshold or substituted for the reporting clock.

Zero back-to-back differences are valid quantization observations: retain them
in the clock-pair distribution and report their count/fraction. Compute each
pre/post pair p99 over all 10000 observations, including zeros. If either whole
pair set is zero, classify CLOCKPAIR-CALIBRATION-UNRESOLVED and retain raw data
without quantitative cost claims; this is not evidence of a backward clock.
Backward readings, arithmetic overflow or failed timer controls invalidate the
cost process. Integer threshold arithmetic is checked for overflow.

Before evidence, set `Fpre = max(100 raw ticks, 20 * pre-pair p99)`. Run exactly
64 calibration-only no-operation-handshake batches at each batch size 1, 16,
256 and 4096. A candidate size qualifies only if every one of its 64 durations
is strictly greater than Fpre. In particular, any zero batch makes that size
insufficient; do not drop zeros or take a minimum over only positive values.
Freeze the smallest qualifying size for that child's evidence. If none
qualifies, report UNRESOLVED-AT-INSTRUMENT-RESOLUTION and no quantitative cost;
do not tune further. Report gross intervals and divide-by-count averages, not
individual-operation percentiles inferred from batch averages.

After evidence, set `Ffinal = max(Fpre, 20 * post-pair p99)`. Every one of the
1000 evidence batches must be strictly greater than Ffinal. Any zero or
sub-threshold batch makes the whole child's cost result resolution-unresolved;
preserve all raw observations but do not select a favorable subset or publish
that child's quantitative cost summary. Do not retune batching after seeing
evidence. A zero batch is insufficient resolution, distinct from a backward
reading or overflow. The same fixed rule applies to all reported timed phases:
an unresolved subphase cannot inherit resolution from a longer gross interval.
No subtraction of baseline yields a claimed pure API latency. Publish both
gross distributions with trace/instrument configuration; comparative causal
effect estimation and confidence intervals belong to Q-04-01/Q-05-08.
