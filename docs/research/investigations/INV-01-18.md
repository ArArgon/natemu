## Question and decision relevance

- Question ID and text: `Q-01-18` — What host-side cross-thread protocol makes
  a shared code cache and process-wide mapping changes safe while other vCPU
  threads execute—code publication and instruction-cache coherence, live-code
  patching, and quiescence/safepoint entry and exit—and at what latency and
  cost?
- Decisions affected: translation-family admissibility under SMP; the
  `INV-01-02` family register; `Q-01-19`; correctness work in `Q-02-02`; and
  the later cost model in `Q-04-01`.
- Why this must be resolved now: accepted mechanism probes cover only pieces
  of the composition. None establishes that concurrently executing vCPU
  threads can safely observe, stop for, patch, invalidate, and reclaim shared
  translated code at the required 2/4/8-vCPU topologies.

## Assumptions

- Declared assumptions: routine operation is unprivileged and uses public APIs;
  the acceptance topology is 2/4/8 vCPUs; correctness failures invalidate cost
  measurements; observations remain host/OS/signing-cell specific.
- Assumptions to challenge: a shared mutable cache is necessary; writer-side
  cache invalidation is sufficient for every reader; atomic entry publication
  makes code bytes coherent; all vCPUs can reach a safe point promptly; and
  single-thread transition costs transfer to contended publication.

## Hypothesis and falsifier

- Hypothesis: one or more immutable-publication, patch-and-quiesce,
  epoch/RCU, per-vCPU-cache, or indirection protocols can meet the correctness
  conditions at 2/4/8 threads using public APIs in an admissible distribution
  configuration.
- Falsifiers: wrong/partial/stale code executes; entry metadata and code bytes
  disagree; a retired block executes; an invalidation is missed; safe-point or
  reclamation completion is unbounded under an admitted scheduling cell; or
  every protocol depends on a prohibited API/signing condition.
- Predicted outcomes: none frozen before source analysis and method review.
