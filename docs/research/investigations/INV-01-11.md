## Question and decision relevance

- Question ID and text: `Q-01-11` — Are contemplated dependencies and
  sources of study license-compatible with intended distribution?
- Decision(s) affected: family eligibility (`INV-00-06` family-kill item 4);
  `KA-10`; the still-open `Q-01-01`/`Q-06-03` distribution-model decision,
  which this record cannot itself make but must resolve conditionally
  around.
- Why this must be resolved now: a technically admissible architecture
  family could still be unusable if its required dependencies are
  license-incompatible with every distribution model the project could
  plausibly choose; that must be known before `Q-01-02`'s family register
  closes, not discovered after planning begins.

## Assumptions

- Declared assumptions: the distribution model is undecided — `INV-00-05`
  keeps distribution form, signing/notarization, and entitlement
  feasibility as mandatory `Q-01-01`/`Q-01-11`/`Q-06-03` research, not a
  settled input — so every compatibility judgment below is conditional on
  one of two candidate models, never absolute; "study only" (reading source
  to understand behavior), "link" (compiling against or embedding a
  library), and "redistribute" (shipping a dependency's code or a
  derivative inside NatEmu's own binary) are treated as three different
  obligations, and a dependency's compatibility is asked separately for
  each use mode a family might need.
- Assumptions to challenge: that "the project is open source" settles
  license compatibility (a permissive-open-source binary can still be
  license-incompatible with a copyleft dependency it links, per the
  analysis below); that reading source code to understand an algorithm
  ("study only") itself triggers redistribution obligations (it does not,
  under copyright — but reimplementing from memory without a clean-room
  process can still create a derivative-work risk, which is a distinct,
  unresolved question this record flags rather than resolves); that a
  specification document's copyright terms are the same question as
  whether implementing the standard it describes is patent-encumbered
  (they are legally distinct, and this record resolves neither for the
  hardware/firmware specifications it has not yet inspected).

## Hypothesis and falsifier

- Hypothesis (`KA-10`): every dependency and source of study this record
  can currently classify is compatible with at least one of the two
  candidate distribution models under an appropriate use mode; no
  dependency is unconditionally incompatible with both models under every
  use mode a family might need.
- Falsifier(s): a dependency found incompatible with *both* candidate
  models under *every* use mode a surviving family requires is a candidate
  family kill under `INV-00-06` family-kill item 4 (see the combination
  table in Resolution). A future finding that Intel SDM/AMD APM/Arm ARM
  terms restrict even "study only, no redistribution of the text" use would
  be a project-wide falsifier, since every family needs some ISA reference.
- Predicted outcomes: GPL-2.0 dependencies (QEMU, Linux) are compatible with
  both models under "study only" and "run as unmodified guest/external
  comparator" use, and compatible with a permissive-open-source-binary model
  only if that model accepts GPL-2.0-compatible terms for any combined,
  redistributed work — never compatible with a proprietary-binary model
  under "link"/"redistribute" use. Permissive dependencies (LLVM, Capstone,
  Zydis) are compatible with both models under every use mode.

## Method

- Procedure and versions: fetch each dependency's own license text at a
  pinned tag/commit (not a secondary summary or package-registry badge);
  classify its use mode(s) a plausible NatEmu family would need; judge
  compatibility against each of the two candidate distribution models
  below; leave unjudged what has not been inspected.
- Inputs and configuration: the enumerated dependency/source-of-study list
  from `BP-01-11-start.md`.
- Evidence labels assigned to planned claims: Source-backed for the license
  texts actually fetched (`CLM-01-11-01`–`-05`); Inferred for the
  compatibility reasoning applying those texts to the two use-mode/model
  combinations (`CLM-01-11-06`, `-07`); Hypothesis for everything not yet
  inspected (see Limitations).

### Candidate distribution models

Per `INV-00-05`, the distribution model is undecided; this record uses two
named candidates so every compatibility judgment below is legible once
`Q-01-01`/`Q-06-03` narrow the actual choice:

- **Model A — permissive open-source binary.** NatEmu's own source and
  compiled binary are published under a license that itself permits
  redistribution and modification (for example MIT, BSD, or Apache-2.0),
  but the distributed *combined* binary may still be bound by any copyleft
  license among its linked/incorporated dependencies — Model A is not
  itself a promise that every combination is GPL-free.
- **Model B — proprietary binary.** NatEmu's compiled binary is distributed
  under terms that do not grant source access, modification, or
  redistribution rights to end users.

### Legal-uncertainty statement

This audit applies ordinary, non-legal-professional reasoning to published
license texts and is not legal advice. Four categories of uncertainty
remain open regardless of which rows above are later completed: (1) whether
"study only" followed by independent reimplementation, without a
documented clean-room process, creates derivative-work risk under a
copyleft dependency's license — a process question this record does not
resolve; (2) whether implementing an instruction set a specification
describes carries a separate patent dimension distinct from the
specification document's copyright terms — for Intel specifically,
`CLM-01-11-09` shows the SDM's own document license grants an
implementation right explicitly scoped to software "intended to execute on
the Intel product(s) referenced in this document," and whether an
arm64-hosted emulator reproducing x86-64 semantics without executing on
Intel silicon falls inside or outside that scope is a real, unresolved
question this record surfaces rather than answers; the corresponding Arm
and AMD document-license terms were not reached this session (`SRC-146` got
only Arm's public-distribution classification, and amd.com was unreachable
— see Limitations), so the same question is open for those ISAs too, sourced
or not; (3) `libslirp`'s core permissive grant (`CLM-01-11-14`) does not by
itself clear the six other bundled copyrights its own `COPYRIGHT` file
discloses and defers to per-file headers — an unaudited residual risk, not
a cleared dependency; (4) every remaining "Hypothesis" row is an explicit
gap, not a compatibility finding, and must not be read as clearance.
`Q-06-03`'s lifecycle-cost estimate should include the effort to close
these gaps (dedicated legal review for any family that reaches planning,
and specifically counsel on the Intel/Arm/AMD implementation-scope question
above) as a recurring cost, not a one-time task this record has already
discharged.

## Controls

- Positive controls: a dependency with an unambiguous, fetched, permissive
  license (MIT/BSD-family — Zydis, Capstone) must resolve "compatible" under
  both models for the linking use mode; this is the sanity check that the
  method's compatibility logic is not systematically over-restrictive.
- Negative controls: GPL-2.0 QEMU/Linux under the "link/embed into NatEmu's
  own binary" use mode must resolve "incompatible" under Model B; this is
  the check that the method's logic is not systematically under-restrictive.
- Baselines: none; this is a document-classification audit, not a
  comparative measurement.

## Confounders

- Known confounders: a project's license can change between the pinned tag
  cited here and a later version NatEmu might actually depend on; a
  dependency can itself bundle third-party code under a different license
  than its top-level LICENSE file states (not checked for any dependency
  above); "GPL-2.0-or-later" versus "GPL-2.0-only" changes compatibility
  with some (but not this record's) permissive combinations and must be
  read precisely per dependency, not assumed uniform.
- Mitigations and residual risk: every Source-backed row cites an exact
  tag/commit, not "latest"; the QEMU and Linux rows explicitly separate
  the GPL-2.0-only carve-out and syscall-note exception from the general
  GPL-2.0(-or-later) statement rather than collapsing them. Residual risk:
  bundled third-party code inside any dependency is unaudited.
