## Question and decision relevance

- Question ID and text: `Q-01-13` — What exact guest machine contract
  defines transport, discovery, ACPI tables, APIC mode, timers, UART,
  reset/shutdown, and negotiated device features?
- Decision(s) affected: the machine-contract option set `Q-01-09`'s device
  backings must be compatible with; `Q-02-03`'s CPU/vendor contract; the
  boot method Track 02 tests; no production machine design.
- Why this must be resolved now: `KA-12` — "A guest machine contract
  satisfiable by stock Linux drivers exists for the device set without
  firmware (direct boot)" — gates project stop input 3, and `INV-00-02`'s
  accepted compatibility-boundary resolution explicitly assigns this
  investigation the job of selecting "the Virtio transport and negotiated
  features, ACPI/APIC table subset, discovery path, timers, reset/shutdown
  behavior, and verify[ing] required stock drivers" (`INV-00-02`,
  "Resolution").

## Assumptions

- Declared assumptions: direct boot without firmware (BIOS/UEFI absent, per
  `Q-00-02`'s accepted boundary); the guest kernel/distribution candidates
  are `Q-00-02`'s pinned Linux 6.12.108/6.18.49 upstream and Ubuntu 26.04
  LTS/Debian 13 stable; "unmodified" per `INV-00-02`'s definition (stock
  kernel/initramfs, no rebuilt kernel config); the device backings this
  investigation may combine into a machine contract are bounded by whatever
  `INV-01-09` finds admissible; no production machine design is selected
  here.
- Assumptions to challenge: that "no ACPI" and "no firmware" are the same
  constraint (they are not — a loader can synthesize ACPI tables in guest
  memory and hand the guest a pointer without any BIOS/UEFI firmware being
  present or executed, which this investigation's source analysis below
  finds is exactly how Linux's own boot-protocol ABI is designed to work);
  that virtio-pci requires ACPI (Virtio's own PCI-discovery text does not
  say so; whether the underlying PCI configuration-access and interrupt-
  routing mechanism requires it is a question this investigation's inspected
  sources do not fully settle, recorded as an open item below); that xAPIC
  and x2APIC are independent choices from the ACPI table set (MADT itself
  encodes which one is present, per the source analysis below).

## Hypothesis and falsifier

- Hypothesis: at least one internally-consistent machine-contract option set
  exists — combining a transport (virtio-mmio or virtio-pci), a discovery
  path, an ACPI-table subset (from none/minimal through the full named
  subset), an APIC mode, a timer set, a UART-or-console choice, and a
  reset/shutdown mechanism — that (a) is satisfiable by drivers enabled in
  at least one accepted stock Linux kernel/initramfs configuration, and (b)
  does not require any firmware to execute. `KA-12`'s falsifier is that no
  such option set exists. The upstream Kconfig inventory alone does not
  establish condition (a).
- Falsifier(s): if every combination assembled from this investigation's
  bounded candidates turns out, on Track 02 boot testing, to require either
  firmware execution or a kernel/driver feature absent from every candidate
  stock distribution's default build, `KA-12` fails and routes to project
  stop input 3. A narrower falsifier already identified above: if
  `CLM-01-13-15`'s open PCI/ACPI coupling resolves such that virtio-pci
  categorically requires ACPI, virtio-mmio would be the only no-ACPI
  transport candidate in this inventory; that would not by itself establish
  that the candidate is admissible.
- Predicted outcomes: the testable Hypothesis is that Track 02 can assemble
  at least one bootable contract from the bounded candidates below. Source
  inspection has not established that a complete virtio-mmio/no-or-minimal-
  ACPI or virtio-pci/ACPI combination works, and this record neither selects
  a combination nor predicts comparative performance.

## Method

- Procedure and versions: for each named decision-point dimension (transport,
  discovery, ACPI-table subset, APIC mode, timers, UART/console,
  reset/shutdown, e820), inspect the primary specification section(s) named
  in the brief, fetch and locally capture the exact text/section cited
  (Apple-doc-style JSON where applicable is not relevant here; captures are
  PDF/HTML for the specifications and plain-text `git.kernel.org/plain`
  fetches pinned to Linux tag `v6.12` for kernel documentation/source), and
  cross-reference the exact stock-driver Kconfig symbol(s) each option
  requires. No production design is selected; the deliverable is the
  decision-point table in Results, separating source-established mechanisms
  from inferred or unestablished composition dependencies under
  `INV-01-09` and `Q-01-07`. No option set is declared executable by this
  source analysis.

## Confounders

- Known confounders: (1) OASIS Virtio 1.4 CS01 is a fixed committee
  specification, but ACPI 6.6 and the Intel SDM are living documents that
  can be revised; a later ACPI or SDM revision could renumber the cited
  sections, which is why each source-inventory row states its exact
  version/date rather than relying on a bare "ACPI 6.6" label. (2) Linux
  documentation prose (kernel-parameters, boot.rst) and the pinned kernel
  source's actual `.h`/`Kconfig` files can drift out of sync during a
  development cycle; this investigation cross-checked the `possible_cpus=`
  and `acpi_rsdp_addr` claims against the actual `v6.12` source rather than
  documentation prose alone specifically because the boot-protocol
  documentation's own "Protocol 2.14... DO NOT USE" note (visible in
  `SRC-024`'s capture) is a case where trusting prose alone would have
  produced a wrong, overly pessimistic claim about `acpi_rsdp_addr`'s
  availability.
- Mitigations and residual risk: every specification capture is hashed and
  stored under `artifacts/research/track01/source-snapshots/2026-09-03/`
  (git-ignored, per the evidence policy); the residual risk is that a
  distribution-specific kernel config (not inspected here, `Q-05-03`'s job)
  could disable a Kconfig symbol this investigation found present at the
  pinned upstream tag, which would not falsify this investigation's claims
  (which are about upstream Linux 6.12 as built, not about any specific
  distribution's shipped configuration) but would narrow which stock-distro
  guest a given option set actually works on.

### Implications for `KA-08`/`KA-12`/`KA-13` and families F1–F4 (no design selected)

This investigation bounds inputs to `KA-12`; it does not establish that a
complete guest machine contract is satisfiable. The open composition,

`KA-12` remains unresolved until the relevant source work and Track 02 boot

`KA-13`/`INV-01-14` and is not quantified here.

No option in the decision-point table is exclusive to one of F1–F4
(interpretation, dynamic binary translation, translation-under-
Hypervisor.framework, or AOT/dynamic-fallback): the guest machine contract
is a device/firmware-visible property of the *guest's* view of the machine,
independent of how the host executes guest instructions. A family that
cannot honor a chosen machine-contract option (for example, a family unable
to service device-generated interrupts at the latency `Q-01-07` requires)
would be screened by `Q-01-07`/`Q-01-08`'s own findings, not by this
investigation. This investigation therefore records the same bounded
candidate set and open dependencies for every family; it selects neither a
family nor a production machine design.
