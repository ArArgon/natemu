## Question and decision relevance

- Question ID and text: `Q-01-06` — Can guest faults be delivered precisely and
  restartably through available host mechanisms (signals, Mach exceptions, or
  explicit checks in generated code) on the supported hosts?
- Decision(s) affected: `KA-04`, and through it the admissibility of every
  family that relies on lazy faults; the protection-fault tracking scheme of
  `Q-01-05`; the composition question of `Q-01-19`; the prototype of `Q-01-12`;
  the containment classification of an unclassifiable fault in `Q-02-04`; and
  the fault-cost component of `Q-04-01`.
- Why this must be resolved now: an unmodified guest requires architecturally
  precise exceptions, and every lazy mechanism proposed elsewhere in Track 01 —
  protection-based write tracking, demand paging of guest memory, MMIO
  detection — assumes the host will deliver a fault with enough state to
  synthesize the guest exception and resume. If it will not, only explicit
  software checks remain, and only if `Q-01-12` shows they compose.

## Assumptions

- Declared assumptions: generated code runs on ordinary host threads in the
  emulator process; a fault raised in that code must be caught in that same
  process; the emulator, not the host, decides what guest-visible exception
  results.
- Assumptions to challenge: that "precise and restartable" is a host property
  — half of it is a property of the generated code's commit discipline, and
  this record cannot establish that half; that a faulting address is sufficient
  to synthesize a guest `#PF`, when access type, width, and destination
  register are also needed; that `ucontext` writes are honored; that a resume
  PC can be an arbitrary integer on a platform with pointer authentication;
  that signals and Mach exceptions are interchangeable; that a single-threaded
  latency describes delivery under concurrency; and that a successful resume
  implies correct resumed state.

## Hypothesis and falsifier

- Hypothesis: POSIX signals with `SA_SIGINFO` deliver faults raised in
  generated code to the faulting thread with the complete arm64 thread state
  and the arm64 exception syndrome and fault address, and writes to that state
  are honored on return, so the host half of precise restartable exceptions is
  available without Mach exception ports and without private API.
- Falsifier(s): the handler does not receive the faulting PC or the general
  registers; `__far`/`__esr` are not populated for a memory fault, forcing
  instruction decoding; a modified PC or register is ignored on return; a
  resume PC must be a signed pointer that a handler cannot legally construct;
  delivery under concurrency reports another thread's state; or a fault class
  the guest needs is not deliverable at all.
- Predicted outcomes: all three fault classes delivered as distinct signals
  with the stub PC and, for the memory case, a matching `__far`; both resume
  paths succeeding with the declared register value observed by the caller;
  single-digit-microsecond median delivery; correct per-thread state under two
  concurrent faults; and `KERN_SUCCESS` from every Mach exception-port call.
  The most consequential negative would be an ignored state write, which would
  kill lazy-fault families outright.

## Method

This section records the method used for the retained original evidence. Its
collection-time repository/commit checks remain historical interpretation only;
new work follows the research workflow and builds from retained snapshots.

- Procedure and versions: `experiments/INV-01-06/src/probe.c`, built by
  `Makefile` with Apple clang 21.0.0 at `-O1 -Wall -Wextra -std=c11` against
  SDK 26.4, driven by `run.sh`. The probe records the compiled state-struct
  configuration, then assembles three arm64 stubs into a `MAP_JIT` region —
  an unmapped load (`ldr x2,[x1]` with `x1` a chosen bad address), an undefined
  instruction, and `brk #0` — each followed by `ret`. Handlers are installed for
  `SIGSEGV`, `SIGBUS`, `SIGILL`, `SIGTRAP`, and `SIGFPE`. The handler resumes
  **only** a fault the faulting thread armed, at a program counter inside the
  JIT region: an unarmed fault exits the process with status 96 and a fault
  outside the region with status 95, rather than being advanced past and
  reported as a successful resume. Before the return cycle the handler resumed
  any fault anywhere in the process, so a stray write elsewhere in the probe
  was silently swallowed and the run still reported `PASS`. Each stub is called
  with the bad address in the second argument register and a zero in the first;
  the handler records the program counter, stack pointer, `x0`, `x1`, `__far`,
  and `__esr` into thread-local storage, then advances the PC past the faulting
  instruction and writes a declared sentinel into `x0`, so the caller's returned
  value is a direct test of whether the requested state took effect. The PC is
  written through `__darwin_arm_thread_state64_set_pc_fptr`, the portable
  accessor, and the build's `__DARWIN_OPAQUE_ARM_THREAD_STATE64` and
  `ptrauth_calls` settings are recorded so a reader knows whether that accessor
  and a direct field assignment are the same operation here (they are). Each
  case also records the `uc_mcsize` the kernel reported. Each case's
  single cold delivery interval is recorded under a name that says so
  (`cold_delivery_ns_single_observation`) and supports no timing claim.
  Delivery latency proper is then measured over 3000 faults as the interval
  from immediately before the faulting call to the first statement of the
  handler; an attempt in which no fault was delivered is counted as a miss and
  excluded rather than recorded as an unsigned wraparound of a stale
  timestamp, and any miss fails the run. Two threads
  are released together to fault on distinct bad addresses, each verifying that
  the `__far` it observed was its own. Finally a scratch thread that takes no
  fault allocates a Mach port, inserts a send right, inspects the task's
  `EXC_BAD_ACCESS` ports, installs and immediately removes a thread-level
  exception port, and records every `kern_return_t`.
  The probe emits `mach_timebase_info`'s numerator and denominator so a later
  reader can evaluate any reported interval against the clock quantum without
  this host, and it deallocates the thread send rights it acquires.
- Inputs and configuration: no external inputs; the bad addresses, the declared
  sentinel, and the iteration count are compiled in and echoed in the output.
  `run.sh` enforces the `NATEMU_RAW_ROOT` rule and builds into the run
  directory. The environment capture is as in `INV-01-03`, including the
  binary's signing configuration.
- Evidence labels assigned to planned claims, as resolved by the 2026-09-04
  evidence run (`MAN-01-06-01`): `CLM-01-06-06` through `CLM-01-06-12` are now
  **Observed** for this host and build configuration, and `CLM-01-06-13` is
  **Inferred** over them, remaining explicitly partial with respect to the
  commit-discipline half of restartability. `CLM-01-06-14` (the per-thread
  property of an alternate signal stack) stays a **Hypothesis**: the probe
  installs no alternate stack and did not test it. No planned claim was
  refuted.

## Controls

- Positive controls: the caller's returned value must equal the sentinel the
  handler declares it wrote — control returning without the requested state is
  not a restart; the reported PC must be the faulting stub's address; the stack
  pointer must be non-zero; for memory faults `__far` must equal the attempted
  address; in the concurrent case each thread's observed `__far` must be its
  own.
- Negative controls: `probe --negative` makes the handler write a value one
  less than the declared sentinel, so control returns but the state does not.
  `src/check.py` must print `FAIL` on that output and `PASS` on the normal
  output; `run.sh` runs both and prints each verdict.
- Baselines: the single-thread case is the baseline for the concurrent case.
  The resume path has no baseline, because the probe uses one path: a direct
  `__pc` assignment is not an independent comparator in this build, since the
  accessor preprocesses to it. No cross-system baseline applies.

## Confounders

- **Declared assumption: async-signal-safety of the probe's own handler.** The
  handler calls `mach_absolute_time()`, writes thread-local variables, reads
  and writes the `ucontext_t` the kernel supplied, and on a refusal path calls
  `_exit`. Of these only `_exit` is on the POSIX async-signal-safe list. This
  record treats the others as valid on this platform because
  `mach_absolute_time()` reads a user-mapped timebase page rather than taking a
  lock or entering the kernel, thread-local writes touch storage owned by the
  faulting thread alone and by nothing else in the process, and the `ucontext_t`
  is the kernel's own per-delivery structure. That reasoning is an assumption,
  not a finding, and it is the reason the timing figure is a mechanism cost
  including one timestamp read rather than a pure delivery cost. It is exactly
  the handler-discipline question the group filed as `Q-01-19` and is routed
  there; a realistic emulator handler that allocates, locks, or logs needs that
  question answered before its discipline can be called admissible.
- Known confounders: an attached debugger or the crash reporter intercepting
  faults before the process sees them; the compiler reordering the timestamp
  read relative to the faulting call; handler code, alternate stacks, and lazily
  bound symbols being cold in early iterations; P/E-core placement and
  migration; thermal drift over 3000 faults; the two concurrent threads not
  overlapping; the handler's own `mach_absolute_time` read being counted in the
  latency it measures.
- Mitigations and residual risk: the environment capture records whether the
  run was made under any interposing configuration; the timestamp is taken
  immediately before the call and immediately on handler entry, and the
  resulting interval definition is stated with the result rather than left
  implicit; 3000 iterations make cold-start a small fraction and full order
  statistics are reported rather than a mean alone; the concurrent threads spin
  on a shared gate. Residual risk: placement is uncontrolled and the sample
  mixes P- and E-core executions; the latency necessarily includes the kernel's
  signal-frame construction and one timestamp read, so it is a mechanism cost,
  not a pure delivery cost. Both are stated as limitations, with placement
  routed to `Q-05-06` and timer validity to `Q-05-08`.

## Sample plan

- Units, repetitions, randomization/order, warm-up, and power/precision target:
  fault-class and resume-path cases are single observations, since delivery

  max because the tail is the product-relevant quantity. The concurrent case is
  one release of two threads. No warm-up is discarded; cold-start appears in
  the maximum rather than being hidden in a mean. No statistical precision

### Kill-assumption disposition and family implications


All dispositions below are bounded to `Mac16,10` (M4) / macOS 26.6.2 (`25G83`)
/ SDK 26.4 / ad-hoc signing, one host, one build configuration. None of them
disposes of a kill assumption as written, because every one of `KA-01`,
`KA-03`, `KA-04`, and `KA-07` quantifies over "the supported hosts" and `P1`
replication is owed. A kill assumption that is not falsified on one host
*survives*; it does not pass. No architecture family is selected here and no
production design is chosen.

- **`KA-04` survives on this host for the half a host can decide.** A fault
  raised inside generated code was caught with the full register set, the
  faulting PC, the stack pointer, the fault address, and the exception
  syndrome; the thread was resumed at a chosen PC with a chosen register value;
  this held for three distinct fault classes and for two threads faulting
  simultaneously, each seeing its own state. Delivery costs about 2.9 µs with a
  tight tail (p99 1.17× the median), and no fault of 3000 went undelivered.
  Mach exception ports are available at API level as a second mechanism.
- **The half this record cannot decide.** "Precise and restartable" also
  requires that generated code leave no partially applied guest state at the
  fault point. That is a property of a translator's commit discipline, not of
  macOS, and nothing here touches it; it belongs to `Q-02-01` and `Q-01-12`.
  The probe also *skips* the faulting instruction rather than restarting it,
  which suffices to test state installation but is not guest-visible restart
  semantics. Fault-cause recovery is better than the breadth pass feared:
  `__esr` and `__far` were populated for the memory fault and differ per fault
  class, so a handler can classify without decoding the faulting instruction.
- **Family implications.** The families that rely on lazy faults — `F2` and
  `F4`, and any `F1` variant using demand paging — are **not** killed on this
  host, and the fallback branch of `KA-04` (explicit checks in generated code)
  is not needed here, so the `INV-01-12` composition condition attached to that
  branch is not activated. `F3` would take guest faults at EL1 inside a VM and
  is untouched by this record. The pre-existing task-level `EXC_BAD_ACCESS`
  handler observed in an ordinary process is a live constraint on any design
  that would install its own Mach catch server, and the signal-versus-Mach
  ordering it raises is unresolved.

## Correctness status

- Correctness criteria and outcome: restart fidelity held in every case. All
  three fault classes and both concurrent threads returned exactly the sentinel
  the handler declared it installed; the handler attested it installed the
  state in every case; the reported PC was inside the faulting stub every time;
  no attempted fault went undelivered; and the armed guard never fired, so no
  fault outside the probe's own generated code was resumed. `check.py` returned
  `PASS` on the normal artifact and `FAIL` on the `--negative` artifact, in
  which the handler installs a value one less than the sentinel — so the
  checker demonstrably detects a resume that returns control without the
  requested state. No guest exception semantics are asserted; `Q-02-03` owns the manifest
  of guest-visible exceptions and `Q-02-01` the tests.
- Open correctness risks: a handler that misclassifies a host fault (for
  example a `SIGBUS` from a truncated file-backed mapping) as a guest fault
  would synthesize a spurious guest exception and corrupt the guest silently;
  this probe never encounters a host fault and therefore does not test the
  classification path, which is recorded for `Q-02-04`. Nested faults, faults
  taken while the thread holds JIT write permission, and faults during code
  patching are not exercised and are `Q-01-19`. The probe skips a faulting
  instruction rather than restarting it, which is sufficient to test state
  installation but is not the guest-visible restart semantics an emulator needs.

## Alternative explanations

- Alternatives considered: (1) the sentinel is observed because the compiler
  folded a constant rather than because the register write took effect —
  distinguished by the stub returning whatever is in `x0` after a fault the
  compiler cannot see through, in code the probe wrote at run time; (2) the PC
  advance worked because the faulting instruction was re-executed harmlessly —
  excluded, since re-executing the unmapped load would fault again and the case
  would not terminate; (3) `__far` matches by coincidence — implausible with a
  chosen, distinctive bad address, and separately confirmed by the two
  concurrent threads using different addresses; (4) the accessor path appears
  equivalent only because both compile to the same assignment in this
  configuration — acknowledged; that is exactly the configuration-dependence
  `CLM-01-06-05` records, and the ptrauth-enabled build remains an owed cell;
  (5) latency is dominated by the probe's own timestamp reads — not excluded,
  which is why the interval definition is reported with the result.

  Post-run disposition: (1) is excluded — the `--negative` variant returned
  1515870809 through the identical code path, which a folded constant could not
  do; (2) is excluded, since re-executing the unmapped load would have faulted
  again and the case would not have terminated, and all 3000 latency attempts
  terminated; (3) is excluded — `__far` matched a distinctive chosen address and
  the two concurrent threads matched two different ones; (4) is confirmed and
  is why the two paths are no longer presented as a comparison; (5) remains
  open and bounds the latency figure, though the cross-record arithmetic with
  `INV-01-05` shows the delivery interval is a coherent fraction of a full
  fault cycle rather than an artifact.
- Evidence distinguishing them: each is separated by a recorded field, by a
  control, or by an explicit statement that the record does not settle it.

### M06-M1 method and source-dependent stop boundaries

right, install only EXC_MASK_BAD_ACCESS with behavior
`EXCEPTION_STATE | MACH_EXCEPTION_CODES` and flavor `ARM_THREAD_STATE64`, and
associate that receive port with exactly one immutable worker descriptor.
The main task ports are inspected and recorded but not replaced. A dedicated
server is a normal host thread, not a signal handler or faulting vCPU; it owns
no lock needed by a stopped worker. Receive rights are not exported or reused
while the child runs. No host exception-port operation, elevated entitlement,
task-for-pid, private routine, thread_set_state, or raw IPC syscall is used.

The planned public MIG build consumes the pinned SDK mach_exc.defs and include
chain with user-space settings, all optional MACH_EXC_SERVER_* extensions off,

NDR representation and variable-array count checks from that output. Do not
hand-pack a guessed kernel message layout or copy an inherited catch server.

flavor, old-state count/natural_t words; the success reply carries return code,
flavor and new-state count/words. Any unexpected complex descriptor, routine,
NDR conversion, malformed count/size, truncated trailer or port identity is
