## Proposed coupled mechanism — hypothesis, not accepted finding

Everything in this section is **Hypothesis**: a concrete direction for the next
reviewable argument. It deliberately retains SMP parallel ordinary execution;
it does not substitute single-vCPU emulation for the required SMP architecture.

### Paging and all-writer admission

Use software x86 walks and native 4-KiB shadows initially, even for supported
2-MiB guest mappings. Walks enforce the selected CPU's address, reserved-bit,
privilege and access rules; native misses are classified from guest context.
Internal write traps and missing shadows are not automatically x86 #PF.
Page-fault error priority and A/D side effects come from the chosen x86 semantic
implementation, not from copying Arm syndrome fields.

Track translated-source and discovered table pages by guest physical identity,
including every shadow alias. Before first trusting a page as table or source,
stop admission, bring participants to a recoverable boundary, remove writable
aliases and complete maintenance, then read/validate its current contents. This
promotion must not leave a window where an old writable TLB entry can mutate
bytes after validation. New aliases consult the same physical-page state.

Guest writes to tracked pages trap before modification; the coordinator performs
or authorizes their architectural operation while peers cannot access conflicting
state. A/D updates use the same coherence/atomicity rules and preserve concurrent
software changes. The first write must establish required dirty state before
making a shadow writable. Changing x86 table pages triggers conservative shadow
revocation and rewalk; INVLPG, CR3 and relevant CR4/control changes retire the
required translation state even if eager tracking already evicted it. Avoid
persistent Arm ASID reuse initially: use distinct active contexts and a completed
full flush before reassignment. Exact global/non-global and no-invalidate x86
semantics still require the CPU-profile case analysis; hiding PCID does not
remove CR3, PGE or INVLPG obligations.

All shim stores, loader stores and backend writes participate. Use host bounce
buffers for host-kernel I/O, then commit into RAM through a coordinator request;
no `read`/DMA destination points directly into guest RAM. Backend readers also
join exclusion where an atomic fallback requires indivisibility. An operation
carries VM/device lifetime and validated GPA ranges; validation alone does not
pin ownership. RAM remains pinned until completion/cancellation is acknowledged.
Completion notification follows committed bytes and applicable code/table
invalidation. A device input may target a page that became code or a table after
submission; classification occurs again at commit.

Memory-type emulation is still a blocker: normal WB RAM and separately routed
MMIO do not alone account for guest PAT/MTRR/cache-control operations. Do not
silently map all permitted guest types to one Arm attribute. Establish allowable
strengthening, aliases and ordering against the exposed CPU before choosing that
shortcut. Hardware page sizes larger than 4 KiB remain an optimization only after
code/table write tracking works at its required physical-page granularity.

### Remapping, atomicity and partial effects

A split or helper operation validates its architecturally required accesses under
a pinned mapping generation; remapping cannot change routing between permission
check and commit. Ordinary single-native-instruction operations can overlap until
a rendezvous closes admission and drains in-flight effects. Any sequence requiring
multiple native operations must declare its guest commit/recovery points. Preserve required instruction-specific partial progress and choose an
architecturally permitted fault outcome; there is no requirement to reproduce
every hardware decomposition or every optional partial effect. Already-visible
effects cannot be rolled back or replayed. Do not replay an already committed
MMIO transaction or invent a split-lock #AC to avoid implementing a valid operation.

Use native aligned atomics only for forms whose host width/alignment/ordering
contract is established for the chosen lowering. Otherwise rendezvous **all**
ordinary guest accesses, helpers and backend observers, perform the emulated
operation, then release them. A mutex used only by atomic helpers is insufficient.
The coordinator must not park a participant holding a lock needed by another
participant to acknowledge quiescence. Control requests and recovery proceed
independently of emulated guest IF, halted state and translator response arrival.
A host-forced native-PC stop must first recover to a valid x86 boundary or retain
the in-flight operation; it is not an acknowledgement by itself. On timeout,
terminate the VM and drain host work; never resume an unsafe partial operation.
Unaligned but cache-line-contained ordinary x86 accesses and AVX-dependent
16-byte operations need their own lowering guarantees or this fallback too.
Selected translator sequences, not the TSO bit, determine whether those
operations are indivisible. TSO also does not order host publication by itself;
host/guest synchronization needs explicit release/acquire and barriers justified
for the selected shared-memory attributes.

### Code identity, invalidation and reclamation

A translation request identifies VM lifetime, address-space/mode/control-state
identity, guest linear PC, all source GPAs and their generations. Freeze source
bytes under the same writer admission protocol; the translator receives a copy.
Before accepting a reply, revalidate its lifetime, source generations and mapping/
CPU dependencies. Enabling a new writable alias or accepting a new writer cannot
race this check. Validate response size, relocation targets, metadata and allocator
ownership; the reply never chooses an arbitrary VM destination.

Start with the accepted register-transfer publication direction: shim copies host
bytes to an unentered allocation, completes the required native cache maintenance,
then exposes metadata and an entry with an ordering protocol. Every executor
performs the required context synchronization. Permission transitions, if chosen,
need their own TLBI argument. Use immutable blocks and guarded data links; no
live instruction-patching requirement. Lookup and links both check the applicable
identity/generation, so removing only a central lookup entry is insufficient.

For mutation, prevent new entries, quiesce conflicting execution, retire lookup
and links, apply the write, increment physical-source generations, then resume
through dispatch. A trapped self-write resumes at the correct next guest boundary
or instruction-specific partial-progress point, never blindly at an old native
continuation. Early invalidation is proposed as a conservative implementation;
the candidate note's stronger universal claim about the immediately next x86
instruction is not used as the architectural source contract.

Initially reclaim with a whole-cache quiescent flush under pressure, avoiding a
new fine-grained collector. Reuse requires **no** outstanding native PC, return
address, exception frame, helper continuation, recovery lookup, link or publication
callback into the retired allocation. Merely exiting `hv_vcpu_run` does not meet
that predicate. Parked CPUs must canonicalize or retain their referenced objects;
a timed wait never substitutes for an acknowledgement. A stale reply cannot
publish into a newly reused slot. A CPU unable to leave an in-flight operation
causes bounded VM failure rather than unsafe reuse. A practical recovery protocol
and its cost remain unestablished; an ever-growing pinned cache is not selected
as a solution to resource exhaustion.

### Privilege and private-address constraints

The architecture record now prioritizes **guarded EL1** execution; EL0 with
EL1-only shim mappings remains an alternative, not complete isolation. Generated-code pages and any EL0-accessible CPU state still occupy
native addresses forbidden to guest operations. The x86 noncanonical/native-valid
space can host private allocations only if **every** guest-originated effective
address is formed and checked according to its current x86 mode, including
segment/mode rules and the entire access span before a native access. Long-mode
canonicality checks do not replace protected32 segmentation, address-size wrap
and limit checks. Overflow is handled as the selected instruction/mode specifies,
not uniformly rejected where x86 wraps. Upper/lower boundary crossing and vector/REP
forms count. Helpers cannot bypass those checks. Guest branches resolve through
validated guest-PC lookup; they cannot use raw guest numbers as native targets.
Guest RAM is native non-executable. Trusted native links and payload installation
have separate destination validation. EL1 execution would need at least the same
software exclusion for shim state and additionally lacks the EL0/EL1 permission
barrier. Track 01's controlled RWX layout proves neither alternative safe.
The architecture record owns the final privilege and translator trust boundary.

### States, admission and authority

Coordinator state is `OPEN(e)`, `CLOSING(e)`, `EXCLUSIVE(e)`, `RELEASING(e+1)`,
or `DEAD`, with a strictly increasing nonwrapping VM generation `e`. Exhaustion
terminates this VM lifetime instead of wrapping. Exactly one coordinator owns
transitions and request ordering. Other host/vCPU threads enqueue requests;
none can become a second coordinator while holding an operation in progress.

A participant is either `IDLE`, `ACTIVE(e)`, `DRAINING(e)`, `PARKED(e)`, or
`MAINTENANCE(e)`. Participants include every vCPU owner and every host/shim actor
that reads or writes shared RAM, source/code publication state or relevant
mapping/metadata. Native execution under one vCPU is one participant, including
its helpers and synchronous exception handling; nested calls do not acquire new
admission. Kernel I/O into private bounce buffers is not a RAM participant, but
its eventual completion/commit is. Device descriptor reads and output snapshots
are participants as well as input writes; otherwise split-atomic exclusion would
be incomplete.

The host admission mutex protects coordinator state and the participant registry.
It is held only for state changes and queue operations, never during guest
execution, RAM access, I/O, guest recovery or a wait for another participant.
Under that mutex, `OPEN(e)` grants `ACTIVE(e)` and records the participant **before**
the owning thread may enter the VM or touch shared data. Closure changes
`OPEN(e)` to `CLOSING(e)` under the same mutex. This change is the admission
linearization point. An already-admitted thread that has not yet entered still
counts as active and must cancel that entry or drain under its old token. No
new RAM access path can bypass the registry by being called “maintenance.”

For the guarded-EL1 candidate, a shadow context identity includes x86 address
space, paging mode, CPL and CR0.WP plus every selected permission control. A
CPL/control transition ends the prior generated interval; it cannot directly
link into a block under the old view. Before admitting the next interval, its
owner selects the matching shadow root and completes required context/TLB
maintenance. A root/tag reassignment or permission transition needing shared
maintenance is a coordinator transaction. Shared cached blocks may be reused
only when their state guards and mappings match. Native EL1 permission alone
never substitutes for an x86 supervisor/user check.

Code running inside a VM uses the owner's existing token. Generated block-entry
and loop polls inspect a privileged stop request; guest instructions cannot
modify its storage. Host VM reentry while closing is allowed only to drain that
same token toward a canonical park point. It is not permission to begin a new
guest interval. Queued host completion/request processing continues without
starting new guest/RAM work. Requests carry lifetime and source/queue generation;
an originator never assumes its queued operation was already committed.

### Request arbitration and drain

1. A tracked write, mapping update, fallback atomic, translation snapshot,
   source invalidation or cache flush produces a prepared request. Its issuing
   vCPU returns to a declared guest boundary with a pending operation descriptor
   rather than waiting while holding an execution-side lock. REP may present its
   architecturally valid completed-prefix state. A backend finishes its bounce
   I/O before requesting RAM commit. Preparing the request must not perform the
   protected effect that the transaction is supposed to serialize.
2. The coordinator chooses one request in FIFO arrival order, closes admission
   and requests every active participant to drain. Simultaneous vCPU requests
   queue behind that winner; their originators release their active tokens once
   canonical and do not wait for ownership while blocking the winner. A later
   request is revalidated against the state after earlier commits; FIFO does not
   make its stale address/permission assumptions valid.
3. A native interrupt or `hv_vcpus_exit` can prompt progress but cannot declare
   `PARKED`. A returned vCPU may still have a native PC or helper frame inside
   generated code. Its owner either resumes only the finite recovery/drain path
   or retains the reference and reports it cannot park. It does not acknowledge
   merely because the OS thread is stopped. Guest IF does not gate the host
   request or generated-code polls.
4. To acknowledge, the participant finishes required visible effects, preserves
   an architecturally valid restart/pending-fault state and removes all native
   continuations into retiring code. Required memory completion precedes its
   release acknowledgement; the coordinator acquires that acknowledgement.
   An in-VM participant uses the specified completion barrier before exit/ack;
   actual cross-host/VM attributes and barrier placement remain platform premises
   to establish, not consequences of the abstract state machine.
5. No park point holds a lock needed by another participant's drain. Helpers with
   local locks release them before acknowledgement; those unable to reach such
   a point report failure. Helpers cannot wait for external I/O while holding a
   RAM token. Any internal loop must have a finite bound or a recoverable stop
   poll. Translation waits have already spilled canonical state and relinquished
   execution, so they can acknowledge without awaiting their translation reply.
6. Only after every pre-closure token is accounted for and drained does the
   coordinator enter `EXCLUSIVE(e)`. A halted or host-waiting vCPU may already be
   canonical and idle; its owner confirms the same generation and absence of
   references rather than waking the emulated guest merely to obtain an ack.

A guest operation that cannot supply a permitted canonical stop after an external
side effect is a **lowering counterexample**, not permission to discard that
side effect. Such an operation must finish through bounded recovery before
acknowledgement, retain its references and prevent reclamation, or fail the VM.
A design in which ordinary valid instructions routinely require the last outcome
has not preserved the product's required behavior; fail-stop is a failure policy,
not a substitute for implementing those instructions.

### Exclusive transaction and release

In `EXCLUSIVE`, only the coordinator and a specifically granted maintenance
executor may access the protected resources. The grant is a distinct scoped token
whose authority permits a named transaction, not arbitrary guest execution. A
maintenance executor runs permanently retained shim routines, not reclaimable
translation-cache code; guest event delivery remains pending. For example the
coordinator stages code bytes and asks a stopped vCPU owner to run the shim's
copy/cache/TLBI routine via the selected request mechanism. Other participants
stay parked. If this routine itself faults outside its validated contract, the
transaction fails and the VM remains stopped.

The transaction rechecks lifetime, addresses, current guest permission/mapping
identity and source generations. Its architectural operation can return a guest
fault instead of committing a requested write, while retaining required earlier
architectural effects. A/D or nested metadata updates belonging to that operation
are performed inside the same exclusive transaction; they cannot enqueue a new
rendezvous and wait for it. A genuine new operation is queued for later. The
selected semantics implementation must define this distinction for nested faults
and event delivery.

For source/table mutation: revoke lookup/link/shadow eligibility, perform required
native maintenance, apply the authorized write, advance relevant source/mapping
generations, and prepare the resumed guest state. For code publication: validate
source and CPU identity, allocate/copy code and metadata, finish instruction-cache
publication, then expose eligibility. The guarded-EL1 baseline now uses runtime-only RWX native code allocations,
immutable while admitted, with all writes governed by this publication/retirement
protocol. Guest-derived data/control cannot reach them; guest RAM remains native
NX and private backing stays outside the guest-physical resolver. W^X is optional
hardening, requiring its own permission/maintenance assessment if later selected;
its absence does not remove any guest-exclusion or lifetime obligation. For reclamation: assert every code/metadata
reference is absent, detach all indexes/links and outstanding request identities,
then reuse storage. A stale callback can remain queued only as inert data bearing
its old lifetime; it has no pointer granting write access to the reused object.

Atomic fallback performs the whole operation while every conflicting observer is
excluded; barriers implement its required ordering before guest execution resumes.
No host/backend observer receives a maintenance grant to inspect the intermediate
value. The fallback does not merely protect competing LOCK helpers. Mapping pins
and lookup generations are checked inside the same transaction, avoiding a
check-under-one-map/commit-under-another split. Non-atomic operations retain their
specified partial-progress model rather than being silently made restartable.

The coordinator waits for completion of any maintenance grant before release.
`RELEASING(e+1)` installs the next identities and resume descriptors; each vCPU
performs required context synchronization before running new code. Opening
`OPEN(e+1)` under the admission mutex is the next admission linearization point.
Old tokens/acks/replies cannot authorize entry. Pending timer/IPI/device events
remain in their architectural queues and are delivered only at the execution
choice's legal boundaries. If another request is already queued, the coordinator
may process it while still exclusive after revalidation, but bounded batching must
not starve ordinary guest execution; its scheduling budget belongs to the final
progress/cost policy.

### Failure, limits and next decision-changing work

No automatic rollback, transparent retry or resumption of partially committed

Storage-durability policy remains with the device investigation.

### Concrete composition counterexample after findings return 1

## Rendezvous revision 2 — native pause and canonical park are distinct

**Current refinement:** independently accepted INV-03-01 claim19 reuses these
PAUSED/DRAIN_SERVICE states while replacing the every-instruction forced-exit
construction below with queued cold completion and bounded old-view drain before
mutation. Its admitted-route, exact special-event, partial-effect, lifetime and
fair-admission rules govern current work. The historical checkpoint proofs remain
valid for those particular lowerings, not a universal current requirement.


**Conditional proposal, subsequently reviewed in scope:** this revision supersedes revision 1's
requirement that every participant be canonical before exclusive maintenance.
It retains single-coordinator arbitration, admission closure, lifetime checks,
host bounce buffers and bounded failure. The semantic change is a weaker pause
predicate sufficient for exclusion, with a stronger predicate still required
for code/mapping retirement and ordinary resumption.

### Revised states and linearization points

Add `PAUSED(e, continuation)` alongside `PARKED(e)`. A pause means ordinary guest
and shared-RAM execution has stopped, earlier native accesses have completed,
and every remaining native continuation/temporary has an owned immutable record
with pinned dependencies. It does **not** claim an x86 instruction completed.
A park additionally means architectural state is canonical at a legal boundary,
with no outstanding native PC/helper return/recovery reference into a retiring
allocation. An idle translation wait may park; a second-half YMM shadow fault
normally pauses. The owner reports the distinction explicitly.

`OPEN → CLOSING` is still the admission linearization point under the host mutex.
`CLOSING → EXCLUSIVE` now requires each old token either (a) native-memory-quiescent
`PAUSED`, (b) canonical `PARKED`, or (c) a completed host operation with no remaining
RAM authority. Release acknowledgements still require the actual native/host
completion and visibility premises; a host exit at arbitrary PC is only a prompt
to acquire this state, not proof that all effects and registers were captured.

A paused continuation pins native code, metadata, helper frames, source/decode
identity, checked access routing/mapping versions and the owning VM lifetime.
It contains the complete saved native state or an equivalent proven semantic
continuation. Access phase identifies completed effects and the next operation;
a guest RIP alone is insufficient. The captured decoded instruction cannot be
silently replaced by freshly read source bytes while its effects are incomplete.
Unperformed access checks still use the instruction's specified fault ordering;
there is no blanket whole-instruction prevalidation requirement.

### Drain service under exclusion

Once all participants are memory-quiescent, the coordinator can grant **one**
paused participant `DRAIN_SERVICE(e)` using its retained continuation. Other CPUs,
ordinary host RAM readers and writers remain paused/parked; admission stays closed.
This is exclusive execution of the captured in-flight operation, not ordinary
guest scheduling or entry into another guest instruction. Permanent shim routines
may repair a shadow, classify a true fault, service a pending tracked write or
perform an atomic fallback. They use the same transaction's authority; no recursive
wait for a second coordinator is allowed.

For internal shadow repair, preserve native temporary state, install the needed
shadow under the selected mapping/permission protocol, then retry only the
faulting native operation. For a true architectural fault, use the selected
instruction metadata and committed-state record to abandon native execution and
park with a pending guest fault. The classification uses x86 access intent,
not merely the native load/store syndrome. A tracked-page write is a coordinated
architectural operation, not permission to convert the page permanently writable
and let arbitrary old blocks run.

To complete an in-flight guest instruction, the emitter/runtime must provide a
**forced next-boundary exit**: after the captured instruction (or legal REP
iteration) reaches its commit boundary, spill its authoritative state and transfer
to permanent dispatch before fetching/executing another guest instruction from
the saved block. The next guest instruction is redispatched with current source,
mapping and CPU generations. Executing the rest of an old multi-instruction block
is not an acceptable substitute after source mutation.

This is a new concrete emitter obligation, not a capability inferred from a PC
map. A conservative implementation can emit a stop-flag check and a state-spilling
exit at every guest-instruction/REP-iteration commit boundary. Coarser boundaries
need proof that no incompatible source/mapping or event can intervene. Its guard,
spill and lost-chain costs belong in Track 04; do not claim it is free because the
stop flag is usually clear. The generator ABI must establish correct boundary
placement before this protocol can be accepted for actual translated code.

When a retained operation encounters another memory fault, it yields its updated
phase to the same coordinator; it does not wait while holding a separate service
lock. If that phase is a valid canonical boundary it parks, otherwise it remains
paused with its dependencies pinned. Each service segment is finite or contains
a resumable poll. A service may finish with a guest fault and pending exception
state; exception delivery is a subsequent architectural operation with its own
checked memory accesses, not an unbounded recursive special privilege.

### Mutation, mappings and reclamation

Queued requests are still selected by one coordinator and revalidated at service.
A read-modify-write request retains its already read operand, computed result,
flags/deferred-state inputs and phase when those are architecturally needed.
For an ordinary non-LOCK operation, peer modifications between its read and write
may be permitted; re-reading source bytes or replaying a side-effecting read is
not how that interleaving is represented. A locked operation must begin its
indivisible effect while exclusion holds or use a proven native atomic path;
pausing after an unprotected half-completed LOCK is not a valid lowering.

Changing guest table bytes does not free a paused operation's checked physical
routing or shadow dependencies. Retain those mappings/backing until the captured
access completes or is safely abandoned. A completed x86 invalidation/shootdown
acknowledgement must not be exposed while any covered stale access can still
execute. Thus source writes may invalidate future block admission while a current
decoded instruction is pinned, but page/tag reuse and invalidation completion
wait for the stronger drain predicate. If applying a native root update would
redirect a retained access, preserve its old view or finish that access first;
never resume it against an accidentally substituted mapping.

Backend commits can write code/table pages only under exclusion and invalidate
future eligibility before guest observers resume. Backend source/output reads
cannot observe intermediate atomic fallback values. Device-memory operations
need an explicit side-effect record (request identity, phase and actual outcome)
and must not be reissued merely to obtain a canonical park. Mixed RAM/MMIO and
multi-effect instructions remain outside the accepted source traces. A valid
implementation must either retain their resumable phases or supply a semantic
slow path; routine unsupported valid instructions are not made correct by VM
termination.

A whole-cache reclaim still requires all relevant participants `PARKED` and every
native reference gone. `PAUSED` is never sufficient. Drain captured operations
before reusing their code, recovery metadata, mapping tags or callback resources.
A shadow repair therefore no longer waits for canonical park, while a reclaim
correctly does. The coordinator may service the operation needed to obtain that
park first. This removes the identified dependency cycle at the protocol level;
termination/progress for each selected instruction remains a generator premise.

## CLM-03-04-07 — an atomic native load may require a shadow write

**Source-backed, subsequently accepted in findings Return 2:** pinned QEMU revision
`c1c18d1e640b64292859ce9f30f3c344edfb0294`,
[`tcg/aarch64/tcg-target.c.inc`](https://github.com/qemu/qemu/blob/c1c18d1e640b64292859ce9f30f3c344edfb0294/tcg/aarch64/tcg-target.c.inc),
`tcg_out_qemu_ldst_i128`, chooses its paired path from `h.aa.atom` and `have_lse2`.
For the applicable aligned 16-byte atomic load without that paired path, the
emitter uses an `LDXP`/`STXP` loop writing the loaded bytes back. This is a real
native write even though the guest operation is a read. The author directly
inspected the pinned convenience-source copy after root identified this path.

**Inferred counterexample to unchanged lowering:** a guest-readable but native
read-only shadow (guest read-only, tracked code/table page or first-write dirty
tracking) can fault on `STXP`. Treating its syndrome as a guest write would invent
a write-permission #PF or dirty/code-write effect for a guest load. Temporarily
making the shadow writable without the full coherence protocol also breaks the
assumption that all guest writes trap. The SoftMMU host-backing execution context
and a permission-enforcing direct shadow are different environments.

**Proposed remedy:** classify faults by guest access intent and choose a
read-preserving lowering. An actual VM-qualified LSE2 paired operation may be an
option once its width/alignment/attribute contract and virtual feature exposure
are established. Otherwise, for **RAM only**, perform the guest read under all-observer
exclusion using ordinary reads of the validated range, with no writeback and no
guest dirty-bit update. Discard the original LDXP pair as uncommitted: it has not
passed the STXP atomicity validation and may be torn. Re-read the complete guest
RAM operand atomically under exclusion, rather than skipping STXP and committing
those old temporaries. MMIO requires its exact device width/side-effect contract;
exclusion does not authorize decomposing one device read into ordinary reads. Merely seeing a host `have_lse2` feature during host compilation does
not establish the VM's instruction/atomicity contract. Reuse the same mechanism
for any atomicity-required ordinary read that lacks a qualifying native lowering.
This choice can alter both exposed AVX support and fallback cost; it supplies no
new native observation or M2 claim. The full access-form inventory remains open.

### CLM-03-04-08 — metadata and entry polls cannot stop a live block internally

RIP and running a new block can replay its earlier effects; this is not a general
remedy for a live partial instruction or side-effecting read.

### Concrete candidate remedies and cost boundary

**Hypothesis A — explicit conditional commit checkpoint, preferred for further
source work:** after a normally completed guest instruction (`DISAS_NEXT`), emit
a real TCG conditional branch on the runtime stop request, while keeping the
existing optimizer/register allocator's synchronization semantics. Its taken
edge records the correct next guest PC, instruction/mode/CS identity and CC
selector, then uses a valid inherited end-of-block/event-boundary path to reach
permanent dispatch. It must not merely read `env.eip`: INV-03-02 claim 12 establishes
that chaining can leave that value stale. Deferred flags need both synchronized
operands and the correct selector. The not-taken path continues within the block.

This is prospective **code generation**, not post-fault patching or a metadata
interpretation. All affected blocks contain their checkpoints before publication.
A paused native continuation can then finish A and encounter its actual branch
before B executes. Instruction-start metadata remains useful for faults, not the
source of the executable checkpoint. Native interruption of the checkpoint itself
still captures/resumes its private state; x86 event delivery waits until the
canonical exit is complete.

The source's conditional-branch synchronization offers a simpler initial path
than arbitrary native-PC deoptimization. It does impose per-instruction flag-load,
branch and potential spill/reload work even when stopping is rare; Track 04 must
include that cost. Skipping checkpoints requires a proof that a removed boundary
cannot be required by a source/mapping/event transition. No such proof is assumed.
Control-flow instructions already terminate or specialize their exits and need
those actual paths audited separately. A cold path cannot call `gen_eob` in an
ad-hoc way that corrupts the frontend's continuing compile-time state; its
context/flags and emitted edge must be specified explicitly. REP needs a real
checkpoint at legal completed-iteration/chunk boundaries preserving RCX/RSI/RDI,
RF and CC rules. An instruction-count limit alone does not restrict REP to one
iteration, since its frontend can emit an internal loop. Helpers with intermediate
visible effects still require the retained-phase protocol before any checkpoint
is reached. These are adaptation obligations, not a complete emitted-code proof.

**Hypothesis B — prospective block splitting:** end the block after every
instruction that may require coordinator service, including implicit memory and
memory-touching helpers. Then a repaired instance of that instruction naturally
reaches an existing block-end commit. This needs a complete classification and
pre-mutation drain policy for a CPU paused before such a boundary; it cannot simply
let arbitrary peers continue into stale code after mutation. Frequent memory and
helper operations make fragmentation and lost optimization substantial potential
costs. Neither “only stores” nor “only explicit memory operands” is a complete
classification by inspection of opcodes alone.

**Control/material alternative — one guest instruction per block:** pre-generate
count-one blocks and ensure no direct/indirect exit bypasses the rendezvous
boundary. The ordinary one-instruction mode is distinct from debugging single
step. This is useful as a correctness control or explicitly costed candidate;
it is **not selected as the architecture** to avoid the harder boundary design.
It cannot repair an already paused multi-instruction block by toggling flags, and
REP/helper partial effects remain inside the one architectural instruction.

### CLM-03-04-10 — a cold exit must not change the continuing translation context

**Source-backed:** at pinned QEMU revision
`c1c18d1e640b64292859ce9f30f3c344edfb0294`, `gen_update_cc_op` may clear the
translator's `cc_op_dirty`; `gen_update_eip_next/cur` changes `pc_save`;
`gen_set_hflag`/`gen_reset_hflag` changes both emitted runtime state and the

**Inferred counterexample to inserting an ordinary cold call blindly:** suppose
only the stop-request path emits the current CC selector via `gen_update_cc_op`,
but emission clears the shared frontend `cc_op_dirty`. The not-taken path has
not executed that store, yet later translation may assume it did. Likewise a
cold-only EIP update that mutates shared `pc_save` invalidates later hot-path
PC-relative arithmetic. A terminal cold `gen_eob` can incorrectly mark the
continuing block terminal. The compile-time effect occurs regardless of which
runtime edge is taken. This is a source-derived transformation counterexample,
not a demonstrated defect in unmodified QEMU.

**Smallest prospective remedy:** generate the cold edge using a separate snapshot
of the boundary's frontend fields, with TCG values referenced rather than copied
as guest state. The snapshot includes `pc`, `base.pc_next`, `pc_save`, `cs_base`,
code/address mode and flags, `cc_op`, `cc_op_dirty`, `base.is_jmp`, and `jmp_opt`;
any additional fields actually read by the selected exit helpers belong in it.
Its jump mode is forced nonchaining. Cold-only field updates do not flow back to
the hot translation context. This is a semantic snapshot for code generation,
not use of the copied `sigjmp_buf` or another compiler's mutable runtime context.
The emitted TCG still goes through the complete liveness/materialization pipeline;
separating C fields must not fork register allocation or bypass branch analysis.

### Concrete ordinary fallthrough checkpoint

**Hypothesis:** admit this form only when the just-decoded instruction completed
normally with `base.is_jmp == DISAS_NEXT`. At this point
`i386_tr_translate_insn` has assigned `base.pc_next = pc`. Control transfers,
mode-changing helpers, new/inherited interrupt shadows and special terminal
instructions retain their existing exit paths and must reach the common admission
boundary separately. The selected scalar-memory traces do not change CPL, CR0.WP,
CS or permissions; the dispatcher nevertheless rechecks their current context
before any later instruction is admitted.

The prospective IR control flow is:

1. After **all** effects of A, read the private runtime stop request with the
   selected atomic-acquire/visibility contract and branch to the hot continuation
   when stopping is not requested. This must be a real conditional TCG branch
   present before optimization; a metadata annotation is insufficient. The load
   must not be folded/hoisted as immutable CPU state. A conservative non-elidable
   runtime-query helper is an available design alternative if the chosen direct
   query lacks that contract; its call/spill cost must be recorded.
2. The taken stop edge uses the boundary-context snapshot. Materialize its CC
   selector if dirty, then invoke the semantics of `gen_jmp_rel_csize(cold, 0, 0)`
   with `cold.jmp_opt = false`. This computes the **next** guest PC with CS/code-size
   truncation and the existing PC-relative rules, and reaches `gen_eob` through
   the nonchaining path. Do not use a raw `pc+length` store or stale `env.eip`.
3. The cold block ends in the VM's nonchaining block-exit ABI. That ABI commits
   globals through the normal TCG exit pipeline, switches to permanent dispatch,
   releases generated-code references and acknowledges canonical park. No native
   return into the old block remains. The hot-continuation label emits no cold
   frontend side effects; it still sees the original compile-time state.

The conditional-branch pipeline establishes the values needed on each edge.
Some selector/PC stores are required only on the cold edge; branch analysis must
see those uses so it preserves their operands. `cc_srcT` may be a useful
translator-only temporary, but runtime flags are represented by the canonical
CC operands and selector. No claim that a copied native `NZCV` is x86 RFLAGS is
made. The selected instruction's globals/temporaries must obey the existing TCG
lifetime classes; the checkpoint cannot insert references to an already dead
local value merely because a C variable still names it.

**RF and interrupt-shadow context:** `gen_eob` applies the inherited completion
rules, including RF clearing and shadow reset/set as appropriate. The normal
fallthrough form does not substitute its own simplified flags logic. For a block
entered with `HF_INHIBIT_IRQ_MASK` or `HF_TF_MASK`, the frontend already switches
to `DISAS_EOB_NEXT` after translation, outside this ordinary checkpoint form.
Instructions that introduce a shadow use their special exit classification;
they must not be forcibly reclassified as ordinary `DISAS_NEXT`. Debugger
single-step behavior is not enabled just to obtain a runtime coordination point.
The context snapshot prevents cold-only hflag updates from contaminating hot
translation assumptions.

### Scalar memory trace, including serviced stores

Let A be an ordinary scalar RAM instruction and B the next guest instruction.
Before A's access, retained `qemu_ld/st` semantics synchronize the required old
architectural state. A native shadow fault captures the complete native frame
and source/metadata identity. The coordinator pauses all observers without
requiring A to have completed, then returns exactly one access outcome:

- `RETRY_ACCESS` follows internal mapping repair only. Restore the captured frame
  and repeat the still-unperformed native access. On a load, its result becomes
  the input to the remaining emitted destination assignment; do not prematurely
  acknowledge A completed while the result exists only in a temporary.
- `ACCESS_COMPLETED` follows a coordinated access performed by the service, such
  as a tracked store to B's source. Restore its declared result/status updates
  and enter the emitter-owned success continuation, **not** `native_pc+4` and
  not the original store. This completes any remaining register/flags effects.
- `GUEST_FAULT` abandons that native continuation through the exceptional ABI,
  preserves required earlier effects and leaves the architectural PC on A.
  It never reaches the ordinary successful checkpoint for A.

On successful A, its real checkpoint sees the drain request. The cold snapshot
sets PC to B and commits A's CC/GPR effects through inherited exit semantics.
The block is pinned until the native frame/return is gone. Only then does permanent
dispatch acknowledge park or admit B with its new source generation. If B's bytes
changed during A's service, none of old B executes. If stop was not requested,
the unchanged hot path still has the original frontend PC/CC bookkeeping; no
cold-path assumption leaks into later code generation. This trace is conditional
on the query visibility, emitted success locations and complete access-frame ABI;
those are not established merely by the frontend source ordering.

### REP MOVSB: checkpoint after a committed iteration

**Source-backed:** `gen_movs` performs its load and store before updating ESI/EDI.

Otherwise `cur_insn_len` can be zero and the proposed backward offset is wrong. It has RF suppressed in the local

next iteration, while the required count/indices already describe that next
iteration. Do not accidentally use the once-decremented *future loop temporary*

exit, including its RF clearing. A zero initial count takes that completed path

condition-failed decision before choosing same-PC versus next-PC; this pass does
not claim their exact insertion site from a MOVSB trace. When inherited TF or

An internal same-PC park has preserved a legal REP progress boundary. If source
mutation affects the REP instruction itself, retain its decoded-instruction
identity until the code-coherence policy decides whether the captured operation
continues or a permitted new fetch occurs. A same numeric RIP alone does not

silently treated as a guest interrupt/IRET serializing episode. This intersection

### CLM-03-04-11 — architectural interruption is not internal coordination

**Source-backed:** [Intel SDM Vol. 3A revision 092](https://cdrdv2-public.intel.com/922487/253668-092-sdm-vol-3a.pdf),
§7.6 describes fault restart and interrupt delivery at a repeat-iteration boundary
with registers positioned for subsequent progress. §11.1.3 specifies software
synchronization for self/cross-modifying code and warns that unsynchronized
execution is model-specific. These sections do not require an emulator's
invisible coordination pause to behave as an architectural interrupt, or establish
one physical Haswell's unsynchronized self-modification behavior.

**Inferred:** do not restart a paused REP through ordinary guest-PC lookup merely
because its iteration registers have been made inspectable. Keep the admitted
decoded operation until it completes or an actual architectural event abandons
that execution. The guest's code-modification synchronization still applies to
subsequent admitted execution; this rule is not permission to miss required code
changes after an architectural restart/serialization boundary.

### Operation identity and two independent state facts

A live repeated operation has a private handle naming VM lifetime, vCPU,
operation sequence, admitted native allocation/generation, original guest PC,
original decode/source identity, relevant CPU/mode state and the original REP
completion policy (including RF context). It holds references to native code,
recovery metadata and any required helper/stack frames. Native resume locations
are emitter-owned labels inside that allocation, never guest-controlled numbers.
Ordinary lookup and direct links cannot use the handle to enter invalid source
code; it authorizes resuming **only the already admitted operation**.

At a completed iteration, guest registers/progress can be architecturally
inspectable while a native loop continuation remains necessary. Record these
separately:

- **Boundary state:** current count/indices/CC and the architecturally meaningful
  REP PC, with no element access left halfway committed.
- **Reference state:** native resume PC/SP/registers and all code/metadata/stack
  dependencies remain pinned. Such an operation is `PAUSED`, even if its boundary
  values are canonical; it is not reclaimable `PARKED`.

The runtime's stored `env.eip` may still be a PC-relative translation anchor.
Materializing a guest-facing boundary PC must not silently replace that anchor
and then resume native code compiled against its previous value. Either keep the
boundary PC in the explicit paused-operation record, or retain and restore the
original runtime anchor as part of the native continuation before loop resumption.
The selected representation is part of the ABI; a numeric RIP by itself is not
sufficient. This reuses the earlier distinction between guest boundary identity
and the native execution representation rather than inventing an x86 PC update.

There must be distinct emitter-owned continuation routes for internal resume and
architectural event exit. The latter can reuse the earlier cold-context recipe
for the original REP PC/RF semantics; the former must not execute that recipe and
then pretend no architectural event happened. A single cold exit used for both
purposes loses this distinction. Final completion also returns through permanent
dispatch before reference release; it cannot drop its own code pin while still
executing the final instructions in that allocation.

The transition decision uses the canonical boundary and actual event-eligibility
state. It does not assume native interrupt arrival implies x86 delivery. CPU
mode/CPL/DF/segment/control state is not independently changed while this vCPU's
operation is suspended; an operation that legitimately changes that state or an
actual event invalidates the old continuation through its specified path. Memory
mappings remain governed by current access checks and previously checked-route
pins. A new REP iteration is a new element access: code pinning does not authorize
using a stale data mapping after a covered invalidation has completed.

### Same-instruction mutation schedule

CPU0 is partway through REP MOVSB; after iteration k, it pauses internally with
remaining count and the original operation handle. CPU1's coordinated store
changes bytes of that REP instruction. The store invalidates future translation
eligibility and advances physical-source generations, but does not overwrite
CPU0's immutable native object. CPU0 resumes the retained next-iteration label
and continues the already admitted decode. It does not compile the new bytes
as the continuation of the old operation, and it does not reset count or duplicate
iteration k. On final completion it dispatches the next guest instruction using
current identities.

If CPU0 instead receives a real eligible guest interrupt, the architectural
partial-progress transition abandons the native loop. A subsequent guest return
is a new instruction fetch/restart subject to the guest's valid mappings and code
synchronization; no old operation handle overrides the new source bytes. This
is a proposed deterministic emulator policy for an already admitted decode,
not an assertion about every unsynchronized physical-x86 outcome. The §11.1.3
synchronized protocols remain required. REPZ/REPNZ state and special string-I/O
partial effects still need their own trace; the source-only MOVSB argument does
not silently cover them.

### Reclamation change: batch eligible objects, retain live operations

The prior “whole-cache flush waits for every CPU to become reclaimable” policy
is too strong. A valid long REP must not need to finish all remaining elements
merely because the translator cache is under pressure. **Revised provisional
mechanism:** close admission and reach memory-quiescent pause as before; detach
lookup/link eligibility for the chosen reclaim batch; retain the union of every
active-operation/native-frame/host-callback dependency; reclaim only allocations
outside that union. Pinned objects remain immutable and resumable only through
their existing-operation handles. Reopen admission with current generations while
those objects remain reserved. No global arena reset may overwrite the pinned
islands. Per-allocation free/retained ownership is therefore a real change from a
single resettable code region, not a renamed whole-cache flush.

A batch has these exact predicates: no active native PC/return/frame/metadata
reference to a freed allocation; all incoming links detached or invalidated;
no in-flight publisher/callback owns its generation; and completion of the needed
native memory/cache maintenance before reuse. Canonical guest state alone proves
none of these. Whole-cache reclamation remains a special case when the pinned
union is empty, not the universal gate.

Bound resource use prospectively: cap translation/reply admissions, bound each
allocation and generated-block/helper frame size, and reserve permanent dispatch,
frame, cancellation and one drain-service capacity before granting an execution
lease. Reserve enough code/control capacity for the maximum admitted pinned set,
which depends on vCPU count and reachable native/helper/host references, not REP's
remaining element count. Reject or wait on **new translation admission** when a
nonreserve pool is exhausted; keep existing operations able to resume and handle
required events. Do not claim that a bound exists until the selected helper/native
frame and callback inventories establish it. The machine proposal's initially
bounded vCPU counts make such an inventory finite in principle, not yet complete.

If no reclaimable object remains, backpressure publishers and continue bounded
existing-operation/drain work using the reserved resources. A deadline can detect
a stuck runtime or fail an allocation request according to the declared failure
policy, but must not force a healthy REP to complete its entire count merely to
avoid routine termination. True configured resource exhaustion may terminate the
VM safely; systematic exhaustion on ordinary valid long REP is a falsifier of
this capacity/admission policy, not a satisfactory success case. No real-time
latency or uninterrupted resource-growth promise is introduced.

### Alternatives, cost and falsifiers

Captured-decode regeneration remains a material alternative: at a completely
committed iteration it might discard the old native loop and generate a new
operation-owned continuation from the original instruction bytes and canonical
progress. It would need an explicit continuation key exempt from ordinary source
lookup, correct original mode/DF/RF policy, no remaining native/access phase and
a proof that reconstructed code resumes exactly the same operation. Existing
host byte-snapshot compilation may be reusable, but it does not supply those
identity/entry rules automatically. Retaining the original loop requires fewer
new semantic mechanisms and is the provisional choice here.

Costs now include retained code fragments, allocation bookkeeping, batch unlinking,
reserved drain capacity and poorer cache compaction, alongside checkpoint
queries/spills and global admission pauses. Unlike universal count-one blocks,
this policy preserves multi-instruction translation and SMP ordinary execution.
It still needs a qualified cost comparison before economic selection.

Concrete falsifiers: reclaim touches a pinned island; source invalidation permits
an unrelated dispatch through an operation-only handle; internal stop executes
event-exit RF semantics; resumed PC-relative code uses a replaced anchor; actual
guest IRET restores an abandoned old native handle; a new iteration uses an old
mapping after required invalidation completion; or publication exhaustion prevents
an already-admitted long REP from resuming despite its reserved resources.

Repeated invalidation updates/reuses bounded records; it cannot allocate an immortal tombstone per generation. |

K = 3 is a conservative protocol envelope, not a claim that three distinct TBs
are normally needed. A vCPU in a permanent helper/service still identifies its
one originating object. A handover can temporarily name old/new objects; the
third allowance avoids conflating a separately recorded current-operation origin
with that transient pair. The construction forbids nested generated-code calls
and forbids a helper from recursively invoking the dispatcher. A source finding
that an enabled helper requires either behavior must revise this construction
and its bound before acceptance. At a pause, native-PC/range lookup, explicit
origin and handover record must together discover every such reference. Merely
incrementing a counter on ordinary TB entry is not that proof.

The repeated-operation record is constant-space: remaining count, indices,
current phase and outstanding request identity. Completed iterations have already
committed guest effects and do not require an appended history of every read or
write. An outstanding side-effecting request remains owned until completion or
acknowledged cancellation; duplicate responses are rejected using that slot's
generation. Reuse requires the callback-lifetime protocol, and generation wrap
requires draining the namespace before reuse, not elapsed-time guessing. This
also applies to translation replies. An unbounded completion history is neither
needed by the proposed sequential protocol nor permitted by the bound.

### Symbolic reserve and progress argument

Let B be the maximum whole generated object size, including native instructions,
literal/veneer storage, recovery/access/checkpoint metadata and its object/link
record. Choose a pool of C equal-capacity slots with:

`C >= K*V + P + V + 1`, with `K = 3`.

The first K*V covers all live execution/handover/origin objects; P covers admitted
publisher outputs; V reserves one successor/miss object per vCPU; the final slot
is spare for serialized handover/reclamation work. These are conservative counts
and may overlap. Ordinary cache occupancy can use otherwise free slots, but the
admission controller must recover the required reserve before granting leases
that consume it. The entire maximum code pool costs at most C*B; pinned execution
alone costs at most K*V*B. Fixed slots are chosen here to make fragmentation
irrelevant to the existence argument; a later allocator can improve utilization
without weakening those reserved-capacity predicates.

For resident runtime state, let F bound the complete per-vCPU execution/helper
stack plus retained register/origin/IRQ records, A bound its current access
record and backing-route references, J bound one host translation job's input and
workspace, Q bound one admitted device/backend request and bounce storage, and
R bound permanent code, coordinator records, shadow pools and global indexes.
Then the construction has the conditional memory envelope:

`M <= C*B + V*(F + A) + P*J + D*Q + R`.

Guest RAM itself is configured separately; R must count its tracking indexes and
the selected finite shadow cache, rather than silently allow all historical
CR3/context combinations to remain resident. This formula is a construction
budget, not an estimate of useful numeric values, host RSS or scheduling latency.
F in particular requires the enabled helper/call inventory; Q/J require the
selected device/compiler operation bounds. Their finiteness is an explicit
premise with identified owners, not inferred solely from finite V.

If cache pressure occurs while every vCPU retains a long REP, closed admission
finds at most K*V execution objects and at most P publisher outputs. It detaches
and reclaims eligible other objects; each admitted REP resumes its existing
object using permanent drain storage, without requesting a new object for each
iteration. If a real guest event abandons a REP, its references are dropped from
permanent code; one reserved successor slot permits the architectural handler's
next translation. If it merely pauses internally, it consumes no successor slot.
Thus no dependency requires waiting for REP's remaining count to reach zero.

Publication under pressure is serializable and cancellable before guest effects:
discard a stale unpublished output, release its slot, then admit its retry. A
valid guest instruction already in service cannot be cancelled as though its
side effects never happened. Device completion may still wait for the actual
external backend; that is not code-space deadlock. Required host refill cannot
consume the last resident drain reserve or require a paused vCPU to unpin first.
The reserved shadow/control work must suffice for one admitted drain step;
otherwise the supposed resident service is not within R.

Each B/F/A/J/Q/R must be chosen to support every enabled single operation on its
declared path. Code-output overflow may shorten a multi-instruction TB, using
existing generator limits, but an enabled single instruction that exceeds B is
a counterexample requiring a larger bound or a reusable bounded semantic path,
not an excuse to reject that guest instruction. REP trip count cannot enlarge B
or F: it remains a native loop. This construction does not select universal
single-instruction blocks or serialize ordinary SMP execution.

### Counterexamples, costs and disposition

The first failure of a naive finite-vCPU argument is an asynchronous callback
that keeps one old TB per completed operation, or a retire list that waits for a
long REP before clearing every historical generation. Both grow with time even
at V = 1. The selected slot/generation contract and per-object batch reclamation
remove those ownership rules; they are actual adaptations. Another failure is
pinning the transitive direct-link graph: two outgoing links per block do not
bound that graph by V. Eligibility edges must be unlinkable independently of
retained execution, as specified above.

Other falsifiers are an uncounted handover native PC, a recursive generated
helper entry, a per-iteration effect log, an output/metadata finalizer exceeding
B, or routine repair requiring a fresh frame/table that the promised reserve
cannot provide. Fixed slots waste capacity; reserves reduce cache available to
ordinary code; callback identifiers and admission checks add work; unlinking can
touch O(C) links in a worst-case batch. This is an architectural existence and
ownership argument, not a performance result or complete helper stack proof.

### Admission, mutation and publication

1. **Prepare without effect.** The captured guest operation owns its original
   decode/native frame and current walker phase. A suboperation descriptor names
   its VM/vCPU/operation/access serial, original x86 intent, PTE GPA/width,
   comparison/update values where applicable, and owned routing capability.
   Descriptor publication does not itself perform a device read or A/D update.
   Earlier completed walk reads/updates remain recorded by the current phase.
2. **Acquire one mutation authority.** If the operation already owns
   DRAIN_SERVICE, its A/D update borrows that transaction. Otherwise a mutation
   needing tracked-page authority pauses and asks the single coordinator to close
   admission. It does not hold a RAM/topology lock while waiting and does not
   acquire a second exclusive epoch. All ordinary RAM observers and writers must
   be quiescent before exclusive service. New source/table registration and
   publication use the same admission domain, so a racing publisher cannot turn
   an untracked page into executable source behind an unchecked writer.
3. **Prepare affected identities.** Resolve the actual physical backing and
   gather its source and shadow dependency indexes, including every alias.
   Snapshot their current versions on exclusive entry and compare them with
   the saved walk expectations **before** applying any owned delta. Retain every
   preexisting mismatch as a separate revalidation obligation; a matching CAS
   target word does not validate other saved entries or bytes in the same page.
   Revoke new lookup/link/shadow admission for potentially affected objects before
   the write can become observable to newly admitted work. Mark affected live
   operations as requiring their next legal boundary decision; retain their
   immutable code/metadata. Preparation may be conservative even if compare later
   fails. It must not clear a still-needed native continuation or guest flag.
4. **Perform one semantic phase.** RAM conditional update uses its specified
   compare-exchange under current authority. A mismatch returns the walker result
   without changing bytes. Non-RAM read/conditional-write uses the host route
   contract and explicit phase/results under the same authority. If a device
   handler causes guest-RAM effects, those effects also borrow this transaction
   and pass the all-writer gateway; the callback may not acquire ordinary RAM
   admission and wait for the coordinator that is waiting for it.
5. **Commit coherence before exposing completion.** For `RAM_CHANGED`, record
   the affected physical interval, advance source/dependency generations and
   finish required shadow/TLB/cache maintenance before reopening admission.
   Publish the suboperation completion only after this bookkeeping is owned.
   `NO_WRITE`/`RAM_UNCHANGED` does not fabricate a byte change; conservative prior
   invalidation can stand. `DEVICE_WRITE_OR_DISCARD` follows the host result and
   separately accounts for any RAM mutation rather than inventing one.
6. **Continue the same operation or yield its phase.** Return the typed result
   to the walker. A completed update is not retried because service paused.
   A true later guest fault preserves already committed earlier A/D effects.
   At the next legal guest boundary, affected ordinary instructions dispatch
   through current identities; an internally paused REP retains its admitted
   loop according to revision 3. No later stale instruction may execute merely
   because it shares the pinned allocation.

Effect completion, generation update and the eventual result form one owned
transaction, not one necessarily atomic native store. Admission remains closed
through their intermediate states. If the runtime fails after a write but before
finishing metadata/publication, it keeps the VM stopped; it cannot reopen or
repeat the write speculatively. This is fail-closed containment of a broken
runtime, not an ordinary guest page-fault path. Phase storage is reserved before
the effect, as required by claim 12.

The initial mechanism uses exclusive authority for tracked A/D mutations. It does
not require serialization when bits are already set and no update is needed.
An optimized untracked-RAM update path would need a stable classification token
across its compare-exchange and exclusive source/table promotion; that fast path
is not established here. The cost of A/D first touches on tracked paging pages
can therefore include global rendezvous and dependent shadow invalidation. This
is a material workload cost, not eliminated by calling the operation metadata.

### Self-invalidation without recursive restart

A page may hold both guest instruction bytes and paging entries. An A/D update
can change bytes in the source of an already running block. The coordinator
invalidates **future admission** and sets the affected boundary request, while
the captured instruction continues its admitted decode. For a REP operation,
the captured loop identity survives internal coordination, but the next distinct
instruction is dispatched from current source. This is the existing retained
decode policy, not a special exemption for page walkers.

The same update may invalidate a shadow dependency used by its own walk. A naive
rule that sees its own generation increment and restarts the whole operation is
wrong for side-effecting prior reads and can repeatedly reenter coordination.
Instead, record the transaction's own RAM delta and fold the resulting versions
into that walk's validation record while exclusion prevents competing mutations.
The fold is permitted only for dependencies that matched the exclusive-entry
baseline, and only for the known A/D delta with unchanged address, permission
and routing fields. It must not clear the previously recorded mismatch set.
A saved parent-entry read that predates another writer cannot be relabeled current
merely because this transaction successfully sets A in a different leaf word.
The inherited walk
still takes its specified compare-failure restart when the compared value is
stale; a new walker read gets a new serial identity and retains earlier effects.
For device-backed entries, retain the host phase/result rather than infer that
an arbitrary device write left all address/permission bits unchanged.

An unresolved baseline mismatch forbids publishing a reusable shadow as current.
An already-admitted checked access can finish through its retained route, but
that permission does not validate a new access or reusable mapping. Otherwise
resolve the mismatch through the selected walk's semantic revalidation/restart
phase, with explicit new access identities and preserved earlier effects; do not
silently replay a completed device request. If that phase lacks such a transition,
the composition remains blocked for that case. This is the precise prerequisite
for own-delta folding, not a claim that every raced walk needs an atomic snapshot.

If the new A/D bits only affect access bookkeeping, the selected initial policy
may conservatively evict dependent shadows. It must then build the new shadow
from the completed walk and updated versions without asking another epoch to
approve the same owned mutation. A future selective invalidation optimization
needs a proof of the relevant delta; it is not necessary for this composition.

### Routing references, remapping and invalidation acknowledgements

A routing capability is an owned reference to checked backing/attributes and its
generation for **one admitted suboperation**. It is not a topology mutex held
across a host wait, and it is not a guest TLB permission to use an old mapping
forever. Its lifetime is separate from the current instruction's code pin.

| Suboperation phase when remap is requested | Required ordering |
| --- | --- |
| Prepared but no route/access admitted | Resolve the unperformed phase against current authority when serviced, preserving earlier architectural effects. Do not invent a prior physical access. |
| Route admitted, effect not yet complete | Finish or explicitly cancel that suboperation using its retained route before acknowledging a conflicting remap/invalidation. Cancellation must prove no effect occurred; a queued device request cannot be assumed cancellable. |
| Host effect complete, result awaiting consumption | Deliver the recorded result exactly once. Once no replay/native access can use the old route, release its routing reference even if the instruction's native code remains pinned. |
| Current suboperation consumed; later operand or REP element not admitted | Resolve that later access using the applicable current mapping/permission state and its instruction-specific ordering. Retaining the old decode does not retain every future data route. |

The coordinator may reorder service work needed to discharge an old route ahead
of a queued remap. FIFO request arrival does not force the remapper to wait for
a release that only its blocked drain could produce. It must not move the remap
acknowledgement ahead of the old effect: a guest shootdown must not report complete
while a covered stale access can still run. Physical backing/tag reuse requires
the same stronger no-reference predicate. A topology change may mark old routes
unavailable to new admissions while retaining the old backing for pending ones.

With a native RETRY_ACCESS continuation, the old route includes the needed native
shadow/view until that exact access finishes. If installing a new root would
redirect it, finish the old phase first or use the explicit service-completed
success continuation. Never restore the saved PC into a newly substituted route.
An ACCESS_COMPLETED result carries the original result/status and needs no second
memory access merely to release its route. All required barrier/maintenance
premises from the earlier protocol remain; object ownership alone is not TLBI.

### Admission predicate: an old walk is not a new access

Before the first PTE read, register the guest access identity, linear span,
access intent, CPU/shadow permission context and invalidation generation. This
is a **walk/access lifetime record**, not a pinned final physical route, which
may not yet be known. Per-suboperation route admission remains unchanged.
The record survives an internal pause without authorizing ordinary RAM activity.
It is included when testing whether a covering architectural invalidation or
conflicting backing-retirement operation can be acknowledged.

Continuing the retained walk requires all of the following:

- It is the same guest access/phase and CPU context, not a new operand or the
  next REP element reusing an old walk. Its original guest read/fault ordering
  and captured instruction identity remain authoritative.
- No architectural fault/event has abandoned that operation. Guest handler
  return begins a new access even if numeric RIP/CR3/CPL happen to match; it
  cannot revive the old walk handle. A paging/permission-control change likewise
  ends the old context through its defined transition, not this caching rule.
- No covering architectural invalidation has been acknowledged since admission.
  Pending shootdown delivery/acknowledgement must wait until this admitted access
  can no longer issue a covered old translation. Table-byte generation changes
  alone are distinct from that architectural completion condition.
- Each issued physical suboperation retains its own route until completion or
  acknowledged cancellation. A later unissued physical suboperation resolves
  the retained walk's computed GPA against the applicable current physical
  topology; a saved parent entry is not a pointer into freed host backing.
- Final memory execution uses the existing access width, fault/partial-progress,
  atomicity and device-phase recipe. SERVICE_ONLY supplies a translation and
  publication policy, not permission to replace a wide atomic access with
  unrelated narrow reads or to repeat earlier portions of a split operation.

If a covering invalidation was already acknowledged while this walk could still
produce an old access, the coordinator invariant was violated. SERVICE_ONLY
cannot repair that by claiming the access happened earlier. This is an explicit
counterexample to omitting walk records from the invalidation drain set. The
smallest remedy is prospective registration and acknowledgement gating; it does
not require a complete physical route before a walk begins.

No reusable shadow, dependency-generation relabeling or future-access authority
is produced from SERVICE_ONLY. After its exact final access/result is consumed,
retire the walk record and route references. Other native code pins may remain
until the instruction's legal boundary, as before. A subsequent operand or REP
element has a new walk/access identity and current context. The pending
architectural invalidation can then complete when its whole covered set is clear.

### Concrete schedule with a completed device read

Take an ordinary aligned scalar guest load using four-level paging and a 4-KiB
leaf. CPU0 reads the nonleaf RAM PDE U after eligible PML4E/PDPTE ancestors

to another child, advancing U's dependency generation; no covering invalidation
has yet been acknowledged for CPU0's admitted access.

On service, CPU0 detects the mismatch and sets SERVICE_ONLY. It consumes L once,
retains the source walk's accumulated permission checks, and completes any
required A/D phase using the existing conditional-update policy. For this trace,
choose L's A/D bits already set so no further conditional PTE read is required.
It then resolves the final GPA and performs the one scalar read under drain
authority, returning ACCESS_COMPLETED. It does not read the device PTE again,
does not install an old-U shadow tagged with U's new generation, and does not
undo the device's earlier side effect. The following access resolves current
state. Any source mutation in this transaction still forces the previously

The PDE-cache entry retention is compatible with the cited permitted paging cache

The cache argument is deliberately limited to eligible entry types and valid

If the leaf's A/D compare actually fails, the source's semantic retry can

duplicate delivery of the old request: the old side effect remains committed
and the new read is part of the declared walker algorithm. A hostile changing

### Publication and tradeoff

Only CACHE_CANDIDATE may attempt reusable shadow installation. It must satisfy
the full baseline/own-delta/version validation before publication. A failed
validation downgrades to SERVICE_ONLY; it never restarts a device operation just
to regain caching eligibility. Conservative false-positive page-generation
mismatches therefore cost a serviced access and a later fresh walk, not a new
guest fault. RAM-only walks could later use more precise dependency validation,
but that optimization is not required here.

This selects an existing service path over a special temporary shadow/root for
one use. It avoids adding one-shot native mapping retirement and arbitrary-PC
retry rules. It costs service entry/result handling and forfeits shadow-cache
reuse on the affected access; repeated accesses through side-effecting PTE
regions may be expensive. Normal stable RAM-backed walks retain the hardware
shadow path. It does not serialize every ordinary guest instruction or require
all translations to be single-instruction blocks.

### Source-byte admission without speculative device effects

Keep the ordinary cacheable-RAM translation fast path. Speculative compiler
lookahead is admitted only where current dependencies establish cacheable,
side-effect-free RAM and any required translation traffic is itself permitted.
If resolving another page would require a UC/speculation-forbidden table read
or unknown device route, stop the speculative block extension. An already legal
cached translation may supply information according to its architectural lifetime;
a missing translation does not authorize an arbitrary host walker fetch.

For UC source, select **demand capture of the currently required instruction**.
The dispatcher issues an operation identity at an actual guest fetch boundary;
the decoder may request continuation fragments for that same instruction, with
the x86 length bound and mode-specific fetch faults. Crossing a page requests
only continuation needed for that instruction; it does not prevalidate the next
instruction or consume a device read for a predicted branch target. Captured
bytes and completed effects survive host translation waits under existing route,
source and operation pins. A decoder restart must not blindly repeat a completed
side-effecting fetch. A genuine guest fault/event that abandons the fetch follows
the existing architectural restart rules.

UC instruction capture need not regenerate native code each time: a cache of
translations may match the newly admitted immutable bytes/context. It may not
substitute an old object identity for required guest-visible fetch activity on a
side-effecting route. For RAM, the source-generation protocol must still prevent
execution of invalidated following instructions. For device-backed source, the
machine must define the supported fetch transaction widths/results; this text
does not manufacture byte transactions for an arbitrary device. The existing
checked service route can carry admitted fetch fragments, but its platform-specific
transaction contract is a premise, not permission to reject legal guest code
solely because the generator prefers host pointers.

This selected single-instruction admission applies to the conservative UC path,
not universally to WB workloads. It forgoes permitted UC fetch batching and may
cost guest-boundary/host-request traffic. Finite byte capture and code reuse
bound storage; retaining an operation during an internal pause does not make
its code reclaimable.

### Authority and admission

A request identifies a typed operation, its device/fetch origin and current phase,
VM lifetime, request/slot incarnation, direction, checked logical byte ranges,
backing/route identities, applicable policy/context dependencies and completion
owner. Source requests additionally retain the source-fetch operation and
translation-job identities/dependencies from claim 01-11. Physical RAM identity
is not inferred from a WB guest leaf or an FD. The resident runtime selects the
extent list; the host callback cannot substitute a GPA, installation pointer,
length or destination supplied by guest bytes.

This is an internal interface between trusted runtime components in a per-VM
worker. It does **not** create process-enforced isolation between a compiler,
device model and copier in that same address space. Compromised native code can
violate an internal pointer contract; the outer worker boundary from INV-03-03
owns crash/host containment. A disk/network handle grants backend I/O authority,
not guest-RAM commit, live architectural-state mutation or interrupt publication.
The scoped direction agrees with 03's bounded bytes/status backend contract and
introduces no arbitrary path/PID/FD/Mach-right broker.

Before requesting the window, reserve its bounded operation/result record,
immutable incoming payload or outgoing snapshot destination, route/backing pins,
and required invalidation/publication bookkeeping. External incoming I/O has
already produced the bytes/status in host-owned storage. Outgoing I/O starts
from the immutable snapshot **after** the memory window closes. Host compilation,
filesystem/network waits, allocation, arbitrary callbacks and decoder work do not
run while ordinary guest execution is excluded. The window is a bounded leaf
copy and resident commit, not a lock held throughout I/O or compilation.

A configured finite byte/extent quantum bounds a window. Larger transfers use
operation-contract-permitted units with retained progress; this is not permission
to split a device atomic transaction or prevalidate a whole x86 instruction's
later faulting phases. Snapshot coherence is promised for the admitted unit;
a consumer requiring a larger coherent unit must reserve/admit that unit, rather
than concatenate independently captured epochs and call them atomic. Numerical
quantum and throughput remain conformance/cost choices, not silently inherited
from the probe's four-word payload.

### Concrete window transitions

| Transition | Required authority and effect |
| --- | --- |
| Ready → closing | Resident coordinator arbitrates the single window and closes new affected ordinary/service/source/publication admission. Register its exact operation/phase and reserved lifetime record before requesting drains. Existing independent host I/O may finish into host-only storage, but cannot touch guest RAM or publish completion. |
| Closing → drained | Every resident executor and existing memory writer discharges its admitted memory phase under the established `PAUSED`/service rules and returns its matching native DSB acknowledgement. Already stopped native PCs alone are insufficient. Existing host windows/aliases must already be retired. The all-observer exclusion is a conservative baseline for **these service
windows**, not an added stop-the-world action or host call on each ordinary WB
guest access. Existing parallel WB execution and its separately owned x86
ordering/atomic lowering remain. Retained native continuations/REP loops keep
operation pins; canonical guest state is not required just to grant the memory
window, and the window does not authorize stale subsequent instructions.

Backend RAM writes report committed byte extents. The runtime may conservatively
invalidate dependencies intersecting written extents without claiming that every
byte changed; a true no-write result must not fabricate a write. Guest paging
A/D semantics, watchpoints, locked operations and instruction partial effects are
not synthesized by this generic backend copier. Those semantic owners decide
what the original admitted operation means. In particular, physical backend DMA
authority is not a guest virtual store and does not automatically set a guest
PTE dirty bit.

### Typed source capture and device completion

For cacheable, side-effect-free RAM source, the resident fetch owner first admits
exact fragments/lookahead permitted by claim 16, including its paging traffic and
mode-specific fault/effect rules. The service routine then copies those checked
bytes during the window; the compiler receives only the immutable result and
identities. Host decoding that needs more bytes requests a continuation from the
resident owner; it cannot extend a host pointer or rewalk guest memory itself.
A snapshot token never grants code publication. At reply time, claim 01-11 checks
request liveness and dependencies under the same mutation/publication authority.

For an incoming backend write to a page also holding source or paging entries,
all memory participants are drained before direct commit. After the host store
and completion barrier, resident invalidation/generation work precedes device
completion and release. A previously copied translation job may finish compiling,
but its stale reply cannot publish. Its immutable input/storage remains retained
until producer/delivery references end; no code or RAM pin is freed just because
publication was cancelled. This is the conditional composition argued by the
protocol; claim 25's small generation comparison is not its runtime proof.

For outgoing data/descriptor snapshots, the host backend consumes copied bytes
after release. Completing capture does not claim the disk write, network send,
flush or durability has completed. Conversely a host I/O result waiting for RAM
commit cannot publish a guest-visible used-ring/status/interrupt early. Device
partial-transfer and cancellation rules still determine the permitted unit and
result. Independent backend buffering is allowed; concurrent unmediated guest-RAM
DMA is not introduced by calling a pointer a buffer.

### Lifetime, remap, cancellation and failures

An admitted route remains pinned through the actual leaf access and its recorded
completion. A conflicting remap may close future admissions, but cannot retarget
that access or acknowledge completion while an old covered access can still run.
The coordinator can service a pending old unit before the remap to avoid waiting
on a completion that the remap itself prevents. Later unadmitted units resolve
under current authority; an old token never gives the entire transfer perpetual
mapping permission. This inherits claim 13's route/operation separation.

Cancellation before a grant can revoke a no-effect request. Cancellation after
access starts cannot assume rollback: retire only after the matching copier has
finished or been proved unable to access storage. A deadline may terminate the
VM, but cannot revoke a raw pointer and reuse its backing while that thread can
still write. A crash or unknown partial write keeps admission closed and triggers
contained failure; it does not resume the VM with guessed metadata or retry the
unit. Already committed units and external I/O effects retain their recorded
status. These are lifetime rules, not a numerical lease expiry mechanism.

Initial host loading, OS-managed mapping/page activity and final unmap/reuse stay
within claim 25's named-platform assumptions and existing teardown protocol.
The interface does not prove them away. A changed native mapping/platform or a
contrary observation reopens the affected premise; a copied path is usable only
if its own resident mapping/transfer assumptions still hold.

### Error result: choose REPORT without inventing a partial count

[`virtio_blk_rw_complete` and its error handler, lines 71–134](https://github.com/qemu/qemu/blob/c1c18d1e640b64292859ce9f30f3c344edfb0294/hw/block/virtio-blk.c#L71)
receive `ret`, not a valid-byte count. The source expressly allows failed reads
to have dirtied their buffers. STOP retains the request, REPORT completes IOERR,
and IGNORE falls through to OK. Consequently neither “error means no write” nor
“error means the entire requested data is valid” follows for the stock direct
path.

For **this staged incoming-read adapter**, select REPORT: a failed backend read
has modified only private staging, so discard its unknown payload, perform zero
guest payload copies, write the final IOERR status and publish the used entry
with `len = 0`. Do not reuse QEMU's unconditional `req->in_len`: writing a status
at the tail does not establish that the first inbound bytes were overwritten.
Virtio 1.3 §2.7.8.2 permits an underestimated used length and requires the claimed
prefix to have been written before used-index publication; §5.2.6 defines the
final error status. This is a selected realization of that contract, not a claim
that QEMU's old completion count is retained unchanged. [Virtio 1.3](https://docs.oasis-open.org/virtio/virtio/v1.3/virtio-v1.3.html)

Driver consumption is a separate compatibility question: §2.7.8.3 tells the
driver not to assume bytes beyond `len` and recommends ignoring them. The
zero-prefix device policy therefore does not establish that every driver will
consume a tail status byte. Independent Return 22 checks the specific
[Linux v6.12 path](https://github.com/torvalds/linux/blob/v6.12/drivers/block/virtio_blk.c#L306):
`virtblk_done` retrieves the used length without gating completion on it, and
`virtblk_request_done` reads status through `virtblk_vbr_status` independently
of that length. This supports that named source path only; actual target-driver
selection, other versions/drivers and boot compatibility remain separate.

This removes the need to reconstruct an unknowable failed-read byte count for
this path. It does not roll back any already committed guest unit or external
disk write. STOP/IGNORE are not secretly translated into REPORT; selecting either
later requires its own retained-result and completion recipe. A callback error
causes no automatic retry. A host failure during the *guest RAM copy*, rather
than during private staging I/O, is claim 26's unknown-partial-commit failure:
keep admission closed and contain the VM, not report an ordinary disk IOERR and
resume with uncertain memory/dependencies. The extra private buffer and copy are
material costs; no whole-device performance conclusion follows.

### Reset, cancellation and a late source result

Pinned [`virtio_blk_reset`, lines 1147–1174](https://github.com/qemu/qemu/blob/c1c18d1e640b64292859ce9f30f3c344edfb0294/hw/block/virtio-blk.c#L1147)

those obligations and pending IRQ offers to be retired or canceled. Virtio 1.3

The handoff fixture's generation comparison did not test this real translator

### FD ownership and order

Construction binds the supervisor-authorized FD to disk identity, worker and
lifetime incarnation; verify regular file, appropriate read/write access, fixed
sector-aligned capacity and representable offsets. Reject O_APPEND, and do not
change FD status flags while jobs exist. No path reopen, guest-provided FD,
seek-plus-read/write, mmap writer or extra duplicate is needed. The admitted
configuration excludes another writer or truncator of the same backing during
that disk lifetime. This is an ownership/deployment condition; an advisory lock
would not force an unrelated process to obey it. Claim 49's outer worker
containment does not establish such internal ordering by itself.

Device dequeue assigns monotonically ordered disk operations. A job includes its
request/queue incarnation, command, checked offset/length, immutable OUT staging
or owned IN staging, and completion token. Check sector multiplication, end
addition and `off_t` representability before submission, in addition to the
128-KiB/profile limits. Reserve a result slot before dispatch. The lane does not
skip an earlier accepted operation merely because its RAM snapshot is not yet
ready; the device owner and coordinator continue progressing that snapshot
without holding a disk lock or a RAM window during I/O.

Exactly one disk operation executes at a time, including all positive short-call
continuations and any required full-sync. Therefore overlapping writes A then B
cannot interleave their suffixes: B starts only after A settles. A following read
samples after the preceding operation settles, including any actual partial
failed-write effect. This is the selected scheduling order, not a new promise that
failed writes are sector-atomic. Guest completion publication remains the separate
admitted RAM transaction; a backend return never directly touches guest status,
used ring, source generations or IRQ state.

### Transfer and result rules

For a nonempty request, let `done` be the sum of positive returns, initially zero.
The next call uses private staging at `done`, file offset `base + done`, and
`length - done`. Only positive progress advances `done`; advancing within one
operation is not replaying that operation.

| Return/phase | Selected disposition |
| --- | --- |
| Positive count within the requested remainder | Advance by that count; continue the remaining suffix until complete. Preserve operation identity and disk order. Never resend the confirmed prefix. An impossible count larger than the remainder is a host-interface failure, not guest success. |
| IN reaches full length | Publish successful staged payload through claim 27. A zero-length legal data operation needs no syscall; ordinary request validation still applies. |
| IN returns zero before full length, or `-1` | Treat premature EOF/error as IOERR, discard all private partial payload, and perform only the selected error status/ring completion. Do not manufacture zeros for truncated backing. Capture errno on the I/O thread before other calls. |
| OUT reaches full length in negotiated writeback mode | Backend data phase is complete; OK may be published without asserting durability. |
| OUT returns zero for a nonempty remainder, or `-1` | Stop this job with IOERR. Preserve confirmed positive-prefix progress and mark the failing call's possible additional effects unknown; do not claim rollback, an exact final written extent, or perform a blind retry. |
| `-1` including EINTR | Initial policy returns the operation's error rather than an automatic retry. This is conservative error reporting, not an assertion that interrupted calls always had no effects. Later retry policy would need its own no-duplicate/progress argument. |
| OUT completed data in stable-write mode | Keep this job active through F_FULLFSYNC before deciding its OK/IOERR result. A sync error is a failed stable write even though all data bytes may already be present. |

A positive one-byte-at-a-time progression remains finite under the 128-KiB bound;
zero progress cannot spin. There is no claim that a blocking filesystem call has
a fixed completion deadline. Private buffers are resident owned allocations,
not guest pointers; read errors can modify them without creating an uncertain
guest-RAM commit. OUT errors can leave real disk changes, which IOERR does not
undo. Later reads may expose those effects; a later successful flush can persist
them without making the earlier request successful.

The selected writable profile has no discard/zeroing/zoned operations to dispatch.
GET_ID is an admitted memory result, not disk I/O. Every operation still uses the
claim-28 feature mask and REPORT status mapping; this backend does not secretly
turn a failed write into OK or install a different STOP/IGNORE policy.

### Full-sync boundary and failure

A FLUSH job sits in the same ordered lane after preceding accepted disk work.
After that work settles, call F_FULLFSYNC once. Only its successful return permits
FLUSH OK. Any error—including unsupported-command, I/O or interruption—returns
IOERR; there is no substitution of `fsync`, `fdatasync`, close or process exit.
Later disk operations remain behind this call. With offered-but-unnegotiated
FLUSH, each successful OUT data phase has the same full-sync step before write
completion, as claim 28 requires. A driver choosing writeback instead receives
its normal distinction between volatile write completion and flush completion.

Full-sync is outside the coordinator window and holds no guest execution lock.
The file FD and operation record remain live while it blocks. Unsupported
full-sync does not permit a weaker writable configuration to masquerade as this
one: reject such a backend at configuration/capability determination or report
truthful sync/stable-write errors. The previously accepted finite host API probe
supports only its named tested file/platform, not every future backing mount.

### Cancellation, reset and teardown

Logical cancellation never uses `close(fd)` or asynchronous thread cancellation
to make a live syscall appear finished. The I/O lane is not pthread-canceled
while it owns a request; cancellation is an explicit queue/result-state change.
Apple's [close(2)](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/close.2.html)
describes descriptor removal and possible errors, not an application-level
rollback of earlier writes or a safe replayable cancellation operation.

- A queued job not yet dispatched can be removed with no disk effect. Release
  its storage only after queue/result references end.
- A running read/write/full-sync retains its FD and staging until the call
  returns. On reset, stop further suffix calls after that return; record any
  actual progress, suppress obsolete guest completions and do not replay it into
  the next queue incarnation. A syscall already in progress may finish before
  cancellation is observed; reset acknowledgement waits for that outcome.
- A fully returned result waiting for a RAM grant can be retired without a guest
  completion when reset cancels it. A granted RAM unit instead settles under
  claim 27 before reset acknowledgement. Disk effects already happened in either
  case; withholding an old IRQ does not erase them.
- Device reset closes old admissions and drains these jobs/results without
  holding RAM exclusion or blocking the sole device owner. Only after old disk
  calls, RAM grants and notification references are retired can the guest reuse
  queue memory. New queue operations cannot overtake an old still-running disk
  write. Normal reset retains the same backing FD and capacity.
- Final orderly teardown closes admissions and posts its selected stop flush as
  the last lane job. After that result, drain/join-stop the lane and retire all
  result references; the device owner does not execute the blocking flush itself.
  Close the FD once only after no worker can use it; a close error is reported
  and is not a successful flush. Never retry a numeric FD after it might have
  been recycled. Forced
  worker termination uses the existing contained-failure path, retains uncertain
  external effects and never synthesizes a successful reset or disk completion.

If an I/O call does not return within the management deadline, successful reset
or resource reuse cannot be promised. The permitted outcome is contained VM
failure, not resuming with a new FD/queue while the old syscall still owns its
buffer or may write the disk. This preserves progress for the device/coordinator
threads without inventing cancellability of an arbitrary filesystem operation.

### Selected service boundary for the ordinary non-self-overlap case

Detect the split **before any operand read/write**, preserving decoded operation,
RIP, effective address, old RAX, source RCX, original flags and CPU/translation
context in the existing operation identity. Do not execute half a fast-path
operand then promote it to a supposedly untouched atomic fallback. This is a
generator-neutral access contract; none of TCG/FEX/Box64's current emitted paths
is accepted merely by naming it.

1. Enter the existing all-observer coordinator. Close competing admissions,
   drain prior ordinary guest/shim/backend effects with the required native
   barriers, and retain all live continuations. Only admitted maintenance for
   this transaction runs while it owns the operand. Guest IF, a paused vCPU's
   lock or a synchronous device callback cannot be its progress prerequisite.
2. Resolve both linear fragments as a **write-intent RMW**, using the complete
   permission/context key. Check both pages even if a peek would suggest the
   comparison will fail. Retain physical routes and backing lifetimes for this
   operation; an intervening remap cannot retarget its second fragment. RAM-only
   walks here use the existing borrowed maintenance transaction, not a recursive
   exclusion acquisition. Preserve earlier walk effects and dependency mismatch
   checks from claims 13–14.
3. Finish guest fault checks for the complete eight-byte operand before any
   explicit operand store or result publication. A updates performed by the
   selected legal walk may already be visible. **Do not obtain this preflight by
   blindly invoking a per-fragment STORE helper that commits D on the first
   page before the second page's permission is known.** The selected path must
   distinguish permission/readiness from final operand-write maintenance.
4. Once both accesses are valid and backing is pinned/resident, perform required
   translation write-maintenance and the indivisible read/compare/write/result
   phase without another guest-visible fault point. In the non-overlap case,
   doing D maintenance before the operand access is a selected conservative
   implementation order; the cited specifications do not require that exact
   internal order. The self-overlap case below is deliberately not inferred
   from this statement.
5. Read all eight bytes under exclusion into one little-endian value `old`.
   Compare original RAX with `old`; compute flags for that 64-bit comparison.
   If equal, write captured RCX and retain RAX. Otherwise write `old` back and
   set RAX to `old`. A software sequence of bounded ordinary native RAM accesses
   is sufficient **only because every relevant observer is excluded throughout**;
   a helper-only mutex or separate atomic updates to each fragment are not.
6. Commit the result and all source/shadow consequences before releasing
   observers. Return the existing `ACCESS_COMPLETED` outcome with the selected
   instruction's committed result to its emitter-owned success continuation.
   Do not retry the native access or guess `PC + 4`. A source mutation forces the
   already selected next-boundary/redispatch behavior while retaining this
   decoded operation until its own completion.

A native mapping/host failure after guest preflight is not converted into a late
second-page guest #PF after a half store. The selected backing/repair premise
must prevent such an architectural commit failure; an unexpected uncertain
partial native effect invokes contained failure with admission closed. This is
not a normal way to handle a valid guest locked instruction. The service uses
coordinated serialization only for the exceptional split access, not all ordinary
WB loads/stores or all guest SMP execution. Its global pause/barrier cost remains
material and unmeasured.

### Three concrete outcomes

| Case | Required/selected outcome and ledger |
| --- | --- |
| Second page absent or denied for write | No explicit CMPXCHG operand store, no comparison-result RAX/flag commit. Preserve original instruction state and deliver the appropriate write-intent #PF at its original RIP through the architectural fault owner; CR2 identifies the failing second-fragment access. For the stated simple CPL3 case, nonpresent gives P=0/W=1/U=1; write protection gives P=1/W=1/U=1. Additional exposed protection causes require their actual error bits. Retain any lawful A effects; do not roll back the walk. |
| Both pages writable, comparison unequal | The instruction still has a write access to both pages and the corresponding D obligation. Write back the old operand value, update RAX and all comparison flags, then publish completion. Identical final data bytes do not justify skipping write permission or D maintenance. Conservative source invalidation for the admitted operand-write spans is allowed by this candidate even if the bytes match. |
| Both pages writable, comparison equal, destination aliases code or an unrelated PTE | Commit captured RCX over both physical fragments as one excluded operand action, update comparison flags and preserve RAX. Track the physical write union, including aliasing views, retire future source entries and invalidate affected shadow dependencies. A PTE modified by the operand affects future translation admission; the already validated/pinned routes for this operation do not change halfway through its store. |

A/D maintenance retains the selected translation-cache rules: this is not a
promise to rewrite an in-memory D bit on every instruction when a legal cached
translation already records it as dirty. The self-overlap example concerns an
update actually required by the admitted walk, not an invented unconditional
PTE write.

Arithmetic flags and RAX remain at preinstruction values on the fault path;
exception delivery's CR2, saved RF, frame writes and restart rules belong to the
existing fault-entry contract. An internal pause is not an architectural interrupt
between the two halves. A pending guest event can be taken at the appropriate
instruction boundary after completion or through the fault/event-priority rules,
not by publishing a half result.

#### Concrete fence and execution-order boundary

Select a conservative data-barrier baseline for exposed SFENCE/MFENCE/LFENCE,
with an additional **LFENCE-only result dependency sink**:

1. Complete earlier **architectural memory/service effects of this vCPU** through
   their existing completion identities before the fence can retire. A completed
   MMIO command-register write need not wait for all background disk/network work
   it triggered; device completion has its own specified lifetime. Conversely,
   merely queuing the register write is not its architectural completion.
2. For **LFENCE**, before the native completion barrier, consume the still-live
   results of preceding guest work in non-elidable stores to reserved private
   resident scratch. The sink covers GPR/vector results and live dependencies
   of authoritative deferred representations, including inherited FP/status
   results. It is a dependency sink, not a mandatory full canonical-state spill:
   already completed/stored values need no duplicate store, a dead computation
   eliminated before the fence is not resurrected, and deferred flags may remain
   in their valid representation. Every prior producer whose result can still
   affect later guest-visible behavior must feed a completed store or an already
   completed semantic operation. Do not use an algebraically constant checksum
   or a metadata-only use that an optimizer can erase in place of that dependency.
3. Emit a compiler/IR scheduling boundary and native `DSB SY; ISB`, then admit
   later guest work. DSB completes the preceding explicit stores, including the
   LFENCE sink, whose data cannot be committed without the corresponding live
   producer results. ISB prevents later functionality from crossing the boundary.
   The guest instruction's privilege/feature/decode semantics remain with its
   owner. The barrier recipe also orders stores for LFENCE and loads for SFENCE;
   the **result sink is not required by this choice for MFENCE/SFENCE**.
4. Keep later guest side effects, helper invocation and timestamp reads after
   that boundary. A DMB alone is insufficient for LFENCE's local execution rule;
   neither is colloquial “pipeline flush” a proof that all prior pure computation
   has completed. No translation-block exit or full state canonicalization is
   inherently required if the generator preserves these dependencies, scheduling
   and recovery rules. A cold helper may use its existing ABI but must retain the
   live-result completion property rather than assuming a C function call is a
   native serializing instruction.

#### One order across native locks, exceptional transactions and host observers

Native locked operations obtain their memory linearization at the successful
exclusive store. Their surrounding full barriers compose with ordinary TSO
accesses and other fully fenced atomic operations; the architectural total order
of locked operations is not implemented by a separate helper-only mutex. When
an exceptional transaction closes admission, every existing native participant
must finish/retain its allowed phase and provide its own DSB drain acknowledgement.
A native successful store is either before that drain, with its committed result
retained, or after release; it cannot be replayed across the service. This inserts
the exclusive service's commit between the drained prefix and released suffix.
Two service transactions are ordered by the one coordinator's admission order.
Together these rules extend the native lock order through serviced locks without
serializing unrelated ordinary WB execution throughout its lifetime.

All relevant observers participate: ordinary guest code, native/helpers' guest
accesses, page walkers and A/D writes, source capture/publication, device payload/
status/ring writes, host snapshots and backend commits. Raw host aliases exist
only during exact granted windows; both host and resident sides use the accepted
DSB/compiler boundaries. Claims26–29 already prevent a device completion/IRQ
from becoming actionable before its RAM/source commit. Cache/PTE aliases update
all applicable generations before reentry. A data-ready word or host API return
cannot replace the owner/epoch acknowledgement, nor does a writable pointer grant
independent mutation authority.

Deadlock avoidance retains the existing distinction between memory-quiescent
PAUSED and canonical/reclaimable PARKED. Internal stops preserve decoded REP and
native continuation/code pins; repair may run under exclusive maintenance without
first forcing the faulting instruction to a canonical boundary. Control progress
uses permanent resident resources and cannot depend on guest IF or guest locks.
No disk wait, callback wait or reset drain may hold a live RAM grant. Resource
bounds/admission reserves are the existing protocol construction; finite timeout
may contain failure, never resume a partially committed transaction as success.
These are architecture requirements with concrete prior state transitions, not
an assertion that a host native-PC stop alone implements them.

#### Device transaction seam: synchronization is not a fabricated device operation

For a locked access reaching a memory-mapped endpoint, select one admitted
**endpoint transaction** rather than an exclusive retry loop. Its semantic owner
performs the required read/compute/write (including compare-failure writeback)
with no intervening CPU access or conflicting device-register event admitted
between its phases. Input arrivals may queue; they do not mutate that endpoint's
transaction state midway. The owner returns exact result/effect/commit status.
Guest RAM fragments in a mixed route remain reserved under the same coordinator.
This is a software bus transaction over emulated components, not a claim that
an arbitrary host peripheral implements native locked MMIO.

The endpoint determines supported bus widths, split response and specified
ignored/error behavior. Unsupported device widths must receive the **selected
machine's defined response**, not an invented guest #PF, a RAM byte-copy or an
unlimited callback. If a read has an irreversible side effect and a later phase
fails, retain that effect/progress; do not replay the read or roll it back merely
because the guest operation has no final result yet. Mapping/permission checks
and any permitted walk effects are distinct from endpoint completion. The
transaction freezes admitted routes; a later remap cannot retarget its remaining
phases silently. These are the same exactly-once typed access and route-lifetime
rules already used by the concrete block completion adapter.

This supplies the row6 synchronization mechanism, but **does not define every
row11 device register**. Before an endpoint is exposed, its width/split/error
response and transaction phases must be bound to that device's specification.
A device that requires reentrant guest execution to finish the locked transaction,
retains a forbidden RAM alias, or cannot preserve the phases is incompatible with
this seam and reopens its device choice. One cannot mark that incompatibility
ordinary implementation testing. Background I/O uses staged results and release
of RAM grants, so the selected block backend does not impose such a requirement.

**Source/design choice accepted in root Return36.** Select a concrete baseline

#### Why move the miss admission point

Claim14's optimistic retained walk is conditional on a legality predicate for
every saved component after an intervening dependency change. Its accepted example
covers a particular eligible nonleaf cache, not all faults, memory types, hidden
PAE state or device reads. Reusing SERVICE_ONLY as a universal permission to
continue those old values would be unjustified. Retrying the whole walk after a
completed device read would duplicate an effect. Neither is selected as baseline.

Instead select this state sequence for a **new access requiring translation**:

1. Register access identity, original instruction phase, complete required span,
   intent, mode/permission context and invalidation epoch. Request coordinator
   admission before the first PTE read; do not speculatively read a side-effecting
   route while waiting. Existing native participants reach memory-quiescent
   PAUSED using permanent resident control code and drain acknowledgements.
   A participant faulting on a missing shadow retains its unperformed access;
   it does not need to acquire walker authority or become canonical to acknowledge
   quiescence. This preserves the earlier repair/deadlock resolution.
2. Once exclusive, resolve the root/physical routes and run the selected mode's
   walker through INV03-02 claim17's serial suboperation result interface.
   Ordinary table writers, other walks' A/D writes, backend remaps/commits and
   permission-context changes cannot interleave. Already published operations
   finish or transfer their retained phase before this ownership begins.
3. Perform required A/D mutations under the same authority. Actual changed bytes
   participate in source/shadow invalidation even on a later #PF. Preserve the
   original walker-defined compare/restart semantics for changes caused by the
   operation's own earlier effects or a device-defined response; no coordinator
   bookkeeping race fabricates an algorithmic restart or repeated device read.
4. For a successful service access, consume the exact physical transfer once
   and return ACCESS_COMPLETED. Alternatively, install an eligible shadow for
   a still-unperformed native access and return RETRY_ACCESS; the two outcomes
   cannot both occur for the same access serial. Install writable authority only
   after the actual write-intent/D requirements are satisfied. Fault reports
   preserve vector/error/linear address and earlier effects without inventing an
   explicit operand write or updating CR2 on internal native repair.
5. Finish dependency/invalidation/maintenance publication, release ownership and
   admit the next epoch. An operation can retain code/frame references after its
   memory phase completes. A later translation miss is a new access, not reuse
   of the old walk's SERVICE_ONLY authority.

The coordinator is held through finite resident work and bounded endpoint
transactions, **not disk/network waits, guest execution, callbacks requiring a
RAM grant, or reset drain**. A physical paging read reaching an emulated register
must use a bounded exact endpoint response; external I/O proceeds through queued
staged results outside RAM ownership. If a proposed endpoint needs guest progress
while retaining the walk transaction, it is incompatible and its device choice
must change. Treating that conflict as an ordinary timeout would not preserve
valid guest execution.

This removes the baseline preexisting-raced-read mismatch: no foreign table or
route mutation can occur between the walk's reads. It does not make side-effecting
entries safe to cache. Such walks remain SERVICE_ONLY; already completed values
and route references still survive a host-service pause exactly once. Own-A/D
alias effects continue to use claims13/31–32 rather than being ignored. The
optimistic concurrent-RAM-walk option remains a future optimization with an
explicit validity proof, not a requirement for the selected baseline.

Miss serialization can be economically significant for page faults, working-set
churn and many-vCPU workloads. It is not a claimed optimal or measured design.
It preserves native shadow hits and does not place every ordinary memory access
behind a host call or global lock. No empirical performance conclusion follows.
