## M23-L1 proposed deterministic lock-holder method — 2026-09-05

Author: `/root`. Preparation only; no new observation or method acceptance.
The immediate decision is whether the harness can distinguish an intentionally
unavailable owner, a released owner that fails to progress, a lost wakeup and
an invalid observer while retaining every actor's actual state. It is not a
claim that an injected condition-variable wait reproduces OS preemption.
This first method measures a host-only dependency; actual guest spinlocks,
soft-lockup/RCU warnings and the shared-code protocol remain untested.

### Fixed inputs and actor protocol

Use one child process per cell. N={1,2,4,8} counts the worker threads, including
worker0 as owner; one independent controller and H={0,C,2C} runnable helper
threads are additional. C is the recorded online logical CPU count at campaign
start; refuse C outside1..64 or a changed C between cells, preserving unknown
applicability rather than resizing mid-campaign. Helpers run bounded arithmetic
on private storage and record their own start/end/count. Their existence and
observed work do not prove continuous runnable occupancy or actual oversubscription.
The maximum child thread inventory is8+1+128, recorded explicitly. No affinity
or P/E control is requested or inferred.

N=1 is owner/controller lifecycle diagnostics with no peer contention. N>=2
has N−1 peers. At each of20 fixed epochs (first2 warmup, next18 checked), owner0
acquires an ordinary process-local pthread mutex and publishes the epoch and
owned status through a separate controller mutex/condition variable. Peers
publish ready before attempting the owned mutex. Controller waits for every
ready record, then holds the owner behind an explicit release predicate for
100ms of its own operational timer; owner retains the target mutex throughout.
This injected delay is recorded as intentional, never charged to post-release
host scheduling. After controller publishes release and signals, owner checks
the predicate, records release receipt, updates protected epoch data, unlocks,
and records completion. Every peer must acquire, observe exact epoch data,
update a protected per-peer count exactly once, release, and acknowledge before
the next epoch starts. Readiness must not require acquisition of the held lock.
N=1 uses the same20 owner/controller epochs without fabricating peer events.

Three peer waiting strategies remain distinct: repeated pthread_mutex_trylock;
trylock plus sched_yield after each EBUSY; or blocking pthread_mutex_lock.
Owner/controller coordination always uses predicate loops, independent of the
peer strategy. A blocked-mutex outcome must not be called a condition-variable
notification measurement. API errors other than expected EBUSY terminate the
child with durable operation/actor/epoch/return identity. Inspect emitted loop
machine code before execution; counter-only instrumentation cannot certify the
actual yield call. Normal spins have a finite controller watchdog, not an
assumed scheduler fairness bound. Controller and helpers request the same QoS
as workers: user-interactive or background. Record requested QoS and setter
results; do not report effective overrides or physical placement from getters.

### Cause-specific controls and direct evidence

Each control changes one actual producer branch. Labeling synthetic JSON with
an expected failure is insufficient. All execute in owned child resources.

| Control | Actual trigger and required witness | Expected classification |
| --- | --- | --- |
| Held owner | Controller withholds its release predicate after all peer-ready records; owner remains in predicate wait holding target mutex | Expected withheld-owner timeout, with incomplete peer progress; not actual OS-preemption attribution |
| Missing yield | Yield strategy omits the actual sched_yield call while trylock observes EBUSY | Strategy-integrity failure from call-site record/counter versus observed EBUSY, corroborated by emitted code; no claim that absence necessarily stalls |
| Stale acknowledgement | One peer publishes previous epoch in the controller acknowledgement slot after its actual protected operation | Exact epoch acknowledgement failure |
| Lost-wakeup protocol | Under the controller mutex, publish the release predicate and notification before the owner deliberately calls its wait API without rechecking that predicate; retain actual predicate/read/call order | Wait-predicate protocol failure even if a spurious wake later returns; timeout alone is insufficient |
| Falsified placement | Alter one retained raw CPU-sample validity/result field to an out-of-range/error-inconsistent value at its producer seam | Observer-integrity failure only; never certification that an in-range CPU identifies P/E |
| Broken ordering | Owner deliberately publishes protected epoch data as previous epoch before actual mutex unlock | Exact protected-data mismatch; deterministic data-publication control, not proof that a weak-memory reordering was induced |
| Frozen worker | One peer enters an explicit never-released owned wait after ready, before lock attempt | Expected missing-peer timeout distinct from owner release/receipt/unlock, which must be observed |

The lost-wakeup control deliberately violates the predicate-loop discipline.
Its oracle pairs the true release predicate observed under the controller
mutex with an actual subsequent pthread_cond_timedwait return of0 or ETIMEDOUT.
Construct the absolute deadline from checked CLOCK_REALTIME plus250ms, validate
input tv_nsec, normalize carry, and reject time_t overflow; retain the original
clock read, normalized deadline and actual API return. Missing return or another
API error is unresolved/invalid. This proves the unconditional API invocation
even if it was descheduled before the call or the deadline expired before any
blocking. It establishes no blocked duration or lost OS notification. A clock
jump can alter this operational wait; the independent parent watchdog still
bounds the child and the outcome cannot become a host-clock/scheduling claim.
Spurious success cannot erase the witnessed predicate-loop violation. A mere
precall label or rejection before invoking the API is insufficient.
Likewise, CPU-number samples can reject malformed records but cannot detect
all plausible false samples; a source mapping or second independent
observation is still required for a stronger placement claim.

The5s no-progress timer resets only when a new, expected worker/controller
transition is available in the external complete-record prefix: actor start
once; owner lock-acquired/published-held; peer ready/first attempt (and at most
one first-EBUSY); controller release; owner receipt/unlock; peer lock-acquired,
verified update/unlock/ack; epoch completion; and final join/exit. Each has an
exact actor, epoch and phase identity. Repeated transitions, helper activity,
spin/retry counts, arbitrary output bytes and partial records cannot reset it.
Unexpected identities/sequence transitions stop as invalid rather than extending
liveness. Controller's deliberate withheld-release state is recorded once;
its repeated observation does not count as progress. The30s total timer remains
independent of progress and is never extended.

Each actor owns one externally opened append-only trace file and writes each
bounded record with checked write completion and an increasing sequence number;
no mutable shared append buffer or after-join-only log is sufficient. Owner
publication/release and acknowledgement records must finish their write before
the corresponding release-store/predicate transition. These complete kernel-file
prefixes survive child SIGKILL; this is not a promise of survival across host
power loss. The parent tails only complete newline records for progress. After
killing/reaping, it flushes/checksums the complete prefix and retains any partial
suffix verbatim. Missing required cause records remain unresolved. A partial
suffix never gets reconstructed or counted as a complete transition. Per-file
32MiB limits apply to actor files as well as stdout/stderr; aggregate1GiB checks
and the2GiB free reserve remain operational stop thresholds. Retain aggregate
retry/yield counts at phase boundaries, not a record per spin. This keeps log
volume bounded by actors×20epochs×fixed phase records; code review must verify
the exact bound and all write-error/overflow paths before execution.

Retain one writer-owned bounded actor log per thread, not a racing shared
counter as an ordering oracle. Synchronization edges, actual lock/API outcomes,
raw per-actor sequence/epoch records and complete thread joins reconstruct the
partial order. Cross-thread timestamp order alone does not prove happens-before.
A separate checker rejects duplicate/missing actors or epochs, stale/mixed
run/build identity, missing controls, buffer overflow, impossible lifecycle
orders and contradictory terminal classifications. Synthetic adversarial traces
must challenge each rule before any native review; baseline fixtures include
all N values and exactly20 epochs. The runner must build from retained sources
and retain shuffled input, signatures, environment, every partial result and
artifact hashes outside Git under NATEMU_RAW_ROOT.
