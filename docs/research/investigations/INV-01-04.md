## Question and decision relevance

- Question ID and text: `Q-01-04` — Can generated code be made executable under
  macOS code-signing and write/execute rules on the supported hosts without
  private APIs or restricted entitlements, and what does each write/execute
  transition cost?
- Decision(s) affected: admissibility of every translation family (`F2`, `F3`,
  `F4`); the translation-cost model in `Q-04-01`; the code-cache share of the
  virtual-address budget in `Q-01-03`; the cross-thread publication protocol in
  `Q-01-18`; the prototype method in `Q-01-12`; and the deployment boundary
  retained by `INV-00-05`.
- Why this must be resolved now: `KA-01` is the kill assumption for the whole
  translation branch of the family register. If no public, unprivileged path to
  alternately writable and executable memory exists in the form the project
  would actually ship, every translation family fails `INV-00-06` family-kill
  item 1 and only interpretation (`F1`) remains.

## Assumptions

- Declared assumptions: the target product is an ordinary user-space process
  run by a standard user without root or an installed privileged helper;
  generated code is written and executed inside that process; the code cache is
  shared by every vCPU thread.
- Assumptions to challenge: that a capability observed on an ad-hoc-signed
  command-line binary transfers to a Developer ID-signed, hardened-runtime,
  notarized distribution (it does not, and the difference is the point);
  that one toggle latency characterizes the design; that a single-threaded
  measurement describes an emulator with 2–8 vCPU threads; that storing
  instructions makes them executable without explicit cache maintenance; that
  "the project needs a JIT" — `F1` does not depend on this question at all.

## Hypothesis and falsifier

- Hypothesis: public API provides alternately writable and executable memory in
  a single unprivileged process, with a per-thread write/execute state whose
  transition cost is small enough to be an amortizable per-batch cost rather
  than a per-instruction one, and the constraint that actually binds a shipped
  product is the hardened-runtime single-region rule rather than the toggle.
- Falsifier(s): `pthread_jit_write_protect_supported_np` reports no support;
  `MAP_JIT` mappings of the sizes a code cache needs fail; a write after
  disabling protection still faults; instructions do not execute after
  invalidation; the transition requires an entitlement unavailable to the
  project's distribution model; or the per-thread scope does not hold, so no
  vCPU thread may execute while any thread is writing.
- Predicted outcomes: support reported; all three `MAP_JIT` sizes obtained;
  toggle cost tens of nanoseconds; the stub returns its declared value;
  cross-thread execution succeeds while another thread holds write access;
  same-thread execution while writable faults, as does a write without the
  toggle. A cross-thread fault would be the most consequential negative result
  because it converts the code cache into a global serialization point and
  makes `Q-01-18` a gating question rather than a protocol question.

## Method

- Procedure and versions: `experiments/INV-01-04/src/probe.c`, built by
  `Makefile` with Apple clang 21.0.0 at `-O1 -Wall -Wextra -std=c11` against
  SDK 26.4, driven by `run.sh`. The probe emits one JSON object covering
  `pthread_jit_write_protect_supported_np()`; `MAP_JIT` mappings at 256 MiB,
  1 GiB, and 4 GiB with `errno`; 20000 timed `pthread_jit_write_protect_np(0)`
  and `(1)` calls plus 2000 batched samples of 100 off/on pairs each, all with
  `mach_absolute_time` converted through `mach_timebase_info`; an assembled
  arm64 stub (`movz w0, #42` then `ret`) written with protection disabled,
  invalidated with `sys_icache_invalidate`, and called; a two-thread case in
  which thread A disables write protection, stores a known witness word into a
  scratch slot of the region, and only then releases thread B to call the stub,
  holding write access until B has finished — the witness word is read back and
  reported, so a run in which A never acquired write access cannot be reported
  as one in which it did (without it, removing A's acquisition changed neither
  the output nor the verdict); the
  same call from the thread that holds write access; and a write with
  protection enabled. Every execution and write is performed under
  `SIGSEGV`/`SIGBUS` handlers with per-thread `sigsetjmp` state, so a fault is
  recorded rather than fatal, and an unexpected fault outside an armed region
  exits with a distinctive status rather than being silently swallowed. No
  alternate signal stack is installed, so the handlers are registered without
  `SA_ONSTACK`. The probe also emits `mach_timebase_info`'s numerator and
  denominator, so a later reader can evaluate any reported interval against the
  clock quantum without access to this host.
- Inputs and configuration: no external inputs; sizes, iteration counts, and
  the declared stub value are compiled in and echoed in the output. `run.sh`
  enforces the `NATEMU_RAW_ROOT` rule and builds into the run directory, so
  nothing is written under `experiments/`. The environment capture records
  `sw_vers`, `sysctl hw.model hw.memsize hw.ncpu hw.pagesize kern.osversion`,
  `clang --version`, SDK path and version, `git rev-parse HEAD` with tree
  status, `codesign -d -vvv`, and `codesign -d --entitlements -` for the
  measured binary.
- Evidence labels assigned to planned claims: `CLM-01-04-12` through
  `CLM-01-04-17` are Hypothesis until the evidence run and its manifests exist;
  `-12` to `-16` then become Observed for the recorded host and signing
  configuration, and `-17` becomes Inferred over them and remains explicitly
  incomplete for the hardened-runtime cell.

## Controls

- Positive controls: the stub must return the value the probe declares it
  assembled; the cross-thread case must return that same declared value when it
  executes; the witness word stored by the writing thread must be read back
  intact, or the cross-thread result is vacuous; order statistics of every
  timing distribution must be monotone; and the batched timing must meet its
  declared precision target. Each of these can fail: with thread A's
  acquisition removed the probe now terminates with status 97 on the unarmed
  fault rather than reporting a pass.
- Negative controls: `probe --negative` assembles the stub to return 41 while
  the record still declares 42 — a code-generation defect. `src/check.py` must
  print `FAIL` on that output and `PASS` on the normal output; `run.sh` runs
  both and prints each verdict.
- Baselines: the raw single-call toggle measurement is its own baseline for the
  batched measurement, and the two are reported together precisely so a reader
  can see that the single-call interval sits at the timebase granularity. No
  cross-system baseline applies: this is a capability and cost measurement, not
  a comparison.

## Confounders

- Known confounders: timebase granularity larger than the quantity measured;
  instruction-cache, branch-predictor, and page-fault warm-up in the first
  iterations; P-core versus E-core placement and thread migration; thermal
  drift over long iteration counts; the compiler optimizing away a measured
  call; the signing configuration of the measured binary differing from the one
  described; the two threads in the concurrency case not actually overlapping
  in time.
- Mitigations and residual risk: the batched form raises the measured interval
  above the timebase tick; the toggle loop runs 20000 iterations so warm-up is
  a small fraction and the min, median, p99, and max are all reported rather
  than the mean alone; `pthread_jit_write_protect_np` is an external call that
  cannot be elided; the environment capture pins the signing configuration to
  the exact measured binary; the concurrency case uses an explicit ready flag
  so thread B executes only after thread A has disabled protection, and thread
  A is released only after B has finished. Residual risk: placement is not
  controlled, so timing distributions mix P-core and E-core samples; that is
  stated as a limitation and routed to `Q-05-06` rather than mitigated here.
  The concurrency case establishes that B executed while A held write access,
  not the reverse ordering of every instruction, which is `Q-01-18`.

## Sample plan

- Units, repetitions, randomization/order, warm-up, and power/precision target:
  capability outcomes are single observations. Timing units are individual
  toggle calls: 20000 samples for the raw form and 2000 samples of 100 pairs
  for the batched form, in a fixed order within one process. No warm-up is
  discarded; instead the full order statistics are reported so warm-up appears
  as the maximum rather than being hidden in a mean. No randomization is
  applied because there is a single treatment and no cross-condition
  comparison. The precision target is that the batched median be at least an
  order of magnitude above the timebase tick, which the batching factor of 100
  is chosen to secure.

- Predeclared exclusions: any run whose environment capture shows a signing

- Stop/failure conditions: if the shortest timed batch spans fewer than 100
  timebase ticks, the batched figure is at the clock quantum, the run supports
  no timing claim, and the method returns to the method gate for a larger
  batching factor; the checker enforces this and fails the run. If the checker
  reports `FAIL` on the normal output for any reason,
  the run yields no claim and the code returns to the code gate. If
  `pthread_jit_write_protect_supported_np()` reports no support, the toggle
  branch stops and the callback branch (`pthread_jit_write_with_callback_np`)
  becomes the required follow-up before any `KA-01` conclusion. If cross-thread
  execution faults, the result is escalated to `Q-01-18` and `Q-01-12` before

## Alternative explanations

- Alternatives considered: (1) the stub returns the right value because the
  compiler inlined a constant rather than because generated code ran —
  distinguished by the stub being reached through a function pointer into a
  `MAP_JIT` mapping whose contents the probe wrote at run time; (2) cross-thread
  execution succeeds because thread A had already re-enabled protection —
  distinguished by the explicit ready flag and by A being released only after B
  completes; (3) the toggle appears free because the call was optimized away —
  distinguished by it being an external libSystem call and by the batched form
  producing a non-zero per-pair interval; (4) allocation success at 4 GiB
  reflects lazy reservation rather than a usable code cache — acknowledged and
  not resolved here, since only the stub page is written; (5) the ad-hoc result
  generalizes to hardened runtime — explicitly rejected by `CLM-01-04-06`.
- Evidence distinguishing them: each is separated either by a recorded field or
  by an explicit statement that the record does not settle it.

## Limitations

- Scope, applicability, and uncertainty limits: observed evidence will apply to
  `Mac16,10` (M4) / macOS 26.6.2 (`25G83`) / SDK 26.4 only, and to the ad-hoc
  signing configuration recorded in the run's environment capture; `P1` (M1 Pro
  / Sequoia 15) replication is owed before any platform-wide use. The
  Developer ID, hardened-runtime, and notarized configurations — the ones a
  distributed product would use — are not measurable in this session and remain
  a declared Hypothesis cell, bounded by the documented single-`MAP_JIT`-region
  rule. The probe measures one and two threads, not 4 or 8; it writes one stub,
  not a working code cache; it never patches executing code; it never exercises
  the stale-instruction-cache case; and it does not measure the callback-based
  write model at all. Toggle cost is measured in isolation, so the amortized
  cost at any real transition frequency is not established and belongs to
  `Q-04-01`. Placement is uncontrolled (`Q-05-06`) and timer validity is
  `Q-05-08`. Nothing here selects a code-cache design, a write model, or an
  architecture family.
