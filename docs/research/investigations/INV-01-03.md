## Question and decision relevance

- Question ID and text: `Q-01-03` — Can guest physical and virtual address
  spaces be represented within a host process on the supported hosts, and at
  what limits (virtual reservation, host page size versus guest page size,
  aliasing, and guest RAM up to the accepted 8 GiB)?
- Decision(s) affected: admissibility of every family that needs a large host
  reservation (`F2`, `F4`, and any direct-map variant of `F1`); the tracking
  granularity available to `Q-01-05`; the virtual-address budget shared with
  the code cache of `Q-01-04`; the prototype method of `Q-01-12`; the resource
  budgets of `Q-01-14`; and the memory component of the cost model in
  `Q-04-01`.
- Why this must be resolved now: `INV-00-02` makes 8 GiB guest RAM a mandatory
  acceptance size at 2, 4, and 8 vCPUs. If one process cannot represent that
  much guest-physical memory alongside translated code and metadata, the
  mandatory cell is unreachable and `INV-00-06` project stop input 3 is in
  play. Every later mechanism question assumes an answer here.

## Assumptions

- Declared assumptions: guest-physical memory is represented inside one host
  process; the accepted guest uses 4 KiB and 2 MiB pages under four-level
  paging; the host page size is a property to be read at run time rather than
  assumed; a reservation and its backing are distinct capabilities.
- Assumptions to challenge: that guest-physical memory must be one contiguous
  host range (a direct-map convenience, not an envelope requirement); that a
  successful `PROT_NONE` reservation says anything about backing; that resident
  size, footprint, and compressed pages are one number; that a 2 GiB touch
  sample extrapolates linearly to 8 GiB; that `hw.pagesize`, `vm_page_size`,
  `getpagesize()`, `sysconf(_SC_PAGESIZE)`, and the compile-time `PAGE_SIZE`
  macro necessarily agree; that aliasing two host addresses onto one physical
  page is free of kernel bookkeeping cost.

## Hypothesis and falsifier

- Hypothesis: a single unprivileged host process can reserve address space far
  in excess of 8 GiB, can back a bounded sample of it at observable cost, can
  produce a second address for the same physical pages, and is restricted to
  host-page granularity for protection changes, so guest-physical memory is
  representable at 16 KiB tracking granularity and 4 KiB guest pages must be
  resolved above the host mechanism.
- Falsifier(s): an 8 GiB reservation fails, or fails once a code-cache
  reservation of the size `INV-01-04` probes is also held; backing the sample
  fails or its cost is unbounded; `mach_vm_remap` cannot alias; a sub-host-page
  protection change is silently rounded so that a guest page's protection
  cannot be expressed independently of its three neighbours; or the page-size
  readings disagree in a way that makes the effective granularity indeterminate.
- Predicted outcomes: reservations succeed at all three sizes; the 2 GiB touch
  raises resident size by approximately 2 GiB; aliasing succeeds in both
  directions; the sub-host-page `mprotect` is rejected with `EINVAL`; all five
  page-size readings are 16384. A silent-rounding outcome would move the
  granularity mismatch from a cost problem to a correctness problem and would
  be the most consequential single result of this investigation.

## Method

- Procedure and versions: `experiments/INV-01-03/src/probe.c`, built by
  `Makefile` with Apple clang 21.0.0 (`clang-2100.0.123.102`) at `-O1 -Wall
  -Wextra -std=c11` against SDK 26.4, driven by `run.sh`. The probe emits one
  JSON object covering, in order: the five page-size readings; `PROT_NONE`
  reservations at 8 GiB, 64 GiB, and 1 TiB with `errno`; an 8 GiB read/write
  anonymous mapping with a bounded 2 GiB sample touched one host page at a
  time, bracketed by `MACH_TASK_BASIC_INFO` and `TASK_VM_INFO` reads;
  a `mach_vm_allocate` region aliased with `mach_vm_remap`, with a same-view
  read-back positive control and byte comparisons in both directions; a
  `mprotect` of a 4 KiB-aligned range that is not host-page-aligned, followed
  by a writability probe of each 4 KiB slot of the containing host pages under
  a trapping handler; and `mincore` and `madvise(MADV_FREE_REUSABLE)` return
  values with the `mincore` vector decoded into its documented bit names, read
  once before a write, once after writing a page, and once after the
  `madvise`. The probe also emits `mach_timebase_info`'s numerator and
  denominator, so a later reader can evaluate any interval in the artifact
  against the clock quantum without access to this host.
- Inputs and configuration: no external inputs. Sizes and the 2 GiB touch bound
  are compiled in and recorded in the output. `run.sh` refuses to run unless
  `NATEMU_RAW_ROOT` is set, is an existing directory, and lies outside the
  repository; it builds into the run directory so nothing is written under
  `experiments/`. Run identifier `<UTC timestamp>-<git short rev>`; environment
  capture records `sw_vers`, `sysctl hw.model hw.memsize hw.ncpu hw.pagesize
  kern.osversion`, `clang --version`, the SDK path and version, `git rev-parse
  HEAD` with a working-tree status, and `codesign -d -vvv` plus
  `codesign -d --entitlements -` for the measured binary.
- Evidence labels assigned to planned claims, as resolved by the 2026-09-04
  evidence run (`MAN-01-03-01`): `CLM-01-03-07` through `CLM-01-03-11` and
  `CLM-01-03-14` are now **Observed** with this host's applicability, and

## Controls

- Positive controls: bytes written through a mapping must read back through
  that same mapping (`alias.self_readback_matched`); a host-page-aligned
  `mprotect` must succeed where the sub-page one fails; `pages_touched` must
  equal `touch_bytes / step_bytes`.
- Negative controls: `probe --negative` writes a pattern through the source
  mapping that differs from the one it then compares against, so the
  same-view read-back control fails. `src/check.py` must print `FAIL` on that
  output and `PASS` on the normal output; `run.sh` executes both and prints
  each verdict, so the code gate can see the checker detect a defect.
- Baselines: none. This investigation establishes capability and limits, not a
  comparison. The checker judges the probe, not the platform: an absent
  platform capability is reported as a `NOTE`, never a `FAIL`.

## Confounders

- Known confounders: first-touch commit faults conflated with steady-state
  access cost; the macOS memory compressor converting a capacity question into
  a CPU-cost question invisibly; resident size, `phys_footprint`, and
  compressed pages being different quantities; other processes on a 16 GiB host
  competing for physical memory; VM-map fragmentation from prior probes
  changing later mapping costs; P/E-core placement and thermal state affecting
  any timing; run order within a single process.
- Mitigations and residual risk: this probe reports counts, return values, and
  residency deltas rather than throughput, so it is largely insensitive to
  placement and thermal drift; the touch loop is bounded at 2 GiB to stay well
  inside 16 GiB and avoid the compressor; both `resident_size` and
  `phys_footprint` are recorded so the two accountings can be compared rather
  than conflated; the environment capture records `hw.memsize`. Residual risk:
  the 2 GiB sample cannot establish behavior at 8 GiB, and no reading here
  distinguishes compressed from swapped pages. Both are stated as limitations
  rather than mitigated.

## Sample plan

- Units, repetitions, randomization/order, warm-up, and power/precision target:
  the units are single capability outcomes, not timing samples, so one
  observation per capability is sufficient and no randomization or warm-up
  applies. The touch loop is 131072 host pages (2 GiB at 16 KiB), a fixed
  bound chosen so the sample stays far inside host physical memory; it is
  reported as a count, not a rate. The alias comparison is 4096 bytes in each
  direction. No statistical precision target is set because no claim here is a
  distributional estimate; a repeat of the whole run on a second host is
  replication, owned by the replication gate rather than by this sample plan.

## Exclusion and stop criteria

- Predeclared exclusions: a run whose environment capture shows a dirty working
  tree at a revision other than the committed experiment revision is excluded;
  a run on a host under concurrent memory pressure from another instance of
  this or any group's probe is excluded; the `--negative` output is never a
  source of a claim and exists only to exercise the checker.
- Stop/failure conditions: if the checker reports `FAIL` on the normal output,
  the run produces no claim and the code returns to the code gate. If the 8 GiB
  reservation fails, the run stops and the result is reported as a `KA-03`
  falsifier candidate requiring replication before any kill is recorded. If a
  sub-host-page `mprotect` is silently rounded, the granularity result is
  escalated to `Q-01-05` and `Q-02-01` as a correctness hazard before any cost
  work continues.

### Kill-assumption disposition and family implications


All dispositions below are bounded to `Mac16,10` (M4) / macOS 26.6.2 (`25G83`)
/ SDK 26.4 / ad-hoc signing, one host, one build configuration. None of them
disposes of a kill assumption as written, because every one of `KA-01`,
`KA-03`, `KA-04`, and `KA-07` quantifies over "the supported hosts" and `P1`
replication is owed. A kill assumption that is not falsified on one host
*survives*; it does not pass. No architecture family is selected here and no
production design is chosen.

- **`KA-03` survives on this host, partially exercised.** 8 GiB, 64 GiB, and
  1 TiB reservations succeeded, and a 2 GiB sample was backed at full residency
  alongside the 4 GiB `MAP_JIT` region `INV-01-04` obtained in the same session
  — so guest RAM and a code cache did not compete destructively within one
  process's limits. What is *not* shown: 8 GiB fully resident. The host has
  16 GiB, and `INV-00-02` makes 8 GiB a mandatory acceptance size, so the
  mandatory cell remains unreached; whether it is reachable is a host-memory
  coverage question for `Q-05-02` and a budget question for `Q-01-14`. No
  `INV-00-06` project stop input 3 is triggered, and none is ruled out.
- **`KA-07` is materially affected from here.** The 16 KiB host page is now
  Observed from four independent readings rather than assumed, which converts
  the granularity premise `INV-01-05` reasons from into evidence, and the
  sub-host-page `mprotect` was *rejected* rather than silently rounded — so on
  this host the guest/host page mismatch is a cost and imprecision problem, not
  a permissions-corruption hazard.
- **Family implications.** `F1` and `F2` both depend on representing
  guest-physical memory in one process; nothing observed here obstructs either
  on this host, and neither is killed. `F4` additionally wants a stable address
  for statically translated code, which the reservation results permit but do
  not establish. `F3` is unaffected by this record: its guest-physical mapping
  contract would come from Hypervisor.framework, which is `INV-01-01`'s
  `KA-02`, untested here. The contiguity assumption this record set out to
  challenge remains unforced — a 1 TiB reservation succeeding means a direct-map
  layout is *available*, not that it is required or preferred.

## Alternative explanations

- Alternatives considered: (1) a large reservation succeeds because the kernel
  defers all work, so the result says nothing about backing — distinguished by
  the separate commit-and-touch probe and its residency deltas; (2) the
  residency delta reflects the probe's own allocations rather than the touched
  pages — distinguished by bracketing the loop with before/after reads and by
  the page count; (3) the alias comparison passes because both pointers refer
  to the same address — distinguished by recording `distinct_addresses`;
  (4) the sub-host-page rejection is an artifact of the specific offset chosen
  — distinguished by the host-page-aligned control at the same address;
  Post-run disposition of the alternatives: (1) is
  excluded by the commit-and-touch probe, whose resident delta rose by the full
  2 GiB rather than remaining at reservation cost; (2) is excluded by the
  before/after bracketing and the page count, and the 1050112-byte excess of
  footprint over resident delta is small and accounted for; (3) is excluded by
  `distinct_addresses` being true; (4) is excluded by the host-page-aligned
  control succeeding at the same address the sub-page request failed at; (5) is
  excluded by construction; (6) remains open and is the one alternative this
  run does not settle — the `MINCORE_MODIFIED` bit cleared after
  `MADV_FREE_REUSABLE`, which is consistent with a real modification tracker
  but also with the bit being an attribute of the page's backing state, and
  nothing here distinguishes the two.

  (5) page-size agreement is an artifact of counting a
  dependent reading — addressed by excluding the compile-time `PAGE_SIZE`
  macro, which `mach/arm/vm_param.h` defines as `vm_page_size` and which
  therefore cannot disagree with it, leaving four genuinely independent
  sources that the checker actually compares; (6) `MINCORE_MODIFIED` is set
  merely because the page is resident and anonymous rather than because it was
  written — not excluded by this probe, which is why `CLM-01-03-14` is
  confined to what the bits do across a write and a `madvise` and why the
  fault-free dirty-reporting question is recorded as open for `Q-01-05` rather
  than answered.
- Evidence distinguishing them: each alternative is separated by a field the
  probe records; none is settled until the evidence run exists.

## Limitations

- Scope, applicability, and uncertainty limits: the observed evidence applies to
  `Mac16,10` (M4) / macOS 26.6.2 (`25G83`) / SDK 26.4 / ad-hoc signing only;
  `P1` (M1 Pro / Sequoia 15) replication is owed before any platform-wide use.
  The host was not idle during the run — an out-of-band `uptime` reading by the
  executor showed a 1-minute load average of 2.43, with other agents' processes
  active; no `env.txt` carries a load figure, so this is not artifact-borne
  evidence. It does not affect the capability outcomes and exact byte counts
  this record reports, since none is a timing measurement. The host has
  16 GiB of physical RAM, so this record cannot establish behavior for a fully
  resident 8 GiB guest; it bounds reservation and a 2 GiB commit sample only,
  and the host memory configuration required for a valid mandatory 8 GiB cell
  is owned by `Q-05-02` and `Q-01-14`. The probe measures one process with one
  thread: contention for the process-wide VM map across 2–8 vCPU threads is not
  measured here and is owned by `Q-01-05` and `Q-01-18`. No guest runs, so no
  claim about guest paging semantics is made. Residency counters are used as
  named by the SDK header; their validity as instruments is `Q-05-08`. Nothing
  here selects a memory layout, a contiguity policy, or an architecture family.
