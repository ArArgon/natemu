## Question and decision relevance

- Question ID and text: `Q-01-12` — Can an approved prototype integrate
  translation, paging, precise exceptions, interrupts, and at least two
  concurrent vCPUs?
- Decision(s) affected: the Track 01 exit criterion that requires an integrated
  prototype; kill assumption `KA-11`; the narrow parts of `KA-06` and `KA-04`
  named below; and, through `Q-01-02`, whether family `F2` remains a candidate
  mechanism set. It affects no architecture selection and no performance
  estimate.
- Why this must be resolved now: the track states that feasibility cannot be
  closed on paper. `Q-01-03`–`Q-01-08` establish each mechanism separately;
  only this record puts them on one critical path in one process, which is
  where a composition failure would appear.

## Assumptions

- Declared assumptions:
  1. "Integrated" means one process, one build, one positive run, with the five
     mechanisms on a shared critical path — the faulting instruction is
     translated, the fault is delivered through the guest's own IDT into a
     translated handler, that handler edits the same page tables the software
     MMU walks, interrupts arrive at translated-block boundaries, and both
     vCPUs share one guest-physical memory. Five mechanisms demonstrated in
     five modes would satisfy the words and not the requirement.
  2. Concurrency must be witnessed by something a single-threaded round-robin
     scheduler cannot produce.
  3. The prototype's x86-64 semantics are defined by this method, not validated
     against the ISA specifications; conformance is `Q-02-01`/`Q-02-03`.
  4. The host-API facts the prototype consumes (`MAP_JIT` and per-thread
     write-protect toggling, `sys_icache_invalidate`, `mach_absolute_time` and
     `mach_wait_until`) are dependencies owned by `Q-01-04` and `Q-01-07`. This
     record does not re-establish them and may not be cited for them.
- Assumptions to challenge: that a passing prototype says anything about `F1`,
  `F3`, or `F4`; that composition on one host generalizes; that a mechanism
  exercised once is a mechanism that works; that an invariant with no control
  that breaks it is an oracle; that absence of a memory-ordering violation is
  evidence of ordering.

## Hypothesis and falsifier

- Hypothesis: `KA-11` holds on the host of record — translation, guest paging,
  precise exceptions, interrupts, and two concurrently executing vCPUs compose
  in one process. Narrowly, the explicit-check branch of `KA-04` composes (a
  fault raised inside generated code is caught with full guest state and the
  vCPU resumed at a chosen PC), and the `KA-06` emission rule survives real
  concurrency at the predeclared iteration count.
- Falsifier(s): any of — the faulting instruction's effect applied zero or two
  times; a wrong CR2, error code, or pushed RIP; interrupts delivered while
  `IF` is clear; a halted vCPU that never wakes; IPIs sent but not received;
  a counter that is not exactly `2K`; any message-passing violation; no overlap
  between the two vCPUs' execution windows; a modified instruction executing
  with its old behaviour; any `#GP`; a watchdog timeout; or any negative
  control the checker reports as PASS. A single failed repetition out of five
  falsifies the hypothesis; it is not a censored sample.
- Predicted outcomes: as recorded per claim above. A failure caused by an
  incomplete or defective prototype falsifies nothing about the platform —
  `INV-00-06` family kill 3 requires a structural incompatibility surviving
  independent replication and states that an ordinary implementation defect is
  not structural impossibility.

## Method

- Procedure and versions:
  1. Assemble the guest program with `clang -target x86_64-elf -c` (Apple clang
     21.0.0, `clang-2100.0.123.102`). Extract `.text` and its symbols with
     `src/elfextract.py`, which **rejects** any relocation against `.text`
     rather than applying one, because an unapplied relocation would silently
     point the guest at a wrong address.
  2. Build `prototype/proto.c` with `clang -O2 -std=c11 -Wall -Wextra`, sign it
     ad hoc with `com.apple.security.cs.allow-jit`, and keep an unentitled copy
     so both outcomes are recorded.
  3. Allocate 16 MiB of guest-physical memory and load the guest at guest
     physical `0x00100000`. Each vCPU gets its own `MAP_JIT` region, code cache
     keyed by guest-physical address, and software TLB.
  4. Start a host timer thread and two vCPU threads; a watchdog terminates the
     run at 180 s and records `timed_out`.
  5. Each vCPU translates a documented x86-64 subset into arm64: guest state
     lives in a per-vCPU structure, arithmetic and control flow are emitted
     natively with lazily evaluated flags, address translation for each memory
     access is a helper call, and the access itself is an inline `LDAR`/`STLR`
     (or `LDADDAL`/`CASAL`/`SWPAL` for locked operations) in the generated
     code. Blocks end at control flow, at a control-register write, at a page
     boundary, or after 64 instructions, and return to the dispatch loop, where
     pending interrupts are checked.
  6. The guest builds its own 4-level page tables and IDT, identity-maps
     `[0, 0x00E00000)`, creates four aliases at `0x40000000` — not-present,
     not-present, present-read-only, and not-present — over pre-filled backing
     pages, maps the LAPIC page, loads CR3 and enables paging, and releases the
     second vCPU. The `#PF` gate names IST slot 1 so that a fault on the guest
     stack is delivered on a separate stack instead of nesting.
  7. Both vCPUs pass a two-party sense-reversing barrier, stamp an execution
     window through an exit-to-host `out`, run 100 000 contended `lock xadd`
     increments each and 4096 message-passing iterations each in opposite
     directions, and stamp the window closed. vCPU 1 sends 64 IPIs with an
     acknowledgement handshake during that phase; vCPU 0 takes timer interrupts
     throughout.
  8. After a second barrier, vCPU 0 runs the three alias page-fault tests, reads the
     accessed and dirty bits back out of its own PTEs, runs a fourth fault test
     in which a stack `push` stores to a not-present page, then a `#UD` test,
     the self-modifying-code test, a `lock cmpxchg` success-then-failure test,
     an interrupts-disabled region, and a `sti; hlt` that must be woken by a
     timer interrupt, while vCPU 1 spins. A third barrier, a timer drain, and
     both vCPUs halt with `IF` clear.
  9. `src/check.py` evaluates invariants `I1`–`I15` over the JSON and prints
     PASS or FAIL, exiting non-zero on FAIL. For a control run it is given the
     invariants that control targets and fails if any of them did not fire.
  10. A second binary built with `-fsanitize=thread` runs the same positive
     path once. Any ThreadSanitizer race report is a code-gate failure.
- Inputs and configuration, frozen before any evidence run: guest RAM 16 MiB;
  two vCPUs; `KLOOP = 100000` locked increments per vCPU; `NLOOP = 4096`
  message-passing iterations per vCPU per direction; `NIPI = 64` IPIs; timer
  period 1 ms (1 kHz) under post-on-EOI; bounded spin `SPINMAX = 1000000`;
  parallelism floor `1.50`; watchdog 180 s; five repetitions of the positive
  run; one run per control; one ThreadSanitizer run. `src/check.py` **asserts**
  the frozen values (`jit_mapping`, `injection`, `loop_k`, `loop_n`, `nvcpu`,
  `timer_period_ns`) rather than reading them out of the document, so a run of a
  different build cannot pass as the frozen experiment.
- **Coalescing rule, frozen here.** The host timer thread posts a tick only when
  it observes neither a pending nor an in-service timer interrupt for vCPU 0.
  That guard is two separate atomic loads, so it does **not** guarantee that at
  most one tick is ever outstanding: a post can interleave between the delivery
  path clearing the pending bit and setting the in-service vector. What it does
  guarantee, and what the oracle uses, is the exact identity
  `timer_posted - timer_ticks == timer_pending_at_end`, evaluated after both
  vCPUs have halted and the timer thread has stopped. No coalescing rule beyond
  that identity is claimed.
- **Fault-versus-interrupt priority, frozen here.** Pending interrupts are
  examined only at translated-block entry, before the block runs. A fault raised
  inside a block therefore always preempts a pending interrupt: the fault
  unwinds out of the block and is delivered first, and the interrupt is taken at
  the entry to the handler's first block, with `IF` clear until the handler sets
  it or `iretq` restores it. An interrupt is never delivered between the fault
  and its handler.

## Controls

- Positive controls: the run itself is the positive case, and several
  invariants are two-sided within it — the `lock cmpxchg` test requires a
  success *and* a failure with the old value loaded; the self-modifying-code
  test requires the old behaviour before the patch and the new behaviour after;
  the interrupts-disabled region requires zero deliveries while the surrounding
  phases require many.
- Negative controls, each a flag on the same binary so that the control
  exercises the real checker, and each required to produce a **completed** run
  whose JSON the checker marks FAIL with a non-zero exit:

  | Flag | Defect injected | Targeted invariants | Determinism |
  | --- | --- | --- | --- |
  | `--inject-push-order` | `push`/`call` commit RSP before the store that can fault | `I6d`, `I6e` | deterministic |
  | `--inject-skip-restart` | `iretq` resumes after the faulting instruction | `I5d`, `I6a`–`I6c` | deterministic |
  | `--inject-nonatomic-rmw` | `lock xadd` emitted as load/add/store | `I3` | near-deterministic over 200 000 contended increments |
  | `--inject-drop-ipi` | every third IPI discarded by the LAPIC model | `I11a`, `I11c` | deterministic |
  | `--inject-stale-cache` | store-side self-modifying-code check suppressed | `I8b`, `I8c` | deterministic |
  | `--inject-no-barrier` | ordinary accesses emitted as `LDR`/`STR` | `I4a`, if a violation surfaces | **stochastic** |

  The four deterministic and one near-deterministic control carry the code
  gate. The no-barrier control is predeclared as informative only: arm64 need
  not exhibit the reordering in any given window, so a PASS is not evidence
  that the acquire/release emission is unnecessary.

- **Targeted versus collateral failures.** Each control's targeted invariants
  are passed to `src/check.py --expect`, which labels them and fails the run if
  any targeted invariant did **not** fire. Everything else a control breaks is
  collateral and is **not** a witness for anything:
  `--inject-skip-restart` corrupts the guest and then aborts, so it also trips
  `I1a`, `I2b`, `I2c`, `I2f` and most of phase three; `--inject-drop-ipi`
  starves the peer through its bounded acknowledgement spin, so it also trips
  `I4b` (about 21 message-passing spin timeouts) and inflates the concurrent
  phase from roughly 60 ms to roughly 8 s, which distorts the concurrency
  instrument in that run and is the reason its `I13` values are not comparable

## Confounders

- Known confounders:
  1. Host scheduling is uncontrolled and the threads are not pinned. If macOS
     interleaves both vCPU threads on one core, the marked windows still
     overlap for the whole phase — overlap is therefore no defence — but the
     consumed thread CPU time per unit of wall time falls towards one thread's
     worth, which is what `I13b` measures. A run scheduled on efficiency cores
     is slower without changing that ratio.
  2. The overlap instrument is an exit-to-host from inside translated code; it
     serializes the vCPU at the measurement point, so the windows measured are
     instrumented execution.
  3. The clock granularity on this host is coarser than a nanosecond, so two
     marks taken close together can be equal.
  4. Absence of a message-passing violation may mean the window was never hit
     rather than that ordering held.
  5. The guest is synthetic and small, so translation, TLB, and code-cache
     pressure are far below guest scale.
- Mitigations and residual risk: the barrier excludes a non-preemptive
  single-threaded schedule structurally; the CPU-time ratio excludes preemptive
  time-slicing on one core quantitatively, with a floor frozen before data; the
  windows span the whole concurrent phase, so the exit-to-host cost is
  negligible relative to them; the iteration counts are frozen before data and
  the memory-ordering result is stated as "no violation in N iterations" rather
  than as an ordering guarantee. Residual risk: the CPU-time ratio is a
  host-reported aggregate, not an instruction-level simultaneity proof, and a
  run under heavy external load could fall below the floor without any
  mechanism being wrong — a false negative routed to `Q-05-06`. Scale is not
  addressed at all and is routed to `Q-01-03` and `Q-04-01`.

  one run of each of the five controls, in the fixed order emitted by `run.sh`,

## Exclusion and stop criteria

- Predeclared exclusions: wall time and every derived rate are excluded from
  all analysis except run characterization in the manifest, and may not enter
  `Q-00-04` aggregation, `Q-04-01` cost modelling, or any comparison with the
  `Q-00-03` baseline. Runs performed before the method and code gates pass are
  excluded from evidence entirely, including every smoke test performed during
  development, whose output went to a scratch directory and supports no claim.
- Stop/failure conditions: the run stops on watchdog timeout (180 s), on an
  unsupported instruction, on a guest access to unbacked guest-physical memory,
  on a **nested fault while delivering an exception**, or on a null or absent
  IDT gate. The nested-fault case is implemented rather than merely stated: the
  raise path records a per-vCPU `nested_fault` flag, aborts with a message, and
  unwinds, so the failure is a named invariant (`I1c`) rather than a livelock
  ending at the watchdog. Any of these is a FAIL, not a discarded run. If a
  control produces PASS, or fails without its targeted invariant firing, the
  code gate must fail: the invariant that control targets is not an oracle.
  A host-level death that writes no JSON at all is caught by `run.sh`, which
  synthesizes an abort document so the verdict arrives as `I1a` rather than as
  a checker traceback.

## Alternative explanations

- Alternatives considered:
  1. *The vCPUs did not really run in parallel; one core time-sliced them.*
     The barrier excludes only a **non-preemptive** single-threaded schedule,
     and window overlap excludes nothing further, because both windows span the
     whole concurrent phase. What distinguishes the alternative is the
     consumed-CPU-time ratio (`I13b`): two threads interleaved on one core
     cannot consume more than one thread's worth of CPU time per unit of wall
     time, so a ratio at or above the frozen floor of `1.50` is inconsistent
     with time-slicing on a single core. It remains consistent with two threads
     that are each idle part of the time, which is why the claim is stated as
     concurrent execution at a measured rate and not as instruction-level
     simultaneity.
  2. *The invariants hold for any implementation and prove nothing.*
     Distinguished by the five deterministic and near-deterministic controls,
     each of which must break its named targeted invariants, and by the
     README's witness table, which names for every assertion the control or
     self-check mutation that breaks it and declares the two that nothing
     breaks.
  3. *The counter is exact because there was no real contention.* Distinguished
     by the `--inject-nonatomic-rmw` control: with atomicity removed the same
     workload loses updates.
  4. *Faults were simulated rather than raised from translated code.*
     Distinguished by the per-vCPU `faults_raised` counter incremented on the
     raise path inside the memory helper called from generated code, and by
     the pushed RIP matching an address the guest computed with `lea`.
  5. *The self-modifying-code result comes from never caching translations.*
     Distinguished by three enforced requirements rather than one stated one:
     `I2g` requires every vCPU to have executed more than twice as many blocks
     as it translated, so a translator that never cached fails; `I8c` requires
     the flush to be recorded on **vCPU 0**, the vCPU that performed the store,
     so a flush on the peer does not satisfy it; and `I8a` requires the
     pre-patch value to have been observed first.
  6. *Passing shows the platform supports a full emulator.* Not distinguished
     and not claimed: the guest is synthetic, the topology is two vCPUs, the
     host is one machine, and the scale is trivial.
- Evidence distinguishing them: the controls and the counters named above,
  once the evidence run exists. Until then these are the predeclared
  discriminators, not findings.

## Limitations

- Scope, applicability, and uncertainty limits:
  1. Observed on `Mac16,10` (M4) / macOS 26.6.2 (25G83) / SDK 26.4 only; `P1`
     (M1 Pro / Sequoia 15) replication owed before any platform-wide use, per
     the executor guide's incremental replication rule.
  2. Two vCPUs only. Nothing here covers the 4- and 8-vCPU acceptance
     topologies of `INV-00-02`; 1 vCPU is diagnostic under `INV-00-06`.
  3. The guest is a synthetic assembly program. This record establishes nothing
     about the `Q-00-02` compatibility boundary, direct boot, the `Q-01-13`
     machine contract, the `Q-02-03` CPU contract, or any device.
  4. **Cross-modifying code** (one vCPU writing code another vCPU is executing)
     and **cross-vCPU TLB shootdown** are out of scope and unexercised. The
     code cache is per vCPU and a store-side check flushes only the writing
     vCPU's translations. No claim here may be leaned on for either; they are
     routed to `Q-01-05` (tracking mechanism and granularity), `Q-01-08`
     (cross-vCPU invalidation and events), and `Q-01-18` (cross-thread code
     publication and instruction-cache coherence).
  5. This record instantiates the mechanism set of family `F2` (dynamic binary
     translation with a software MMU). It is one instance, not the family. It
     is **not** evidence about `F3` — whose paging, TLB, and exception
     mechanisms are the hardware ones under a Hypervisor.framework VM — in
     either direction: an `F2` pass does not support `F3` and an `F2` failure
     would not kill it. Whether the shared mechanisms transfer to `F1` or `F4`
     is a `Q-01-02` judgment, not a statement of this record.
  6. `KA-06` is addressed only as the narrow statement in `CLM-01-12-10`; the
     litmus suite that would support the assumption is `Q-01-08`/`Q-02-02`.
     `KA-04` is addressed only on its explicit-check branch — faults are raised
     by checks in the helper called from generated code and resumed by a chosen
     PC — while the signal/`ucontext` and Mach-exception branches remain
     `INV-01-06`'s. `KA-01`, `KA-03`, `KA-05`, and `KA-07` are consumed as
     dependencies and are not tested here.
  7. Guest memory accesses must be naturally aligned and must not cross a
     guest page; anything else raises `#GP` and fails the run. x86 permits
     arbitrary unaligned accesses and a Linux guest performs them, so the
     `CLM-01-12-10` emission-rule statement is bounded to naturally aligned
     accesses. Routed to `Q-01-06`.
  8. The `LOCK` prefix is honoured only on the two forms emitted as a single
     atomic instruction and is rejected elsewhere, so no non-atomic locked
     sequence can be emitted unnoticed — but no locked ALU form is exercised.
  9. `#PF` is delivered on a fixed per-vCPU IST1 stack rather than one read
     from a TSS, and no TSS or GDT exists. Routed to `Q-01-13`.
  10. The scope of the self-modifying-code flush is unobservable here: the
     whole guest program is one 4 KiB guest page, so page-scoped tracking and a
     whole-cache flush are indistinguishable. `KA-07` granularity is routed to
     `Q-01-05`.
  11. `I4a` has no deterministic control, so this record does not establish
     that the acquire/release emission rule is **necessary** — only that it
     was used and that the invariant held. `I7b` has no control either.
  12. ThreadSanitizer covers the C helpers, the device model, and the shared
     page-table walk; it does not instrument the generated arm64, so races
     between translated code and helpers on one vCPU's own state are outside
     its reach.
  13. No timing value here is a performance result, and the prototype being
     slow would prove nothing.
  14. The prototype is discarded after Track 01 and never becomes the emulator.
