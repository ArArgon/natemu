## Question and decision relevance

- Question ID and text: `Q-01-14` — What quantitative per-instance resource
  budgets preserve containment without excluding accepted workloads?
- Decision(s) affected: the containment method `Q-02-04` builds its
  fault-injection oracle on; the family-admissibility premise `KA-13` tests;
  whether the accepted 2/4/8-vCPU, 2/8-GiB-RAM workload matrix (`Q-00-02`,
  `INV-00-01`) can be served within a budget that also holds under a fault
  case.
- Why this must be resolved now: `KA-13` — "Per-instance containment budgets
  can be enforced with public mechanisms without excluding accepted
  workloads" — gates project stop input 3, and `BP-00-end` records an
  explicit, currently unassigned cross-record tension between `INV-00-08`'s
  1-second post-breach termination requirement and `INV-00-01`'s requirement
  that every mandatory workload run to accepted completion, owned by this
  question.

## Assumptions

- Declared assumptions: macOS has no cgroups-style hierarchical
  resource-control facility; the candidate public mechanisms are
  `setrlimit(2)` (`SRC-035`), `dispatch_source`
  `DISPATCH_SOURCE_TYPE_MEMORYPRESSURE`, and `task_info(TASK_VM_INFO)`
  self-accounting; budgets must be sized against the accepted workload
  matrix (2/4/8 vCPUs, 2/8 GiB guest RAM, per `INV-00-02`'s Resolution) on
  this session's only available host (16 GiB RAM, 10 cores: 4 P + 6 E).
- Assumptions to challenge: that a host-wide memory-pressure notification
  can substitute for a per-instance memory budget (it cannot — see
  Confounders); that `RLIMIT_NPROC` does not exist on Darwin (it does, per
  the SDK header inspected below, contradicting this investigation's own
  breadth pass's more cautious phrasing — corrected here); that
  `RLIMIT_AS` and `RLIMIT_RSS` are independent limits on Darwin (the SDK
  header declares `RLIMIT_RSS` as a literal alias for `RLIMIT_AS`, not a
  distinct limit); that CPU-seconds budgets are vCPU-count-independent (a
  process-wide `RLIMIT_CPU` sums all threads, so an 8-vCPU guest accrues
  CPU-seconds roughly 8x faster than wall-clock for the same workload
  duration as a 1-vCPU guest, per this investigation's own breadth pass).

## Hypothesis and falsifier

- Hypothesis: a workload-class-scoped budget table (below) exists that (a)
  every mandatory workload in `INV-00-01`'s accepted matrix can complete
  within, at its declared vCPU/RAM class, and (b) a pathological/fault-
  injected case exceeds within `INV-00-08`'s 1-second post-breach
  termination window, using only mechanisms confirmed admissible by this
  investigation's evidence run — without requiring any mechanism this
  investigation's probe finds non-enforced on this host.
- Falsifier(s): `KA-13` fails (routes to project stop input 3) if no
  combination of the candidate public mechanisms can both (a) bound a
  resource class low enough to terminate a pathological case within
  `INV-00-08`'s timeout and (b) stay above every mandatory workload's actual
  peak use of that resource class. A per-mechanism falsifier: if
  `RLIMIT_AS`/`RLIMIT_DATA` prove wholly unenforceable, the memory-budget
  mechanism narrows to self-accounting via `task_info` polling plus
  voluntary termination, which is weaker (relies on the instance's own
  cooperation, or an external supervisor's periodic check, rather than
  kernel-enforced hard refusal) and must be recorded as such rather than
  silently treated as equivalent. **This branch is now Observed, not
  hypothetical**: `CLM-01-14-10` resolved to `setrlimit(RLIMIT_AS/DATA)`
  failing outright (`EINVAL`) with the limit provably unchanged
  (`soft_after_set == soft_before`) — see Results.
- Predicted outcomes: see the claims above (`CLM-01-14-07`–`11`). The
  evidence run (`MAN-01-14-01`) relabelled all five as Observed MEET; none
  was refuted, and `-10` resolved the per-mechanism falsifier's negative
  branch rather than avoiding it.

## Method

- Procedure and versions: build `experiments/INV-01-14/src/probe.c` (Apple
  clang, `MacOSX26.4.sdk` headers); ad-hoc sign (no entitlement is needed for
  any check here); run the resulting binary twice — normal and `--negative`
  — each emitting newline-delimited JSON, one self-contained object per
  check (a header line, then one line per check), flushed as each check
  completes: `RLIMIT_DATA`'s 256 MiB `memset` and `RLIMIT_CPU`'s busy loop
  are the hazards most likely to kill this process, and incremental,
  flushed output means a process death partway through leaves a file of N
  valid lines rather than one truncated object (`REV-048` required change
  8). Every `getrlimit` call site checks its return value before using the
  returned structure (`REV-048` required change 11); every rlimit checked —
  `RLIMIT_NOFILE`, `RLIMIT_CPU`, `RLIMIT_AS`, `RLIMIT_DATA` — reports its
  prior soft/hard limit and the read-back effective limit after the
  `setrlimit` call, not only `RLIMIT_NOFILE` as before (`REV-047`/`REV-048`
  required changes 12/12), so an `EINVAL` from `setrlimit` is interpretable
  rather than a bare boolean. The `RLIMIT_CPU` arm restores the rlimit
  before restoring the default `SIGXCPU` disposition, closing a window in
  which the kernel could otherwise re-raise `SIGXCPU` against the default
  (terminating) action while still over the still-installed 1 s limit. An
  unrecognized flag exits 2, and every line carries
  `"experiment":"INV-01-14"` so this experiment's output cannot be
  interchanged with `INV-01-09`'s (`REV-048` required change 13). Validate
  each output with `src/check.py`, an independent Python 3 standard-library
  checker that reads line by line (a line that fails to parse is dropped,
  not raised, so a truncated file is reported by missing-check name rather
  than crashing). In parallel, derive a limit-proposal table (below, under
  Results) from `INV-00-08`'s oracle contract (1 s post-breach termination,
  100 ms sampling cadence, 30 s case timeouts for most properties) and
  `INV-00-01`'s accepted workload/vCPU/RAM matrix, explicitly addressing the
  `BP-00-end` termination-vs-correctness-failure tension with a proposed
  rule. The derivation procedure for the limit-proposal table is stated once
  in Results, immediately before the table: for each resource class, the
  candidate mechanism's enforcement status (Observed once the evidence run
  exists; Hypothesis until then) bounds which design is admissible, and the
  numeric ceiling for a row is either read from an already-accepted upstream
  record (`INV-00-01`/`INV-00-02`'s vCPU/RAM classes for the CPU and Memory
  rows) or explicitly marked a placeholder pending a named future record
  (`Q-01-03`/`Q-01-04` for the Memory and VM-map rows) — no row's number is
  asserted as a result of this investigation's own analysis alone
  (`REV-047` required change 4).
- Inputs and configuration: `RLIMIT_NOFILE` lowered to 8; `RLIMIT_CPU`
  lowered to 1 s under a `SIGXCPU`-catching busy loop with a 10 s wall-clock
  safety cutoff; `RLIMIT_AS`/`RLIMIT_DATA` lowered to 64 MiB, then a 256 MiB
  `mmap` (anonymous, private) and a 256 MiB `malloc` (touched via `memset` to
  force real commit) are attempted; a memory-pressure dispatch source is
  created and resumed (not fired under load — host-wide pressure is not
  controllably induced; only `create_ok` is reported, since
  `dispatch_resume()` returns `void` and a `resume_ok` field would be
  tautological, `REV-048` required change 7); `task_info(TASK_VM_INFO)` is
  snapshotted before and after first-touching every page of a 1 GiB
  anonymous mapping.
- Evidence labels assigned to planned claims: every runtime-outcome claim
  (`CLM-01-14-07`–`11`) is Hypothesis until the evidence run and its
  manifest exist; every header/documentation claim (`CLM-01-14-01`–`06`) is
  Source-backed now, pending the source gate; `CLM-01-14-12` is an Inferred
  candidate measurement interpretation pending adversarial review.

## Controls

- Positive controls: `rlimit_nofile`'s `EMFILE`-at-8 outcome and
  `rlimit_cpu`'s `SIGXCPU`-within-10s outcome are expected to hold
  unprivileged on any conforming host per documented BSD/POSIX behavior; a
  run where these fail would indicate a probe or environment defect, not a
  genuine platform finding, and must be investigated before the result is
  trusted.
- Negative controls: the `--negative` probe invocation fabricates
  `rlimit_cpu.sigxcpu_delivered = false` regardless of whether `SIGXCPU` was
  actually caught, which `check.py`'s fixed invariant (`sigxcpu_delivered`
  must be `true`, per `setrlimit(2)`'s documented behavior) must catch.
- Baselines: none; this is a capability-and-enforcement measurement, not a
  performance comparison. `INV-00-08`'s oracle-contract cadences (100 ms
  sampling, 1 s/30 s timeouts) are the *design* baseline the proposed
  budgets must be compatible with, not a measured baseline here.

## Confounders

- Known confounders: (1) `DISPATCH_SOURCE_TYPE_MEMORYPRESSURE` monitors
  *system-wide* pressure (`CLM-01-14-06`); a firing handler cannot attribute
  pressure to a specific instance, so it is unsuitable as the sole
  per-instance memory-budget signal and must not be reported in this
  investigation's proposal as equivalent to `task_info`'s per-process
  `phys_footprint`. (2) Periodic `task_info`/CPU sampling at the cadence
  `INV-00-08`'s oracle contract specifies (at most every 100 ms) itself
  consumes host CPU; a tightly-budgeted instance's own measurement apparatus
  could, at the margin, contribute to a CPU-budget breach it did not
  otherwise cause — the limit-proposal table below reserves explicit
  headroom for this. (3) `RLIMIT_CPU` is process-wide (sums all threads'
  CPU time per `CLM-01-14-14`, an Inferred premise this investigation's
  single-threaded probe does not itself test — `REV-047` required change 9),
  so an 8-vCPU guest running busy on every vCPU thread would accrue
  CPU-seconds roughly 8x faster than a 1-vCPU guest for the same wall-clock
  duration; a bare CPU-seconds constant would systematically under-budget
  high-vCPU-count guests, which is why the proposal below expresses CPU
  budget as a percent-of-host-cores ceiling checked by periodic sampling
  (`task_info`/similar), with `RLIMIT_CPU` retained only as a coarse,
  generously-sized runaway backstop. The CPU row's design therefore rests on
  documentation and inference alone until a multi-thread arm tests it.
- Mitigations and residual risk: the probe records `set_ok`/`set_errno`
  separately from the allocation outcome for `RLIMIT_AS`/`RLIMIT_DATA`
  specifically so a "limit could not even be set" finding is not
  conflated with a "limit was set but not enforced at allocation time"
  finding — these have different implications for `KA-13` (the former
  suggests the mechanism itself is unusable for this purpose; the latter
  suggests enforcement must move to first-touch/page-fault time or to
  self-accounting). Residual risk: P/E-core placement effects on CPU-second

  ### Proposed rule for the `BP-00-end` termination-vs-correctness-failure tension

  `BP-00-end` (Architecture table) records two unassigned questions: whether
  budgets *bind* during a measured workload run (i.e. whether enforcement
  and `INV-00-08`'s 1 s termination action are armed at all), and, if a
  breach occurs, whether it counts as containment success or correctness
  failure. This investigation proposes the following predeclared rule for
  both halves, to be adopted by `Q-02-04`'s fault-injection method (not
  itself selected here — this is a proposal, not a method adoption):

  **Budgets bind unconditionally.** Enforcement is armed identically for
  every run — fault-injection and measured alike — because a budget that is
  disarmed for measured runs would not be the mechanism `KA-13` is asking
  about (it would be a different, unenforced mechanism during exactly the
  runs whose resource use matters most). `INV-00-08`'s 1 s post-breach
  termination action therefore fires on a measured-run breach exactly as it
  would on a fault-injection breach; what differs is only how the breach is
  *classified* afterward, by which of two predeclared run types produced it:

  1. **Fault-injection/adversarial case** (`INV-00-08`'s method: a
     deliberately pathological or malicious input/workload designed to
     probe containment) — a breach here is **containment success**, and
     `INV-00-08`'s 1-second termination-and-recovery oracle applies exactly
     as written.
  2. **Measured workload run** (one of `INV-00-01`'s mandatory workloads, run
     under the budget class matching its declared vCPU/RAM profile from the
     limit-proposal table above) — a breach here is **not** classified as
     the emulator misbehaving; it is a **method/correctness failure of this
     investigation's budget sizing** for that workload class. It invalidates
     the affected performance sample (per the general correctness-gates-
     performance rule already established by `INV-00-02`/Track 00) and
     routes back to this investigation to widen the budget class for that
     workload — it must never be silently treated as either a passed
     containment test or a workload-portfolio exclusion.

  The discriminator is the predeclared run-type label, not the resource
  class or the breach's cause; a workload that turns out to need a larger
  budget than proposed here reopens this table's row for that resource
  class rather than reopening `INV-00-08`'s oracle contract.
