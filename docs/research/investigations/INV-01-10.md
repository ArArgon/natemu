## Question and decision relevance

- Question ID and text: `Q-01-10` — Does the required build, test, debug,
  and profiling toolchain exist from public sources and remain sustainable
  on the supported hosts?
- Decision(s) affected: experiment-code eligibility for every Track 01
  investigation with an `Observed` claim (evidence policy: experiment code
  must be C/Apple-clang or Python 3 standard library, built with a
  `Makefile`/`build.sh`); replication feasibility on `P1`; lifecycle-cost
  inputs to `Q-06-03`; and `KA-09` (family-kill item 1 under `INV-00-06` if
  false for a mandatory host/OS cell).
- Why this must be resolved now: every other Track 01 investigation that
  produces `Observed` evidence depends on this question's answer for its own
  code-gate eligibility; an unsustainable toolchain blocks replication on
  `P1` even if `P2` results pass every other gate.

## Assumptions

- Declared assumptions: this session's Command Line Tools (CLT) install, at
  `/Library/Developer/CommandLineTools`, with no Xcode.app present, is the
  baseline toolchain; Homebrew is a candidate secondary source for tools CLT
  does not ship, not a substitute for the experiment-code rule's Apple-clang
  requirement. Corrected at the `REV-053` return (M1): "sustainable" is
  defined two ways, and this record is scoped to only the first. (a) *This
  record's own scope*: existence, and public-versus-private **provenance**,
  on this host/OS/CLT-build cell at capture time — what `tools.sh` actually
  measures. (b) *Cross-release, public-distribution availability across both
  accepted macOS releases* — the fuller property the question's name
  suggests — is **not** measured by this record's method; it is routed to
  the `P1` evidence run (a second host/OS cell, still a measurement, not a
  documentary guarantee) plus the documented-availability source check
  already in the inventory (Apple's CLT distribution channel implied by
  `SRC-060`, and Homebrew's own supported-macOS-version statement,
  `SRC-061`). Locally installed SDK directories or a single-host tool
  resolution are evidence for (a), not (b).
- Assumptions to challenge: that CLT alone is sufficient for every later
  Track 01/02 need (profiling in particular is untested); that Homebrew
  formula availability is stable rather than needing its own version pin;
  that the default SDK CLT selects (`MacOSX26.4.sdk`) will still be default
  on a later CLT update.

## Hypothesis and falsifier

- Hypothesis: the build/test/debug/profiling toolchain this track's own
  experiment-code rules require (Apple clang, `lldb`, `llvm-objdump`,
  `python3`, `git`, `codesign`, plus Homebrew-sourced `cmake`/`ninja`/QEMU
  for later tracks) exists from public Apple and Homebrew distribution and
  is sustainable — reinstallable and functionally equivalent — across both
  accepted macOS releases.
- Falsifier(s) (`KA-09`, **build/test/debug limb only** — see the partial-disposition
  note below, `REV-053` M7): a tool this track's rules require is unavailable
  from any public source on a mandatory host/OS cell (for example, if a
  future macOS release removes a currently shipped CLT tool with no public
  replacement). The falsifier text previously also named "Homebrew drops
  Apple Silicon support for a required formula" as a failure mode; this
  record's method has no observable for it — `tools.sh` queries only
  Homebrew's own presence and version, never per-formula availability for
  `cmake`/`ninja`/`qemu-system-x86_64` — so that clause is removed here
  rather than left as an untestable falsifier (`REV-053` M6). It is
  predeclared **out of scope** for this record: Homebrew-sourced QEMU
  version pinning is `Q-05-05`'s, and a future round may add a formula-availability
  check to `tools.sh` (for example `brew info --json=v2 <formula>`) if a
  later track's method needs that observable.
- Predicted outcomes: the CLT-only toolchain satisfies the experiment-code
  build/debug requirement (`clang`, `python3`, `git`, `codesign`) without
  Xcode.app, though `rustc` (this session's dependency, not a CLT one) and
  `codesign` resolve from user-local/OS locations rather than CLT
  (`CLM-01-10-04`) — a provenance distinction, not a presence failure.
  Instruments/`xctrace` profiling remains a documented gap requiring either
  Xcode.app or a CLI substitute, to be resolved (not by this record) when a
  later track first needs GUI-level profiling.

**Partial disposition (`REV-053` M7):** any `KA-09` finding this record
supports covers the build/test/debug limb only. The predicted outcome above
concedes the profiling limb is an open gap routed to a
`Q-01-01`/`Q-06-03` scope decision, not resolved here — so `KA-09` must be
recorded as *partially* disposed, build/test/debug survives on this cell
pending the evidence run, profiling stays open, never as `KA-09` surviving

## Method

- Procedure and versions: (1) primary-source audit of the sources above;
  (2) `experiments/INV-01-10/src/tools.sh` (POSIX `sh`, no dependency),
  which records as one JSON object: for `clang`, `lldb`, `llvm-objdump`,
  `python3`, `rustc`, `git`, and `codesign`, the resolved path (via
  `xcrun --find <tool>`, falling back to `command -v` for tools `xcrun`
  does not register, e.g. `rustc`/`brew`), a **`provenance` classification**
  (`CLT` / `OS` / `Homebrew` / `user-local` / `other`, by path prefix — added
  at the `REV-053` return, M2, since "present on this host" and "publicly
  distributed for the supported hosts" are different claims) and, where the
  tool supports it, a one-line `--version` string (`codesign` has no
  `--version` option, confirmed by direct invocation; its entry now reports
  `version: null` plus a separate `version_unavailable_reason` string
  instead of a placeholder version text a reader could mistake for real,
  and `check.py` exempts it from the non-empty-version rule explicitly —
  `REV-054` C6); the active developer directory (`xcode-select -p`);
  `xctrace` presence *and* whether it is actually functional without
  Xcode.app, tested by invoking the **resolved** binary
  (`"$XCTRACE_PATH" version`, not a fresh bare-`xctrace` lookup — `REV-054`
  C2/`REV-053` M4, since `xcrun --find xctrace` and `command -v xctrace`
  demonstrably diverge on this host) with both the exit status and the
  captured failure message ("tool 'xctrace' requires Xcode...") recorded in
  the JSON, not merely asserted in prose; presence/absence of `cmake`,
  `ninja`, and `qemu-system-x86_64` (Homebrew-formula-level availability for
  these is out of scope for this record, `REV-053` M6 — see Hypothesis and
  falsifier); Homebrew presence, path, provenance, and version; the CLT
  `SDKs/` directory listing; the CLT package build identifier
  (`pkgutil --pkg-info=com.apple.pkg.CLTools_Executables`); and the exact
  `$PATH` the probe ran under, so a later reviewer can rule out a
  PATH-dependent false absence. `--negative` deliberately reports `clang`
  as present with an empty version, violating the
  present-implies-nonempty-version invariant; `src/check.py` enforces that
  plus, as of the `REV-054` return (C1), **requires**
  `clang`/`python3`/`git`/`codesign` to be reported present on any
  non-`--negative` run — internal consistency alone let a run with a
  required tool absent PASS before this return. A malformed (non-JSON)
  probe output is now reported as a distinct exit status (`3`), never
  conflated with a rule violation (`REV-054` C3). `run.sh` invokes
  `tools.sh` through the interpreter (`sh src/tools.sh`), never `chmod`s
  anything, and resolves `NATEMU_RAW_ROOT`/the repository root with
  `pwd -P`/`git rev-parse --show-toplevel` so a symlink into the repository
  cannot pass the out-of-repository guard (`REV-054` C4/C5, the same fix as
  `INV-01-01`'s `REV-039` C7/C8). `README.md` completes the package on the
  same pattern as `experiments/INV-01-01/`.
- Inputs and configuration: none; a static host inventory.
- Evidence labels assigned to planned claims: Source-backed for the
  documentation claims (`CLM-01-10-01`–`-03`); Hypothesis for the tool
  inventory (`CLM-01-10-04`, `-05`) until the evidence run and its result
  gate; a development-time run of the same code in the scratch directory
  (not the raw root) confirmed the script produces valid JSON, resolves
  every listed tool with its provenance as predicted on this host, and that
  `check.py` passes the positive run and fails the `--negative` run, a
  `clang`-absent fault injection, and a malformed-input case each with the
  predicted, distinct outcome — this smoke test is not itself cited as
  evidence, per the experiment rules.

- Baselines: none; this is an inventory, not a comparative measurement.

## Confounders

- Known confounders: CLT can auto-update and silently change its default
  SDK between sessions; a Homebrew formula's availability and default
  version drift over time independent of the macOS version; a `PATH` that
  differs between an interactive shell and the probe's execution
  environment could report a different toolchain than a developer actually
  uses.
- Mitigations and residual risk: `tools.sh` captures `xcode-select -p`, the
  CLT build identifier (`pkgutil --pkg-info`), and the exact `$PATH` it ran
  under, alongside each tool's version, so a reviewer can rule out a
  PATH-dependent false absence or a stale-default-SDK reading; residual
  risk is that Homebrew formula versions are only pinned at capture time,
  not asserted as a standing fact — a later run on a different day could
  legitimately report a different Homebrew tool version without that being
  drift in the sense `INV-01-01`'s admissibility rule cares about.
