## Question and decision relevance

- Question ID and text: `Q-01-10` — Does the required build, test, debug,
  and profiling toolchain exist from public sources and remain sustainable
  on the supported hosts?
- Decision(s) affected: experiment-code eligibility for every Track 01
  investigation with an `Observed` claim (evidence policy: experiment code
  must be C/Apple-clang or Python 3 standard library, built with a
  `Makefile`/`build.sh`); replication feasibility on `P1`; lifecycle-cost
  inputs to `Q-06-03`; and `KA-09` (family-kill item 1 under `INV-00-06` if
  false for a mandatory host/OS cell).
- Why this must be resolved now: every other Track 01 investigation that
  produces `Observed` evidence depends on this question's answer for its own
  code-gate eligibility; an unsustainable toolchain blocks replication on
  `P1` even if `P2` results pass every other gate.

## Assumptions

- Declared assumptions: this session's Command Line Tools (CLT) install, at
  `/Library/Developer/CommandLineTools`, with no Xcode.app present, is the
  baseline toolchain; Homebrew is a candidate secondary source for tools CLT
  does not ship, not a substitute for the experiment-code rule's Apple-clang
  requirement; "sustainable" means available from public Apple/Homebrew
  distribution across both accepted macOS releases (15, 26), not merely
  present on this session's build.
- Assumptions to challenge: that CLT alone is sufficient for every later
  Track 01/02 need (profiling in particular is untested); that Homebrew
  formula availability is stable rather than needing its own version pin;
  that the default SDK CLT selects (`MacOSX26.4.sdk`) will still be default
  on a later CLT update.

## Hypothesis and falsifier

- Hypothesis: the build/test/debug/profiling toolchain this track's own
  experiment-code rules require (Apple clang, `lldb`, `llvm-objdump`,
  `python3`, `git`, `codesign`, plus Homebrew-sourced `cmake`/`ninja`/QEMU
  for later tracks) exists from public Apple and Homebrew distribution and
  is sustainable — reinstallable and functionally equivalent — across both
  accepted macOS releases.
- Falsifier(s) (`KA-09`): a tool this track's rules require is unavailable
  from any public source on a mandatory host/OS cell (for example, if a
  future macOS release removes a currently shipped CLT tool with no public
  replacement, or if Homebrew drops Apple Silicon support for a required
  formula); or profiling capability (Instruments/`xctrace`) is unavailable
  without an Xcode.app dependency this track's rules exclude by not naming
  it as a permitted experiment-code toolchain, which would then require a
  scope decision under `Q-01-01`/`Q-06-03`, not a silent substitution.
- Predicted outcomes: the CLT-only toolchain satisfies the experiment-code
  build/debug requirement (`clang`, `lldb`, `python3`, `git`, `codesign`)
  without Xcode.app; Instruments/`xctrace` profiling remains a documented
  gap requiring either Xcode.app or a CLI substitute, to be resolved (not by
  this record) when a later track first needs GUI-level profiling.

## Confounders

- Known confounders: CLT can auto-update and silently change its default
  SDK between sessions; a Homebrew formula's availability and default
  version drift over time independent of the macOS version; a `PATH` that
  differs between an interactive shell and the probe's execution
  environment could report a different toolchain than a developer actually
  uses.
- Mitigations and residual risk: the future probe must capture
  `xcode-select -p`, the CLT build/version identifier, and the exact `PATH`
  used, not just tool versions in isolation; Homebrew formula versions must
  be pinned at capture time, not asserted as a standing fact.
