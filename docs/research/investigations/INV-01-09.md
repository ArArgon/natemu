## Question and decision relevance

- Question ID and text: `Q-01-09` — Can the minimal headless device set
  (timer/APIC, serial, block, network, entropy, shutdown) be backed by public
  macOS APIs without restricted entitlements or privileged helpers?
- Decision(s) affected: device feasibility, the machine-contract option set
  `Q-01-13` may select from, and the containment method `Q-02-04` builds on.
- Why this must be resolved now: `KA-08` — "Each mandated device class has an
  unprivileged public host backing" — gates project stop input 3 for any
  failing class, and `Q-01-13` cannot select among machine-contract options
  that depend on a device backing this question has not yet cleared.

## Assumptions

- Declared assumptions: the minimal device set fixed by
  [Scope and success](../tracks/00-scope-and-success.md) — timer/APIC,
  serial, block, network, entropy, shutdown — is the target set; timer/APIC's
  host-clock mechanism is `Q-01-07`'s scope, not repeated here; shutdown
  (process exit) needs no capability probe; no production machine design is
  selected here (`Q-01-13`'s and Track 03's job).
- Assumptions to challenge: that `vmnet.framework` is the only network
  backing worth checking; that an entitlement's "restricted" documentation
  status predicts a specific `vmnet_return_t` failure code rather than, for
  example, an outright process termination under an unauthorized restricted
  entitlement; that POSIX file-I/O primitives (`F_NOCACHE`, `F_FULLFSYNC`,
  `F_PUNCHHOLE`) carry no hidden privilege requirement; that `getentropy`'s
  documented per-call limit is enforced rather than silently ignored.

## Hypothesis and falsifier

- Hypothesis: every device class in the minimal set except timer/APIC
  (`Q-01-07`'s scope) has at least one unprivileged public host backing on
  this host/OS: network via ordinary BSD sockets (`vmnet.framework` may or
  may not be usable without Apple-granted provisioning, but the envelope
  only needs "BSD sockets or an available `vmnet` mode" per `KA-08`), block
  via POSIX file I/O, serial via `pty`, entropy via `getentropy`, shutdown
  via process exit (no probe needed).
- Falsifier(s): any device class for which every candidate unprivileged
  public backing fails in the evidence run falsifies `KA-08` for that class
  and routes to project stop input 3 for that class specifically. For
  network specifically, the falsifier requires *both* `vmnet.framework`
  (unentitled and entitled-ad-hoc) *and* ordinary `SOCK_STREAM`/`SOCK_DGRAM`
  sockets to fail unprivileged — `vmnet` alone failing does not falsify the
  network class, since `KA-08` accepts "BSD sockets or an available `vmnet`
  mode".
- Predicted outcomes: see the Hypothesis-labeled claims above
  (`CLM-01-09-14`–`19`). No Observed claim exists yet.

## Method

- Procedure and versions: build `experiments/INV-01-09/src/probe.c` (Apple
  clang, `MacOSX26.4.sdk` headers, `-framework vmnet`); ad-hoc sign once with
  no entitlement and once with `com.apple.vm.networking`
  (`src/vmnet.entitlements.plist`); run the unentitled binary normally and
  with `--negative` before applying the restricted entitlement, then run the
  entitled-ad-hoc binary once. A normal process exit emits one JSON object;
  process termination in the entitled arm is retained through its exit-status
  and stderr artifacts. Validate each emitted JSON object with
  `src/check.py`, an independent Python 3 standard-library checker that
  re-derives pass/fail from the raw reported fields rather than trusting the
  probe's own framing.
- Inputs and configuration: `vmnet_start_interface` is called with
  `vmnet_operation_mode_key = VMNET_HOST_MODE` (the minimal viable
  `interface_desc`, per `SRC-119`'s documented key); sockets use
  `AF_INET`/`SOCK_STREAM`, `SOCK_DGRAM`, and `SOCK_RAW`/`IPPROTO_ICMP`; the
  block-I/O and sparse-file checks write transient temp files under the
  run's `$NATEMU_RAW_ROOT/INV-01-09/<run-id>/scratch/` directory, never
  under `experiments/`.
- Evidence labels assigned to planned claims: every runtime-outcome claim
  (`CLM-01-09-14`–`19`) is Hypothesis until the evidence run and its
  manifest exist; every documentation/header claim (`CLM-01-09-01`–`13`) is
  Source-backed now, pending the source gate.

## Controls

- Positive controls: `socket_stream`/`socket_dgram`/`pty`/`getentropy_256`/
  block-I/O checks are expected to succeed unprivileged on any conforming
  host; a run where these fail would indicate a probe or environment defect
  rather than a genuine device-backing finding, and must be investigated
  before the result is trusted.
- Negative controls: `socket_raw` (expected `EPERM` unprivileged) is a
  built-in negative control on socket privilege; the `--negative` probe
  invocation is the code-gate's fault-injection control, fabricating
  `getentropy_over_limit.ok = true` regardless of the real 257-byte-request
  outcome, which `check.py`'s fixed invariant (`getentropy_over_limit.ok`
  must be `false`, per `getentropy(2)`'s documented 256-byte limit) must
  catch.
- Baselines: none; this is a capability-presence measurement, not a
  performance comparison.

## Confounders

- Known confounders: (1) the documented `vmnet_start_interface` contract
  ("non-`NULL` on success, `NULL` otherwise", `SRC-111`) and completion-
  handler contract (`SRC-119`) do not state precedence if the synchronous
  return and callback status disagree. The probe records both; the checker
  must classify disagreement as ambiguous and fail closed rather than choose
  an authoritative field. (2) An ad-hoc-signed binary carrying a
  *restricted* entitlement it was not granted by Apple may be refused
  execution or killed by code-signing/entitlement enforcement (AMFI) before
  or during the vmnet call, rather than receiving an ordinary
  `vmnet_return_t` failure code through the completion handler; the probe
  and `run.sh` do not currently distinguish "process was killed" from "clean
  process exit after JSON was written" beyond the shell's own exit-code and
  empty-output observation, so the manifest step must record the raw process
  exit status alongside the JSON (or its absence) for the entitled-ad-hoc
  run. (3) A probe run under an interactive user account with prior Local
  Network permission grants or other ambient privilege could report a more
  permissive result than a fresh account would; the environment capture
  records `sw_vers`/`sysctl`/`codesign -d --entitlements -` but not TCC
  grant state, which is a residual limitation, not a fixed confound.
- Mitigations and residual risk: `run.sh` records both signing variants'
  `codesign -d --entitlements -` output so the actual applied entitlement is
  auditable per run; the JSON schema records `start_returned_nonnull`,
  `callback_fired`, and `status_code` separately so a return-value/handler
  disagreement is visible rather than collapsed into one boolean. The TCC/
  ambient-privilege residual risk is recorded as an open limitation below,
  not mitigated by this method.

## Sample plan

- Units, repetitions, randomization/order, warm-up, and power/precision
  target: one run of each of the three signing/mode variants
  (unentitled, entitled-ad-hoc, entitled-ad-hoc `--negative`) is sufficient
  for this investigation — these are boolean capability-presence checks
  against a documented API contract, not a latency or throughput
  distribution, so no repetition count or power analysis applies. No warm-up
  is needed (no caches or JIT state to stabilize). Order is fixed
  (unentitled normal, unentitled negative, entitlement signing, entitled-
  ad-hoc normal) so entitlement enforcement cannot pre-empt the checker fault
  injection.

## Exclusion and stop criteria

- Predeclared exclusions: none of the three planned probe invocations may be
  excluded post hoc; a crash, hang (beyond the probe's internal 5 s
  `dispatch_semaphore` timeout on the vmnet completion handler), or
  non-zero-but-uninterpretable exit is a result to record and explain, not
  to discard.
- Stop/failure conditions: if the checker (`check.py`) fails on the *normal*
  (non-`--negative`) output for a reason other than the vmnet-related fields
  this investigation predicts as open, the method is defective and must
  return to the method gate before any Observed claim is written, per the
  executor guide's failed-review disposition.

### Implications for `KA-08`/`KA-12`/`KA-13` and families F1–F4 (no design selected)

Even before the evidence run, the Source-backed documentation claims above
bound what the eventual Observed result can mean. `KA-08` is this
investigation's direct falsifier target: the documented existence of a
second, independent network backing (ordinary `SOCK_STREAM`/`SOCK_DGRAM`
sockets, `CLM-01-09-09`/`SRC-118`) means a `vmnet.framework` failure —
whichever exact status code or termination mode the evidence run observes —
cannot by itself fail `KA-08`'s network clause, which accepts "BSD sockets
*or* an available `vmnet` mode"; only a joint failure of both would. For
block, serial, and entropy, no second candidate is named in `KA-08`'s own
row, so a documented-but-unconfirmed failure of `F_NOCACHE`/`F_FULLFSYNC`,
`posix_openpt`, or `getentropy` would be a direct falsifier for that class
alone. This investigation supplies `Q-01-13` with the device-backing
admissibility premise its machine-contract option table depends on
(`INV-01-13`, Results); a device class this investigation finds
inadmissible removes every machine-contract option that names it, without
this investigation itself choosing among the surviving options.

None of families F1–F4 (interpretation, dynamic binary translation,
translation-under-Hypervisor.framework, or AOT/dynamic-fallback) depends on
device backing for its *core* translation/paging/exception mechanism; device
admissibility is a project-level (`KA-08`) and machine-contract-level
(`KA-12`) gate common to all four families equally, not a discriminator
between them. A device-class failure this investigation might surface would
therefore narrow the deployable machine contract for every surviving family
alike, rather than selecting among F1–F4.
