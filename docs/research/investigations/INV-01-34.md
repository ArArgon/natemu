# INV-01-34 — Secondary CPU startup without real mode

## Current summary

- **Question:** `Q-01-34`: can the thin EL1 shim design start secondary
  CPUs of target stock x86-64 distribution kernels without executing real-mode
  code, and what minimum upstream kernel follows for `Q-00-02`?
- **Conclusion and applicability:** claims 01–10 have an accepted scoped source
  conclusion in the [independent findings review](../reviews/INV-01-34-findings.md):
  Linux **5.19** is the first upstream release of the ACPI mailbox wakeup path.
  This permits a 64-bit handoff without a real-mode entry; it does **not** imply
  that the AP executes only 64-bit instructions. The inspected v5.19 and v6.8
  trampolines deliberately pass through 32-bit compatibility/protected mode.
  Claim 11 and Q34 now have an independently accepted **scoped yes** on
  Apple M4 Mac16,10, macOS 26.6.2 (25G83), SDK 26.4 at two/four vCPUs,
  following complete primary checks and independent rebuilt replication.
  No stock kernel has been booted. The accepted supplement audits
  actual header-package configurations and vendor source for Ubuntu 24.04 GA
  `6.8.0-139.139` and Debian 13 `6.12.107-1`; these are working targets selected

  scope. Debian's newer trampoline can stay 64-bit when LA57 matches; Ubuntu's
  audited GA trampoline still requires the 32-bit transition.
- **Material blockers:** none for the accepted finite Q34 resolution. All

  retained. The source-indexed fixture and declared successful `verify_cpu`
  callee contract do not prove whole-stock boot, general CPU features or
  wider-host applicability.
- **Next action:** no further execution is required for Track 01 closure. The

## Supporting contracts and claims

Claims 01–10 have accepted scoped source findings, including the independently

**CLM-01-34-01 — Source-backed: first upstream mailbox implementation is
Linux 5.19.** Commit
[`f39642d0dbacded8b4a816a9197a73efb74e5702`](https://github.com/torvalds/linux/commit/f39642d0dbacded8b4a816a9197a73efb74e5702.patch)
adds ACPI MADT wakeup parsing and the 64-bit APIC callback. Its message explicitly
uses the mailbox whenever present instead of INIT/SIPI. The implementation is
absent from [v5.18 `arch/x86/kernel/acpi/boot.c`](https://raw.githubusercontent.com/torvalds/linux/v5.18/arch/x86/kernel/acpi/boot.c)
and present in [v5.19 `boot.c`](https://raw.githubusercontent.com/torvalds/linux/v5.19/arch/x86/kernel/acpi/boot.c),
`acpi_parse_mp_wake` and `acpi_wakeup_cpu`. The boundary is for the upstream
feature, not a supported-distribution promise; vendor backports are outside
the charter's audit.

**CLM-01-34-02 — Source-backed: mailbox version 0 specifies a 64-bit AP
handoff.** [ACPI 6.5 §5.2.12.19, Tables 5.43–5.44](https://uefi.org/specs/ACPI/6.5/05_ACPI_Software_Programming_Model.html#multiprocessor-wakeup-structure)
defines a MADT type `0x10`, length 16 entry pointing to 4 KiB aligned,
4 KiB ACPINvs memory. Little-endian mailbox fields are command (`u16`, offset
0), reserved (`u16`, 2), APIC ID (`u32`, 4), and wake vector (`u64`, 8).
The OS fills ID/vector before command 1. The matching AP caches required
fields, clears command to 0, then uses the vector; other APs ignore the ID.
The next command waits for acknowledgment. Each AP consumes this wakeup once.
For Intel execution state, long mode and paging are enabled, IF is clear,
segments are flat, and the wake vector's single physical page is identity
mapped. ACPI's address is a guest physical address in this emulator design.

**CLM-01-34-03 — Source-backed: the initial Linux path is generic ACPI/SMP,
not TDX-gated.** In v5.19, [the ACPI Makefile](https://raw.githubusercontent.com/torvalds/linux/v5.19/arch/x86/kernel/acpi/Makefile)
builds `boot.o` under `CONFIG_ACPI`; the callback/parser in
[`boot.c`](https://raw.githubusercontent.com/torvalds/linux/v5.19/arch/x86/kernel/acpi/boot.c)
require `CONFIG_X86_64`, `CONFIG_X86_LOCAL_APIC`, and `CONFIG_SMP`.
`acpi_process_madt` must successfully reach the MADT parsing path.
[`acpi_wake_cpu_handler_update`](https://raw.githubusercontent.com/torvalds/linux/v5.19/arch/x86/kernel/apic/apic.c)
installs the callback in APIC drivers. `acpi_wakeup_cpu` maps the mailbox WB,
writes APIC ID/vector, release-stores the command, and spins until cleared;
its acknowledgment wait is unbounded. Thus a missing responder is a hang case
requiring an external experiment timeout, not a kernel error expected by the
oracle. Linux serializes AP wake requests; SMP does not mean concurrent writers
to the one mailbox. In [v6.12 `arch/x86/Kconfig`](https://raw.githubusercontent.com/torvalds/linux/v6.12/arch/x86/Kconfig),
`CONFIG_ACPI_MADT_WAKEUP` is default-yes with the same four dependencies.
The original claim does not verify a vendor binary's effective configuration;
supplemental claim 08 supplies separately audited package configurations.

**CLM-01-34-04 — Source-backed: a 64-bit entry still executes 32-bit startup
instructions.** [Linux v5.19 `do_boot_cpu`](https://raw.githubusercontent.com/torvalds/linux/v5.19/arch/x86/kernel/smpboot.c)
selects `real_mode_header->trampoline_start64` when the 64-bit callback exists,
and prefers that callback over INIT/SIPI. In
[`trampoline_64.S` v5.19](https://raw.githubusercontent.com/torvalds/linux/v5.19/arch/x86/realmode/rm/trampoline_64.S),
`trampoline_start64` loads IDT/GDT and far-jumps to `pa_trampoline_compat`.
That `.code32` path disables paging, jumps to `startup_32`, reloads the
kernel's control state/page tables, enables paging, and far-jumps back to
64-bit `startup_64`. [`CR0_STATE` in the v5.19 flag definitions](https://raw.githubusercontent.com/torvalds/linux/v5.19/arch/x86/include/uapi/asm/processor-flags.h)
includes `X86_CR0_PE`; masking only `X86_CR0_PG` therefore retains protected
mode. This accommodates four/five-level paging transitions and
segment reloads. The same transition appears in the independently inspected
[v6.8 trampoline](https://raw.githubusercontent.com/torvalds/linux/v6.8/arch/x86/realmode/rm/trampoline_64.S).
These paths bypass the `.code16` `trampoline_start`; their location in a
directory named `realmode` does not imply real-mode execution.

**CLM-01-34-05 — Inferred: the no-real-mode assumption can survive while
32-bit startup handling remains mandatory for these paths.** From claims 02–04,
providing the mailbox and the specified initial state lets an unmodified kernel
select this route. A model that acknowledges a vector and then directly calls
`start_secondary`, skipping the actual trampoline, would not establish stock
kernel feasibility. The emulator must implement the required mode/control
transitions and instructions, using translation or narrow emulation without
patching the kernel. This is not evidence for general 32-bit application support.

**CLM-01-34-06 — Source-backed: boot-once support does not establish CPU
recycling.** ACPI version 0 has one wake per AP (claim 02). In
[Linux v6.12 `madt_wakeup.c`](https://raw.githubusercontent.com/torvalds/linux/v6.12/arch/x86/kernel/acpi/madt_wakeup.c),
`acpi_parse_mp_wake` requires version 1 and a reset-vector setup for CPU
offlining; otherwise `acpi_mp_disable_offlining` disables it and invalidates
the table's mailbox address to prevent kexec reuse. `acpi_wakeup_cpu` returns
`-EOPNOTSUPP` for a missing cached mailbox. Neither cold SMP boot nor a repeated
synthetic mailbox loop proves offline/online, suspend/resume, or kexec behavior.

**CLM-01-34-07 — Source-backed/Inferred: direct BSP boot is a separate
contract.** The [v5.19 64-bit boot protocol](https://raw.githubusercontent.com/torvalds/linux/v5.19/Documentation/x86/boot.rst)

That is a source contract for the assumed direct loader; it is not supplied by
the AP mailbox and has not been executed here. An unmodified stock kernel needs
both correct initial loading/table discovery and the AP route above.

does not generalize that result to all code executed during boot.

**CLM-01-34-10 — Inferred: a finite handwritten test can model the required
AP startup mechanism, provided it preserves the actual transitions.** The
Ubuntu path, and Debian's LA57-mismatch path, need these semantic operations
from the cited source, beyond mailbox routing:

- In 64-bit entry, descriptor-table loads and a far transfer to a 32-bit code
  segment with `PE=1`, `PG=1`, `LMA=1`, `CS.L=0`.
- In the compatibility path, atomic 32-bit `LOCK BTS` on the shared trampoline
  lock, carry-tested retry/`PAUSE`, 32-bit stack setup, and a `CR0` write with
  `PE=1`, `PG=0`; execution then continues in 32-bit protected mode.
- `startup_32` loads segment registers, adds the physical base to ESP, reads
  trampoline fields, checks the SME flag, loads CR4/CR3, reads and conditionally
  writes EFER, sets CR0.PG, and far-jumps to a 64-bit segment. The mnemonic
  surface is `MOV`, `ADD`, `BT/BTS`, `CMP`, conditional/unconditional branches,
  `PAUSE`, `RDMSR/WRMSR`, control-register moves, and far jump; mode and operand
  widths are part of the semantics. With the modeled CPU advertising no SME,
  the optional AMD SYSCFG branch is inactive; this is a runtime CPU-profile
  condition, not removal of the stock `CONFIG_AMD_MEM_ENCRYPT=y` code.
- The successful 64-bit continuation must switch to per-CPU stacks before releasing the
  shared trampoline lock, as `secondary_startup_64` in each archive's
  `arch/x86/kernel/head_64.S` does. Release at mailbox acknowledgment would
  permit concurrent use of the shared trampoline stack and invalidate the model.

The same source inventory also requires a Debian LA57-match case that stays
64-bit, and an EFER-equal case plus an EFER-write case. The model must keep guest
CR0/CR3/CR4/EFER/CS state separate from host arm64 execution state, select the
correct paging behavior while guest PG is clear, and make each modeled
instruction's effects independently checkable. An assertion trace
can expose a skipped mode transition, wrong bit width, early lock release,
wrong AP, stale vector, or a false 64-bit-only claim. This is a feasible
method candidate, not executed evidence. Handwritten blocks can establish the
shim mechanism in the charter's no-translator experiment; they cannot establish
the correctness of a future general decoder/translator or a full stock boot.

### Concrete state, memory and operation contract

`Q34_PA=0x40700000` reserves the free interval immediately after the Q33 code
pool and before foundation shared storage at `0x40800000`. Compile-time

write is hidden in Q30's separately replayed x86 RAM.

The mailbox prefix is exactly `u16 command`, `u16 reserved`, `u32 APIC ID`,

atomic accesses preserve those widths. A short instrumentation lock orders
mailbox snapshots and trace events across reuse; it is released before startup
execution and is distinct from the trampoline lock. The trampoline uses an
actual atomic **32-bit fetch-OR/BTS-bit 0** operation, records old value/CF and
the source carry branch, and performs a 32-bit zero store on release. An
adjacent `0x89abcdef` word proves that this operation did not silently become
a 64-bit overwrite. Release requires the owning CPU's modeled RSP already

available; this does not invent a successful guest instruction or execute a
general x86 scheduler.

separate from the Q31 long-mode runtime state. The two long-mode memory
profiles use actual stored four/five-level tables with 2 MiB leaves over the

The interpreter executes and logs the relevant loads, stores, ADD/logic,

control-register changes, EFER low/high comparisons and conditional WRMSR,
