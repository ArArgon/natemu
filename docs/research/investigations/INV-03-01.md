### Translation request ownership — scoped conditional decision accepted

September 20, root: one bounded 30-minute design pass for charter questions 3,
7, 8 and 12. This is a protocol argument over the existing requirements and
accepted finite mechanism evidence, not a new experiment or a generator choice.
Stop at an independently reviewable ownership rule and its remaining premises.

**CLM-03-01-11 — Inferred protocol construction, independently accepted. Selected
choice:** the resident runtime owns admission and publication. A
host compiler receives immutable source/decode inputs and produces an unpublished
object; it never receives authority to update live architectural state or an
executable destination. Use bounded request slots and explicit cancellation.
This refines the existing state/communication hypothesis below without selecting
a wire format, shared-memory transport or generator state layout.

The basis is [INV-01-33 claims 05 and 08–10](INV-01-33.md), which distinguish
complete code/metadata publication from transfer and demonstrate the finite
register-transfer path, and [INV-03-04 claim 12](INV-03-04.md#selected-construction-limits-and-inventory),
which already requires bounded job slots and non-reuse while callbacks survive.
Those records do not prove a production transport or generator adapter.

| Transition | Owner and required action |
| --- | --- |
| Free → admitted | Resident runtime captures checked source bytes and the decode/state, source and mapping dependencies coherently under the memory coordinator. Reserve one request slot and one bounded output entitlement before dispatch. Identity includes VM lifetime, slot incarnation and request identity; source version alone is not a request identity. |
| Admitted → producing/receiving | Host works only on the immutable copy. Transfer progress belongs to this request; partial bytes and metadata remain unreachable. Reply fields are bounded and interpreted as object offsets/relocation identities, never host-selected installation pointers. |
| Receiving → ready | Complete bytes, metadata, relocation records and declared lengths are validated before installation. Validation checks the adapter's structural contract; it does not prove arbitrary native code semantically safe. The compiler and resident helpers remain in the VM's trusted computing base. |
| Ready → published | Resident runtime rechecks request liveness and all entry dependencies under the same serialization authority used by invalidation. It registers the complete object's dependency identity before making it reachable, and completes the selected cache/entry synchronization protocol. A dependency change during preparation prevents publication or invalidates the registered object before affected execution is admitted. |
| Any unpublished state → cancelled | Revoke publication eligibility immediately. Retain the slot, input/output storage and transport references until the producer and every delivery path have relinquished them. Cancellation acknowledgement is a lifetime guarantee, not merely receipt of a cancel message. |
| Published → request retired | The executable object's lifetime transfers to the code-lifetime owner. Retire request storage only after all transport/producer references have ended; publication itself does not acknowledge those references. |
| Retired/cancelled → free | Reuse only after that lifetime condition. Advance incarnation before the next admission. Namespace wrap requires a complete drain, including queued deliveries; never rely on a timeout or numerical wrap alone. |

**Admission/publication invariant:** an entry can name only a complete,
registered object whose dependency identity is still admitted. Checking versions
and then publishing without shared serialization violates the invariant: a
source write could occur between them. Holding a global lock throughout host
compilation is unnecessary and would obstruct progress. Only capture and final
admission require coordination; ordinary compilation operates on copied inputs.
The concrete coordinator may use a lock or an equivalent versioned transaction,
but it must establish this ordering, including direct-link admission and saved
continuations. Existing invalidation rules still determine when an already
executing old instruction may finish; this request rule does not tighten or
relax x86 self-modification semantics.

**Cancellation invariant:** a stale/duplicate response cannot publish or write
into reused storage. An identity check at completion is insufficient if a host
callback has already written through a stale destination pointer. Accordingly,
producer-owned output and delivery storage stay retained until acknowledgement,
or delivery resolves the identity under lifetime authority before obtaining any
destination. The latter still needs retention across the actual copy. No device
side effect is rolled back by this rule: compilation has no guest effect, while
device cancellation remains a separate operation-specific contract.

**State and progress invariant:** waiting for compilation preserves the owner's
recoverable guest state and does not make the host its writer. Resident service
and coordination notifications must remain serviceable while waiting; a host
worker cannot wait for a rendezvous acknowledgement from a vCPU it keeps stopped.
The accepted register-transfer WAIT/poll pattern is one finite mechanism, not a
requirement for per-access host calls. If a guest event changes the continuation,
the old demand is cancelled; delivery uses the event/recovery owner's legal
boundary, then dispatches again. A late translation must not resume the old RIP.
Reserve pressure stops new admissions while already admitted operations drain;
it must not consume the permanent service storage required for that drain.

**Failure and teardown:** malformed output is rejected before reachability;
producer failure leaves the continuation recoverable or triggers contained VM
termination. Teardown first revokes admissions and publication, then stops vCPUs
and drains or terminates producers/delivery paths before releasing storage. A
new VM must not inherit old delivery authority merely because a PID, slot or
address is reused. Process exit may end in-process references, but outstanding
external I/O must separately be completed/cancelled under its backend contract.

**Alternatives and costs:** allowing direct host mutation of live state adds
cross-domain ownership and recovery obligations without being needed for
compilation, so it is not selected. Retaining every historical request avoids
reuse races but is unbounded. Cancelling and immediately reusing its slot is
incorrect. Bounded immutable jobs incur snapshot/output storage and final
validation; they do not require spilling registers on every guest instruction.
Transport throughput and the adapter's actual object bounds remain unmeasured.

**Integration with typed source capture (claim 16 in INV-03-04), independently accepted:**
the compilation job and its source-fetch operation have different effect
ownership. Calling compilation effect-free does not make a completed UC/device
instruction fetch cancellable without effects. The resident fetch record retains
completed fragments and their route/effect identity across host waits, cancellation
and decoder retries. An old host response cannot cause those fragments to be
fetched again. Guest fault/event abandonment follows the architectural fetch
contract rather than the compiler-job storage rule.

If host decoding needs more bytes, it returns a bounded continuation request
for the same current instruction, not permission to read guest memory. Resident
admission checks that the fetch operation and continuation are still live and
that the additional bytes belong to the demanded instruction, under the selected
mode/length and typed-fetch rules. Only then can it perform the fetch and extend
the immutable input supplied to host decoding. No output becomes publishable
until the complete captured instruction and its dependencies are bound to it.
Ordinary cacheable-RAM block formation retains its separately permitted lookahead;
this refinement does not impose single-instruction blocks on that fast path.

**Closure scope:** this can settle translation-job ownership independently of
generator choice. It does not settle all of question 3 or 7: coherent capture,
complete dependency enumeration, emitted entry guards, precise recovery,
publication ordering and concrete callback/reference bounds must satisfy their
separately owned contracts. Counterexamples include an untracked source alias,
an uncounted callback, a reply resuming an obsolete continuation, or a wait path
that blocks required coordination. Independent review has accepted the scoped
conditional choice in the existing
findings thread. Concrete adapter, coordinator and transport conformance remain
with their owners; no runtime execution is authorized by this acceptance.

**Hypothesis — private-address protection:** execute translated guest code at
EL0 with the shim at EL1, or use guarded generated accesses at EL1. Neither is
accepted. EL0 permissions alone do not protect private CPU state or code
metadata if that state must also be accessible to generated EL0 instructions.
Likewise, placing private mappings in an x86 noncanonical address range does
not itself establish that translated guest operands cannot access them.
The selected design must distinguish guest-derived accesses from trusted
runtime accesses, check full operand ranges and overflow, prevent raw guest
control targets from becoming native code targets, and honor the correct x86
fault precedence. Address checks may be omitted only with an explicit proof
that the access form and chosen native mapping enforce the same restriction.
This is an outstanding proof obligation, not a measured escape or a claim
that one privilege level is intrinsically sufficient.

**Hypothesis — authoritative state and communication:** each vCPU owns its
architectural state while running. A translation request contains source bytes,
decode state and dependency generations captured coherently; it grants no
host permission to mutate live guest architectural state. The shim accepts a
reply only for the still-live request, VM lifetime and dependencies, installs
code through the selected publication protocol, then resumes. Failure or
cancellation leaves a recoverable continuation or terminates the VM. Service
and coordination notifications must remain consumable while the owner waits
for translation. Full register transfer is the existing evidence-backed
transport fallback, not an asserted economical bulk-code transport.

## Concrete execution candidate — guarded EL1, provisional

**Hypothesis:** assess translated code and native runtime helpers at EL1 first,
with x86 CPL represented explicitly in emulated state and shadow permissions.
This preserves the established Track 01 native execution level and avoids
assuming that an EL0 helper-state mapping protects itself. It does not inherit
an isolation proof from Track 01. EL0 remains an alternative if its protection
benefit exceeds the transition/state-sharing cost under the same guest contract.

The candidate uses four-level x86 virtual addressing. Arm stage 1 uses 48-bit
lower/upper regions and 4-KiB translation granules, with top-byte ignoring off.
[Arm Memory Management, version 1.0, §§5.1 and 7](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/Learn%20the%20Architecture/LearnTheArchitecture-MemoryManagement-101811_0100_00_en.pdf)
describes region sizing by TCR and separate translation bases. The concrete
configuration and its native faults remain subject to review; this older guide
is not evidence for all newer extensions. Proposed virtual allocation:

| Native virtual range | Intended contents | Admission rule |
| --- | --- | --- |
| `0000000000000000`–`00007fffffffffff` | Lower x86 canonical mappings | Software x86 walk and current access/CPL policy |
| `0000800000000000`–`0000ffffffffffff` | Private native code, shim, stacks, CPU state and metadata; allocate only bounded needed subranges | Never a valid guest-derived operand or guest-PC destination |
| `ffff000000000000`–`ffff7fffffffffff` | Unmapped private reserve | No normal access |
| `ffff800000000000`–`ffffffffffffffff` | Upper x86 canonical mappings | Same guest walk and current access/CPL policy, not native privilege alone |

Guest physical addresses, IPAs and native VAs are separate namespaces. A guest
PTE's physical target passes through the machine's RAM/MMIO resolver; it cannot
select private VM backing just by using its numeric IPA. Only shim-owned Arm
tables become native translation roots. Guest RAM is native non-executable;
execution comes only from the runtime or admitted translated allocations.
Private data is non-executable. The initial candidate uses runtime-only RWX
code allocations with immutable admitted bytes: only the trusted publication/
retirement protocol may write them, never guest-derived accesses. Native W^X is
optional hardening, not a baseline requirement: EL1 controls its page tables, so
W^X alone would not contain a compromised EL1 runtime. Guest exclusion, correct
publication, complete continuation lifetimes and no live byte rewriting remain
mandatory. If W^X is later selected, its permission/alias maintenance needs its
own assessment; Track 01 established neither W^X nor guest-access guards. The
private pool's concrete capacity and branch veneers are construction choices
within a bounded layout, not permission to emit unrelocated host pointers.

Every native access belongs to one of these classes:

1. **Guest operand or guest stack:** preserve x86 effective-address calculation,
   address-size/segment rules and exception priority. Validate canonicality and
   the span of each architecturally indivisible access before directly accessing
   the corresponding shadow. Decompose instructions with permitted partial
   completion according to their semantic contract; do not prevalidate a whole
   REP/vector instruction in a way that suppresses required partial effects.
   Canonicality/span checks exclude the private range even when native Arm
   translation would accept it. Shadow policy independently enforces x86 CPL,
   CR0.WP and any selected permission extensions. PG-off startup uses the
   guest-physical resolver, not unchecked IPA dereferences.
2. **Trusted runtime state:** use a compiler/runtime-owned base plus validated
   fixed field offsets, or an allocation handle whose owner and bounds have been
   checked. Guest values are field contents, never native state pointers. A
   helper taking a guest memory operand must use class 1, not a raw C pointer.
3. **Guest control flow:** guest RIP/RET/indirect target goes to guest dispatch,
   validating mode/state/mapping identity and instruction fetch permissions.
   It is never branched to as a native numeric address. Trusted native links
   resolve only to admitted block entries and retain lifetime dependencies.
4. **Runtime control flow and metadata:** helper targets, literals, returns and
   recovery PCs use relocation records and runtime-owned identities. Host replies
   cannot choose arbitrary installation addresses. Unknown fault PCs or invalid
   metadata cause contained VM termination, not speculative recovery.

**Inferred conditional isolation argument, not acceptance:** if the emitter and
every helper respect this complete partition, class 1 cannot select the private
VA interval or private backing, class 3 cannot execute guest bytes or arbitrary
runtime offsets, and class 2/4 permissions derive only from runtime-owned state.
Thus guest-controlled values alone cannot acquire native EL1 authority. The
load-bearing premise is still unproved for the chosen generator; its source
audit must enumerate all memory/control operations, including implicit stack,
vector, helper and exception-delivery accesses. A missing access form or an
incorrect fault-precedence check invalidates this candidate. Compiler/runtime
correctness belongs to the trusted computing base; compromised native code still
requires the separate host/VM containment boundary in INV-03-03.

This narrows a design alternative, not the product envelope. It adds guard,
dispatch and shadow-switch costs that Track 04 must retain in the comparison;
the hardware-MMU hypothesis is not a claim of zero per-access work. No bounds
check may be removed for performance without an equivalent checked invariant.

### Proposed MSR dispatch contract

Use one profile-owned admission/validation layer before inherited or adapted
MSR handlers. An entry names index/range, availability predicate, readable and
writable fields, reset state, value checks, commit owner and post-write effects.
An absent entry raises #GP(0); it does not invoke the permissive upstream default.
The register-specific contract decides reserved and read-only bit handling;
there is no universal “mask unknown bits and succeed” rule. Preserve the
frontend's instruction/privilege/prefix checks and precise origin. Validate
before mutating CPU state or sending a side-effecting host request. Failed
validation leaves the pre-instruction architectural state, apart from the
required exception, intact. This is a proposed adaptation, not new runtime code.

The admitted-family inventory to complete is finite and tied to the selected
feature words, not every physical Haswell facility:

| Family / proposed route | Required contract and identified source mismatch |
| --- | --- |
| TSC 0x10 and TSC_AUX 0xC0000103 | RDTSC/RDTSCP and MSR access share the same clock/offset and auxiliary state; add the missing TSC-MSR handlers. TSC_ADJUST and deadline do not become available merely because TSC exists. |
| APIC_BASE 0x1B; x2APIC indices 0x800–0x8FF | Route to authoritative LAPIC state with mode, index-hole, read/write and reserved-field checks; completion/EOI owns its side effects. |
| SYSENTER CS/ESP/EIP 0x174–0x176; EFER/STAR/LSTAR/CSTAR/FMASK 0xC0000080–84; FS/GS/KERNEL_GS bases 0xC0000100–102 | Reuse state and transition handlers behind validation; enforce canonicality only for the registers whose specification requires it, and EFER/control dependencies before commit. Intel CSTAR is defined but unused by compatibility SYSCALL, not automatically an unknown register. |
| PAT 0x277 and the enumerated MTRR family | Validate memory types, physical width, ranges and writable fields; use coordinated memory-policy transition and required invalidation. Plain field assignment is insufficient. |
| MCG capability/status/control and advertised machine-check banks | Match the exposed capability/bank count, access permissions and reset values; no pass-through of Apple hardware state. |
| MISC_ENABLE, microcode identity and model/platform compatibility registers | Explicitly define retained discovery/control behavior and distinguish optional safe probes from mandatory accesses. No physical firmware update or host power control is implied. |
| Debug and optional feature-owned registers | Admit only with their complete exposed debug/feature behavior. PKRS, BNDCFGS, VMX/SVM or other upstream switch cases are not admitted solely because a helper implements storage for them. |

## Integration pass — access completion must select an explicit continuation

September 19, `/root`, source/protocol work within the 90-minute next action
above; no generated-code execution. This pass composes INV-03-02's proposed
access ABI with INV-03-04 rendezvous revision 2. The following is a **proposed
interface and conditional argument**, submitted for independent review, not
acceptance of an emitter or the whole architecture.

The bounded examples use ordinary aligned scalar RAM accesses with a single
native load/store, and one MOVS iteration whose source and destination are RAM.
They do not stand in for split accesses, MMIO, atomic lowering or every helper.
Those remain required parts of the full architecture. The pinned frontend
ordering is recorded in [INV-03-02 claims 08–10](INV-03-02.md); the requirement
for a real generated checkpoint is established by
[INV-03-04 claims 08–09](INV-03-04.md).

**Missing interface distinction:** a service result cannot simply mean “resume.”
If the coordinator has already performed a trapped store, retrying its original
native instruction duplicates the architectural write. Conversely, advancing
past an unperformed load after installing its shadow leaves the destination
undefined. The continuation must distinguish these outcomes:

| Outcome | Effect owner and permitted resume |
| --- | --- |
| `RETRY_ACCESS` | Service changed only the internal mapping. Restore the complete native frame and retry the same unperformed native access; retain earlier instruction effects and temporaries. |
| `ACCESS_COMPLETED` | Service performed the recorded access exactly once. Restore the frame with the declared result/status updates and resume at that access expansion's explicit success continuation. Do not execute the access again. |
| `GUEST_FAULT` | Preserve required committed/partial state, reconstruct the originating guest PC/CC and fault information, and abandon the native continuation through the VM-local exceptional exit. No success continuation executes. |

These outcomes belong to an immutable operation descriptor keyed by VM lifetime,
vCPU, continuation identity and access phase. The descriptor identifies x86
access intent, checked RAM routing and its lifetime, width, source/result
locations, and the emitter-owned native retry/success locations. Neither a host
reply nor a guest value supplies an arbitrary native PC. A replayed or stale
service result cannot advance the phase or perform the effect again. General
success is **not** `native_pc + 4`: writeback addressing, exclusive loops,
multi-instruction expansions and helper calls have different contracts. Even
the scalar case below requires proof of its chosen expansion and frame layout.
Native syndrome alone cannot decide x86 read/write intent, as INV-03-04 claim 07's
atomic-load writeback counterexample demonstrates.

**CLM-03-01-07 — Source-backed, independently accepted in scope:** the pinned
[QEMU AArch64 backend](https://github.com/qemu/qemu/blob/c1c18d1e640b64292859ce9f30f3c344edfb0294/tcg/aarch64/tcg-target.c.inc)
already records an access-success location. `tgen_qemu_ld` and `tgen_qemu_st`
assign `TCGLabelQemuLdst::raddr` after emitting the direct access when a slow-path
label exists. `tcg_out_qemu_st_slow_path` calls the store helper and jumps to
that location; the load path additionally uses `tcg_out_ld_helper_ret` to restore
the result before that jump. Thus a successful service can continue after an
access without replaying it in the existing generator design. This is a concrete
reuse point, not evidence that its host helper ABI or pointers can run unchanged
inside the VM. The adapted fault metadata must make the corresponding success
location and result contract available for every admitted direct-shadow access;
the upstream conditional creation of a slow-path label does not already do that.
This pass inspected the retained local pinned source; a web-cache fetch failed
and supplied no additional evidence. No runtime result is claimed.

### Three conditional traces

**TCG adapter scope:** these traces depend on the inspected IR synchronization,
live-state and continuation conventions. The shared access-result contract is
not a proof that another generator supplies those conventions. Re-establish
the traces against any selected replacement; they do not rank generators.

1. **Ordinary load A, then instruction B.** The guest-memory IR synchronizes
   required architectural globals before A's access. The guarded backend checks
   the guest address before issuing the native load. A shadow miss captures a
   frame before the destination load has completed. Admission closes and every
   other observer pauses/drains; the requester retains its native frame and
   pinned metadata rather than falsely acknowledging a canonical park. A drain
   service establishes the permitted shadow and returns `RETRY_ACCESS`. Restoring
   the frame and retrying that load preserves its result destination and earlier
   state. A completes, then an actual emitted checkpoint materializes next-PC/CC
   and leaves for permanent dispatch before B. A true x86 permission fault instead
   returns `GUEST_FAULT`, leaving A's architectural destination unchanged. Native
   EL1 privilege never substitutes for the software x86 permission decision.
2. **Tracked scalar store A modifies B's source page.** The trapped access has
   not written RAM. Its descriptor captures the already computed address and
   value from the retained native frame; decoding A again from mutable guest
   bytes is forbidden. Under exclusion, the service checks the captured access
   route/permission, invalidates future eligibility of source-dependent blocks,
   performs the write and advances source generations. It returns
   `ACCESS_COMPLETED`, so A's original store is not retried. A's native code and
   metadata remain pinned while its success continuation finishes the instruction
   and reaches the forced checkpoint. Dispatch sees B's new source identity;
   reclamation waits until the old frame and all other references are gone.
   Pending guest interrupts cannot interrupt this completion between its write
   and architectural boundary. An instruction with another required effect
   follows its recorded phase instead of pretending this scalar trace covers it.
3. **REP MOVS has loaded a RAM element; its destination store traps.** The
   destination in this trace does not overlap the REP instruction's own source
   bytes. The source value is already a live temporary. Save it in the native continuation;
   service the destination as in trace 2, without rereading the source or
   restarting the whole REP instruction. The unchanged semantic order must then
   update the applicable RSI/RDI and count for exactly that completed iteration.
   An architectural event exit at a legal iteration boundary uses the REP guest
   PC if work remains, or the following guest PC if complete, with matching
   CC/RF/interrupt-shadow state. An internal coordination stop instead retains
   the native loop under revision 3 below; it does not execute event-exit RF
   changes. Previously completed iterations survive a subsequent true
   guest fault. INV-03-04's ongoing frontend audit owns the exact checkpoint
   placement; this trace does not yet prove its RF/shadow handling or implementation.

In all three traces the coordinator grants only the retained operation's finite
drain segment while other observers remain excluded. Another fault yields its
updated phase to the same coordinator, not a recursive coordinator acquisition.
A guest fault may park as pending exception state; exception delivery is a
separate checked operation. Mapping/backing dependencies survive until covered
accesses finish; a completed guest shootdown cannot precede that drain. Backend
RAM commits follow the same admission authority, so “all paused” includes them.

**Decision consequence:** retain the two-state pause/park protocol and add the
explicit access outcome to the proposed generator/service ABI. Pinning alone
does not settle effect ownership or retry behavior. The pass stops at concrete
remaining premises: generated success locations/result restoration, the actual
normal/REP checkpoint, and the VM-local exceptional exit. INV-03-02 owns helper
and exceptional exits; INV-03-04 owns checkpoint state and coordinated access
phases. These three traces are reviewable conditional compositions, not a claim
of complete recovery, isolation or all-instruction coverage. The
[independent review, Return 7](../reviews/INV-03-01-findings.md), accepts source
claim 07 and these conditional interface traces, retaining their implementation
and coverage premises. INV-03-04's subsequent checkpoint pass exposes the
same-instruction REP source-mutation case: an internal pause with the same RIP
does not authorize fetching different instruction bytes. That case is addressed
by the subsequent revision below, not by trace 3 alone. Guarding, frame
capture, checkpoint spills and exclusive-service costs remain in the cost case.

#### Commit, invalidation and recovery composition

Use the current all-observer coordinator only when the transition changes shared
mapping/policy resources; state-only changes stay with the single vCPU owner.
Before a control commit, reserve needed descriptors and retain the originating
instruction/recovery state. Stage any required PAE loads and all validation
without publishing a partially updated control tuple. Faults retain the old
register tuple and report the original instruction, while independently allowed
operand/walk effects remain governed by their own ledger. A control operation is
not a rollback transaction for previously committed guest memory.

For a successful transition, serialize the affected semantic state, derived
execution key and mapping generation with publication/invalidation. Complete
native shadow/TLB synchronization required by the selected memory mechanism
before allowing any continuation to use that generation. Returning from an
upstream `tlb_flush` does not establish this for captive native mappings. Select
full eviction of the affected vCPU's cached guest translations on accepted
paging-control writes as the simple initial policy: Intel§5.10.4.1 expressly
permits additional invalidation. Hidden PAE PDPTE registers are not disposable
TLB entries and must not be silently reloaded by that eviction.

End or guard incompatible translated execution, including direct links; retained
code may be reused under an exactly matching entry key. Do not revoke another
vCPU's control registers because a shared shadow object is invalidated. A normal
native pause/reentry still uses its own current controls. State-only XCR0 or TS
updates require no invented global memory flush, although they reselect affected
instruction/FP assumptions. Whole-register spilling at every memory access and
host-side emulation of every control instruction are unnecessary.

A success continuation carries the committed new control state and next guest
instruction phase. An old precommit fault map cannot undo it. If a host failure
prevents required postcommit native synchronization, contain the VM before
reentry; do not deliver a fabricated guest fault after reporting the control
write as complete. Unrelated pending events retain current ownership.

### Concrete object and identity choices

Use finite **bounded translation objects**, including multi-basic-block CFGs.
Each adapter declares a finite maximum E of external data-link cells and the
metadata needed to enumerate every external transfer phase. Internal CFG edges
stay within their object's lifetime; they do not create additional allocation
pins. REP may loop inside its object with explicit iteration continuations.
Guest CALL/RET retain architectural stack effects. Between native objects select
tail transfer through the guarded external-entry interface; permanent resident
helpers do not recursively enter generated execution. This avoids an unbounded
native return-address ancestry independently of any particular slot formula.

A bounded guest-return prediction cache is permitted: its entries contain guest
return identity plus object incarnation and an **external guarded entry** target,
not an unchecked interior native continuation. A hit uses the same entry guard
and transfer-phase census as a data link; a miss performs ordinary resident
lookup. Before reclamation, detach cache entries under closed admission and
include any target already loaded by a CPU in the in-flight census. Cache entries
therefore do not indefinitely pin historical objects or their reachable graph.
This retains a return-prediction optimization without importing FEX's unchecked
native call/return stack. An adapter may omit the cache, but that is a cost choice,
not a correctness requirement. Larger bounded CFGs likewise remain eligible;
no basic-block or two-exit restriction is selected to preserve old arithmetic.

An object identity contains VM lifetime, unique allocation incarnation, admitted
guest entry PC, immutable CPU-profile/adapter identity, decode context, executable
source-fragment identities and their physical source generations, and the
architecturally valid mapping/route dependencies that produced those fragments.
A hash can accelerate lookup but cannot replace comparison of these identities.
The decode/context key includes the relevant architectural mode/segment and
control assumptions. **Conservative specialization rule:** bake only the declared
profile/decode inputs; read other architectural operands at execution. Any
additional CPU value specialized by an adapter becomes an explicit key dependency
with a mutation hook before such code may be published. Control/segment/mode
changes invalidate the corresponding context identity before subsequent entry;
ordinary changes to runtime operands do not invalidate code merely because they
change registers. This distinguishes source identity from all mutable guest state.

Lookup keys also bind the vCPU context when an assumption is vCPU-specific;
cross-vCPU object reuse is permitted only for equal complete declared contexts.
Source tracking uses physical bytes/routes, so writes through a different GVA,
CR3, shim access, backend or A/D update cannot escape merely by changing the
virtual address. All-writer admission from question6 supplies the mutation
boundary. A new writer or writable alias must join that authority before use;
code registration cannot race an unregistered write.

WB source capture under claim11 copies a coherent finite byte/decode input.
A UC/device source fetch instead retains claim04-16's completed effects and
operation identity. Such input is not promoted to freely reusable byte-cache
eligibility: absent a separate stable-fetch contract, bind the generated result
to that admitted fetch/operation only, with a fresh fetch admission required for
new execution. Host decoder continuation requests extend only the same admitted
instruction, without replaying completed fetches. Cancellation of compiler work
does not erase architectural fetch effects.

### Publication and invalidation have one ordering point

Reserve the claim11 request/output slot before compilation. Host receives
immutable inputs and returns bounded bytes/metadata/relocation offsets into its
own retained delivery storage. The resident copies a complete, structurally
validated object into a private unentered slot through the selected register-
transfer installation path; no guest-derived address can target those bytes.
Generated native instructions and recovery metadata are immutable after admission.
Only runtime-owned data-link cells change during execution; no warmed instruction
backpatching is selected.

Under the **same coordinator mutex** used to close writer/entry admission,
revalidate request incarnation, source and context dependencies, and register the
new object's dependency membership while it remains unreachable. Installation
and native cache/entry maintenance occur with relevant executors quiescent under
that closed epoch. Publish the entry/data target only after complete code and
metadata visibility and required executor context synchronization. The resident
publisher's own code writes avoid assuming that a host pointer write alone
publishes executable instructions across domains. This uses the selected
publication mechanism and its platform premises, not a new permission-flip or
cross-domain self-modification protocol.

A writer under that authority first closes conflicting entry admission, obtains
memory-quiescent participant records, revokes matching future entries/links, then
commits its actual physical write effects and advances affected source/mapping
identities. Complete required invalidation bookkeeping before reopening observers.
If publication won the mutex first, the writer sees its registered object and
revokes it; if mutation won first, the publisher's revalidation fails. There is
no check-then-unregistered-publication interval. Changes during the potentially
long host compilation merely make its output stale; no mutex spans compilation.
A duplicate/late result fails the request identity check and cannot reuse old
storage until producer/delivery references drain. Namespace wrap requires drain,
not a guessed sufficiently large generation counter.

Mapping invalidation is distinct from writing PTE bytes. Required guest invalidation
acknowledgement and route/tag reuse wait until covered old accesses cannot
execute; code invalidation does not revoke an already admitted operation's
physical route halfway through its effect. Optional conservative invalidation
must respect the memory owner's selected architectural translation/cache rules.
A/D writes are ordinary tracked writers for this purpose; their own-dependency
fold cannot erase an earlier mismatch, as claim04-13 already requires.

### Entry, active execution and handover

Every external entry—including a warmed data link—targets claim02-37's resident
veneer. Its guard checks live object/context/source admission and acquires or
transfers the execution pin without a host compiler/dispatcher round trip.
This does not make the first veneer instruction safe by itself. Before that
instruction, **incoming cached/link targets and in-flight transfers are lifetime
references**. Reuse waits for their retirement under the existing all-participant
reclamation protocol. Invalidation changes eligibility immediately but leaves
retained entry bytes available to reject a stale target safely.

Use the existing fixed handover record and exact transfer-phase metadata to
account for old object, destination and operation origin (at most K=3). A stop
between loading a data-link target and acquiring its entry pin must identify the
pending target from the captured native context/transfer phase; it cannot fall
into an uncounted interval. Under closed admission, clear relevant incoming
cells/cache entries and census in-flight transfers before freeing their targets.
A link is an independently detachable eligibility edge, not a reason to pin its
entire reachable graph. Unknown/unmapped native phases are a conformance failure;
they do not authorize freeing an object or guessing a target reference.

Inside an admitted object, use a stop checkpoint at **every guest-instruction
commit boundary and every legal REP-iteration boundary** for this construction.
Do not infer it from native-PC maps or TCG `insn_start`. The checkpoint is an
actual conditional transfer with correct current-state recipes and native
continuation identity, as the reviewed TCG/FEX source constructions demonstrate
in their respective scopes. A mutation that paused instruction A can let A's
already admitted effects finish under its retained operation, but cannot let
stale following instruction B execute from that block. Permanent drain service
repairs/services A, then forces its next boundary to dispatch under current
identity. RETRY_ACCESS, ACCESS_COMPLETED and GUEST_FAULT retain their distinct
meaning; completed MMIO/device effects are never replayed for canonicalization.

A healthy long REP keeps its admitted decoded operation and pinned object across
internal iteration pauses; it does not require a fresh lookup or a historical
object per iteration. A true guest fault/event abandons native execution through
the semantic owner, and later architectural restart performs normal current
source admission. Preserve any native PC-relative anchor independently from the
guest-facing boundary PC. Intel's
[self/cross-modification and restart rules](https://cdrdv2-public.intel.com/922487/253668-092-sdm-vol-3a.pdf)

invisible runtime pause; no universal claim about a physical Haswell's
unsynchronized next-instruction prefetch is made. Required synchronization cannot
be bypassed by resuming a completed old operation as if it remained in flight.

### Reclamation and progress argument

ordinary body. E may differ between adapters without changing the argument.

At pressure, close admission, cancel stale unpublished work, and park/pause

Drain service uses permanent reserved storage, does not wait on compilation or

only one exclusive operation segment at a time. Compiler replies/event arrivals
remain serviceable during translation waits. Backpressure stops *new* cache work;
a retained REP resumes in its existing object. An architectural event releases
or retains that operation according to its semantic phase and can use the
reserved successor slot. Thus cache reclamation does not require a healthy REP's
remaining count to reach zero, a second coordinator acquisition or completion
of an unrelated backend I/O. Genuine unrecoverable resource/runtime failure uses
the declared contained-VM teardown, never stale storage reuse.
