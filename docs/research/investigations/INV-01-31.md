## Current summary

## Assumptions and breadth

The charter's host translator, EL1 shim, native stage-1 paging, TSO, own vectors,
GIC and timer remain enabled. Handwritten arm64 sequences stand for translator
output; no floating-point implementation or Linux kernel boot is introduced.
This is a viability investigation, not validation of an eventual translator's
entire x86 instruction set.

Screening for review: (a) QEMU TCG also reconstructs guest state after faults,
while an ordinary same-ISA VM obtains guest instruction semantics directly;
the design-specific issue is composing hardware shadows with host translation
and software guest state. (b) Intel and Arm document their own exception
contracts but do not supply this cross-ISA composition. (c) Conclusions apply
to this shim plus a translator meeting the recorded recovery contract; failure
of a naive translated sequence is not a kill of every translator or emulator.

Required adjacent cases are exceptions during exception delivery, guest code
page writes and aliases, cross-page accesses, repeated operations, and a
concurrent table change during classification. A valid guest mapping can be
absent or deliberately restricted in an Arm shadow; an Arm permission fault
alone cannot determine an x86 protection violation. Conversely, software checks
may need to raise an x86 fault without any Arm memory exception.

Downstream ownership remains `Q-02-01` (full exception/CPU semantics and
instruction coverage), `Q-02-02` (SMP and ordering stress), `Q-02-03`
(machine/feature/address-space contract), `Q-02-04` (host containment),
`Q-03-02` (generator compatibility), `Q-03-04` (paging and code-page mechanism
choice), and `Q-05-02` (other-host coverage). No new identifier is needed.
Retained unknowns include instruction-specific vector partial progress, MMIO
side effects, nested delivery corner cases, and unimplemented feature
combinations. These are not established by scalar RAM tests.

## Supporting contracts and claims

Claims 01–07 are **accepted scoped source findings and explicit inferences**;
this does not accept a runtime mechanism or authorize execution.
The Intel audit uses revision **092**, linked by the
[official manual index](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html)
on 2026-09-06. Its chapter numbering differs from older editions.

**CLM-01-31-01 — Source-backed: a guest fault has an architectural recovery
point.** Intel SDM Vol. 3A, §§7.5–7.6 and Event 14 in §7.15,
[revision 092](https://cdrdv2-public.intel.com/922487/253668-092-sdm-vol-3a.pdf),
specify fault-class restart at the faulting instruction and #PF reporting through
CR2 and an error code. §§7.14.2–7.14.3 specify the 64-bit IDT stack frame and
IRET behavior. The normal scalar fault rule must not be generalized to every
instruction: the manual names exceptions to full rollback.

**CLM-01-31-02 — Source-backed: #PF classification uses guest access context.**
Intel SDM Vol. 3A §5.7, Figure 5-12, identifies P(0), W/R(1), U/S(2),
RSVD(3), I/D(4), PK(5), SS(6), HLAT(7), SGX(15). W/R and U/S describe
the attempted access. Reserved-bit violations require P=1; instruction-fetch
reporting depends on SMEP or PAE plus NXE. CR2 is a guest linear address,
with additional rules for exposed masking/enclave features. §§5.6–5.8 supply
permission and A/D requirements; Event 14 warns that another #PF overwrites
CR2, including during delivery. These are not Arm syndrome bit positions.
[Direct specification](https://cdrdv2-public.intel.com/922487/253668-092-sdm-vol-3a.pdf).

**CLM-01-31-03 — Source-backed: repeated instructions expose defined progress.**
Intel SDM Vol. 2B, `REP`, pp. 4-563–4-564,
[revision 092](https://cdrdv2-public.intel.com/922481/253667-092-sdm-vol-2b.pdf),
keeps the instruction pointer on the repeated instruction while count and
source/destination registers identify the next element after the last successful
iteration. It also warns that REP INS can consume an I/O read before a failed
memory write. Thus repeating all prior work or assuming all side effects can be
undone is not a general restart strategy. The candidate uses RAM REP MOVSB;
device-string behavior remains an instruction-specific case.

**CLM-01-31-04 — Source-backed: Arm supplies Arm exception context.** Arm's
[AArch64 Exception Model 1.3](https://documentation-service.arm.com/static/63a065c41d698c4dc521cb1c),
§§4.1, 5.1.1, 5.2–5.3, describes synchronous aborts, ELR/SPSR state, software
register preservation and ERET. For memory faults ELR identifies the triggering
Arm instruction; this cannot identify the enclosing x86 operation without a map.
Arm's [architecture known issues, 102105 M.a issue 03, C23292](https://documentation-service.arm.com/static/69aac74fe79f9a1d642aa91f)
also constrains when an instruction syndrome is available. Do not depend on
ESR_EL1 containing a complete decoded operand/width/destination description.
Only the deliberately selected synchronous translation/permission fault classes
are candidate recoverable events here; unexpected aborts stop with diagnostics.

**CLM-01-31-05 — Inferred: recovery metadata needs a state recipe, not just
an address pair.** From claims 01–04, one x86 instruction expanded to several
Arm instructions may have changed temporary or architectural state before the
Arm fault. The proposed minimum information, wherever represented, is:

| Information | Why the shim needs it |
| --- | --- |
| Immutable block identity/generation; Arm PC interval and substep mapped to guest RIP, instruction length and execution mode | Distinguish this instruction from its predecessor; prevent reclaimed or rewritten metadata being used. |
| Guest privilege, address-size/segment-base rules and access kind, width and ordered operands | Reconstruct guest linear addresses, fetch versus data and fault precedence; the first operand byte is not necessarily the faulting page's address. |
| Location or reconstruction recipe for live guest GPRs, flags and relevant control state | Preserve earlier committed instructions while restoring this instruction's uncommitted effects. Lazy flags count as state. |
| Commit point and restart/continuation label for each potentially faulting substep | Retry shadow repair internally or deliver at the guest recovery point. |
| Explicit progress for repeated or partially completing operations | Preserve completed iterations/lanes and avoid duplicated effects. |
| Guest address-space identity and translation/code generation dependencies | Validate classification against Q30 coherence and prevent stale code/page ownership. |

A table, calling convention and helper may provide different parts; no
representation is prescribed. Metadata cannot undo a store already visible to
another vCPU or a consumed device read. For ordinary RAM operations, staged
register/flag updates and an exceptional slow path that validates every affected
page while preventing invalidation before commit are candidate remedies. The
lock or generation protocol must cover relevant Q30 state through commit;
checking both pages and then allowing a remap is insufficient. These are
unproved candidate mechanisms, not architecture decisions.

**CLM-01-31-06 — Inferred: internal faults and guest faults need distinct
outcomes.** With a recognized block/substep and coherent guest access state,
classify: permitted access with missing shadow → repair and retry without guest
#PF/CR2 change; permitted write caught for table/code tracking → complete the
tracking protocol and the one guest operation; denied guest access → reconstruct
and deliver its exception. A changed generation requires Q30 revalidation;
a fresh unsynchronized walk is not an oracle for what x86 requires that vCPU
to observe. Unknown PC, invalid metadata or unexpected syndrome is an internal
failure, not a fabricated guest #PF. Separate counters identify Arm entries,
repairs, guest exceptions, attempts and committed effects.

“Exactly once” is per attempted operation requiring delivery. Repair permits
successful retry without duplicate delivery; returning without repair
legitimately causes a new faulting attempt. Do not suppress the second exception
merely because RIP and CR2 match.

**CLM-01-31-07 — Source-backed/Inferred: code-page tracking must preserve
guest execution and synchronization semantics.** Intel SDM Vol. 3A §11.1.3
[self/cross-modifying code rules](https://cdrdv2-public.intel.com/922487/253668-092-sdm-vol-3a.pdf)
provide defined synchronization sequences. The candidate same-page case writes
guest instruction bytes, completes a specified branch/serialization sequence,
then executes the changed target. It must not reenter the same write forever,
execute stale translated successors, or resume the preceding x86 instruction.
A remote modifier uses the documented publication and executing-CPU
serialization pattern. Unordered racing changes do not supply an exact-new-bytes
oracle. Metadata for an executing old block remains available until its
fault/recovery interval ends.

## Method and controls

Source preparation by `/root/retained_runner`, 2026-09-06, bounded to 30 minutes
and 12 primary documents; five substantive documents were used (Intel index,
Vol. 3A, Vol. 2B, Arm exception guide and Arm corrections). Contrary cases sought:
fault versus trap, repeated progress versus full rollback, CR2 overwrite,
syndrome validity, permission versus access classification, and synchronized
versus unordered code modification. No archived material was accessed.

This is accepted method preparation, not a reviewed runnable experiment. Add it
to working Q30 with actual x86-format tables and the same SMP invalidation,
TSO, timer and GIC mechanisms. Handwritten blocks carry metadata; a separately
implemented fixed-case oracle predicts guest frames, registers, flags, memory
and effect counts. Record the feature mask: initial fixtures use ordinary
64-bit four-level paging, NXE/WP set, CPL0/CPL3, and no advertised
PK/CET/SGX/HLAT/LAM/FRED. This does not set the eventual product mask.

| Case | Procedure and decisive oracle/falsifier |
| --- | --- |
| 1. Shadow miss | Guest-present readable page with absent Arm mirror. Load succeeds after repair; no guest exception or CR2 modification. |
| 2. Real absent page | Supervisor read and user write to absent leaves produce vector 14, exact RIP/CR2, codes 0/6. Handler repairs through Q30; retry commits exactly one final effect. |
| 3. Protection/reserved | User write to read-only user page → code 7; user read of supervisor page → 5; supervisor read-only write with WP → 3. Present leaf with a reserved address bit → supervisor-read code 9. Constants use the fixed feature mask. |
| 4. Fetch/address kind | NX supervisor fetch → code 17. Guest instruction bytes crossing into an absent page report the guest fetch address/RIP without partial execution. Noncanonical ordinary data address → #GP(0), CR2 unchanged. |
| 5. Multi-step restart | RMW stages flags/registers before a store fault. Earlier guest effects remain; current uncommitted effects do not. After repair one RMW commits. Mapping to the preceding guest RIP must be detected by its effect counter. |
| 6. Cross-page scalar store | Eight-byte RAM MOV at page-end minus four, second page absent/read-only. Check both halves and registers at handler entry; no first-half store commits for this ordinary MOV fixture. Repair/retry writes the full value once. Another vCPU attempts revocation/remap during validation/commit, challenging the pin/lock. |
| 7. REP progress | REP MOVSB faults on the destination after a known nonzero prefix. Prefix remains; RSI/RDI/RCX identify next byte; RIP is the string instruction. Repair resumes suffix without duplicated prefix. Include zero count and reverse direction. |
| 8. Simultaneous faults | Distinct vCPU addresses, RIPs, error codes and sentinels. Synchronize attempts, then allow concurrent handlers. Reject CR2/frame/metadata contamination or a global pending-fault slot. |
| 9. Repeated/nested delivery | Return once without repair: expect two distinct attempts, then repair. Distinguish fault in a running handler from fault while building its delivery frame. A #PF during #PF delivery follows Intel double-fault rules, not duplicate original #PF delivery. |
| 10. Code-page write/execute | Guest-writable page holds current modeled block and later target. Trap the write solely for tracking, apply bytes once, invalidate and side-exit at a legal guest boundary. After guest synchronization, select the handwritten replacement from changed bytes. |
| 11. Alias/remote writer | Modify same backing page through another VA while another vCPU executes an old version; executing CPU synchronizes before new dispatch. Keep old metadata live through overlapping fault. No stale reentry after the synchronization point. |
| 12. Invalid recovery context | Synthetic wrong/stale metadata, frame, code/CR2 and duplicate-effect checker inputs must fail. Unknown Arm fault sites stop with crash context rather than claim a handled x86 exception. |

Before implementation review, expand case 9 with exact IDT/TSS/stack state and
the Intel Event 8 classification table; a recursion guard cannot stand in for
guest #DF semantics. CPL0/CPL3 fixtures must construct/check the architectural
guest frame and modeled IRET recovery: writing a result structure alone does
not demonstrate delivery. Cases 5–6 need faults at each defined memory substep
and immediate pre/post-commit checks. A memory-unchanged oracle must exempt
permitted page-walk A/D updates and completed REP iterations explicitly.

Cases 10–11 exercise guest code-page correctness, not Q33 host-produced code
publication. Handwritten alternatives must be selected by validated guest bytes
and generations, not a phase number that could ignore the write. Q32 later
adds asynchronous interruption without disabling these cases.

Proposed finite execution budget, subject to code review: three fresh two-vCPU
runs and one four-vCPU run, 16 iterations per fixed scenario/variant in each,
at most six runs including diagnostics, with existing 30-second child wall
limit and 10-second VM watchdog. Stop on first unexplained failure, timeout,

failure without exclusions; changed code receives review before execution.
Independently reviewed preparation then rebuilds the snapshot and repeats one

Prepared by `/root/retained_runner` in a bounded source-only follow-up on

independent source/method acceptance in the [findings thread](../reviews/INV-01-31-findings.md).
The original case-9h recovery-frame return and its correction remain recorded;
no runtime result is established.** This is a finite initial fixture set rather

**CLM-01-31-08 — Source-backed, accepted: exact 64-bit frame and stack source.**
Use IDT delivery with FRED/CET disabled. Gates are 16 bytes, with a canonical
handler offset, a present nonconforming 64-bit code selector (`L=1,D=0`), type
14 (interrupt) or 15 (trap), and a three-bit IST index. For IST=0, a CPL3→0
delivery selects TSS.RSP0; CPL0→0 keeps the old RSP. IST=1 selects TSS.IST1 even
without a privilege change. Align the selected RSP down to 16 bytes before the
pushes. A #PF or #GP frame contains six eight-byte fields; at handler RSP the
offsets are `+0 error, +8 RIP, +16 CS, +24 RFLAGS, +32 old RSP, +40 old SS`.
The resulting RSP is `align_down(selected_RSP,16)-48`, hence aligned for these
error-code fixtures. CS/SS and the error code are zero-extended to their slots.
Preserve the exact old, possibly unaligned RSP. A privilege change or IST switch
sets the new SS to NULL with the new CPL as its RPL; ordinary CPL0/IST0 delivery
does not replace SS. These rules follow Vol. 3A §§7.14.1–7.14.5, Figure 7-9,
and Vol. 2A's `INT n/INTO/INT3/INT1` operation, whose stated scope includes
hardware exceptions. [Vol. 3A revision 092](https://cdrdv2-public.intel.com/922487/253668-092-sdm-vol-3a.pdf),
[Vol. 2A revision 092, pp. 3-469, 3-472–3-479](https://cdrdv2-public.intel.com/922480/253666-092-sdm-vol-2a.pdf).

**CLM-01-31-09 — Source-backed, accepted: saved and live flags differ.**
A fault-class #PF/#GP saves RF=1, even when incoming RF=0. Vol. 3A §8.3.2.1
explicitly describes this as the rule shared with IDT delivery; this citation
does not enable FRED in the fixture. §7.12.1.3 says delivery clears live TF, RF,
NT and VM after saving flags; an interrupt gate also clears live IF, while a
trap gate preserves IF. With incoming `RFLAGS=0x302` (IF and TF set, RF clear),
the #PF saved value is `0x10302`, the interrupt-handler live value is `0x2`, and
the trap-handler live value is `0x202`. An incoming-RF=1 control uses `0x10302`
and yields the same saved/live values. All other exposed fixture flags are
fixed, with IOPL=0. [Vol. 3A §§7.12.1.3 and 8.3.2.1](https://cdrdv2-public.intel.com/922487/253668-092-sdm-vol-3a.pdf).

The handler removes the error slot before modeled IRETQ. IRETQ restores the five
remaining eight-byte fields, including SS:RSP for a same-CPL return. Returning
from CPL0 permits the fixture's IF restoration; RF and TF are restored from the
saved flags. Inspect the logical state immediately after IRETQ, before executing
a TF-enabled resumed instruction; successful restart/effect-count variants use
TF=0, so this flag probe does not silently require an unimplemented #DB handler.
The text and rendered PDF of Vol. 3A §7.14.3 actually show `CPL ? 3`; do not infer
an equality from that character. Vol. 2A's explicit IRET 64-bit exceptions resolve
the relevant rule: NULL SS on return to CPL3 faults with #GP(0); a non-CPL3 NULL
SS is permitted only with RPL matching CPL. The nested CPL0 fixture uses NULL
SS=0; return to CPL3 uses a valid writable user SS.
[IRETQ, Vol. 2A pp. 3-493–3-498](https://cdrdv2-public.intel.com/922480/253666-092-sdm-vol-2a.pdf).

**CLM-01-31-10 — Source-backed, accepted: delivery failure is a distinct state.**
Intel's Event 8, Tables 7-4/7-5, makes the ordered pair decisive: contributory
then #PF can be handled serially; #PF then contributory or #PF produces #DF.
#GP, #NP and #SS are contributory. #DF is vector 8 with error code zero, and its
saved CS/instruction pointer and program state are undefined: the oracle must
not require the original RIP or claim IRET/restart from #DF. A further
contributory/#PF failure during #DF delivery enters shutdown; treating it as
another restartable #PF is invalid. A fault after the first handler has begun
executing is a new fault in that handler, rather than automatically a failure
to deliver the earlier event. Handler-instruction fetch faults require separate
care: Event 8 expressly excludes prefetch faults from the classification table;
the nested fixture below instead executes a defined data-access instruction.
[Vol. 3A §7.15, Event 8, pp. 7-36–7-37](https://cdrdv2-public.intel.com/922487/253668-092-sdm-vol-3a.pdf).

**Fixed fixture state and oracle inputs — candidate choices.** Each active vCPU
gets a disjoint guest-linear region `V=0x10000000+cpu*0x20000`, backed through
Q30 x86 tables. At `V+0x10000/0x1000/0x2000` place GDT/IDT/TSS, with
GDTR.limit=`0x103f`. The GDT occupies two separately mapped pages. GDT selectors are
kernel CS `0x08`, kernel writable SS `0x10`, user CS `0x1b`, user writable SS
`0x23`, and a 16-byte TSS descriptor at `0x28`. Provide a separate valid kernel
code descriptor at `0x38` for #DF so the invalid-main-CS control cannot also
break #DF delivery. Variant 9h also uses an equivalent valid kernel code
descriptor at selector `0x1008`, on the second GDT page. Code descriptors are
present, accessed, nonconforming and
64-bit; data descriptors are present, accessed, writable with matching DPL/RPL.
The loaded TR identifies a busy 64-bit TSS with limit `0x67`; record both its
selector and cached base/limit/type. TSS reserved fields are zero, RSP0 is at
offset 4, IST1 at 36 and IST2 at 44, and the I/O-map offset is `0x68` (no I/O
instruction is used). This uses the TSS layout from
[Vol. 3A §10.7, Figure 10-11](https://cdrdv2-public.intel.com/922487/253668-092-sdm-vol-3a.pdf).

Set ordinary old RSP=`V+0x5ff9`, TSS.RSP0=`V+0x7ff7`, IST1=`V+0x9ffb`, and
IST2=`V+0xbffb`; mapped two-page stack areas end at `V+0x6000/0x8000/0xa000/0xc000`.
The three normal error-frame RSP oracles are respectively
`V+0x5fc0`, `V+0x7fc0`, and `V+0x9fc0`. IDTR.limit=`0xfff`; required gates and
handler code are mapped/present except for the one defect explicitly selected.
Use original fault RIP=`V+0x3000`, #PF/#GP/#DF handler entries at
`V+0x3100/0x3200/0x3300`, and the nested handler's data-fault RIP=`V+0x3110`.
Original/nested absent data addresses are `V+0xd000` and `V+0xe000`; the
noncanonical control uses `0x800000000000`. Pin exact handwritten instruction
bytes and lengths in the subsequent code submission before checking a handler's
intentional RIP advance; ordinary #PF retry keeps the faulting RIP unchanged.
Gate DPL=0 does not block a hardware #PF from CPL3 (software INT privilege
checks are different). Default #PF/#GP gates use IST0, while #DF uses the good
IST1 stack; the IST1 #PF control instead reserves IST2 for #DF. Keep CR0.WP=1,
NXE=1, CR4.PVI/VME/SMEP/SMAP/PKE/PKS/CET/FRED/LASS=0, all LAM controls=0, and
VM/NT=0. Accesses to IDT,
GDT and TSS are implicit supervisor accesses, irrespective of the interrupted
CPL; they must go through coherent Q30 translation with that access context,
not an unchecked host-memory read.
[Vol. 3A §4.2](https://cdrdv2-public.intel.com/922487/253668-092-sdm-vol-3a.pdf),
[Vol. 2A INT operation](https://cdrdv2-public.intel.com/922480/253666-092-sdm-vol-2a.pdf).

9e uses the CPL0/IST0 baseline, and 9f–9i use the CPL3 initial context with
the stated gate/stack changes. All delivery and return events are per-vCPU.

This enumerates eleven fixed variants (9d and 9g each contain two), each using
the existing proposed 16 repetitions and two/four-vCPU matrix. Addresses, table
bytes, incoming registers/flags, chosen defect, handler entry and committed
effects must be independently predicted per vCPU. Record delivery phases such
as selecting gate, reading TSS, building frame, and executing handler, so a
recursion-depth guard cannot pass as the classification oracle. Frame stores,
