## Assumptions and breadth

The charter's single disposable program grows with stage-1 paging, own EL1
vectors, virtual GIC, per-vCPU timer and TSO enabled. Q30 coherence, Q31 precise
faults and code-write recovery, and Q32 interrupts remain active during code
publication, linking and translation requests. Host-generated handwritten
arm64 templates stand for translator output; the shim may copy those bytes
but does not generate the requested instruction sequence itself.

Screening: (a) QEMU TCG also publishes translated code and links blocks, but
usually executes them in the host process. An ordinary VM also loads executable
guest memory. The question here is the host-to-EL1 split composed with translated
state recovery and SMP. (b) documented capabilities answer whether memory can
be mapped and caches synchronized in principle; they do not answer protocol,
generation or continuation correctness. (c) a finding applies to this shim and
a translator honoring the stated contract, not every translator or emulator.

The original shared-staging candidate is superseded by the accepted
register-transfer protocol: the shim installs actual host-produced bytes into
fresh code slots, with full cache synchronization and immutable blocks using
data-based links. Shared staging remains an unestablished alternative; direct
host writes into executable backing are not ruled out. Likewise,
concurrent instruction patching is a documented alternative with narrower
conditions; it is not required to establish block-to-block linking. Every
successful link must actually transfer between generated blocks inside the VM
without asking the host to perform the guest computation.

Relevant boundaries are host virtual address versus IPA versus guest VA,
host/guest permissions and memory attributes, multiple vCPUs, instruction-cache
and page-table invalidation, partially published code, stale host replies,
guest address-space changes, pending fault/IRQ frames, and code-page writes.
Finite pinned code/metadata lifetime is permitted for the first method; reuse
is not inferred from it. Full reclamation, code-cache pressure and generator
compatibility belong to `Q-03-02`; mechanism choice to `Q-03-04`; request cost
and throughput to `Q-04-07`; broad SMP stress to `Q-02-02`; memory layout and
feature contract to `Q-02-03`; host crash containment to `Q-02-04`; cross-host
coverage to `Q-05-02`. Retained unknowns include scalable retirement, direct
patching performance, arbitrary translator relocations and failure policy for
a real translator. No new question identifier is needed.

## Supporting contracts and claims

Claims 01–04 and 05/07 are **accepted scoped source findings and inferences**.
Claim 06 remains an **unestablished hypothesis** accepted only as a bounded
candidate for preparation. These source claims alone do not establish runtime
feasibility; accepted observed claim 10 below supplies that finite finding.

**CLM-01-33-01 — Source-backed: Apple exposes mapping and exit/resume
primitives.** Apple's
[Hypervisor overview](https://developer.apple.com/documentation/hypervisor)
maps a VM to a process and vCPUs to threads, requires the hypervisor entitlement,
and describes unmapped guest-physical accesses causing exits for host emulation.
[`hv_vm_map`](https://developer.apple.com/documentation/hypervisor/hv_vm_map(_:_:_:_:))
maps page-aligned host storage into IPA space; storage must span one host VM
region, typically allocated with mmap or mach_vm_allocate. macOS **26.4 SDK**
Hypervisor.framework `hv_vm.h`, `hv_types.h` and `hv_vcpu.h` document guest
physical R/W/X flags, `hv_vm_protect`, and owning-thread `hv_vcpu_run` exit/reentry.
These permissions are not a cache-publication operation. `hv_vcpus_exit` can
cancel execution, including causing a subsequent run to return immediately
when called for a stopped vCPU; it is not itself a guest safepoint or a proof
that a saved continuation no longer references code.

**CLM-01-33-02 — Source-backed: data stores require an instruction-publication
sequence.** Arm's
[Implementing __clear_cache, 2025-01-20](https://developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/caches-self-modifying-code-implementing-clear-cache)
explains the AArch64 write, DC CVAU, DSB, IC IVAU, DSB, ISB sequence, citing
DDI0487 L.a §B2.7.4.2. Cache-line coverage comes from CTR_EL0, with separate
instruction/data line sizes and rounded range starts. IDC/DIC can relax cache
operations on applicable implementations; they do not eliminate all ordering
and context synchronization. The initial candidate retains the full operations
and records CTR_EL0 instead of assuming a host generation's cache behavior.
This source establishes the guest-side sequence under its memory-system
assumptions, not visibility of an arbitrary host write through a guest alias.

**CLM-01-33-03 — Source-backed: publication to another core needs that
executor's synchronization.** Arm's
[Working with Threads, 2025-01-21](https://developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/caches-self-modifying-code-working-with-threads)
explains full synchronization: finish cache maintenance, publish readiness,
then have the executing core perform a context synchronization event before
entry. ISB is not broadcast. The writer must exclude execution from locations
being rewritten. The article also describes restricted concurrent exchange
of specified instruction forms, including direct branches, where old or new
execution may occur indefinitely without stronger synchronization; multiple
patches can be observed in mixed combinations. Thus an arbitrary multiword
patch and a time-based old-code retirement rule are not justified. The cited
architectural basis is DDI0487 L.a §B2.2.5; this submission does not claim an
independent audit of the entire current Arm ARM.

**CLM-01-33-04 — Source-backed: memory aliases need compatible attributes.**
Arm DDI0487 **M.c**, [§B2.11, Mismatched memory attributes](https://developer.arm.com/documentation/ddi0487/mc/-Part-B-The-AArch64-Application-Level-Architecture/-Chapter-B2-The-AArch64-Application-Level-Memory-Model/-B2-11-Mismatched-memory-attributes?lang=en),
defines mismatch in terms of memory type, shareability and cacheability (with
additional feature-dependent attributes). The mapping API alone does not name
these effective host/stage-2/stage-1 attributes. Therefore the source does not
permit an inference that arbitrary host/guest mappings automatically satisfy
the assumptions of claims 02–03. Pin ordinary shared RAM and record the
attribute/ordering argument before execution; device doorbells need distinct
mapping treatment. TLB maintenance for permission changes is separately owned
by Q30 and cannot substitute for instruction-cache maintenance.

**CLM-01-33-05 — Inferred: a published block is bytes plus matching execution
metadata.** From claims 01–04 and Q31/Q32 recovery requirements, publishing an
entry address before its code, permissions and recovery metadata are complete
permits faults or interrupts to observe an inconsistent object. A response
must identify the request, guest RIP/mode/address-space identity, guest source
bytes and mapping/code generation from which it was produced. Generation
checks must survive a table or source-code change while host production is
outstanding. Rejected stale work is an internal miss/retry, not a fabricated
guest instruction result or x86 page fault. Actual guest fetch/protection
faults still use Q30/Q31 classification.

**CLM-01-33-06 — Hypothesis: staging and immutable targets provide a minimal
viable publication path.** The host writes a completed response into owned
staging storage, then publishes readiness with a reviewed cross-domain
ordering protocol. The shim acquires it, checks identity and bytes, copies
into a fresh unreachable guest code slot, completes permission/TLB and cache
work, and publishes its descriptor. Every entering vCPU performs the required
synchronization and checks the descriptor's validity before branching. Link
changes publish a complete immutable target descriptor through one aligned
atomic data slot, keeping old targets and metadata alive. This is a candidate
composition, not a result. Guest cache maintenance after copying does not
repair a torn or stale staging read; response ownership and first transfer
visibility are independently necessary.

**CLM-01-33-07 — Inferred: link lifetime and guest source-code validity are
different obligations.** Retaining an old allocation makes it addressable;
it does not make its guest semantics current. Intel SDM
[Vol. 3A revision 092, §11.1.3](https://cdrdv2-public.intel.com/922487/253668-092-sdm-vol-3a.pdf)
specifies local and cross-modifying guest-code synchronization. After a guest
is entitled to see modified code, links and saved continuations must obey the
Q31/Q32 invalidation contract. An optimization-equivalent old target may be
allowed during link replacement; an obsolete translation of changed guest
bytes cannot use that allowance. No code or metadata can be reused while an
active block, saved exception/interrupt context, pending host response or
reachable link can still refer to its old identity.

## Method and controls

The source audit is bounded to 30 minutes and 12 primary documents. It checks
the API declarations and Arm's explicit self-modifying-code instructions, then
looks for contrary SMP, alias, partial-patch and lifetime cases. The consulted
set is the Apple overview/map page and three SDK headers, two Arm-authored
articles and the M.c attributes section, plus Intel Vol. 3A 092. The Arm article
references to L.a identify their basis; failed direct access to the full Arm
ARM is not represented as having read it. No source is runtime evidence.

The following is a method for a later code submission, not an executable
protocol approval. The first fixture uses fixed small pools and no reclamation
within a run. Exact pool sizes and exhaustion behavior must be in the snapshot;
exhaustion stops with diagnostics rather than reusing potentially live storage.

1. A translated block reaches a declared Q31/Q32 boundary and has no valid
   successor. The shim fetches its actual guest source through Q30, captures
   source/mapping/generation identity, and exports a 96-byte immutable request
   in three 32-byte register chunks through the unique `q33_transfer_exit`
   HVC36 helper. The host validates its exact instruction/resume PC and reads
   all X0–X15 on the owning vCPU thread. Only this vCPU exits; peers continue
   the existing Q30 polling/acknowledgement protocol. This replaces the earlier
   candidate memory doorbell; no host load of source bytes supplies production.
2. The owning host thread validates the request. Host code emits actual new
   bytes from a finite handwritten arm64 template using a per-request operand
   and the supplied guest source bytes. Retain exact request, emitted bytes,
   relocations/entry offset and expected semantics. A byte-identical block
   already embedded in guest.bin or a host-computed final answer cannot pass
   as production and execution of the requested block.
3. Transfer the complete response through X4–X7 in at most 32-byte chunks.
   X0–X15 also identify operation, transaction, exact offset/length, total,
   generation, status and case/CPU scope. Each host packet read and write is
   individually checked; the run stops before reentry if any setter fails.
   The shim stores response registers into its private packet, validates the
   whole reply, copies bytes into its private code slot and only then sends
   ACK through another HVC. The host cannot offer the next chunk until that
   ACK; cancellation is distinct from consumption. QT_WAIT returns control to
   guest polling instead of holding a stopped owner while waiting for a peer's
   gate acknowledgement. This candidate implements accepted inference 09 and
   avoids relying on claim 06's unestablished host-staging alias contract.
4. The shim rejects stale/malformed work before publication. Code slots use one
   guest identity VA, native Normal WB Inner Shareable attributes, and the
   existing RWX identity mapping. **There is no hardware permission-sealing
   claim:** a fresh slot is unreachable until its complete bytes and descriptor
   pass validation and DC CVAU / DSB ISH / IC IVAU / DSB ISH maintenance; then
   readiness is release-published. Each entering CPU executes ISB. Published
   bytes are never rewritten or reused within a run, including after all old
   users acknowledge a link change. This explicitly replaces the earlier
   proposed stage-1 sealing step with bounded software immutability. Pool
   storage is not mapped into the modeled x86 guest; isolation depends on the
   reviewed finite shim and host, not on execute-only or W^X protection.
   Host/stage-2 permissions are retained separately. This inference and its
   finite limits require review; it does not establish arbitrary JIT safety.
5. A block link is initially a miss descriptor. Publish a pointer to a complete
   immutable successor descriptor in an aligned atomic data slot. The block's
   tail acquires it, checks identity/generation, performs an explicit ISB before
   entering newly selected code, and branches in the VM. The initial method may
   retain that ISB on every link traversal. All guest registers and lazy flags
   follow the recorded block ABI. Replacing the slot while another vCPU executes
   the old immutable target exercises live linking without patching its body.
   A per-vCPU acknowledgement boundary must exclude already-loaded old
   descriptors before claiming that only the new target can subsequently run;
   an atomic slot replacement alone is not that acknowledgement.
6. For guest source-code changes, revoke obsolete descriptors and synchronize
   affected vCPUs through Q30/Q31/Q32's required points before acknowledging the
   guest-visible invalidation. Entry guards and saved continuation checks must
   prevent semantic stale-code execution after that point. Pinned old metadata
   remains available for faults/IRQs that reference it. Runtime recycling is
   deferred and no test outcome will claim it has been established.

The code/metadata submission must specify guest-state locations, block ABI,
host relocation inputs, entry offset/alignment bounds, fault/IRQ maps, precise
source dependencies, all publication/acknowledgement states, link ownership
and lifetime. Host pointers are never accepted as guest entry addresses.
A code hash identifies bytes but does not prove their semantics, memory ordering
or legal branch target. The independent checker needs a tiny specified
arithmetic/memory oracle and an observed PC/control-flow trace, not just an
expected success value printed by the producer.

## Host/guest transfer contract preparation — source findings accepted, 2026-09-07

This source-only pass began at 07:19 UTC with a 20-minute/eight-primary-source
budget. It changes neither the accepted status of claims 01–07 nor the
unestablished status of the staging hypothesis. No Q33 code or VM was run.

**CLM-01-33-08 — Source-backed, accepted scoped finding: the inspected allocation/mapping
declarations do not close the cross-domain attribute argument.** The macOS
26.4 SDK `hv_vm_allocate.h` describes anonymous allocation suitable for guest
memory, with `VM_PROT_DEFAULT` permissions and accurate accounting. Its only
allocation flag is `HV_ALLOCATE_DEFAULT`. The arm64 `hv_vm.h`, `hv_vm_types.h`
and included `arm64/hv/hv_kern_types.h` specify mapping the host region to IPA
and READ/WRITE/EXEC permissions. They do not specify the effective host and
stage-2 memory type, cacheability, shareability or an inter-domain atomic
publication guarantee. This is a limitation of these inspected declarations,
not a claim that Hypervisor mappings are incoherent or that no other Apple
contract exists. The public API entry points are
[`hv_vm_allocate`](https://developer.apple.com/documentation/hypervisor/hv_vm_allocate(_:_:_:))
and [`hv_vm_map`](https://developer.apple.com/documentation/hypervisor/hv_vm_map(_:_:_:_:));
the detailed wording above was checked in the local SDK, rather than inferred
from JavaScript-only web-page responses.

The current guest sets MAIR Attr0 to `0xff` and Normal-memory page descriptors
with inner-shareable SH bits. Those are stage-1 inputs. Arm's
[Armv8-A memory model guide v1.0, §§9, 13–14](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/Learn%20the%20Architecture/Armv8-A%20memory%20model%20guide.pdf?revision=58b1dd0a-3800-4218-b21a-f95a0332034c)
distinguishes cache/shareability from permissions, requires compatible alias
attributes, and explains that stage-2 attributes also affect the result;
HCR_EL2.FWB can change the combination. Consequently, guest stage-1 settings
alone do not establish the host/guest premise. Adding release/acquire,
DSB/ISB, or a checksum does not supply the missing attribute contract.
Changing only the guest alias to noncacheable or Device is not a documented
repair for an unspecified host alias. The named unresolved mechanism remains
**compatible effective attributes and ordering for concurrently accessed
host/guest staging storage**.

**CLM-01-33-09 — Inferred, accepted candidate for preparation: register transfer avoids that
particular staging dependency.** The local SDK `hv_vcpu.h` explicitly exposes
owning-thread register get/set and run operations. Apple's
[vCPU Management](https://developer.apple.com/documentation/hypervisor/vcpu-management)
describes execution until a trap or cancellation and the populated exit
reason. A bounded alternative therefore uses an exact native exit helper and
[`hv_vcpu_get_reg`](https://developer.apple.com/documentation/hypervisor/hv_vcpu_get_reg(_:_:_:))/
[`hv_vcpu_set_reg`](https://developer.apple.com/documentation/hypervisor/hv_vcpu_set_reg(_:_:_:))
for the request and response payload itself, rather than a ready word pointing
to host-written staging memory. This is a candidate composition of documented
primitives, not an accepted protocol or an architecture choice.

The smallest concrete preparation would retain the following ownership:

1. At a declared translated boundary, save canonical guest state and every
   native register the transfer helper clobbers. Export the request identity,
   source bytes/dependencies and continuation in bounded register chunks.
   The host validates the exact exit kind, helper PC and request progression;
   arbitrary exceptions are never advanced as successful transfers.
2. The owning host thread emits and retains the actual instruction bytes,
   then fills payload registers plus request ID, offset, length and status
   while its vCPU is stopped. All setters must succeed before reentry. Other
   vCPUs may continue the established program. No guest consumer runs between
   those setter calls, so they need not form one multi-register atomic write.
3. On reentry, the helper validates the response identity and bounds, stores
   the received bytes into guest-owned unreachable storage, and only then
   issues the next chunk/consumed acknowledgement. Host request state cannot
   advance or be reused before that matching acknowledgement. Partial,
   duplicate and stale responses must be exercised; partial storage never
   acquires a reachable executable descriptor.
4. After the complete response and generation checks, the guest performs the
   existing permission/TLB and instruction-cache publication sequence. Each
   executor still needs its own synchronization and valid metadata. Saved
   fault/IRQ continuations, live links, source-code changes and pinned old
   metadata retain all original Q33 obligations. Events requested while the
   owner is outside the VM are distinguished from native service after reentry.

This transfer removes the need to infer concurrent visibility between a host
store and a guest load for the response bytes. It does **not** establish
arbitrary guest SMP/code-cache ordering, permit incompatible guest mappings,
or remove the existing Q30–Q32 memory assumptions. The code submission must
still give a guest-side attribute/publication argument and exact register
ABI, finite chunk/pool/exit budget, restart recipe and independent byte-to-
execution oracle. Every response crosses the API as host-produced bytes;
returning only a computed result cannot meet Q33.

The [independent extension review](../reviews/INV-01-33-findings.md)
accepts claims 08–09 within these scopes. Register transfer is available for
concrete preparation; shared-memory staging remains open under claim 06.
The concrete method must explicitly replace its staging-specific step/case,
retain a whole-request byte/dependency snapshot and chunk ownership, handle
failed setters and canceled reentry, preserve payload registers across an
immediate native IRQ, avoid a stopped-owner paging-lock/ACK progress cycle,
and retain all guest SMP publication/link/source-generation obligations.
This accepts a candidate transfer mechanism, not a platform-wide coherency
claim, executed protocol, architecture selection or result about cost.

## Concrete register-transfer producer preparation

The current candidate has 28 variants across the ten retained groups:
`[2,2,2,2,3,3,6,3,2,3]`, each repeated 16 times at every configured CPU.
Groups with a designated requester rotate it through every CPU; other CPUs
remain in the same VM and participate in their stated peer roles. The exact
ABI is in `experiments/track01/q33.h`; it is preparation, not a finding.

The finite x86 source set is ADD RAX,imm32 (`48 05`, six instruction bytes),
MOV RAX,[RDI] (`48 8b 07`) and MOV [RDI],RAX (`48 89 07`), plus the existing
Q31/Q32 handler and CPUID contracts. An ADD dependency snapshot fetches eight
bytes: its six bytes and, where a chain exists, the following short JMP's two
bytes. Initial source/mapping validation, register chunks, actual copied native
bytes, decoded native entry/return addresses and guest instruction effects are
independently joined. A block may be shared by distinct CR3 contexts only when
that entering context independently fetches the exact source bytes from the
same guest physical page. It does not inherit the producer's address-space
identity. An epoch-spanning validation plus an atomic expected-generation pin
rejects a changed mapping/generation before entry; explicit peer changes between
source fetch and pin test both rejection paths. Old pins remain alive while an
already-started instruction faults or finishes after a source change.

Fresh native objects are aligned within a fixed three-MiB pool, but their entry
is deliberately offset by 20 bytes to exercise cache-line coverage. Large
4,288-byte objects actually execute their NOP body across a page boundary.
A→B→C links are aligned atomic descriptor IDs; replacing A→B or B→C while peers
are paused inside the old target retains that old allocation. Per-CPU LINK3
acknowledgements occur only after old calls return, followed by a barrier and
fresh traversals. Slots remain pinned for the entire run; real reclamation is
