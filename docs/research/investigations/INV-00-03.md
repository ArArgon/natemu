## Question and decision relevance

- Question: `Q-00-03` — Which systems and configurations are fair baselines,
  and which systems are diagnostic controls only?
- Decisions affected: benchmark methods, performance reporting, the
  materially-better judgment, and economic comparison with alternatives.
- Why now: baseline membership, configuration, and tuning rules must be frozen
  before measurements exist so that a weak or mismatched comparator cannot be
  selected after observing results.

## Assumptions

- Declared assumptions: QEMU TCG is mandatory under the governing decision
  question; the comparison concerns local full-system execution of the
  accepted unmodified x86-64 Linux guest on Apple Silicon; SMP is baseline.
- Assumptions to challenge: every x86 execution facility is a fair
  full-system comparator; defaults are automatically fair; equal vCPU counts
  imply equal host-resource use; native or remote results can enter a
  same-host speedup aggregate; one QEMU release remains representative
  throughout research.

## Resolution

Use an admitted QEMU x86-64 full-system TCG configuration as the only mandatory
decision baseline. This is a normative comparator selection, not a finding
that QEMU executes every accepted cell. At
method freeze, pin the latest stable upstream patch release; on 2026-09-03
this is QEMU 11.1.1, tag `v11.1.1`, commit
`c3d48b7d1e89604920e5b81b91140c2ad39a1943`. Configuration requests MTTCG and
disables incompatible deterministic modes, but the spelling of an option is
not proof that MTTCG is active.

Before a cell is admitted, `Q-05-01` must execute a reviewed capability probe
that records accepted accelerator options, startup diagnostics, all-vCPU-online
state, and a host thread census while all vCPUs run. A serialized fallback,
unsupported host/guest pairing, missing expected vCPU worker concurrency, or
ambiguous state makes the cell non-comparable. Admission also requires accepted
`Q-01-13` machine/device semantics, `Q-02-01`/`Q-02-02` correctness oracles,
and `Q-05-06` resource/placement instrumentation.

Another system becomes a decision baseline only if accepted `Q-00-01` and
`Q-00-02` findings show that it accepts the unmodified x86-64 guest, executes
the same end-to-end job locally on the same Apple Silicon host, permits
equivalent resource allocation, and has a reproducible supported
configuration. Diagnostic controls have zero weight in the materially-better
result. Adjacent-job controls and remote alternatives are audited separately
under `Q-06-04`; their economic relevance never admits them to a local
full-system speed ratio.

### Comparison protocol

1. Measure both systems on the same physical Mac, exact macOS build, power
   mode, host-service state, and test window. Never form a decision ratio from
   different hosts.
2. Use the same pinned guest kernel, initramfs/root filesystem, userspace binaries,
   workload inputs, guest RAM, vCPU count/topology, and declared cold/warm
   state. A shared guest artifact contains drivers for both virtual-device
   realizations; only necessary boot/device identifiers may differ.
3. Expose the accepted Q-00-02 CPU-feature intersection. An unavoidable CPU or
   guest-semantic difference creates a separately labelled, non-comparable
   cell.
4. Require the accepted `Q-01-13` machine contract and Track 02 oracle to show
   equivalent timer/APIC, serial, block, network, entropy, reset, and shutdown
   semantics with the same backing artifacts or endpoints. Similar device
   names are insufficient; an unresolved difference makes the cell
   non-comparable.
5. Pin and publish the QEMU binary hash, source tag, build toolchain, complete
   command line, machine type, CPU model/features, memory, SMP topology,
   devices, backends, and translation-block cache size. Specify
   `-accel tcg,thread=multi`; do not enable `icount`, replay,
   one-instruction translation blocks, tracing, or debugging.
6. `Q-05-01` must preregister finite default and tuned parameter spaces,
   invalid combinations, search order/budget, operator qualifications, the
   tuning log, and one freeze point before decision data. The decision
   comparison may use each side's faster correctness-valid frozen
   configuration only after an independent method review accepts parity; no
   workload-case-specific post-hoc setting is allowed. The former eight-hour
   allowance is withdrawn as an unvalidated proposal.
7. Give both processes the same declared host availability and priority.
   Record vCPU, helper/I/O thread count, CPU-seconds, peak RSS, P/E placement,
   oversubscription, power, and thermal state under `Q-05-06`; unequal
   resources require a preregistered resource-normalized analysis or make the
   cell non-comparable.
8. `Q-05-01` must propose and independently validate an order/blocking design
   that controls same-host drift. Balanced paired blocks with randomized
   `AB`/`BA` order are the candidate design, not an approved method here.
   Predeclare warm-up, cache-reset, timeout, retry, and invalid-sample handling.
9. A timeout, crash, wrong answer, or failed accepted workload/Track 02 oracle is recorded and
    fails the relevant guard; it is never silently excluded. Only
    correctness-valid samples enter performance estimates.
10. A later accepted correctness defect identifies every affected cell in a
    defect-propagation record and invalidates all dependent performance,
    resource, aggregate, and economic estimates until they are rerun or an
    independently reviewed argument proves them unaffected.
11. `Q-05-05` archives the release page/tag/binary/source hashes at method
    freeze and reinspects immediately before synthesis. “Newer” is defined
    by version order, not publication date: any upstream stable release whose
    version compares greater than the frozen release, that is a higher major,
    a higher minor within the same major, or a higher patch on the frozen
    release's own series, triggers the same archive/reinspection step and the
    precommitted full decision-baseline rerun. A release on an older
    concurrently maintained series (a lower major or minor than the frozen
    release) is recorded at reinspection but does not trigger a rerun. If a
    triggered rerun cannot be completed, older measurements retain only their
    pinned-version applicability and cannot support the synthesis aggregate.

## Hypothesis and falsifier

- Hypothesis: QEMU MTTCG under the frozen protocol is a fair full-system
  decision baseline, while the listed controls expose mechanism or alternative
  job costs without contaminating the decision aggregate.
- Falsifiers: discovery of another independently implemented system satisfying
  every baseline-admission rule; evidence that an alleged control satisfies
  the accepted full-system contract; inability to match guest-visible CPU or
  device semantics; a material tuning-effort imbalance; or significant order,
  thermal, cache, or host-placement interaction left unmodeled.
- Predicted outcomes: QEMU MTTCG remains mandatory; controls may explain a
  result but carry zero success weight; non-comparable cells are reported
  rather than coerced into ratios.

## Controls

- Future positive controls: QEMU MTTCG running the exact accepted full-system guest
  and passing its oracle; a repeat measurement block with identical frozen
  configuration.
- Negative controls: QEMU `thread=single`, QEMU linux-user, ARM Linux with
  Intel application translation, native arm64, native x86 on another host, and
  remote execution.
- Baselines: mandatory QEMU MTTCG only after it passes every per-cell admission
  rule, plus any later system independently shown to pass the same rules before
  method freeze.

## Confounders

- Known confounders: host generation and OS, performance/efficiency-core
  placement, thermal and power state, background services, guest CPU/device
  differences, storage/network backend state, cache/warm-up state, binary and
  toolchain version, tuning expertise, helper-thread resource use, order
  effects, and baseline version drift.
- Mitigations and residual risk: same-host controls, frozen artifacts and
  configurations, reviewed tuning parity, full disclosure, Q-00-04 resource
  guards, and pre-synthesis rebaseline. The exact blocking/randomization method
  and macOS scheduling/thermal treatment remain Q-05-01/Q-05-07 proposals and
  Q-05-02 platform-sensitive risks.
