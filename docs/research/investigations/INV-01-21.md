## Question and decision relevance

- Question: `Q-01-21` — Which sleep/wake, App Nap, Low Power Mode, thermal,
  and background-QoS transitions can a running emulator experience, and what
  liveness and timekeeping guarantees survive each?
- Decisions affected: `Q-01-07` timer admissibility, `Q-01-23` scheduling,
  containment and correctness oracles, benchmark eligibility, and platform
  applicability.
- Why now: timer latency measured only in a foreground steady state cannot
  establish guest-visible behavior across normal host lifecycle transitions.

## Assumptions

- Declared assumptions: P1 and P2 are separate platform cells; 2/4/8 vCPUs
  are product cells; correctness failures suppress cost samples.
- Assumptions to challenge: monotonic clocks all advance identically across
  sleep; timers catch up rather than disappear; background demotion is
  detectable; App Nap can be disabled in an admissible product; and a
  thermal/power slowdown is merely performance rather than guest liveness.

### Scope: transition categories, host, and topology

Single available host: `Mac16,10`, Apple M4, macOS 26.6.2 (build `25G83`),
SDK 26.4. There is no P1 (Sequoia 15) coverage and no second host in this
method. **Applicability statement: any finding under `M21-1` is specific to
this exact host, OS build, and SDK; it does not generalize to P1, to other
Tahoe builds, or to other Apple Silicon generations without separate,
independently reviewed replication.**

`Q-01-21`'s five transition categories are expressed as eight conditions
(six transition arms plus two controls, table below), each run at
`N ∈ {1, 2, 4, 8}` busy worker threads — 1 is the diagnostic cell, 2/4/8 are
the product cells, matching the existing applicability matrix.

### Child process design

- Each cell is one fresh `exec`'d child process. No cell reuses a process,
  thread, or thread pool from another cell.
- The child creates exactly `N` busy worker threads, exactly one
  periodic-timer thread, and one control thread that installs the detection
  surfaces and drives the transition protocol.
- **Busy worker**: a bounded spin loop incrementing a private 64-bit counter.
  Per `REV-225` RR1 (R9 not closed at the prior return): a heartbeat is no
  longer triggered by a fixed iteration count. Instead, after each iteration
  the worker reads `mach_continuous_time()` and appends one heartbeat record
  to a preallocated, thread-private ring buffer only when at least 100 ms
  (the timer thread's own fixed period, converted from wall time to raw
  ticks via `mach_timebase_info`, `mach_time.h` lines 46–50) has elapsed
  since its last recorded heartbeat — never on the iteration count alone,
  because a spin loop retires on the order of 10^9–10^10 iterations over a
  30-minute window on this host (~1–2 ns per iteration with one atomic flag
  poll), three-plus orders of magnitude above any capacity a ring buffer
  can hold at a 2^16-iteration trigger. Each record carries: a monotonically
  increasing local sequence number, the current iteration-counter value (so
  per-100 ms throughput is still recoverable even though heartbeat frequency
  itself is now time-bounded), `mach_absolute_time()`, `mach_continuous_time()`,
  `clock_gettime(CLOCK_MONOTONIC)`, `clock_gettime(CLOCK_MONOTONIC_RAW)`,
  `clock_gettime(CLOCK_UPTIME_RAW)`, and its own current QoS class read back
  via `pthread_get_qos_class_np`. Bounding the heartbeat in time rather than
  in iterations also removes the tension `REV-223` R5 identified for good:
  heartbeat cadence no longer moves with T4 (thermal throttling) or T5 (QoS
  demotion), matching the reference-clock design Worker/timer progress
  (Classification, below) already requires. No heartbeat write blocks on
  I/O. Between iterations each worker also polls a shared atomic "demote
  requested" flag (used only by arm T5 below) and, on first observing it
  set, calls `pthread_set_qos_class_self_np` on itself — QoS is demoted by
  the thread itself, never cross-thread by the control thread, since no
  public API in the accepted packet grants that.
- **Ring-buffer capacity and wrap policy** (`REV-223` R9; `REV-225` RR1
  corrects the arithmetic): each thread-private ring buffer is preallocated
  to a fixed capacity sized for the longest observation window in this
  method (T1, 30 minutes; Sample plan, below) at the *time-bounded*
  heartbeat cadence declared above (Busy worker) — the timer thread's own
  fixed 100 ms period, never a busy worker's raw iteration count. Arithmetic
  stated here so it is auditable at the code gate: 30 minutes ÷ 100 ms =
  18,000 records per thread over the longest window; rounded up to a
  power of two, capacity is fixed at 2^15 = 32,768 records per thread
  (headroom factor ~1.82× over the exact count). At an estimated ~64 bytes
  per record (sequence number, iteration counter, five clock readings, QoS
  class — the exact packed layout is a code-gate detail), one thread's
  buffer is 32,768 × 64 B ≈ 2.0 MiB; the largest child (8 workers plus the
  timer thread, `N = 8`) is therefore bounded at roughly 9 × 2.0 MiB ≈
  18 MiB of ring-buffer memory, not the tens of gigabytes the uncorrected
  iteration-triggered heartbeat would have required. This capacity is fixed
  before code implementation and recorded in the manifest (External
  immutable raw artifact, below). On reaching capacity a buffer is
  fail-closed: it stops accepting new records rather than overwriting old
  ones — **wrap = cell invalid**. Each thread also
  maintains a monotonic dropped-record counter, incremented and written into
  the trace whenever a record cannot be written for any reason. A nonzero
  dropped-record counter for a thread makes that thread's classification for
  that repetition `insufficient-samples` by construction and is attributed
  to the harness, never to the host (Classification, below).
- **Timer thread**: a `dispatch_source_timer` (or, if the future code review
  finds it unavailable in this signing/entitlement configuration, a
  `nanosleep`-based loop) with a fixed 100 ms requested period. Each fire
  appends the same six-value clock-plus-QoS snapshot plus its own
  fire-sequence number to its private ring buffer. This thread is the
  primary liveness witness for periodic delivery.
- **Control thread**: before starting workers/timer, installs `NSWorkspace`
  `willSleepNotification`/`didWakeNotification` observers (and the
  accepted packet's screen/session notifications), an `NSProcessInfo`
  `thermalStateDidChangeNotification` observer, and an `NSProcessInfo`
  Low-Power-Mode change observer, then runs a run loop on this thread for
  any surface whose delivery relies on it. Per `REV-225` RR4:
  `NSProcessInfo.h` states, inside the accepted `SRC-156` pin, that the
  thermal and power-state notifications are "posted on the global dispatch
  queue" (lines 231, 240) — an arbitrary, concurrency-managed thread, not
  this control thread's run loop — so a plain thread-private append from
  those callbacks would be an unsynchronized cross-thread write. Every
  detectability-record buffer in `M21-1` is therefore redesigned as a
  fixed-capacity, fail-closed array (the same wrap = cell invalid rule as
  the worker/timer buffers, Ring-buffer capacity and wrap policy, above)
  with one shared atomic write-index per notification source, claimed by
  `fetch_add` before each append: whichever thread actually runs the
  callback claims the next slot and writes only that slot, never another;
  a claim beyond capacity increments the shared dropped-record counter and
  writes nothing. This is a lock-free multi-producer/single-consumer
  design (the post-run checker is the sole reader), so it is correct
  regardless of which thread the delivery mechanism uses. The
  `NSWorkspace`-sourced records use the same atomic-index design: the
  accepted `NSWorkspace.h` excerpt states only that its notifications are
  registered on `NSWorkspace`'s own notification center (line 33 —
  outside the accepted pin, recorded as a supplement candidate below), not
  which thread executes the callback, so a single-producer assumption
  cannot be asserted for that source either. Every observer callback
  appends one record: which notification/property fired, its reported new
  value, the same six-value clock snapshot, and the local sequence number
  in force at that instant. This is the sole detectability instrument for
  `M21-1`.
- After the observation window (Sample plan, below) or on watchdog timeout,
  the child closes its ring buffers, writes one raw trace file under
  `NATEMU_RAW_ROOT`, and exits. The child refuses to start if
  `NATEMU_RAW_ROOT` is unset, resolves inside this repository, or is not
  writable, and it writes nothing under `experiments/`.

### Detectability instrumentation and the IOKit gap

Only the accepted source packet's public surfaces are used for detection:
`NSProcessInfo.thermalState` and its change notification,
`NSProcessInfo.isLowPowerModeEnabled` and its change notification,
`NSWorkspace` sleep/wake (and screen/session) notifications, and
`NSActivity`/`beginActivityWithOptions:reason:` as an opt-out hint. No other
framework is a detection source in `M21-1`. (This sentence covers
*detectability* only; the subsection immediately below the IOKit paragraph
declares every other host mechanism `M21-1` relies on outside the accepted
packet.)

IOKit power-management notifications (for example `IORegisterForSystemPower`
and its `kIOMessageSystemWillSleep`/`kIOMessageSystemHasPoweredOn`
callbacks) would give finer-grained or earlier sleep/wake brackets than
`NSWorkspace`, but they are **outside** the accepted `SRC-095`/`SRC-156`/
`SRC-157` packet. `M21-1` does not use them and records them only as a
**named source-supplement candidate**: before any future method version
relies on an IOKit callback for a Source-backed detectability claim, that
header/documentation must independently pass its own source review. No
IOKit-derived statement anywhere in this record is Source-backed, Observed,
or load-bearing.

#### Operator protocol for privileged/opportunistic arms (T1, T3a, T3b, T4)

1. Preflight: capture host model, build, SDK, power source, current thermal
   state, current Low Power Mode state, and total/performance/efficiency
   core counts (`Mac16,10`'s asymmetric P/E topology) via
   `sysctlbyname("hw.nperflevels", …)` and
   `sysctlbyname("hw.perflevelN.physicalcpu"/"logicalcpu", …)` for each `N`
   (mechanism declared as an unaccepted source-supplement candidate, table
   above; `REV-223` R12; `REV-225` RR9), plus any available placement proxy
   the accepted packet exposes — none is, in fact, available from the
   accepted `SRC-095`/`SRC-156`/`SRC-157` packet, so placement remains
   declared-and-confounded, never sampled (Transition arms, below). Also
   capture the per-clock sampling-granularity value: `clock_getres` for the
   three `clock_gettime` clocks and the `mach_timebase_info`-converted
   duration of one raw tick for `mach_absolute_time`/`mach_continuous_time`
   (both supplement-pending, table above; `REV-225` RR6(c)), before
   starting the child.
2. Launch the child; wait for it to write an `ARMED` marker to its raw trace
   directory, confirming workers/timer/observers are running and at least
   one full 100 ms timer period has elapsed with a live heartbeat from every
   worker.
2a. Delivery-validity control, **T1 only** (`REV-223` R3; `REV-225`
    RR3/RR5 correct its scope, timing, and induction): per `REV-225` RR3,
    this control validates only the `NSWorkspace` notification-center path
    (`SRC-157` line 33: all notifications in that header must register on
    `NSWorkspace`'s own center), the same path T1's own tested surface
    (`willSleepNotification`/`didWakeNotification`) uses; it is therefore
    run for **T1 only**, not T3a/T3b/T4, whose tested surfaces are
    `NSProcessInfo` notifications on a different delivery path
    (Classification and Controls, below). Per `REV-225` RR5, the named
    induction is corrected to one the pinned notifications actually
    document — screen *lock* is not display sleep — and the control now
    brackets T1's induction on both sides:
    - **Before**: immediately before step 3's sleep induction, the
      operator triggers display sleep with `pmset displaysleepnow`
      (source-supplement candidate, table above) and restores the display
      (any input), and confirms the control thread logs the
      `NSWorkspaceScreensDidSleepNotification`/`ScreensDidWakeNotification`
      pair `bracketed` (header lines 325–326, inside `SRC-157`'s accepted
      pin) before proceeding to step 3. If `not-bracketed`, abort this
      repetition as a harness integrity failure (Controls, below) — do not
      perform the induction, and do not record any detectability result
      for this repetition.
    - **After**: once the child wakes from step 3's induction and logs its
      own `didWakeNotification` result (`bracketed` or `not-bracketed`),
      the operator repeats the same `pmset displaysleepnow`-and-restore
      pair once more before the observation window ends. Only if this
      **post-induction** instance is also `bracketed` may a
      `not-bracketed` `didWakeNotification` result in this repetition
      count toward `CLM-01-21-03`'s falsifier (Exclusion and stop
      criteria, below); a `not-bracketed` post-induction instance excludes
      the repetition as a harness integrity failure regardless of what the
      pre-induction instance showed, because it means the instrument
      cannot be shown to have been alive at the moment the transition
      should have been observed. Both display-sleep/wake pairs are a
      predeclared, timestamped part of this protocol, not an unintended
      concurrent transition, and are exempt from the mixed-condition
      confounder rule (Confounders, below).
3. Perform exactly one induction action for that cell:
   - **T1**: `sudo pmset sleepnow`; if `sudo` is unavailable in the
     operator's session, the fallback is the Apple-menu "Sleep" user action.
     Record which method was used. Immediately before the induction, the
     operator captures `pmset -g assertions` output (out-of-band record, R1
     supplement candidate) confirming no outstanding assertion would deny
     the sleep request; per `REV-223` R6, no C1 repetition on this host may
     run concurrently with a T1 repetition, because a live C1 activity
     token (`NSActivityIdleSystemSleepDisabled`, Self-induced protocols,
     below) is exactly such an assertion — the Order rule (Sample plan,
     below) serializes T1 against every C1 repetition. The operator
     confirms wake by an independent external observation (a second
     device's clock) and logs operator-observed sleep-start/wake-end wall
     time, together with a post-wake `pmset -g log` capture (out-of-band
     induction record), in a plaintext companion log. The child's own
     `mach_continuous_time`-versus-`mach_absolute_time` divergence over the
     bracketed interval (Classification, below; subject to the `SRC-095`
     supplement gate, Source inventory above) is retained as a
     corroborating diagnostic only. None of these captures substitutes for
     the child's own recorded evidence; a repetition is recorded
     `not measured` when both the second-device bracket and the
     `pmset -g log` capture agree no sleep was entered, and also — per
     `REV-225` RR8 — when the two out-of-band confirmations disagree about
     whether sleep was entered: disagreement is never resolved in favor of
     `confirmed-delivered`, and such a repetition does not count toward
     `CLM-01-21-03`'s 2-of-3 reachability threshold (Exclusion and stop
     criteria, below).
   - **T3a/T3b**: `sudo pmset -a lowpowermode 1` (or `0`); if `sudo` is
     unavailable, the fallback is the Settings > Battery UI toggle. Per
     `REV-223` R6, the induction is confirmed out-of-band by a `pmset -g`
     capture (R1 supplement candidate) taken immediately after the action,
     never by rereading `isLowPowerModeEnabled`: for T3b (on→off) that
     API's own NO-means-unknown/unsupported fallback (`CLM-01-21-07`) makes
     the reread indistinguishable from a delivered-but-undetected
     transition — exactly the ambiguity Detectability classification
     (below) exists to measure. The child's own `isLowPowerModeEnabled`
     reread and change-notification remain recorded as the detection-only
     observation under test; they are never used as the induction's own
     confirmation.
   - **T4**: no induction action is performed, ever. The operator may
     schedule this arm's repetitions after a sustained `N=8` busy run or on
     a high-ambient-temperature day, purely as scheduling discretion, and
     records ambient/prior-load context. Blocking vents, disabling fans, or
     any other artificial heating/cooling is forbidden.
4. The child continues running to the end of its observation window or
   watchdog. The operator does not force-quit it.
5. If the operator cannot perform the induction at all in a given session
   (no console access, denied toggle, no thermal opportunity), that cell is
   recorded `not measured`. It is never simulated, and it is never silently
   dropped from the planned-cell count.

#### App Nap protocol (T2)

Per `REV-223` R7, T2 is retained as an **uncontrolled, diagnostic-only arm**:
it is never used to test any `CLM-01-21-*` falsifier, confirming or
falsifying. The child is launched unattended and backgrounded: not the
frontmost application, no visible window, no audio, launched via a
detached/background mechanism, and, when the operator can arrange it, on
battery power. `LSUIElement` is a bundle Info.plist key with no effect on
this method's non-bundled `exec`'d child (Child process design, above) and
is **not** used as a control (it is dropped, not carried forward blocked,
per the source-supplement table above). No privileged action and no forced
App Nap entry is attempted — App Nap eligibility is an opaque system
heuristic outside the accepted packet's control surface, and no accepted
surface in this packet observes App Nap directly. T2 cells default to
`not measured`: any App Nap-consistent behavior pattern (Classification,
below) observed within the watchdog window is recorded as an unattributed
diagnostic note only, because it cannot be distinguished from ordinary
background scheduling on this host using any surface `M21-1` has access to.

#### Self-induced protocols (T5, C1)

- **T5**: after the same `ARMED` confirmation, the control thread sets the
  shared atomic "demote requested" flag at a recorded local sequence point.
  Each worker and the timer thread demote themselves (`QOS_CLASS_
  USER_INITIATED` → `QOS_CLASS_BACKGROUND`) on next poll, and every
  subsequent heartbeat's QoS read-back is compared against the requested
  class. Per `REV-223` R8, this is a **harness self-observation control**,
  not a positive control for an OS-originated transition: `pthread/qos.h`
  (source-supplement candidate, above) documents `pthread_set_qos_class_
  self_np` as setting the thread's *requested* QoS class and
  `pthread_get_qos_class_np` as returning that requested class, so the
  read-back proves only that the request was recorded for the calling
  thread, not that the kernel scheduler demoted it.
- **C1**: after `ARMED`, the control thread calls
  `beginActivityWithOptions:(NSActivityUserInitiated |
  NSActivityIdleSystemSleepDisabled) reason:` and records the returned
  activity token (a non-nil token proves the request was accepted), holds
  for the window, then ends the activity and records that call. Per
  `REV-223` R8, this is also a **harness self-observation control**, not a
  positive control for an OS-originated transition: a non-nil token proves
  only that the API accepted the request, against `CLM-01-21-08`'s accepted
  limit that user preferences may override activity requests — it does not
  prove the OS actually altered its sleep/scheduling behavior in response.

### Classification (qualitative only)

A separate, independently reviewed checker — not the child itself —
classifies the raw trace after the run. All classifications below are
categorical buckets, never point latency values:

- **Clock continuity**, per clock (`mach_absolute_time`,
  `mach_continuous_time`, `CLOCK_MONOTONIC`, `CLOCK_MONOTONIC_RAW`,
  `CLOCK_UPTIME_RAW`), compared immediately before/after the transition
  boundary (or, for T2/T4/C2 where no sharp boundary exists, across the
  whole window). Per `REV-223` R4, the buckets are redefined to be mutually
  exclusive and decidable: `advanced` (strictly increasing by more than the
  clock's recorded sampling granularity across the boundary — by this
  definition `advanced` and `frozen` cannot both hold), `frozen` (no
  advance greater than sampling granularity across an interval where the
  operator/self-induced log confirms a transition occurred, **and** the
  sampling thread is confirmed to have continued running throughout that
  interval — see below for which arms can reach this bucket), `backward`
  (observed decrease), or `insufficient-samples` (heartbeats missing across
  the boundary). `insufficient-samples` is not itself evidence of clock
  suspension: per R9 above, it is first attributed to the harness (a
  dropped-record-counter nonzero for that thread) before any host-side
  interpretation is considered; once harness causes are excluded it is
  recorded as inconclusive for that clock, never as a stand-in for `frozen`
  or `backward`. Reaching `frozen` requires a live sampling thread
  throughout the confirmed-transition interval; for T1 (system sleep) the
  workers and timer thread are themselves suspended during the interval
  under test, so T1 can produce `insufficient-samples` but never
  `frozen` — no arm in this method induces host clock suspension while
  keeping a sampling thread alive, so `frozen` is unreachable on every arm
  (see `CLM-01-21-02`, Claim inventory, above, for the resulting falsifier
  narrowing). The `mach_absolute_time` versus `mach_continuous_time` delta
  is separately recorded as a categorical same/diverged/insufficient-
  samples bucket per boundary; per the `SRC-095` re-pin declared in Source
  inventory above (`REV-223` R2), this bucket is blocked as a
  classification input until that supplement independently passes source
  review, and is retained in the raw trace as a diagnostic, unqualified
  bucket only in the interim, never used to test `CLM-01-21-04`. Per
  `REV-225` RR6(c): "the clock's recorded sampling granularity" is, per
  clock, the resolution `clock_getres(clock_id)` reports for the three
  `clock_gettime` clocks and, for `mach_absolute_time`/`mach_continuous_time`,
  the wall-time duration of one raw tick as converted by
  `mach_timebase_info` (`mach_time.h` lines 46–50; both mechanisms
  supplement-pending, Source-supplement table above). This value is
  captured once per repetition in preflight (Operator protocol, above) and
  recorded per clock in the manifest (External immutable raw artifact,
  below), so the `advanced`/`frozen` boundary is computable rather than an
  undefined term. Per `REV-225` RR6(d): in the whole-window comparison used
  for T2, T4, and C2 (no sharp transition boundary), any observed decrease
  at any sampled point within the window classifies that clock `backward`
  for the window regardless of whether the window's net first-to-last
  comparison would otherwise read as `advanced` — `advanced` requires a
  strictly increasing sequence throughout, not merely a non-negative net
  delta.
- **Worker/timer progress**, redefined per `REV-223` R5 to use a single
  named reference clock and a threshold independent of any arm's
  manipulated variable: gaps are measured in `mach_continuous_time` (the
  accepted `SRC-095` clock; `mach_absolute_time` remains supplement-pending
  per R2 above) since the last successfully recorded heartbeat/fire from
  that thread, classified against multiples of the **timer thread's own
  fixed 100 ms nominal period** — the sole period unit for every worker and
  the timer thread, never a busy worker's own iteration-based heartbeat
  cadence, because that cadence varies with the throttling (T4) and QoS
  demotion (T5) under test. `continuous` (never gapped beyond 3× the 100 ms
  nominal period with no accompanying confirmed transition), `paused-then-
  resumed` (a gap beyond that threshold that correlates with a confirmed
  transition per the operator/self-induced log or a `bracketed`
  detectability record), or `stalled` (no heartbeat for more than 3× the
  nominal period — 300 ms; this is the single `stalled` threshold used
  everywhere in this record, replacing the "beyond the watchdog" phrasing
  that previously appeared in Metrics and in `CLM-01-21-02`'s falsifier,
  `REV-225` RR6(a) — with no accompanying confirmed transition, established
  by the child's own ring-buffer evidence — never inferred from a
  supervisor kill alone, Sample plan below). Per `REV-225` RR6(d): for a
  thread with more than one gap in a single window (T2/T4/C2's
  whole-window mode), any gap beyond threshold that does not correlate
  with a confirmed transition classifies that thread `stalled` for the
  window (or excludes the repetition as mixed-condition if it correlates
  with an unintended concurrent transition, Confounders below), even if
  another gap in the same window does correlate with a confirmed
  transition; `continuous` requires no gap beyond threshold at all, of
  either kind. Evaluated separately per worker thread
  and for the timer thread. Because `mach_continuous_time` advances during
  sleep, a gap equal to the sleep duration is expected during T1 and does
  not by itself indicate `stalled`; it is classified `paused-then-resumed`
  when it correlates with the confirmed transition. A `stalled`
  classification at watchdog timeout establishes non-progress within that
  finite window, not unbounded stall or structural impossibility — a scope
  limitation of any finite experiment, consistent with the falsifiers
  already recorded in the Hypothesis and falsifier section above. Stating
  the reference clock here bounds, without violating, the
  no-`INV-01-07`-dependency statement at Proposal boundary and
  prerequisites, above: the qualitative buckets use an under-test clock as
  a coarse ordinal device, not as a calibrated timing instrument.
- **Delivery-validity control, T1 only** (`REV-223` R3; `REV-225`
  RR3/RR5): before relying on any `not-bracketed` `NSWorkspace`
  detectability outcome (below) for a **T1** repetition, the control

  `bracketed` both immediately before and immediately after T1's induction

  found among the accepted packet's surfaces, and none is declared here.
  The delivery-validity control below is the closest available check, and
  it validates notification delivery, not OS-originated transition
  behavior itself. Any claim requiring a genuine OS-originated positive
  control is out of scope for `M21-1` and is recorded as untested rather
  than confirmed (Claim inventory, above, `CLM-01-21-02`/`-03`).
- Delivery-validity control, T1 only (`REV-223` R3; `REV-225` RR3/RR5): a
  display-sleep/wake induction (`pmset displaysleepnow`, plus restoring the

  T1's own induction (Operator protocol step 2a, below). Both instances
  must show `bracketed` before any `not-bracketed` detectability result in
  that repetition may count toward `CLM-01-21-03`'s falsifier
  (Classification, above). A `not-bracketed` delivery-validity control, at
  either bracket, is a harness integrity failure — the notification path
  is a dead instrument for that repetition, distinct from a host that
  genuinely did not notify — and excludes the repetition from both
  confirmation and falsification (Exclusion and stop criteria, below). Per
  `REV-225` RR3, this control does not, and cannot from the accepted
  packet's surfaces, validate the separate `NSProcessInfo` default-center
  path T3a/T3b/T4 depend on; those three arms' detectability is recorded
  diagnostic-only and this control is not run for them.
- Negative controls: C2, the no-transition stable baseline, run for the same
  window length as the matched arm at the same `N`. It must show
  `advanced`/`continuous` for every clock and worker/timer, and
  `not-applicable`/no spurious notification for every detectability
  surface. A false-positive detection or spurious discontinuity in C2 is an
  integrity failure and excludes that repetition; it does not become
  evidence of a host transition.
- Baselines: AC power, nominal thermal state, default QoS, and no pending
  transition are the recorded preflight state for every arm. They
  characterize the starting condition and are not themselves a substitute
  for a product transition cell.

## Confounders

- Known confounders: undetected concurrent transitions (for example thermal
  state drifting during a T5 run), display/user activity, scheduler
  preemption unrelated to the tested transition, ambient temperature,
  battery charge level, unrelated background load on the shared host,
  coalescing of the 100 ms timer, and operator-log timing imprecision (a
  second device's clock is not synchronized to the host).
- Mitigations and residual risk: the control thread logs
  thermal/Low-Power-Mode/QoS state continuously, not only at the intended
  boundary, so an unintended concurrent transition is visible and that
  repetition is flagged mixed-condition and excluded from its arm's
  classification (a mixed-condition T4-adjacent event may separately feed
  the T4 arm's own count, never both). The delivery-validity control's own
  display-sleep/wake pair (Operator protocol step 2a, above; `REV-225`
  RR5) is a predeclared, timestamped part of the T1 protocol, not an
  unintended concurrent transition, and is exempt from this
  mixed-condition exclusion. No statistical inference is attempted; each
  cell is reported as its own qualitative outcome, never pooled across
  confounded and clean repetitions.

## Sample plan

- Units: one fresh `exec`'d child process per repetition per (arm, `N`)
  cell; 8 arms × `N ∈ {1,2,4,8}` = 32 arm×`N` cells.
- Repetitions: 3 fresh-process repetitions per cell, seeds `21001`–`21003`
  (controls worker-thread launch order and any jittered spin-loop bound
  only; it does not control operator induction timing). Privileged and
  opportunistic arms (T1, T3a, T3b, T4) may complete fewer than 3, with the
  remainder recorded `not measured`; self-induced arms (T2, T5, C1, C2) are
  expected to complete all 3.
- Order: arms and `N` values run in an order recorded before execution in
  the frozen input manifest; T1/T3a/T3b/T4 order additionally follows
  operator availability, recorded as it actually occurs, never reordered
  after seeing a favorable/unfavorable result. Per `REV-223` R6, no C1
  repetition may run concurrently on this host with any T1 repetition: a
  live `NSActivityIdleSystemSleepDisabled` token from a concurrent C1 child
  is a known mechanism by which the OS denies a T1 sleep request, and would
  make a failed/delayed T1 induction indistinguishable from a host anomaly.
  The recorded schedule must serialize every C1 repetition against every
  T1 repetition on this host.
- Warm-up: the `ARMED` confirmation (workers/timer live, observers
  installed, at least one full timer period elapsed) precedes any induction
  or the start of the C2/T4 window; warm-up records are retained but
  excluded from transition-boundary classification.
- Observation window (post-`ARMED`; watchdog ceiling enforced by an
  external supervisor process on this same host, using its own wall-clock
  timer read via that supervisor's own `clock_gettime(CLOCK_UPTIME_RAW)`
  call — declared, like every other `clock_gettime` use, a source-
  supplement candidate under R1 above): T1 30 minutes (includes operator
  sleep/wake time); T3a/T3b 10 minutes; T4 20 minutes; T2 15 minutes;
  T5/C1/C2 5 minutes. Per `REV-225` RR2 (R10's clock choice was inverted at
  the prior return): `clock_gettime(3)`, in this SDK, states that
  `CLOCK_MONOTONIC` "will continue to increment while the system is
  asleep" (lines 67–69) and that `CLOCK_UPTIME_RAW` "does not increment
  while the system is asleep" and is "identical to the result of
  `mach_absolute_time()` after the appropriate `mach_timebase` conversion"
  (lines 78–84) — the reverse of what the prior text asserted. The
  supervisor's ceiling clock is therefore corrected to `CLOCK_UPTIME_RAW`,
  the clock that genuinely excludes sleep: the supervisor runs on, and is
  itself suspended by, the same host as the child during T1, and its
  `CLOCK_UPTIME_RAW` ceiling does not tick during system sleep, so a
  30-minute T1 ceiling is measured only across the host's awake time and
  the supervisor cannot itself expire mid-sleep. (If a future revision
  instead uses `CLOCK_MONOTONIC` for this ceiling, the ceiling must be set
  to exceed the maximum planned sleep duration plus the awake window,
  because that clock's value spans sleep.) A supervisor-initiated
  kill of the child — whether by ceiling timeout or a supervisor
  health-check failure — never yields a `stalled` classification by
  itself: the repetition is recorded `timed-out` when the ceiling was
  reached, or `not measured` when the supervisor could not confirm the
  child was ever healthy (for example, no `ARMED` marker seen). `stalled`
  remains reserved exclusively for the Classification-section checker rule
  applied to a completed or partial ring-buffer trace showing an internal
  heartbeat/fire gap beyond threshold — evidence the child itself recorded,
  never inferred from the supervisor's kill alone. Timeout preserves
  partial raw output and is never silently retried into a favorable
  subset.
- No power/precision target is claimed: this is a bounded qualitative
  falsifier design, not a statistical sampling plan.

## Exclusion and stop criteria

- Predeclared exclusions: any repetition where the intended induction did
  not actually occur (per operator log or self-induced read-back) is
  excluded and recorded `not measured`, never a negative finding — and,
  symmetrically, never a positive finding: a `not measured` cell leaves the
  corresponding claim untested, not supported, for that cell (Results,
  below). Any repetition where the delivery-validity control (R3,
  Classification and Controls, above) is itself `not-bracketed` is excluded
  as a harness integrity failure, distinct from a genuine `not-bracketed`
  transition finding, and counts toward neither confirmation nor
  falsification of `CLM-01-21-03`. Any repetition with an unintended
  concurrent transition is flagged mixed-condition and excluded from its
  arm's classification. Any repetition with a supervisor-detected crash,
  unrelated kill, disk-space loss, or raw-trace SHA-256 mismatch is
  excluded and may be rerun with a fresh seed outside `21001`–`21003`,
  recorded as such.
- Reachability rule for `CLM-01-21-01`/`-03` (`REV-223` R11): a
  repetition's induction is `confirmed-delivered` only when an out-of-band
  record (operator log, `pmset -g` capture, or self-induced read-back, per
  R6 above) independently establishes the transition occurred, regardless
  of what any accepted surface logged. Given a `confirmed-delivered`
  repetition with the delivery-validity control `bracketed`: a
  `not-bracketed` result on the transition-specific detectability surface
  counts toward `CLM-01-21-03`'s falsifier; if the delivery-validity
  control is itself `not-bracketed`, the repetition is excluded (above) and
  counts toward neither. `CLM-01-21-01`'s falsifier (a transition category
  unobservable at all, App Nap excluded per R7) and `CLM-01-21-03`'s
  falsifier each require at least 2 of the 3 planned repetitions for that
  arm to be `confirmed-delivered`, delivery-validity-`bracketed`, and
  `not-bracketed` on every accepted detectability surface before the
  category is recorded falsified for this host. Fewer qualifying
  repetitions leave the claim untested for that arm.
- Stop conditions: per `REV-225` RR8(a), a **second** delivery-validity
  control failure (`not-bracketed` at either bracket, RR5) within the same
  arm across its repetitions stops the campaign for re-diagnosis — the
  first occurrence within an arm excludes only that repetition (Predeclared
  exclusions, above), and a second is treated as a systemic harness defect,
  not an isolated event. Any harness self-observation control failure (T5
  or C1 not `bracketed`/confirmed) or any negative-control failure (C2
  showing a spurious discontinuity or detection) stops the campaign
  immediately, on first occurrence, for re-diagnosis before further cells
  run, because it indicates a harness defect rather than a host finding.
  Host identity drift from the
  preflight snapshot (different build number), `NATEMU_RAW_ROOT`
  unavailability, or repeated (more than 2) supervisor kills within one arm
  also stop the campaign.
- No generalization is drawn across unmeasured hosts, releases, or
  topologies; every planned cell remains in the manifest as completed,
  not-measured, mixed-condition, timed-out, or not-run — none is deleted
  from the denominator.
- No experiment starts before this method's independent review and the
  code gate both pass; the `INV-01-07` timing dependency applies only to
  any future promotion of a diagnostic interval, never to the qualitative
  classifications above.

- No experiment code exists or is authorized under `M21-1`; implementation

- Negative/fault-injection and expected behavior predeclared for the future
  code gate: a corrupted or missing heartbeat record, a truncated ring
  buffer, a ring buffer reaching its declared capacity mid-window (must
  fail-closed and increment the dropped-record counter rather than

  independently exclude the repetition even if the pre-induction instance

  (must refuse to start — R13), and a stale or mismatched compiled-bundle

  confirm the checker rejects or flags each, rather than silently accepting

- Per `REV-223` R13 and `REV-225` RR10 (R13 not closed at the prior return;
  house standard: `INV-01-18` Code validation/External immutable raw
  artifact; `REV-210` R3; the `cwd=REPO`/`git rev-parse --show-toplevel`
  specificity `REV-200` R3 required for the sibling `INV-01-18` code gate),
  recording provenance in the manifest is not sufficient by itself — a
  clean-tree check at launch does not detect a retained binary built from a
  dirty/unreviewed tree at the same revision. The harness must **validate**,
  at process start-up and before any work: (a) that the binary currently
  executing matches the compiled-bundle SHA-256 digest recorded for it,
  refusing to start on mismatch — this is the "bind and validate a
  compiled source-bundle digest before work/output" gap `REV-210` R3 names;

  pinned to this repository (`cwd=REPO`) and confirms
  `git rev-parse --show-toplevel` equals that same repository path before
  trusting the result, so the check cannot pass open from an enclosing or
  unrelated repository — the exact failure mode `REV-200` R3 found and
  fixed for `INV-01-18`'s own code gate; and (c) that the manifest also

  exercised at start-up, not merely recorded after the fact. The existing

  when `NATEMU_RAW_ROOT` is unset, repository-internal, or unwritable, and
  no writes under `experiments/` (Child process design, above) — are

  fixed iteration count to a time bound — at most once per the timer
  thread's 100 ms period, with the iteration counter carried in each record
  so throughput information is preserved (Busy worker). Ring-buffer
  capacity is recomputed from that corrected cadence with the arithmetic
  shown in the same paragraph: 18,000 records/thread over the 30-minute T1
  window, rounded to 2^15 = 32,768, ≈2.0 MiB/thread, ≈18 MiB for the
  largest child (Ring-buffer capacity and wrap policy). Wrap = cell invalid
  is unchanged.
- RR2 (R10 not closed): the supervisor's watchdog clock is corrected from
  `CLOCK_MONOTONIC` to `CLOCK_UPTIME_RAW`, matching `clock_gettime(3)`'s
  statement (in this SDK) that `CLOCK_MONOTONIC` increments during sleep
  and `CLOCK_UPTIME_RAW` does not (Sample plan, Observation window). The
  same man page corrects the prior, now-removed claim that `CLOCK_UPTIME_RAW`
  has no in-SDK header capture (Undeclared host mechanisms table), which is
  registered there as a supplement candidate for all five clock IDs.
- RR3 (R3 not closed): the delivery-validity control is restricted to
  **T1 only**, because it validates the `NSWorkspace` notification-center
  path (`SRC-157` line 33) that only T1's own tested surface shares;
  T3a/T3b/T4's tested surfaces are `NSProcessInfo` notifications on the
  distinct global-dispatch-queue/default-center path (`NSProcessInfo.h`
  lines 231, 240), which the accepted packet exposes no way to validate
  independently of the property under test. `CLM-01-21-03`'s falsifier is
  narrowed to T1 only; T3a/T3b/T4 detectability becomes diagnostic-only,
  the same treatment T2 already receives under R7 (Claim inventory;
  Classification; Controls; Metrics).
- RR4: `NSProcessInfo` notification callbacks execute on the global
  dispatch queue, not the control thread, so every detectability-record
  buffer is redesigned as a fixed-capacity array with a shared atomic
  fetch-add write-index per source (lock-free multi-producer/single-
  consumer), eliminating the cross-thread-write hazard for both the
  `NSProcessInfo`- and `NSWorkspace`-sourced records (Control thread). A
  concurrent-notification-delivery fixture is added to the code-gate list.
- RR5: the T1 delivery-validity control now brackets the induction on both
  sides (once immediately before, once immediately after) and uses display
  sleep (`pmset displaysleepnow`) rather than screen lock, matching the
  pinned `ScreensDidSleep`/`ScreensDidWake` notifications; a
  `not-bracketed` post-induction instance excludes the repetition even if
  the pre-induction instance was `bracketed`; the control's own induced
  transition is exempted from the mixed-condition confounder rule
  (Operator protocol step 2a; Classification; Controls; Confounders).
- RR6: `stalled` is unified to a single threshold (3× the 100 ms nominal
  period = 300 ms) used identically in Classification, Metrics, and
  `CLM-01-21-02`'s falsifier (a); the requested `DISPATCH_TIMER_STRICT`
  leeway policy is predeclared and a coalescing/BACKGROUND-QoS-attributable
  `stalled` reading is excluded from falsifying (b); "the clock's recorded
  sampling granularity" is defined per clock via `clock_getres` and
  `mach_timebase_info` and added to preflight/manifest (c); a precedence
  rule resolves multi-gap whole-window ambiguity for T2/T4/C2 (d); and
  `CLM-01-21-02`'s `stalled` falsifier now requires 2 of 3 planned
  repetitions per (arm, `N`) cell, while `backward` remains a single-
  observation falsifier because a monotonic-clock decrease has no benign
  competing explanation the way timer coalescing or QoS scheduling does (e)
  (Classification; Metrics; Claim inventory).
- RR7: `CLM-01-21-02`'s `backward`-clock falsifier is restricted to
  `mach_continuous_time`, the only clock with an accepted source basis for
  this investigation; the other four supplement-pending clocks remain
  diagnostic-only, consistent with R2's own divergence-bucket blocking
  (Source inventory; Claim inventory; Metrics).
- RR8: (a) a delivery-validity control failure excludes only the
  repetition on first occurrence within an arm and stops the campaign on a
  second occurrence within the same arm (Exclusion and stop criteria); (b)
  disagreement between the two T1 out-of-band confirmations is stated to
  yield `not measured`, never `confirmed-delivered` (Operator protocol).
- RR9 (R12's mechanism gap): a `sysctlbyname`/`hw.perflevel*` mechanism for
  total/performance/efficiency core counts is added to the source-
  supplement table and to preflight, with an explicit statement that no
  placement proxy is in fact available from the accepted packet (Undeclared
  host mechanisms; Operator protocol).
- RR10 (R13 not closed): the code gate must validate, at process start-up,
  that the running binary's digest matches the recorded compiled-bundle
  digest (refusing on mismatch), that the dirty-tree check runs with
  `cwd=REPO` and confirms `git rev-parse --show-toplevel` before trusting
  it (matching `REV-200` R3's fix for `INV-01-18`), and that the separate
  classification checker's own revision and digest are bound in the
  manifest; a stale/mismatched-bundle refusal fixture is predeclared (Code
  validation; External immutable raw artifact).

Claims further narrowed in text: `CLM-01-21-01` (the delivery-validity gate
in its reachability rule is stated to be meaningful only for the
`NSWorkspace`-surfaced categories), `CLM-01-21-02` (`backward` restricted

threshold per cell; the single `stalled` threshold is used everywhere), and
`CLM-01-21-03` (falsifier restricted to T1; T3a/T3b/T4 detectability is
