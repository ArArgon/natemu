## Question and decision relevance

- Question ID and text: `Q-01-01` — Which public macOS APIs and supported
  toolchain facilities are admissible across the required Apple Silicon and
  macOS matrix?
- Decision(s) affected: feasibility and platform applicability for every
  Track 01 mechanism question; the falsifier check for `KA-02` and a joint
  input to `KA-01`; family admissibility in `Q-01-02`'s register (`F1`–`F6`);
  and, through the admissibility rule this record states (below), how every
  later Track 01 investigation may rely on header-exposed but thinly
  documented behavior.
- Why this must be resolved now: every other Track 01 mechanism question
  (`Q-01-03`–`Q-01-09`, `Q-01-12`) assumes an admissible API surface; without
  a stated admissibility rule and an observed capability baseline, those
  investigations would each have to re-derive what counts as usable evidence
  from a public header.

## Assumptions

- Declared assumptions: public macOS APIs only, no private API, no kernel
  extension, no unavailable entitlement (`INV-00-05`); ad hoc and
  Developer-ID signing are both in scope, App Store distribution is not
  assumed; the host for this session (`Mac16,10`, macOS 26.6.2, `25G83`,
  SDK `26.4`) is `P2`'s generation/release line but not its exact model
  (brief host-facts table); `P1` (M1 Pro / Sequoia 15) replication is owed

- Assumptions to challenge: that a symbol's presence in a public SDK header

  unentitled and an ad-hoc-entitled build behave identically; that a
  capability observed on `P2`'s line generalizes to `P1`; that `MAP_JIT`
  admissibility and Hypervisor.framework admissibility are gated by the same
  entitlement (they are not — see the source inventory).

## Hypothesis and falsifier

- Hypothesis: on the supported hosts, an unprivileged process signed ad hoc
  or with Developer ID, using only the public APIs in the source inventory,
  can (a) obtain memory that is alternately writable and executable via
  `MAP_JIT` + `pthread_jit_write_protect_np`/`pthread_jit_write_with_callback_np`
  without any entitlement (`KA-01`, jointly with `INV-01-04`), and (b) when
  additionally ad-hoc-signed with `com.apple.security.hypervisor`, create a
  Hypervisor.framework VM and at least one vCPU and read that vCPU's
  `ID_AA64MMFR0_EL1` (`KA-02`).
- Falsifier(s): `KA-01` is falsified if `MAP_JIT` `mmap` fails without an
  entitlement, if the write/execute toggle does not round-trip (executed
  value ≠ 42, or the region is not writable again after re-toggling), or if
  `pthread_jit_write_with_callback_np` does not honor the callback contract.
  `KA-02` is falsified if `hv_vm_create` fails (any code other than
  `HV_SUCCESS`) when ad-hoc signed with the entitlement, or if
  `hv_vcpu_create`/`hv_vcpu_get_sys_reg` fail after a successful
  `hv_vm_create`. The negative control (`--negative`) is designed to make
  `check.py` fail deterministically by misreporting
  `jit_write_protect.executed_value`; a code-gate reviewer who cannot
  reproduce that failure has found a defect in the checker, not evidence
  about the platform.
- Predicted outcomes: `MAP_JIT` succeeds unentitled (per `CLM-01-01-02`);
  `hv_vm_create` returns `HV_DENIED` unentitled and `HV_SUCCESS` entitled
  (per `CLM-01-01-07`–`-09`); `ID_AA64MMFR0_EL1` reads successfully once
  entitled, with PARange/TGran fields whose exact values are not predicted
  (that is the falsifiable content of `CLM-01-01-11`) but which must fall in
  `0`–`15` and be internally consistent across separate reads.

## Method

- Procedure and versions: (1) primary-source audit of the SDK headers and
  Apple developer documentation in the source inventory, at `MacOSX26.4.sdk`
  and the 2026-09-03 documentation captures; (2) a single C probe
  (`experiments/INV-01-01/src/probe.c`, Apple clang `21.0.0`, no
  dependency) that emits one JSON object per invocation covering: sysctl
  host identity; `MAP_JIT` `mmap`; the `pthread_jit_write_protect_np` toggle
  and `pthread_jit_write_with_callback_np` callback path, executing an
  embedded 8-byte arm64 function (`mov w0, #42; ret`, assembled and verified
  with the local `clang`/`llvm-objdump` and embedded as a byte array) and
  checking the returned constant; `mach_vm_remap` two-directional aliasing
  of an anonymous page; `mach_timebase_info`/`mach_absolute_time`
  monotonicity; `pthread_set_qos_class_self_np` and
  `thread_policy_set(THREAD_AFFINITY_POLICY)` return codes;
  `getentropy`/`posix_openpt`/`setrlimit(RLIMIT_NOFILE)`; and
  Hypervisor.framework (`hv_vm_create`, `hv_vm_get_max_vcpu_count`,
  `hv_vcpu_create`, `hv_vcpu_get_sys_reg(ID_AA64MMFR0_EL1)` decoded into
  PARange/TGran4/TGran16/TGran64). (3) `run.sh` invokes the probe three
  times — ad-hoc signed with no entitlement, ad-hoc signed with
  `com.apple.security.hypervisor` (`src/hypervisor.entitlements.plist`), and
  the entitled binary with `--negative` — and captures an environment
  record (`sw_vers`, `sysctl`, `clang --version`, `git rev-parse HEAD`,
  `codesign -d --entitlements -`, `xcrun --show-sdk-path`).
- Inputs and configuration: no external input; the probe is self-contained
  and deterministic apart from the host's own capability state and the
  `ID_AA64MMFR0_EL1` register contents.
- Evidence labels assigned to planned claims: Source-backed for the header
  and documentation claims (`CLM-01-01-01`–`-03`, `-05`–`-09`, `-12`);
  Hypothesis, pending the evidence run, for every claim the probe measures
  (`CLM-01-01-04`, `-10`, `-11`, `-13`, `-14`); Inferred for the admissibility

### Resolution: admissibility rule for header-exposed, thinly documented behavior

`BP-01-06-start.md` ("Adjacent systems") identified that much of what a
handler or probe needs is "exposed by public headers but may be thinly
documented," and assigned the admissibility policy to `Q-01-01` with the
recurring detection cost to `Q-06-03`. This investigation states that rule,
using `SRC-052` (`mach_vm_remap`, no prose documentation at all) and
`SRC-055` (`HV_SYS_REG_ID_AA64MMFR0_EL1`, present without a per-enumerator
availability tag inside an enum whose newer siblings do carry one) as the
worked examples:

1. **Header location governs eligibility.** A symbol is eligible for any
   evidentiary use at all only when it is declared under the SDK's public
   include search path reachable from an umbrella header a public framework
   ships (for example `<Hypervisor/Hypervisor.h>`, `<pthread.h>`,
   `<mach/mach_vm.h>`) — not a header requiring a private, undocumented
   `-I`/`-F` path. Every header this investigation cites qualifies.
2. **An explicit `API_AVAILABLE`-style tag is Source-backed for exactly the
   version it names**, nothing more. `CLM-01-01-01` and `CLM-01-01-05` are
   this case.
3. **Absence of a tag inside an already-tagged enclosing declaration is
   Inferred, not Source-backed**, and only for the nearest bound the
   enclosing declaration or its untagged siblings establish. `CLM-01-01-06`
   is this case: `HV_SYS_REG_ID_AA64MMFR0_EL1` is at minimum as old as the
   surrounding `hv_sys_reg` enum's own baseline (`macos(11.0)`, matching the
   functions that consume it), because later additions to the same enum are
   explicitly tagged `macos(15.2)` while this enumerator is not — but no
   source inspected here states this affirmatively, so the claim is
   Inferred, flagged lower-confidence than a tagged symbol, and open to a
   controlled probe on an older accepted OS if one becomes available.
4. **Any semantic detail neither a header comment nor an Apple Developer
   Documentation page states — exact aliasing behavior, exact bit-field
   layout, exact error-code mapping — is admissible only as an Observed
   claim from this track's own controlled probe on each accepted host/OS
   pair, never as Source-backed from the header alone.** `mach_vm_remap`
   (`CLM-01-01-12`/`-13`) is this case: the header gives a signature and no
   prose; this investigation's Observed result, once run, is what actually

## Confounders

- Known confounders: a debugger or crash reporter interposed on the process
  changes fault/signal delivery and could mask a `SIGBUS`/`SIGSEGV` the
  probe's `sigsetjmp`/`siglongjmp` guard is meant to catch; `codesign`
  caching or a stale signature from a prior smoke-test run could make an
  "unentitled" run accidentally entitled if `run.sh`'s re-sign step is
  skipped; SDK/toolchain auto-update between build and run could change
  which SDK's headers were compiled against versus which OS build executes.
- Mitigations and residual risk: `run.sh` always rebuilds before each run
  and always re-signs immediately before each invocation; the environment
  capture records `codesign -d --entitlements -` for both binaries so a
  reviewer can verify the intended entitlement state was actually in force,
  not merely requested; the fault-guard is a `ponytail`-flagged
  simplification (see `probe.c`) that reports a crash rather than resuming
  precise register state — sufficient for this probe's own robustness, not
  a claim about `KA-04` (owned by `Q-01-06`/`INV-01-06`).
- Deferred, not resolved, by this probe: whether per-thread JIT
  write-protection state and the write/execute toggle are preserved across
  host fault delivery and return — this probe's `sigsetjmp`/`siglongjmp`
  guard only prevents a crash from losing already-printed JSON on this
  single thread; it does not test delivery discipline, nested faults, or
  mid-patch faults, which is `Q-01-19`'s scope. Cross-thread code
  publication, live-patch quiescence, and multi-vCPU code-cache safety are
  entirely out of this single-threaded probe's reach and are `Q-01-18`'s
  scope. The `mach_timebase_info`/`mach_absolute_time` and thread QoS/
  affinity readings are single-sample, foreground-process observations;
  sustained behavior under system sleep/App Nap/thermal throttling is
  `Q-01-21`'s scope, guest time-base policy selection is `Q-01-22`'s, and
  the vCPU-thread scheduling contract (preemption, QoS, P/E migration,
  oversubscription) is `Q-01-23`'s — this probe supplies only the raw
  capability facts (the API returns a success code, the clock is
  monotonic) those investigations build on.
