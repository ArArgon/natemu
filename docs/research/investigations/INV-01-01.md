## Question and decision relevance

- Question ID and text: `Q-01-01` — Which public macOS APIs and supported
  toolchain facilities are admissible across the required Apple Silicon and
  macOS matrix?
- Decision(s) affected: feasibility and platform applicability for every
  Track 01 mechanism question; the falsifier check for `KA-02` and a joint
  input to `KA-01`; family admissibility in `Q-01-02`'s register (`F1`–`F6`);
  and, through the admissibility rule this record states (below), how every
  later Track 01 investigation may rely on header-exposed but thinly
  documented behavior.
- Why this must be resolved now: every other Track 01 mechanism question
  (`Q-01-03`–`Q-01-09`, `Q-01-12`) assumes an admissible API surface; without
  a stated admissibility rule and an observed capability baseline, those
  investigations would each have to re-derive what counts as usable evidence
  from a public header.

## Assumptions

- Declared assumptions: public macOS APIs only, no private API, no kernel
  extension, no unavailable entitlement (`INV-00-05`); ad hoc and
  Developer-ID signing are both in scope, App Store distribution is not
  assumed; the host for this session (`Mac16,10`, macOS 26.6.2, `25G83`,
  SDK `26.4`) is `P2`'s generation/release line but not its exact model
  (brief host-facts table); `P1` (M1 Pro / Sequoia 15) replication is owed
  before any platform-wide claim.
- Assumptions to challenge: that a symbol's presence in a public SDK header
  is sufficient evidence of a stable, documented behavior; that an
  unentitled and an ad-hoc-entitled build behave identically; that a
  capability observed on `P2`'s line generalizes to `P1`; that `MAP_JIT`
  admissibility and Hypervisor.framework admissibility are gated by the same
  entitlement (they are not — see the source inventory).

## Method

- Procedure and versions: (1) primary-source audit of the SDK headers and
  Apple developer documentation in the source inventory, at `MacOSX26.4.sdk`
  and the 2026-09-03 documentation captures; (2) a single C probe
  (`experiments/INV-01-01/src/probe.c`, Apple clang `21.0.0`, built with
  `-isysroot "$(xcrun --show-sdk-path)"` so the SDK the record cites by
  digest is the SDK actually compiled against, not merely the one a symlink
  happens to resolve to — `REV-039` C9) that emits one JSON object per
  invocation covering: sysctl host identity including `kern.hv_support`
  (`REV-038` M5); `MAP_JIT` `mmap`; the `pthread_jit_write_protect_np`
  toggle, executing an embedded 8-byte arm64 function (`mov w0, #42; ret`,
  assembled and verified with the local `clang`/`llvm-objdump` and embedded
  as a byte array) and checking the returned constant, followed by
  `sys_icache_invalidate` before every execution of freshly written code
  (`REV-039` C4, per `SRC-059` ¶26); a **separate** `pthread_jit_write_with_callback_np`
  callback path on the same zeroed region using a *different* embedded
  constant (`mov w0, #43; ret`), so a callback that writes nothing cannot be
  mistaken for one that ran (`REV-039` C2); `mach_vm_remap` two-directional
  aliasing of an anonymous page, now guarded by the same fault-catch
  mechanism as the JIT sections (`REV-039` C3 — this section previously had
  no guard of its own); `mach_timebase_info`/`mach_absolute_time` as a
  two-sample smoke check, not a monotonicity claim (`REV-038` M9);
  `pthread_set_qos_class_self_np` and `thread_policy_set(THREAD_AFFINITY_POLICY)`
  return codes; `getentropy`/`posix_openpt`/`setrlimit(RLIMIT_NOFILE)`; and
  Hypervisor.framework (`hv_vm_create`, `hv_vm_get_max_vcpu_count`,
  `hv_vcpu_create`, `hv_vcpu_get_sys_reg(ID_AA64MMFR0_EL1)` reported as a
  raw hex value only, with every `hv_return_t` rendered as unsigned hex
  (`"0xfae94007"`, not a signed decimal — `REV-039` C6) and every call not
  attempted reported `null`, never a return-code look-alike (`REV-039` C5).
  A fault inside any guarded section is caught by a `sigsetjmp`/`siglongjmp`
  pair that is now armed only while a guarded section is live; a fault
  outside a live guard restores the default disposition and re-raises,
  terminating the process instead of resuming into a returned frame
  (`REV-039` C3 — an unguarded fault in `mach_vm_remap` previously looped
  forever). (3) `run.sh` invokes the probe three times — ad-hoc signed with
  no entitlement, ad-hoc signed with `com.apple.security.hypervisor`
  (`src/hypervisor.entitlements.plist`), and the entitled binary with

  `git rev-parse --show-toplevel` so a symlink into the repository cannot

- Evidence labels: Source-backed for the header and documentation claims

### Resolution: admissibility rule for header-exposed, thinly documented behavior

`BP-01-06-start.md` ("Adjacent systems") identified that much of what a
handler or probe needs is "exposed by public headers but may be thinly
documented," and assigned the admissibility policy to `Q-01-01` with the
recurring detection cost to `Q-06-03`. This investigation states that rule,
using `SRC-052` (`mach_vm_remap`, no prose documentation at all) and
`SRC-055` (`HV_SYS_REG_ID_AA64MMFR0_EL1`, present without a per-enumerator
availability tag inside an enum whose newer siblings do carry one) as the
worked examples:

1. **Header location governs eligibility.** A symbol is eligible for any
   evidentiary use at all only when it is declared under the SDK's public
   include search path reachable from an umbrella header a public framework
   ships (for example `<Hypervisor/Hypervisor.h>`, `<pthread.h>`,
   `<mach/mach_vm.h>`) — not a header requiring a private, undocumented
   `-I`/`-F` path. Every header this investigation cites qualifies.
2. **An explicit `API_AVAILABLE`-style tag is Source-backed for exactly the
   version it names**, nothing more. `CLM-01-01-01` and `CLM-01-01-05` are
   this case.
3. **Absence of a tag inside an already-tagged enclosing declaration is
   Inferred, not Source-backed**, and only for the nearest bound the
   enclosing declaration or its untagged siblings establish. `CLM-01-01-06`
   is this case: `HV_SYS_REG_ID_AA64MMFR0_EL1` is at minimum as old as the
   surrounding `hv_sys_reg` enum's own baseline (`macos(11.0)`, matching the
   functions that consume it), because later additions to the same enum are
   explicitly tagged `macos(15.2)` while this enumerator is not — but no
   source inspected here states this affirmatively, so the claim is
   Inferred, flagged lower-confidence than a tagged symbol, and open to a
   controlled probe on an older accepted OS if one becomes available.
4. **Any semantic detail neither a header comment nor an Apple Developer
   Documentation page states — exact aliasing behavior, exact bit-field
   layout, exact error-code mapping — is admissible only as an Observed
   claim from this track's own controlled probe on each accepted host/OS
   pair, never as Source-backed from the header alone.** `mach_vm_remap`
   (`CLM-01-01-12`/`-13`) is this case: the header gives a signature and no
   prose; this investigation's Observed result, once run, is what actually
   establishes the aliasing behavior, not the header. **Exclusion, added at
   the `REV-038` return (M11): this item does not cover a fact about a
   foreign architecture's own specification, as opposed to a fact about
   macOS behavior.** A macOS probe cannot observe an Arm architectural
   register-field layout — it must assume the layout to decode and report
   it, which is circular, not an observation. Such facts take the
   primary-source route (the owning architecture's own specification, here
   the Arm ARM) or stay unreported. `CLM-01-01-11`'s `ID_AA64MMFR0_EL1`
   field layout was the case this exclusion was written to correct
   (`REV-037` S4): this record no longer reports the decoded fields at all,
   since no source it has inspected states the layout — `SRC-105` (this
   track's existing Arm ARM captures) covers memory-ordering/atomicity
   sections, not the system-register description chapter.
5. **Cross-release drift detection.** Because thinly documented header
   behavior is not covered by Apple's compatibility promise the way a
   documented, availability-tagged API is, every Observed claim resting on
   such behavior must be *re-probed*, not merely re-cited, at each accepted
   macOS release — this session's SDK `26.4`/macOS `26.6.2` and, when
   available, `P1`'s Sequoia 15 build. A value that differs between two
   accepted SDKs/OS releases is drift; the record must then widen its
   applicability statement to name both values with their exact SDK/OS
   rather than silently picking one or averaging. The recurring cost of this
   per-release re-probing is a lifecycle-cost input owned by `Q-06-03`, not
   absorbed silently by this question.

This rule is Inferred (`CLM-01-01-15`); it is itself a methodological
finding of this record, not a Source-backed claim, and it binds every later
Track 01 investigation's treatment of header-only behavior unless a future
adversarial review revises it.

### Resolution: `KA-02` disposition

Added at the `REV-037`/`REV-038` return (S5/M1/M2): the previous version of
this record left `KA-02` — "Hypervisor.framework on Apple Silicon can
execute x86-64 guest code directly" — to be decided by a runtime register
read (`hv_vcpu_get_sys_reg(ID_AA64MMFR0_EL1)` succeeding on an entitled
arm64 process), which tests a different proposition: that Hypervisor.framework
is usable at all on this host, not that it can execute x86-64 code. No probe
on this platform could ever test the real proposition, because the arm64
SDK build this probe links against has no x86-64 VM-creation API compiled
into it to call.

`KA-02` is decided here, documentarily and at compile time, from evidence
already captured and digest-matched before this return (`CLM-01-01-16`):
Apple's own Hypervisor framework overview states, under "Requirements" /
"Supported hardware", that "the Hypervisor framework requires hardware
support to virtualize hardware resources. On Apple silicon, that includes
the Virtualization Extensions. On Intel-based Mac computers, the framework
supports machines with an Intel VT-x feature set that includes Extended
Page Tables (EPT) and Unrestricted Mode." — two named, mutually exclusive
hardware paths, one per host architecture, with no mention of arm64 hosting
Intel VT-x-dependent x86-64 execution. The same page's topic groups
separately title "Apple Silicon" ("Create and run virtual machines on
Apple silicon.") and "Intel-based Mac" ("Create and run virtual machines on
Intel-based Mac computers."). The SDK's own `Hypervisor.h` enforces this at
compile time: `#if defined(__arm64__)` includes only `hv_vm.h`, `hv_vcpu.h`,
and the rest of the arm64 VM API; `#elif defined(__x86_64__)` includes the
entirely separate `hv.h`/`hv_vmx.h`/`hv_arch_vmx.h` x86 VM API instead —
never both — and `hv_vm.h` itself repeats the arm64 gate at line 10. An
arm64 binary therefore has no symbol to call that would create an x86-64
VM even in principle.

**Disposition: `KA-02` is false on Apple Silicon.** Family `F5` (hardware
x86 virtualization) is killed under `INV-00-06` family-kill item 1's
**public-API limb**, on the documentary and compile-time grounds in
`CLM-01-01-16`/`-17`, applicable to every accepted Apple Silicon host/OS
cell without needing `P1` replication (the SDK architecture gate is not
host- or OS-version-specific). This disposition does not depend on, and is
not corroborated or weakened by, whatever the entitled arm64 register read
in `CLM-01-01-10`/`-11` reports; that read is retained only as an input to
`Q-01-08`/`Q-01-12`/family `F3` (same-architecture virtualization, where the
hardware-MMU-EL1 mechanism `F3` needs is exactly what an entitled arm64
VM/vCPU creation and system-register read demonstrate access to). Corrected
at the `REV-096` return (A2): this record previously cited item 1's
"unsupported toolchain behavior" limb, which an adversarial reviewer found
fit only by argument; `CLM-01-01-17`'s Derivation cell now states the exact
reading — the required x86-64 VM-creation API is a genuinely public Apple
API, not a private one, but it is absent from the public SDK surface of
every accepted (arm64) build, which this record reads as falling under the
**private-API limb** (no callable symbol exists in any accepted build,
the same practical outcome a private API would produce), and independently
satisfies project-level stop input 1's own "mandatory public-API ...
constraint" wording without needing that argument at all.

**Bound against a looser restatement, added at the `REV-096` return (A3):**
this disposition is that Hypervisor.framework exposes no x86-64
VM-creation API on Apple Silicon — it must **not** be restated as the
broader, false claim "x86-64 code cannot execute in a virtual machine on
Apple Silicon" or "x86-64 code cannot run under an arm64 host at all."
Rosetta for Linux executes unmodified x86-64 user-mode Linux binaries
inside an arm64 Linux guest by dynamic translation — a real, shipping
Apple Silicon capability — without contradicting this disposition, because
it does not satisfy `KA-02`'s envelope: `KA-02` concerns Hypervisor.framework
directly executing an **unmodified, full-system x86-64 guest** (an x86-64
kernel and userspace, hardware-virtualized, no translation), and Rosetta for
Linux is neither hardware virtualization of x86-64 (it is binary
translation), nor full-system (it translates individual user-mode
processes inside an already-running arm64 guest kernel), nor unmodified
(the translated binary's instruction stream is rewritten, not executed
as-is). Rosetta for Linux therefore neither disturbs `KA-02`'s disposition
nor `F5`'s kill, but it does defeat the looser, unqualified statement above,
which this record must not make.

## Controls

- Positive controls: the unentitled and entitled probe runs are each other's
  control for the Hypervisor entitlement-gating F3 input — `hv_vm_create`
  must differ between them (`HV_DENIED` versus `HV_SUCCESS`) for the run to
  be informative at all; an identical result on both would indicate a
  signing or entitlement-application defect in `run.sh`, not a platform
  fact. Corrected at the `REV-038` return (M7): this is now a procedure, not
  only a sentence — `run.sh` runs a Python comparison of the two runs'
  `hv_vm_create_hr` values and writes `positive_control.txt`, flagging a
  match as a probable defect.
- Negative controls: `probe --negative` deliberately reports
  `jit_write_protect.executed_value` as `0xBAD` regardless of the real
  executed value; `check.py` must FAIL that output. `run.sh` always
  produces this run and its checker output.
- Baselines: none required; this is a capability probe, not a comparative
  performance measurement.

## Confounders

- Known confounders: a debugger or crash reporter interposed on the process
  changes fault/signal delivery and could mask a `SIGBUS`/`SIGSEGV` the
  probe's `sigsetjmp`/`siglongjmp` guard is meant to catch; `codesign`
  caching or a stale signature from a prior smoke-test run could make an
  "unentitled" run accidentally entitled if `run.sh`'s re-sign step is
  skipped; SDK/toolchain auto-update between build and run could change
  which SDK's headers were compiled against versus which OS build executes.
- Mitigations and residual risk: `run.sh` always rebuilds (into a fresh
  `mktemp -d` directory, `REV-039` C7) before each run and always re-signs
  immediately before each invocation; the environment capture records
  `codesign -d --entitlements -` for both binaries so a reviewer can verify
  the intended entitlement state was actually in force, not merely
  requested; `build.sh` now pins `-isysroot "$(xcrun --show-sdk-path)"`
  rather than relying on the default SDK symlink (`REV-039` C9); the
  fault-guard now arms only while a guarded section is live and restores
  the default disposition otherwise (`REV-039` C3, corrected at this
  return — the previous shared-`sigsetjmp`-with-one-guarded-section design
  let a fault in the then-unguarded `mach_vm_remap` section loop forever,
  reproduced by the reviewer and fixed here), and `run.sh` wraps every
  invocation in a 30 s timeout as a backstop. The fault-guard is still a
  `ponytail`-flagged simplification (see `probe.c`) in that it reports a
  crash rather than resuming precise register state — sufficient for this
  probe's own robustness, not a claim about `KA-04` (owned by
  `Q-01-06`/`INV-01-06`).
- Deferred, not resolved, by this probe: whether per-thread JIT
  write-protection state and the write/execute toggle are preserved across
  host fault delivery and return — this probe's `sigsetjmp`/`siglongjmp`
  guard only prevents a crash from losing already-printed JSON on this
  single thread; it does not test delivery discipline, nested faults, or
  mid-patch faults, which is `Q-01-19`'s scope. Cross-thread code
  publication, live-patch quiescence, and multi-vCPU code-cache safety are
  entirely out of this single-threaded probe's reach and are `Q-01-18`'s
  scope. The `mach_timebase_info`/`mach_absolute_time` and thread QoS/
  affinity readings are single-sample, foreground-process observations;
  sustained behavior under system sleep/App Nap/thermal throttling is
  `Q-01-21`'s scope, guest time-base policy selection is `Q-01-22`'s, and
  the vCPU-thread scheduling contract (preemption, QoS, P/E migration,
  oversubscription) is `Q-01-23`'s — this probe supplies only the raw
  capability facts (the API returns a success code, the clock is
  monotonic) those investigations build on.
