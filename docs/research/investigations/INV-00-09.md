# INV-00-09 — UEFI and Windows implications boundary

## Metadata

- Investigation ID: `INV-00-09`
- Owner/session: Codex `/root`; source context `/root/scope_boundary`

## Question, assumptions, and breadth pass

- Question: `Q-00-09` — What analysis of UEFI and Windows implications must
  research deliver without implementing either?
- Decisions affected: non-goals, architecture extensibility, economic risk,
  and synthesis unknowns.
- Declared: specification-only implications register; Linux direct boot cannot
  establish firmware/Windows compatibility.
- Challenged: UEFI is merely a kernel-entry shim; Linux virtio implies Windows
  drivers; one Windows edition/licensing scheme represents all scenarios.
- Breadth pass: `../breadth-passes/BP-00-09-start.md`; no new issues found.
- Later source/review discoveries: `SRC-029`, `SRC-040`–`SRC-045`; their
  implications are registered below while legal conclusions remain with
  `Q-01-11`.

## Falsifiers, controls, and limitations

| Falsifier | Disposition |
| --- | --- |
| UEFI is treated only as an entry shim or TPM/Secure Boot as Boolean flags. | Register failure; reopen `Q-00-09`. |
| Linux driver success is used as Windows driver evidence. | Method/source failure; return `Q-01-13` and `Q-01-11`. |
| A Windows edition/build or license program is generalized beyond its source. | Boundary/source failure; narrow applicability and reopen the affected register row. |
| A required future subsystem is impossible for one family. | Family kill only after accepted/replicated evidence; other families remain open. |
| A future requirement makes the accepted Linux jobs impossible or economically irrelevant. | Reopen Track 00 scope/economics; otherwise deferred Windows absence is not a project kill. |
| A register row lacks one required field. | Analysis-method failure; the register is incomplete and cannot feed synthesis. |

- Method: clause-level register against the accepted Linux boundary. Positive
  control is a row with all required fields; negative controls are an
  unspecified edition, a Boolean TPM entry, and inference from Linux driver
  success. Completeness is checked row-by-row, not by boot success.
- Host/OS/guest/SMP applicability varies by Windows scenario and future family;
  no platform-wide feasibility claim is made. `Q-05-02` would name admissible
  host/OS pairs for any future experiment, but no Windows experiment is in
  scope here.
- No experiment, sample, code, raw artifact, or result exists. Correctness and
  performance for UEFI/Windows are explicitly not claimed.
- Newly surfaced questions: source gaps and legal scenarios are assigned to
  existing `Q-01-11`; machine/driver surfaces to `Q-01-13`; CPU/APIC/topology
  to `Q-02-03`; lifecycle cost to `Q-06-03`. No new issue ID is required.
